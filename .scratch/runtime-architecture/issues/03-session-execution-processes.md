## Question

在单次 Agent 执行卡死或崩溃不能拖垮文献库、应用宿主和其他会话的要求下，harness 哪些职责留在应用宿主、哪些进入独立执行进程？进程应随会话、执行尝试或其他明确执行单元建立与回收？

比较每个活动会话独立进程、每次执行独立进程及可满足同等故障要求的复用方案。必须明确会话、执行尝试、子执行、advisor 与 PID 的关系，不能只用进程数判断方案。

讨论空闲回收、启动成本、应用级并发和模型资源调度、健康检查、协作取消与强制停止、子进程树归属、委派者结束后的子执行寿命。区分可捕获工具失败、事件循环阻塞、进程崩溃、进程内存耗尽与系统资源耗尽；给出保护范围及不承诺的范围。

文献计算、共享插件宿主、模型调用和原生依赖应放在哪里，按实际失败传播判断。用户允许应用宿主故障后中断并显式接续，不要求另建常驻守护进程保障执行不停机。

按[模块依赖票](01-module-dependencies-and-authority.md)中用户明确的产品构成，人工编辑、预览及编译不依赖 harness。进程管理需区分这些路径共同使用的基础执行能力和 Agent 执行监督；重新核对原“执行环境为 harness 子系统”的归属，不以停用 harness 为由移除人工操作所需执行能力。

系统启动、资源持有、取消结果与宿主适配沿[平台契约](02-platform-access.md#answer)。本票确定哪些进程和执行拥有这些资源、何时回收和如何监督，不能把平台机制层当作另一个 Agent 调度器，或把请求断开当作已确认进程退出。

## Answer

2026-10-18，用户依次回复“全部采纳”“采纳”“采纳”，确认 Q1–Q9。本票完成进程粒度、职责分配、生命周期、监督、取消及故障范围的决策；以下为目标契约，尚未实现或实跑验证。

### Q1：每次活动执行独占进程

Agent 的一次活动执行独占受管 OS 进程，运行结束后回收；同一会话串行推进。一次执行可包含多次模型请求、工具调用和运行中追加的指令，不按每条消息或每次工具调用新建进程。

可独立调度的子 Agent 执行同样独占进程，advisor 触发的执行使用同一规则；不能通过在父执行进程内嵌套运行另一个 Agent 来宣称具有独立故障隔离。普通工具调用不因此各建一个进程，具体计算与原生依赖按实际失败传播选择部署位置。

会话、持久执行身份与当前 PID 分别表达。兼容 checkpoint 接续原执行时可以更换 PID，不因进程重建而自动要求新的会话或执行身份；恢复身份与写入细节由[持久化与恢复票](04-execution-persistence-and-recovery.md)细化。

首阶段不采用会话常驻进程或跨执行进程池；只有实际启动成本证明有需要时再评估复用及其状态清理保证。等待期间的资源占用与安全回收条件沿 Q4。

### Q2：委派方负责收尾，后台继续需要显式移交

默认由委派方承担子执行的收尾责任：正常交付前等待或停止仍在运行的子执行；确需后台继续时，显式移交宿主管理，保留可查询、可取消的执行归属，不因父执行结束留下无主工作。用户停止默认覆盖其委派链，已完成产物与修改保留。

向已有其他会话发送协作请求不建立父子关系，也不授予停止对方的权限。advisor 沿已有有限等待规则处理，不因等待超时无限续跑；用户关闭或停止后停止新增监督及自动继续，已有建议保留。

### Q3：宿主统一准入，平台机制与 Agent 监督分工

应用宿主持有统一准入和额度控制，执行进程负责实际推进。子执行、advisor、上下文压缩与重试等模型调用共同服从应用及连接限制，不能各自复制进程内计数器后叠加突破总量。等待子执行结果不占模型调用名额；执行进程容量与模型请求额度分别管理，等待与资源不足行为沿 Q4。

平台提供受管进程及进程树的创建、控制和退出确认机制；harness 承担 Agent 执行监督，宿主装配相应实现。人工预览、编译和程序执行使用独立于 harness 的公共执行能力，不要求建立 Agent 会话或调用模型。平台不因提供进程机制而成为另一个 Agent 调度器。

### Q4：等待、安全回收与容量不足

短等待保留进程；长等待只在安全暂停边界回收，回收前保存接续所需状态，并确认没有仍由该进程负责的在途操作。不能按无输出时长直接终止。安全暂停及恢复所需状态由后续持久化票细化；不假设任意模型请求或工具调用都能中途迁移。

进程数量与模型并发分别设限。调度识别父子等待关系，不能让父执行占据子执行必需的最后资源后无限排队；无法安排时返回可诊断的资源限制。实际仍存在的进程需要计入占用，不能仅通过将父执行标为等待来宣称其物理资源已释放。具体上限和等待参数在实现中按实际负载验证。

### Q5：职责与进程分配

| 工作 | 承载位置 |
| --- | --- |
| 模块装配、broker、应用级资源控制、执行监督 | 应用宿主 |
| LangGraph 推进、上下文处理、模型 SDK 调用、执行侧工具编排 | 对应 Agent 执行进程 |
| 文献、项目等共同数据权威及轻量领域操作 | 所属模块，保留集中部署基线 |
| PDF 解析等可能阻塞或导致进程崩溃的计算、原生处理 | 受管计算进程，供人和 Agent 共用 |
| 用户脚本、编译器、外部程序 | 各自受管进程 |
| Zotero 兼容插件 | 按需启动的独立共享兼容宿主 |

Worker 可作为这些进程内部的计算手段，不能替代所需的 OS 进程隔离。共同领域权威不随执行进程复制，跨模块调用继续经 broker；模型连接及凭据政策沿所属模块，实际 SDK 调用服从应用统一准入。

共享插件宿主故障会影响依赖它的调用，不因此终止其他会话。不能为了取消单个请求终止整个共享宿主；某项插件能力无法局部取消时，明确报告限制。具体插件内部状态与调用恢复由其契约处理，不以重启宿主宣称原请求没有产生效果。

### Q6：健康检查与取消完成依据

存活、响应和工作进展分别观察：进程退出是明确故障，PID 仍存在不代表事件循环可以响应；由执行进程自身事件循环回应健康检查。长期无日志、模型等待或计算耗时不能单独判为卡死。操作期限、健康检查超期及用户停止分别记录原因，进入对应的中止、核查或取消路径。

取消先阻止后续调度并请求协作退出，宽限期后终止该执行及其受管子进程；确认相关执行单元停止后才报告本地取消完成。无法确认退出或实际效果时保留未知，不以连接断开报告取消成功，不据此宣称远端模型停止计算或计费。已保存成果与实际修改保留；具体健康检查期限、宽限期及平台收尾机制随实现验收。

### Q7：执行归属与宿主异常退出

全部受管进程及后代按实际执行归属登记，包括经 broker 由公共执行模块启动的程序；业务归属不等同于 OS 父 PID。平台负责实际控制，监督方决定停止范围。正常交付、失败或取消均需收尾仍属于该执行的工作，显式移交后台的工作保留新的管理归属，不留下无主执行。

宿主失联后，执行停止新增动作并退出，配合平台提供的进程组等机制收尾。具体机制必须覆盖执行事件循环无法响应时的收尾需要，按平台实际支持验证；首阶段不增加常驻守护进程，也不承诺宿主故障时执行不停机。工作台或普通客户端断线不等同于宿主失联，不因此取消后台执行。

宿主重新启动先核查遗留执行及其进程身份，不仅凭旧 PID 终止进程；旧执行尚未排除时，不启动可能重复写入的接续。恢复前核查实际效果，已明确停止的工作不自动重启。具体遗留身份、记录及接续顺序由[持久化与恢复票](04-execution-persistence-and-recovery.md)细化。

### Q8：旧执行实例与迟到操作

停止或替换执行实例时，撤销旧实例发起新动作的资格：旧实例不能继续申请模型、委派工作、发起工具操作，或覆盖新实例状态。持久执行身份可以延续，不表示旧实例继续有操作权；具体身份字段和校验随持久化及通信契约落实。

已受理操作单独收尾。终止 Agent 进程不表示所属领域模块中的保存操作已经停止；报告本地取消完成前，核对相关本地操作确已完成或停止，无法确认时保留未知。已经发生的写入和已完成产物保留，不因取消而撤销。

迟到结果可以用于记录历史、核查产物和实际效果，不能覆盖新实例状态或自动恢复已停止的执行。远端请求的计算、费用及未知效果继续按实际可确认范围报告，不等待无法取得的远端保证来伪造本地结论。

### Q9：故障传播与资源保护范围

| 故障 | 处理范围 |
| --- | --- |
| 可捕获的工具错误 | 该调用失败，Agent 可处理错误并继续 |
| 独占执行进程阻塞、崩溃或进程内内存耗尽 | 停止该执行，收尾所属工作；宿主和无关会话继续 |
| 共享计算或插件宿主故障 | 标记依赖它的调用受影响，保留无关能力和会话 |
| 应用宿主故障 | 允许相关执行中断，恢复后显式接续 |
| 系统级内存、CPU、磁盘或句柄耗尽 | 提供资源限制与诊断，不承诺其他部分仍完全可用 |

进程数、等待队列、输入和输出有界，避免执行进程经共享入口产生无界负载。内存和 CPU 强制限制按平台实际支持提供，JS 堆上限不等于整个进程内存上限；进程内内存耗尽与系统级资源耗尽分别判断。拆进程不构成任意代码的强安全沙箱，继续沿可信代码执行范围。
