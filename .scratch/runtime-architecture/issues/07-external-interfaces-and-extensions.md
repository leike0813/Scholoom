## Question

哪些操作开放给人类客户端、兼容宿主、插件及独立外部系统？Scholoom 是否提供 MCP 和／或 A2A，各自面向谁、承诺什么，如何适配同一领域与执行能力？

区分插件使用外部 MCP 能力与 Scholoom 对外提供 MCP 服务，也区分外部请求受管科研操作与第三方 harness 接管原生执行。既有统一内置 LangGraph 的决定作为基线，不因开放协议隐式扩大执行入口。

讨论文献查询与写入、材料读取与外发、会话控制、能力调用、研究任务及产物的开放范围；身份、授权、撤销、版本与发现；长任务引用、等待／补充输入、断线、取消、幂等与效果未知。明确外部“任务”与持续研究任务、会话、执行尝试的映射，不能以协议名称推导额外保证。

MCP／A2A 的规范或 SDK 能力若影响选择，先创建范围明确的 research 票并查官方资料，再作取舍。本票可以确认暂不提供其中一个入口，但不能将用户要求讨论全部接口缩成只标注候选而跳过评估。

### 当前依据

- [执行与扩展边界](../../scholoom-foundations/issues/07-agent-runtime-boundaries.md)及[多 Agent 初设](../../scholoom-foundations/issues/46-multi-agent-interaction.md)原将对外 MCP／A2A 保留为候选。本票已确认 MCP 的用途、开放范围与公共契约，以及 A2A 后置的选择；原决议同步引用本票。
- [Zotero 兼容宿主](../../../apps/zotero-host/src/main/index.ts)当前为独立入口骨架，未接入内核监督；插件兼容对象语义与跨进程 DTO 的职责不能合并。

### 结束条件

用户确认各类调用方的开放范围、MCP／A2A 的采纳或后置决定及理由、公共契约和权限边界，并明确哪些原决议与设计文档需同步；后续接口实施仍通过 OpenSpec。

### 当前边界核对

- [既有执行与扩展决议](../../scholoom-foundations/issues/07-agent-runtime-boundaries.md#answer)已确认插件系统管理 harness 消费的 MCP 能力；对外提供 MCP 是不同方向，不能把任意内核操作自动发布。多模型共用内置执行机制，不支持第三方 harness 接管。

## Answer

2026-10-18，用户确认 Q1–Q14，文档同步与静态核对完成，本票 resolved。以下是对外接口与扩展的目标契约，尚未完成 MCP、Tasks 或远程 HTTPS 接线。本文中的工作请求统一沿 Q8，历史讨论中的“委托”不表示已批准独立对象。

### Q1：对外支持领域能力调用与内置 Agent 工作请求

支持两类用途：外部应用或 Agent 在授权内使用 Scholoom 文献与项目等领域能力，由调用者组织自己的工作；外部 Agent 向 Scholoom 内置 Agent 提出明确工作请求，查询进展、补充材料并取得成果，由 Scholoom 组织内部执行。

两类入口复用共同领域能力、事实权威及有效授权，不将任意内核操作自动对外开放。提交工作请求不取得内部图节点、checkpoint 或凭据控制权，不改变内置 LangGraph 执行路线；协议选择见 Q2，首批开放范围见 Q3。

### Q2：先提供 MCP，A2A 待明确对接需求后增加

对外先提供 MCP，以领域能力调用与内置 Agent 工作请求为两类用途；首批实际开放范围受 Q3 限制。工作请求通过提交工作、查询进展、补充信息、请求撤回及取回成果等工具承载，共用既有领域和执行权威；不强制开放内部会话，也不要求客户端必须支持 Tasks 扩展才能提交工作请求。

A2A 本阶段暂不提供，待出现明确使用 A2A、需要其标准 Agent 发现或任务交互的实际对接对象时增加适配。两种协议都能承载长工作，此选择基于 MCP 已能覆盖当前两类用途，以及维护第二套协议发现、状态、认证映射和互操作验证的成本，不以长短任务划分协议职责。

当前调查版本不自动成为首发支持版本。所选协议、SDK、扩展和实际客户端的互操作仍须实施前核对；传输、操作、授权与对外部署按下述结论，功能实施由后续 OpenSpec 承接。

### Q3：首批开放查询与有限工作控制

首批对外 MCP 开放获授权的文献、项目材料、工作状态与成果查询；读取本身不隐式启动科研分析或改写领域对象。工作控制限于基本不会和内置动作产生竞争的三类请求：

| 操作 | 处理边界 |
| --- | --- |
| 提交工作请求 | 内置 Agent 结合当前工作安排处理 |
| 为自己发起的请求补充信息 | 作为输入交给负责的 Agent，不直接改写其工作状态 |
| 请求撤回自己发起的工作请求 | 内部协调停止，返回实际处理结果，不等同立即停止或回滚 |

首批不向外部开放直接修改题录、共享文件、正式任务状态，或抢占及控制其他会话的操作。新建会话也可能让多个 Agent 修改同一材料，不能仅凭新会话或请求排队认定没有竞争；仍沿既有协作、授权与领域并发保护处理实际动作。

Q1 的两类总体用途及已有内部方法不代表全部领域读写、科研能力和会话控制已获准公开。普通 MCP 业务工具不暴露内部执行图、checkpoint、进程控制与凭据管理，也不因安装插件而自动转供其工具。

### Q4：按外部调用方授予可撤销的范围权限

每个外部调用方具有可识别、可撤销的授权，按文献库／项目、操作及材料接收方等范围判定。已有 GUI 或内置 Agent 授权不自动成为外部访问许可；向外部返回材料须满足对该接收方的外发授权。查询也不豁免材料读取和外发检查。

工作请求的执行沿用户授予该请求的范围，不借内置 Agent 的其他权限扩大执行；范围内不重复逐调用确认，新增资源、接收方或操作范围再授权。权限模型可以区分读取与写入，但取得权限不会自动发布 Q3 尚未开放的操作。撤权效果见 Q5。

### Q5：撤权阻止后续受影响动作，按工作请求协调收尾

撤销外部调用方授权后，拒绝其后续受影响访问和成果外发，阻止其工作请求继续使用已撤销权限，并协调收尾在途工作。只处理该请求受影响的部分，不据此停止整个共享会话或研究任务。已发生的效果与已保存成果保留，已发出的资料无法追回；实际停止、未知效果及局部取消限制沿既有进程和恢复规则表达，不以撤权本身证明全部在途操作已经停止。

用户希望继续保留工作时，须明确接管并授予所需权限，不静默借用其他授权。普通连接断开或请求等待超时不是撤权，也不自动撤回工作；继续沿既有规则核对实际状态。

### Q6：对外 MCP 默认关闭，按需明确启用

对外 MCP 默认关闭，按需明确启用；与内置 Agent 消费插件 MCP 分别管理。安装或启用 MCP 插件不自动向外提供 Scholoom 服务，启用对外服务也不自动授予外部调用方访问权限。具体调用方仍按 Q4 授权，首批操作继续受 Q3 限制。

### Q7：首批同时支持 stdio 与 Streamable HTTP

首批对外 MCP 同时支持 stdio 和 Streamable HTTP，不将 HTTP 留待后续对接需求出现后再提供。两种传输沿共同领域权威、调用方授权和 Q3 的操作范围，不因传输不同复制领域实例或扩大权限。

HTTP 网络接入见 Q10，支持两种传输不表示采用全部可选协议扩展。SDK、协议版本和真实客户端在两种传输上的互操作须由后续实施验证，当前未交付接线。

### Q8：统一称工作请求，先明确含义再决定承接形式

工作请求指调用方向 Scholoom 内置 Agent 提出、由其组织处理的一项工作要求，例如比较三篇论文并保存报告。它可以推进已有研究任务或完成临时工作，不因提交请求自动创建研究任务。会话承载交互与临时工作上下文，研究任务保存持续科研目标、进展与成果，执行记录表达实际工作经过，科研工作包表达委派的目标、材料与授权约定。

此项确认概念及用词，其含义不预设独立对象、稳定引用或生命周期；关联处理沿后续确认的 Q9。领域定义保存于 [CONTEXT.md](../../../CONTEXT.md)，本票保存取舍与接口边界。

### Q9：沿协作请求机制承接，关联输入与处理结果

沿已有协作请求机制的设计承接外部工作请求。提交形成带调用方来源与授权范围的请求消息，补充信息、撤回要求关联原请求，由负责的 Agent 处理。查询区分已受理、已消费及实际处理结果；请求已受理或已消费均不等同工作完成，研究事实和成果仍保存于所属材料及研究记录。

复用收件、请求与回复的关联，不另建独立委托资产或复制一套工作状态。临时 RPC 编号不替代请求关联，断线和效果未知沿既有规则核对原请求与实际结果；不因重连重复开工，不从消息去重推导外部副作用恰好一次。接收会话沿 Q11，实现字段由实施规格确定，本机制尚需对外适配。

### Q10：HTTP 默认回环，支持明确配置的远程 HTTPS 接入

Streamable HTTP 默认只监听本机回环地址，支持用户明确配置远程网络接入；远程直接接入使用 HTTPS，并对具体调用方认证、授权。可使用部署环境提供的 HTTPS 入口，不要求内核自行管理证书。SSH 隧道继续作为可选连接方式，工作台原有 SSH 部署决定不因此改变。

远程接入不扩大 Q3 的公共操作、Q4 的授权或材料外发范围；服务仍按 Q6 默认关闭。具体认证接线、配置和端到端验证由后续实施规格明确，支持远程访问不表示已经交付公网部署。

### Q11：可指定获准接收请求的会话，未指定时创建普通会话

调用方可指定获准接收外部工作请求的已有 Agent 会话；未指定时，内核为新工作创建普通 Agent 会话。返回实际承接会话与请求关联，后续补充和撤回沿原请求交给负责的 Agent，不因每次工具调用创建新会话，也不引入专门的外部会话类型。

接收外部请求不自动授予调用方读取整个会话上下文或控制其中其他工作的权限。已有会话正在运行时沿执行边界消费；用户停止或归档时遵守原有规则，不因来信自动唤醒或静默改送替代会话。具体唤醒和并发保护沿协作与进程决议，新建会话本身不证明没有竞争。

### Q12：插件经统一契约与明确发布扩展公共能力

插件可以扩展对外 MCP 能力，通过统一契约声明能力，由宿主明确注册发布；首批仍限于 Q3 的查询与有限工作控制。参数、结果、错误及领域规则复用原能力的同源契约，不将插件全部原始工具直接透传。安装或启用插件不自动对外发布，发布后仍核对调用方的有效授权。

插件停用或不可用时，如实报告其公共能力不可用，不影响无关能力。插件的原生领域、图与 UI 扩展继续沿既有接口，不要求所有插件能力改走 MCP；此项公共发布不改变内置 harness 消费插件 MCP 的独立管理方向。

### Q13：稳定维护公开接口，发现反映实际可用范围

已公开工具的名称、参数、结果和语义作为稳定公共契约维护。复用能力提供方 schema、领域规则与副作用声明，不因内部重构或插件替换静默改变公共含义；破坏性变化通过明确版本升级处理，公共工具契约版本与 MCP 协议版本分别表达。

发现信息来自实际注册和调用方可见范围，不将候选、禁用或尚未实现的能力报告为可调用；发现也不替代调用时的有效授权检查。首发具体协议和 SDK 版本按真实客户端验证确定，不要求应用版本同号，不承诺无依据的全历史版本兼容。参数、结果、错误与操作语义继续沿共同契约生成及适配，不在对外入口另维护业务规则副本。

### Q14：首批支持 Tasks 扩展，保留普通工具路径

首批提供官方 MCP Tasks 扩展的标准长工作交互。双方声明支持时，将工作请求处理映射为协议任务，沿实际请求与结果提供查询、补充输入及协作式取消；普通工具的提交、查询、补充与撤回路径同时保留，不支持 Tasks 的客户端仍可使用 Q3 能力。

两条路径共用请求状态、调用方归属与权限，不复制领域工作状态。协议取消映射为对所属工作请求的协调撤回，不能借此停止共享会话、控制他人工作或绕过用户停止意图；受理取消不等于确认全部工作停止。协议 Task 终态不等于持续研究任务结束，已保存成果和实际效果沿 Q3、Q5 及既有恢复规则处理。

所选协议版本、SDK 与扩展组合须在实施前核对，并验证两种传输及标准 Tasks／普通工具路径的互操作。支持该扩展是已确认交付目标，不能由 schema 标为 Stable 推定当前 SDK 已完整支持或把未验能力报告为可用。

### 各类入口的规则归属

| 调用方 | 开放与适配边界 |
| --- | --- |
| 工作台／CLI | 沿共同客户端及其已注册产品操作，人工文献管理与编辑等基础动作不依赖 harness；不受 MCP 首批工具清单替代 |
