## Question

哪些科研任务场景最能揭示 Scholoom 需要处理的业务问题？在每类场景中，Zotero＋zotero-agents＋ResearchSpec 已有工具链怎样处理输入、科研工作、人的参与、产物与后续使用，哪些机制值得保留，哪些限制或实际问题需要新设计解决？

本轮先建立有来源依据的场景入口与工具链分工，结合用户的实际使用经验选择首个深入复盘的场景。每个场景从研究者的目标与起始材料出发，沿实际操作、Agent 工作、人类判断、产物落点、跨工具交接与后续变化重建业务路径，逐步提出业务模型问题。

### 首轮复盘的场景

用户选择“从选题、检索到文献综合”。本轮按这一范围核对旧路径并与用户交流实际体验；其他科研场景继续保留在地图，不展开执行接口或预设新的固定流程。

已确认的领域术语、总体原则和七个逻辑模块作为核对依据；场景若显示缺漏或冲突，明确提出再讨论，不把旧模型或旧工具边界直接作为 Scholoom 的设计答案。

### 用户确认的实际体验

- 工具链分散，工具之间的配合有很多环节需要手动操作；用户明确将改善这一点视为 Scholoom 最大的改进目标。具体路径见下，交接涉及的材料与判断仍待继续复盘。
- Zotero 的文献管理很好，值得保留；但它主要面向人类操作，对 Agent 不友好，用户开发 zotero-agents 时因此遇到很多困难。不能把文献管理能力本身不足作为本场景的问题。
- Zotero 运行时限制使文献综合算法需要妥协和取舍，调试与排障困难，用户评价最终效果一般。具体算法取舍及质量表现尚未核对；改变运行环境提供改进条件，不能据此保证综合质量。

### 用户描述的实际路径

1. 开始研究时，先在 Agent 环境中使用 ResearchSpec 与 Agent 讨论。
2. 讨论后到 Zotero 建立研究所需文献库。前一个 Agent 可以通过插件 CLI 指挥 zotero-agents 中的 Agent 执行，但用户评价此链路摩擦很大、使用体验不好且调优困难；自动调用的存在不能等同于科研协作顺畅。
3. 建库后，用户需要在 Zotero 导出研究文献包，再放回前一个 Agent 环境继续撰写。这是用户实际使用路径中的必要交接，不代表源码没有其他消费入口。
4. 撰写主要通过对话开展。用户后来为 ResearchSpec 加入交互界面，但体验仍不如 harness 原生内建的交互舒服；具体界面行为尚未拆解。
5. 同一篇论文有时需要多个 Agent 协作。用户举例 GPT 用于推理、Gemini 用于文风处理，这是其使用偏好，不作为模型性能的普遍结论。当前通过手动让多个 Agent 工具在同一工作区内工作实现协作。
6. 用户以库中 100 篇文献为例，明确希望 Agent 渐进式、按需读取材料；跨工具链实现这类读取摩擦大，难以调到理想状态。因此目前先由 zotero-agents 中的 Agent 综合分析，再导出独立研究包：筛选出的核心文献包含原文，其他文献仅包含 Digest，另含相关主题分析报告。
7. 该研究包提供可直接消费的交付，但预先筛选可能遗漏后续写作所需信息。用户指出打包 Agent 与写作 Agent 的倾向、能力差异会影响这一风险；材料补充或修改后的继续使用也很麻烦。此处的信息损失指后续工作可能无法从包内取得所需信息，不表示文献库原材料已丢失。
8. 用户说明跨文献综合的生成与维护在 zotero-agents 中依靠精心编写、以 Skill 呈现的流水线；虽能实现，但编写和维护困难。用户希望在 Scholoom 中以 LangGraph 重构这些 Agentic 流水线，并通过自主定义的数据类型、依赖关系和触发器，实现顺滑、自动化、对用户无感的维护。

### 当前场景已确认的要求

- Q1：用户回答“都有可能，任何情况都有可能”。研究可从宽泛方向、已有材料、明确问题或候选假设等不同起点开始，文献探索与研究讨论允许往返；不把问题成熟程度作为文献工作开始的统一前置条件。
- Q2：用户明确希望建库交付覆盖筛选理由、单篇分析、主题比较、争议与研究空白等支持继续研究的成果，仅收集题录和全文不足以满足本场景目标。具体工作深度和完成条件仍需随当次研究目的明确。
- 用户明确希望按需、渐进读取文献，避免将全部原文一次性放入 Agent 上下文；后续 Agent 应能根据自己的研究需要继续取材。现有独立研究包是跨工具链取材困难下的实际做法，其便利与筛选局限都需要纳入新设计。
- Q3：用户明确整个文献库通过工具按需、多层级披露进入 Agent 上下文：第一层是标题与元数据，可包含论文摘要；第二层是 Agent 抽取的 Digest，指 zotero-agents 定义的文献分析产物；第三层是原文。支持分层管理的语义检索系统串联三层，允许 Agent 按研究需要接触库内任意主题、范围和深度的知识。授权沿既有任务范围约定；具体检索实现和层间导航契约待后续讨论。
- Q4：用户采纳在当前研究中持续处理材料补充与修改：新材料可被检索发现，相关分析和综合按需补充或修正，再检查受影响的论证；重要交付保留所用版本。研究包用于独立交付、迁移或归档，日常工作直接连接库中的材料与成果。此处采纳业务行为，不代表增量更新已实现。
- Q5：用户基本认可跨文献主题报告作为关联多个来源、可被检索发现并可追到 Digest 和原文的综合成果，进一步要求以 LangGraph 重构其生成与维护的 Agentic 流水线，并由明确的数据类型、依赖关系和触发器支持自动维护。这是已选 LangGraph 与原生融合路线在本场景中的具体要求；Skill 仍可表达分析方法，自动维护的具体覆盖范围待讨论。
- Q6：没有 Digest 时可以回退读原文，但用户更希望自动生成 Digest 等文献分析产物，使用户无需手动维护。首批产物与自动启动行为由以下 Q7／Q9 细化。
- Q7：用户采纳文献入库且可用材料就绪后自动生成基础分析产物；已有库中缺失或受材料实质变化影响的产物后台补齐、更新，当前研究需要的材料优先。必要材料缺失时保留可用层级与实际状态，材料补齐后继续。
- Q8：用户采纳明确主题目的与可用材料范围后，自动发现和评估范围内的新材料，并据此维护综合，用户无需逐篇加入。相关性评估与是否支持结论分别表达；项目正式判断及稿件编辑沿已有授权与变更规则处理。
- Q9：用户采纳以旧工具链的四类成果为起点，自动维护 Digest、参考文献提取、引用分析和文献评价；内容按原生研究用途定义，评分保留评价维度、依据和条件。旧文件名、Schema 和评分规则不自动成为 Scholoom 契约，缺少必要材料的维度保留真实缺项。
- Q10：用户采纳库中的基础分析面向文献自身，供不同任务复用；围绕具体问题的定向分析可以补充或修正文献理解，并按研究语境归属。不同目的、方法或观点的分析可并存，后续 Agent 能识别适用条件和来源；新分析不因生成得更晚就覆盖已有分析。可靠的来源事实更正可以依授权修正基础分析，项目相关性与结论仍归项目。
- Q11：用户采纳主题与研究问题分别表达。主题组织某一领域、现象、方法或议题的相关知识；研究问题表达当前希望弄清的具体问题及其条件。一个主题可服务多个问题，一个问题也可横跨多个主题；综合可围绕主题梳理知识，也可围绕研究问题比较证据与分析争议。主题成果归属沿已有库级复用与项目研究语境规则。
- Q12：用户采纳系统自动发现库中的初步主题组织，人和 Agent 可调整、合并、拆分；研究过程中可按目的形成或重组项目主题。库中长期保留的知识主题和持续研究所需的主题自动维护；临时语义查询即时探索，有后续研究价值时再保留为持续维护主题。
- Q13：用户基本采纳综合发现持续反馈选题、候选研究问题及路线的方向，并明确 zotero-agents 的主题综合设计已经体现这一思想，应借鉴融合。[已有主题综合的融合依据](../research/research-scenarios-existing-toolchain.md#主题综合已有设计的融合依据)核对路线、主张、争议、未来方向、覆盖与写作输入方法；据此继续明确 Scholoom 在原生取材与自动维护方面需要重构的部分，避免重复设计。

### 后续模块与场景待细化

- 不同起点的研究讨论怎样形成文献工作的依据，检索、阅读和综合的发现怎样进入后续讨论并调整研究问题。
- 研究所需文献集合与分析、综合成果如何在同一研究中持续用于写作，哪些信息目前依赖导出包交接，何种结果足以支持下一步。
- 本场景保留原生多 Agent 协作、减少用户手动协调的需求；具体分工、交互和交接方式按用户要求后置到业务功能与 Agent 架构设计阶段。
- 三层文献知识、主题报告的检索及来源关联、LangGraph 自动维护方向、主题形成及持续维护边界已明确；综合反馈选题的方向基本采纳，需借鉴融合旧主题综合已有设计。单篇 Digest、论文摘要和跨文献综合分别表达，主题与研究问题的关系已确认。
- 材料变化后的持续工作、研究包职责、自动分析启动与补齐方式、首批产物及通用与定向分析并存已确认；受影响成果的更新范围与实际质量要求仍需进一步明确。现有归属、授权和变更原则继续沿正式决定。

上述体验说明旧链路的实际问题，不代表已确认新的固定流程或完整业务模型。继续从研究起步、文献工作的交付及其对选题的反馈讨论业务行为，再细化模块契约。

### 后置到业务功能与 Agent 架构设计的协作问题

用户明确 Q15 的实际交接操作应在业务功能与 Agent 架构设计中讨论，本场景暂停此追问。当前保留用户已说明的需求：同一研究中能使用不同模型的 Agent，原生协作减少手动组织多个工具的摩擦。主 Agent 统筹、worker 工作包、职责模型配置和工作台中切换交互对象已有决定；具体发起者、处理范围和交接内容待后续模块讨论时细化，不作为当前场景复盘的前置条件。

## 事实与讨论的分工

- 本地参考文档是历史快照，关键能力和交接核对当前源码并标明版本；声明、静态可追踪与实际运行结果分别记录。
- 只读调查收集入口、输入、产物、权限和交接机制；主 Agent 与用户分析科研含义和设计取舍。
- 用户实际操作、感受、失败与需求通过交流确认；不能从模块拆分、代码限制或参考文档推断用户曾手工搬运、遇到质量问题或发生数据丢失。
- 同时检查已有优势与问题，不为推导新设计只选择负面证据。具体场景先还原旧路径，再选择 Scholoom 应保留或改变的行为。
