## Question

文献元数据、附件、稿件、证据关系、流程状态和搜索索引分别以什么为权威，如何保持开放文件与数据库职责一致？用户、Agent 和兼容插件同时工作时，怎样提交修改、发现冲突、恢复或撤销？

[研究对象与领域边界](06-research-domain-boundaries.md)已确定材料版本、证据定位、主张与稿件关联、变更审查与实际应用的区分，以及缓存重建保留正式决定、绑定和合并结果的要求。本票落实这些语义的物理承载、版本与恢复机制。

[科研 Agent harness 与执行路线](07-agent-runtime-boundaries.md)已确定统一运行时内的科研事实、正式流程进展与执行 checkpoint，以及关窗、暂停、取消和恢复语义。本票明确其持久化与写入权威，并协调节点重新执行和实际操作结果。

[科研能力的运行时契约](18-native-capability-runtime-and-content.md)已确定必要方法与材料信息、分批交付、正式决定及按需恢复。本票选择其持久化方式；普通修改采用轻量文件操作，明确要求复现或不可轻易重复的操作按实际需要保存依据与结果。

[阅读与写作路线](11-reading-writing-format.md)已确定正文源文件权威、编辑模式及原文与稿件定位要求。本票落实源文件与多文件工程、研究关系及派生视图的协调，并覆盖外部编辑器修改、可视写回、材料位置与渲染产物的版本绑定。

检验用户已经改稿而 Agent 基于旧版本提交、进程中途退出、插件修改条目、索引重建及正式迁移 Zotero 文献等情境。确定版本标识、候选与已采用产物、事务边界、派生索引和迁移责任。不要把文件与数据库各保存一套当前状态，也不要默认文件临时备份已经提供跨资源的崩溃原子性。此票决定存储和变更模型，具体数据库库名由技术栈票确定。

## Investigation

- [本地存储与崩溃恢复边界](../research/local-storage-and-crash-recovery.md)：依据 SQLite、Node.js 与 Git 官方文档区分数据库事务、内容发布与跨资源恢复；只有静态调查，尚未选择或运行实现。
- [Zotero 存储与插件权威调查](../research/zotero-storage-and-plugin-authority.md)：核对固定源码版本下 BBT 的 Zotero 原生 SQL／citationKey 依赖、茉莉花的条目与附件写入，以及托管附件、外部链接文件、插件专属状态和迁移备份的区别。兼容视图或存储需与原生权威确定共同写入协议，不能形成两份可自由修改的文献事实；具体实现仍由兼容宿主原型验证。
- [既有 LangGraph harness 调查](../research/langgraph-harness.md)提供执行套件的职责入口。本轮另核对当日官方 [Persistence](https://docs.langchain.com/oss/javascript/langgraph/persistence)、[Checkpointers](https://docs.langchain.com/oss/javascript/langgraph/checkpointers) 与 [Deep Agents Backends](https://docs.langchain.com/oss/javascript/deepagents/backends)：checkpointer 保存执行图状态，store 承载应用数据，文件工具可以接入不同 backend。Scholoom 的科研事实权威、实际版本保存及变更应用仍需沿已确认契约定义；本票未选择 saver／backend 或依赖版本。

## Answer

用户已分轮确认事实归属、项目本地持久化、开放编辑、按价值留存，以及材料、引用文件与备份。2026-10-04 两次回复“同意”，分别采纳低摩擦协同方案及最后三项使用选择，本票解决。以下为当前正式结论；具体数据库、目录与接口由后续架构及技术栈落实。

### 事实按归属持久化

先确定事实属于文献库还是项目，再选择保存位置；Evidence／Claim 等对象类型不决定全局持久化。

| 事实 | 归属 |
| --- | --- |
| 长期文献库的题录、附件记录、批注、可复用摘录和文献自身主张 | 随来源由文献库管理 |
| 文献作者如何使用材料论证其主张 | 对来源实际内容的还原随来源保存，区分提取准确性和判断成立 |
| 项目选用证据及其如何支持、限制或反驳本研究主张 | 项目关系，被引用的库对象保留原归属 |
| 项目自己的数据、实验、代码、计算结果及相应证据和主张 | 项目事实 |
| 稿件表述、采用主张、审稿意见与回应的关系 | 项目内，与对应稿件关联 |
| 文献库与项目的任务、计划、重要决定和必要执行记录 | 跟随负责的文献库或项目 |
| 跨项目复用的综合成果 | 按明确整理和适用条件形成库资产，项目结论不自动成为全局判断 |

Source 可以属于文献库或项目，证据随相应材料归属保存。对证据如何支持、限制或反驳主张的判断按研究语境归属；来源出处与对象归属分别表达。核验文献确实如此表述，不等于本项目接受其判断或认为它适用。术语统一见 [CONTEXT.md](../../../CONTEXT.md)。

### 全局文献库与项目本地数据库，加开放文件

- 全局文献事实保存在文献库数据库；项目结构化事实保存在项目目录内的数据库。正文、笔记、代码、数据、图件及原生方法内容保留开放文件形式。
- 应用全局目录登记项目位置和必要摘要；跨项目查询读取项目权威或可重建索引。项目读取与恢复不依赖应用全局登记数据库。
- GUI 和 Agent 通过共同领域服务处理明确管理的结构化事实；普通文件在授权内直接读写，无需先注册全部工作文件。
- 解析、搜索、全文／向量索引与普通定位视图可以按需刷新或重建。研究决定、明确建立的证据关系、身份绑定及合并结果独立保存，重建索引不能覆盖这些事实。
- 对象保有稳定内部身份，DOI、Zotero key、citekey 和路径沿既有映射语义处理；关键材料及重要交付的版本按实际用途保存。

不让文件和数据库各自保存一份当前正文。具体数据库产品、接入库、Schema、目录名与 checkpoint 接入由后续选型确定。

### 开放编辑与低摩擦协同

默认采用：**开放文件直接工作，Agent 适应变化，内核提供必要保护，重要成果按需留存。**

- 人、Agent、外部编辑器与科研脚本可以在授权内操作普通文件。编译缓存和临时产物按用途过滤，变化不自动产生审查事项。
- 已保存正文以源文件为权威；未保存草稿提供恢复，可以显式交给 Agent。草稿与外部编辑冲突时保留已知内容。
- 修改当前目标时保护实际编辑范围。普通变化由 Agent 重新读取、调整工作或重做补丁，不因整份文件修订不同而停止任务。
- 对同处研究含义有实质歧义、持续竞争或无法保留各方内容时，仅暂停相关修改；其他工作继续。正式研究承诺及授权范围沿已有决定规则处理。
- 普通授权修改直接应用，可查看差异并撤销。用户要求先审或已有授权需要时，再使用候选提案。
- 文件监听是变化线索，相关读取与修改按需核对实际内容。它不提供对任意外部程序的互斥；局部保存机制由架构实现。
- 定位移动、可重建索引过期等问题按需刷新；仍有歧义时在相关工作中提示，不形成要求用户清空的全局待办。
- 正文变化不自动改写已确认研究判断。科研检查聚焦当前任务的关键数字、引用、结论范围与审稿回应，允许局部不完整继续工作，准确表达尚未完成的部分。

工具参数、数据库完整性与授权由程序提供必要保障；Agent 负责适应常见变化和科研判断，人处理确需其判断的事项。

### 任务延续、历史与恢复

- 当前会话承担即时记忆，任务长期保留目标、关键约束、计划、产物、重要决定、已知问题与下一步。中断或换 Agent 后，从这些信息与当前材料继续工作。
- checkpoint 与执行日志用于恢复和必要诊断。普通调用保留必要来源、方法及结果信息，不完整冻结每次调用的 Skill、程序、图、全部输入和运行环境。
- 日常提供撤销、草稿恢复与有界本地历史，Git 是可选工程工具。撤销保护后续编辑。
- 关键证据保留来源、位置、必要片段与研究条件；重要决定留存理由；关键结果、提交稿及审稿轮次保存有意义的版本或快照。
- 完整审查、固定输入与方法版本及精确复现用于明确需要它们的任务。缓存、临时文件与可重建产物按用途清理，明确留存的成果及未解决的内容损失问题得到保护。
- 数据库使用自身事务，文件工具提供必要保存和局部覆盖保护；普通改稿不建立通用跨文件／数据库事务或持久操作状态机。
- 中断后针对下一步核查必要实际结果并续做。不可轻易重复或代价较高的操作保留必要结果线索，未知情况局部核查，避免盲目重复。
- 迁移、批量破坏性操作、备份恢复及明确复现任务按具体风险采用更强机制，不扩大为所有普通修改的默认成本。

### 材料管理

- 新导入文献的附件默认由文献库托管，同时支持已有外部链接。
- 项目稿件、代码、数据与图件直接使用当前目录，不自动复制到应用私有资产区；大型外部材料可以保留链接。
- 移动目录或材料缺失时支持重新定位；缺项只影响实际依赖它的工作。
- 题录字段、附件内容和派生索引各有职责，更正元数据或重建索引不等于改变原材料。

### 引用文件与题录权威

- 已有 `.bib`／CSL JSON 直接作为项目资源使用，保留手工维护内容。
- Agent 加入或更正文献时，按项目约定补充相关条目，或使用用户选择的明确自动导出文件。库导出不整份替换人工维护文件。
- 项目引用键通过映射关联库来源，键名差异由 Agent 处理，实际冲突在相关引用处解决。
- 项目引用文件承载本工程使用的内容，库数据库管理当前文献题录。普通文件改动不自动写回全局题录；更新库事实仍使用相应领域服务。

### 共享材料、备份与独立打包

- 日常共享文献库全文，项目保有自己的研究事实、必要题录、证据片段及分析内容。关键证据和重要交付保留所用材料版本；普通使用按需记录。
- 快照表达历史使用内容，不形成第二份可自由编辑的当前库记录。
- 普通项目目录移动保留本地研究事实；库外材料是否可读取决于材料随目录保存或重新连接。
- 提供可关闭的自动备份，优先保护数据库、稿件、笔记和已管理的重要材料；排除缓存与临时编译产物，大型外部材料按选择纳入，范围明确。
- 独立迁移／归档提供含选用材料的项目包，列出实际未包含的依赖。更换机器保留可持续研究上下文，完整原文核对和计算复现依据实际材料及环境判断。
- 数据库采用所选引擎支持的备份接口，文件保存选用内容。具体一致性范围、执行时机与恢复实现由后续实现核对；日常备份不要求保存完整执行历史或精确重放全部会话。

### Zotero 生态与迁移责任

- 指定版本 Better BibTeX、茉莉花的原包兼容目标保留，详见[兼容策略](05-zotero-compatibility-policy.md)。
- 宿主需满足插件所见的对象、SQL 与文件契约，将条目更新落实到明确的文献权威；插件设置、资源及专属状态按职责保存。不能形成两份可自由修改并各自宣称当前状态的题录。
- 具体兼容视图、Schema 映射或宿主存储由[兼容宿主原型](16-zotero-host-prototype.md)比较验证，不把兼容目标当作实现成功，也不将插件所有副作用扩展成通用事务或审计。
- 正式迁入 Zotero 需保留文献身份映射、集合、字段、引用键、笔记／批注及附件关系，按托管或链接材料的实际位置与可达性搬迁。迁移安排保留源数据，索引可重建；迁移后的各类数据权威明确。
- 具体迁移步骤、支持范围与恢复验证随宿主、选定存储及实现规格落实，本票不执行真实文献迁移。
