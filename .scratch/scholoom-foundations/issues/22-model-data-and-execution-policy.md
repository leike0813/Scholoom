## Question

采用 LangGraph 系列之后，用户怎样配置模型与供应商、选择不同任务所用模型，并控制外部数据发送、凭据、诊断信息及执行资源？

本票确定产品运行配置，承接[科研 Agent harness](07-agent-runtime-boundaries.md)、[领域模块与 Electron 架构](09-electron-architecture.md)和[原生内容与执行契约](18-native-capability-runtime-and-content.md)。前置票均已 resolved，本票可提前讨论，无需等待科研效果评价。

需要明确以下问题：

- 用户怎样配置模型、供应商及不同任务的模型选择；配置在应用、项目和任务之间怎样生效。
- 哪些材料可以发送给外部模型；密钥怎样保存和使用，诊断记录怎样处理可能包含的研究材料与凭据。
- 超时、限流、重复失败、并发及费用上限怎样控制；触及限制时怎样向用户说明实际状态及继续工作的条件。
- 切换模型时怎样保留任务上下文，并明确实际采用的模型；自动重试、回退或切换是否需要用户选择，以及怎样影响数据发送和费用约束。

讨论应考虑现有模型适配与运行时组件能直接提供哪些能力，项目需要补充哪些政策与配置，具体能力以供应商官方说明及固定版本实现为依据。无法获得准确用量或价格时，应明确可控制的范围，不能把估算宣称为可靠的费用上限。

### 与已有票的职责关系

[#21 真实科研 Agent dogfooding 与评价](21-agent-dogfooding-and-evaluation.md)在初步功能形成后选择评价场景、样本、指标和实验预算。本票定义日常产品运行的模型、数据与资源政策；评价运行遵循该政策，并另外选择本轮实验配置。

用户指定的编码子 Agent 委派模型是开发协作偏好，不自动成为 Scholoom 的默认产品模型、支持供应商或科研评价模型。

## 结束条件

用户确认上述配置的职责、默认行为及可调整范围，后续实现规格能够据此定义配置接口、可观察状态和必要验证。具体供应商支持名单及实现版本随接入核对；本票讨论不直接调用付费模型、处理用户实际研究材料或修改现有凭据。
