## Question

什么验证足以证明首阶段产品可用于真实研究工作，怎样控制跨平台发布、数据迁移和 Zotero 生态升级带来的回归风险，同时保持单人项目的维护负担合理？

以[全流程产品形态与真实使用验收](01-first-product-loop.md)确定的产品要求为前提，落实完整科研链路、无工作台执行及工作台随后接入的实际验收。沿 #12 已确认的 Linux 主验证平台与三平台稳定版要求安排检查，真实论文样本在实际验收前补齐。

[UI 调试与 e2e](20-ui-debugging-and-e2e-harness.md)选择 Orca 浏览器与真实 Electron 的调试、检查及框架安排；[真实科研 Agent dogfooding](21-agent-dogfooding-and-evaluation.md)选择隔离的真实任务运行和量化评价。本票在这些决定上落实日常检查、整体验收和发布所需的组合、平台及标准，不将单元测试通过等同于接线或科研效果通过。

依据选定架构明确必要的类型检查、稳定行为测试、端到端情境、手工验收和性能检查，重点包括关键依据定位、保留用户编辑并适应普通变化、局部歧义不阻塞无关工作、会话结束后的状态延续、插件主功能与浏览器保存。按已确认的[低摩擦协同方案](13-storage-and-change-model.md)验证真实工作效果；选择平台验证次序、构建与发布方式、兼容版本维护和迁移恢复策略。避免追求覆盖率或精确锁定 UI 文案和内部实现；发布操作本身不在本票执行。

[源码复用取舍](19-existing-source-and-rust-reuse.md)确认 Synthesis 先用 TypeScript 并独立执行重计算。本票将总耗时、峰值内存、工作台与 Agent 调度响应、取消延迟、数据传递及输出效果纳入适当性能验收，复用已有代表数据；不将旧主线程或完整 Rust 生产链路的结果自动视为新执行环境的验证。

## Answer

用户于 2026-10-04 分两轮回复“采纳”，确认 Q1–Q7。本票确定验证、兼容维护与发布政策并 resolved；#21 保留为稳定版真实科研效果验收的前置事项。具体运行结果随实现记录。

### 按影响范围验证（Q1）

| 改动范围 | 必要验证 |
| --- | --- |
| 普通局部修改 | 受影响包的类型检查及已有相关稳定行为测试；涉及构建或打包接线时验证对应构建 |
| 跨模块或跨进程修改 | 增加对应的真实接线 e2e |
| 共享协议、存储、进程或核心运行时修改 | 扩大到相关入口、数据保护与生命周期 |
| 发布候选 | 产品关键链路、插件主功能、数据保护及目标平台检查 |

本地与 CI 复用包脚本。新增测试覆盖有价值的稳定行为风险；不规定覆盖率门槛，也不为每次修改机械增加测试。长耗时场景按变更影响和发布需要运行。

### 发布阶段与平台验收（Q2）

开发构建用于迭代；预览版明确已验收功能、平台和已知限制，使用隔离样本验证；稳定版需要完整科研流程及真实科研效果验收，具体评价由 [#21](21-agent-dogfooding-and-evaluation.md)承接。

从开发开始维护 Windows、macOS、Linux 构建，Linux 持续运行关键 e2e。发布前在每个声称支持的目标系统上验证实际分发包的启动、独立 Node／原生模块、兼容宿主、文件路径、阅读与渲染工具及关键生命周期；首个稳定版本完成三平台验收。源码或构建成功不代替分发包运行验证。

### 依赖与兼容维护（Q3）

锁定每次发布实际采用的 Electron、Node、Zotero 10 宿主源码、插件／translators／Connector 和所吸纳组件基线。按实际兼容关系记录版本组合及已验收功能，不枚举无意义的全量排列。

升级先在开发版本验证受影响接线及现有关键场景，通过后扩大支持记录。原插件包保持不修改，宿主适配由 Scholoom 维护；具体功能继续沿 [#05](05-zotero-compatibility-policy.md)。普通升级按需要推进，紧急修复及时验证；Electron／Node 的安全维护与 Zotero 兼容基线分别推进，按实际兼容关系选择升级组合。

### 高影响变更与恢复（Q4）

Schema 升级、Zotero 正式迁入及批量高影响修改先在副本／样本中验证实际结果和恢复路径，保留源数据与必要备份。检查既有身份、字段、集合、引用键、笔记／批注、附件关系及用户编辑是否保留；针对失败、中断和重新启动检查可恢复性，备份必须实际恢复核对。

应用版本回退与数据恢复分别处理。旧应用能否读取新 Schema 需有明确支持；恢复时保护升级后新增的研究成果。普通改稿继续沿 [#13](13-storage-and-change-model.md)的轻量局部保护，不扩大为全库冻结或通用事务。

### 性能验收（Q5）

复用已有代表性数据，加上长稿、批量文献、PDF／图谱和长 Agent 会话的实际使用样本。在明确硬件、数据规模与环境下记录总耗时、进程／整体内存、界面交互与内核调度响应、取消延迟及数据传递成本；重计算时实际操作工作台，并检查其他任务能否推进。

相同条件重复必要测量，报告波动与影响；模型或网络等待与本地执行分别记录。初步实现后依据首次测量及日用体验确定规模与门槛，相关改动比较回归。迁入 Worker、旧 Rust 指标或单次算法速度不证明整体性能已经通过。

### 分发与更新（Q6）

优先 GitHub Releases 保存版本、分发包、支持范围及已知限制；CI 准备候选产物，公开发布沿具体授权执行。早期预览版手动下载安装更新，保留既有研究数据；自动更新以后按实际需要使用 `electron-updater` 的现成链路，保留手动安装入口。

更新在用户选择的时机执行，先保存编辑，等待或暂停受影响任务，再协调独立内核及兼容宿主停止／重启，检查旧版到新版的迁移和恢复。仅关闭桌面窗口不足以认定后台已经停止，更新不能静默中断科研任务。

签名、公证、安装包格式及 CPU 架构按实际公开分发条件落实，所需凭据及费用另行授权；具体支持的系统和架构以分发包实际验收为准。依据见 [分发与更新核查](../research/desktop-release-and-update-facts.md)及 [签名与构建核查](../research/desktop-signing-and-build-facts.md)。这些调查仅核对官方能力，未证明本项目发布链路可用。

### 整体验收与本票结束条件（Q7）

整体验收组合包含已确认的全流程产品要求、[#20](20-ui-debugging-and-e2e-harness.md)的实际接线、数据保护与迁移恢复、插件和 Connector 关键功能、性能及目标分发包检查。科研指标及实际论文样本留待 #21 恢复；未满足前不宣称稳定版验收完成。

本票政策定案、实际验证与发布分别记录，具体规格及检查脚本随实现落实，不另建长期验收账本。当前未运行应用测试、构建、迁移、性能测量、签名或发布；性能门槛、科研评价细则、具体系统／架构组合及发布凭据仍需在相应阶段落实。

本票完成不自动启动实现规划、安装依赖或发布；实现规划继续由用户决定启动时机。
