## Question

隔一段时间回到已有研究，或将已有材料、分析和成果用于新的研究问题时，Zotero＋zotero-agents＋ResearchSpec 怎样支持接续工作和复用？用户实际怎样操作，有哪些值得保留的能力或需要改善的问题，据此是否显露尚未明确的核心业务关系？

本场景关注研究进展与成果的长期使用。文献自动维护、分层读取、稿件修订以及多 Agent 的具体交接已在前序场景定位，不重复展开；不预设用户存在遗忘进展、来源丢失或复用失败等问题。

## 已有依据与讨论边界

- [领域边界](06-research-domain-boundaries.md)已区分长期文献库的通用分析与具体项目的判断，复用保留必要来源和适用条件。项目成果可以主动整理为跨项目知识，不能自动将项目结论视为全局判断。
- [存储与变更模型](13-storage-and-change-model.md)已确认开放文件、项目本地研究事实与任务延续。中断或更换 Agent 后从长期目标、计划、产物、重要决定、已知问题及当前材料继续；完整会话重放和精确复现按明确需要采用。
- 术语以 CONTEXT.md 为准。本轮先对照旧做法和用户体验，不重新选择存储方案，不设计记忆系统、索引接口或自动整理触发器。
- 具体研究项目与资产、科研业务和 harness 的设计留到场景与核心业务模型明确后讨论。本票完成不自动启动 OpenSpec 或实施。

## 当前调查

只读核对旧工具链普通文件与正式流程中的接续方法、进展与产物读取，以及已有文献分析和研究成果的复用路径。复用前序调查，不将缺少专门字段或命令推断为功能缺失；方法要求、程序实现与运行证据分别记录。

依据见[续做与复用事实底稿](../research/research-continuation-existing-toolchain.md)。普通工作从任务笔记与当前材料恢复，正式 run 按状态与 instructions 接续；用户的实际体验与静态源码事实分别记录。

用户已明确：如果工具链版本不更新，续做和复用其实还好；主要麻烦是补充材料，这一点已在首个场景提出。本轮不将该条件扩大为已确认的版本升级故障或新产品需求。

## 结束条件

有依据地说明旧路径，与用户明确本场景真实问题、应保留的能力及需要补充的业务关系；具体模块机制后续承接。

## Answer

2026-10-08，用户确认在工具链版本不更新的条件下，本场景基本顺畅；主要问题仍是补充材料的摩擦。用户进一步解释，ResearchSpec 已采用不同 session、不同 Agent 可以几乎无损地从工作区获得所有上下文并承接此前工作的设计，要求 Scholoom 采用这一设计。本票按场景复盘范围收束，保留并明确这项已有优势，不新增领域概念。

### 工作区承接设计

- 科研上下文在工作区中持续保存并可取回，支持不同 session、不同 Agent 几乎无损地承接此前研究；这是用户明确要求吸纳的 ResearchSpec 设计。
- 承接所需上下文覆盖研究目标与约束、已有材料与分析、进展与产物、决定及理由、已知问题和后续工作，并能按需回到具体内容。后续设计和验收需检查新 session／Agent 能否理解并继续已有研究，不将简短交接摘要视为全部上下文。
- 与首个场景的渐进取材一致：上下文可以完整取得，实际进入模型上下文的材料按需分层披露。持久化、来源与适用条件继续沿已确认领域和存储边界，具体组织、维护和取回机制后置到模块设计。

“几乎无损承接”在本轮作为用户体验与设计目标记录，实际效果仍需后续验证；精确执行重放继续按明确科研需要采用。

补充材料的问题沿[首个场景](26-research-scenarios-and-existing-toolchain.md)已确认方向处理：日常研究直接连接文献库，Agent 按需分层读取；新材料可被发现，相关分析与综合按需补充或修正，再核对受影响的论证。研究包用于独立交付、迁移与归档。这些业务行为尚待实现和验证。

任务延续和跨项目复用继续沿既有领域、harness 与存储决定。用户没有报告其他续做或复用痛点；工具链版本变化的具体影响本轮未讨论、未验证。本票解决不代表所有科研场景或模块设计已经完成，也不自动推进 OpenSpec。
