## Question

“All by agents”在长期开发中要求什么协作方式？人类保留哪些产品和架构决策，Agent 怎样调查、计划、实现和审查，如何让多个 Agent 的产物与同一套契约保持一致？

明确地图、决策票、CONTEXT、ADR、OpenSpec、项目 AGENTS 与代码各自承载什么，避免重复维护事实。讨论任务粒度、上下文入口、并行协作与合并责任、实现前的契约，以及何时需要人工确认。进一步讨论 production-ready 的 Agent native 开发模式：让 Agent 能够理解当前项目、运行和观察应用、验证实际行为、继续未完成工作，并根据真实开发反馈改进环境。沿用用户全局规则作为当前约束，新增纪律必须有实际维护价值，不建立形式化流程或纯文本匹配门禁。本票先决定原则及需要继续探索的方法，具体工具与规范按后续讨论落实。

## Answer

用户于 2026-10-04 经多轮讨论确认以下工程纪律，最后回复“同意”确认代码组织、UI／e2e 分工和 dogfooding 评价原则。本票解决共同约定；具体工具、目录布局、接线及验收阈值在后续票中落实。

### 开发环境也是 Agent 的工作对象

以 Agent 能持续交付可用、可维护的改动，并减少人工救火、重复解释与返工为目标。项目提供可发现、可运行、可观察、可验证并持续改进的开发环境；文档、规格与记忆提供方向和背景。

现有编码 Agent 承担执行，项目维护开发工具入口、样本、观察能力、必要检查与 Skills。工程资产跨会话延续，先接通实际使用的运行时；是否需要自建开发调度器或让 Scholoom 自身承担开发，依据真实需要另议。开发配套与产品内的科研 Agent harness 各有职责，产品运行时选型不自动决定开发编排技术。

### 人机分工与协作

- 用户把控产品目标、体验、领域语义与核心架构，主 Agent 调查、说明取舍、协调并完成整体交付。宏观判断由主 Agent 与用户直接讨论。
- 在已批准方案内，Agent 持续实现、整理、修复和验证，自行处理局部选择；实质改变已确认方向时回到讨论。适应用户编辑，保护已有改动，既有决定无需反复确认。
- 任务按独立成果、模块与责任拆分。事实调查、独立实现和审查按收益委派，使用用户当前指定模型；共享接口有明确负责人，主 Agent 实际整合并验证跨模块行为。
- 小改动自查并做相关验证；数据损失、关键接口、并发或复杂整合安排独立实现审查，不建立固定角色流水线。
- 实际操作继续遵循用户现有授权规则。本票确认不自动授权安装依赖、启动开发服务器、创建工作树、提交或切换 Git。

### 规格与文档

新功能、公开接口／状态语义变化、数据迁移及核心跨模块约定采用 OpenSpec，按实际复杂度组织变更。已有契约内的小范围清理、文字调整与简单修复采用轻量路径。实现前明确涉及的语义与接口，已批准范围内的新事实同步到相应规格；方向改变再讨论。

| 工件 | 职责 |
| --- | --- |
| 地图与决策票 | 探索问题、保存选择与理由；地图只作索引 |
| OpenSpec | 当前行为约定及正在实施的变更、设计与任务 |
| CONTEXT.md | 领域术语与含义 |
| AGENTS.md | 简洁执行约定与上下文入口 |
| README／开发说明 | 实际使用、上手及工具链入口 |
| ADR | 少量难逆转、确有取舍且需要解释的架构决定 |
| 代码与测试 | 实际实现及稳定可观察行为 |
| Skills／OpenViking | 可复用方法／可检索经验，补充当前事实 |

同一事实集中维护，其余引用；已有决策解释充分时直接引用，避免重复 ADR 和任务账本。Agent 按当前任务读取相关资料，代码与规格不一致时查明并修正相应事实源。交付说明实际成果、必要验证与结果、未解决事项；续做保留目标、相关入口和下一步。进度沟通围绕成果、发现及真正需要用户决定的事项。

### 代码组织与检索

目录表达领域能力及职责，文件名表达具体用途，符号尊重已确认领域语言，如 `ResearchTask`、`CapabilityInvocation` 和 `Source`。技术对象使用清楚的技术名称。

领域实现保持职责集中；Electron 启动、IPC、进程装配和第三方适配有明确位置。共享概念与接口只有一个事实源，通过明确接口协作。依据职责和调用关系决定文件粒度，避免无关功能堆入通用目录或巨型管理器，不强制一实体一目录、一函数一文件或固定行数上限。

具体目录在进程与技术栈确定后落实。索引、语义检索和文本查询沿用 CodeGraph、OpenViking 与 ripgrep，不另建上下文或索引工具链；CodeGraph 继续遵守用户对已索引仓库的规则。

### 开发操作与 UI 调试

构建、运行、样本准备、观察及检查有清楚入口、参数和结果位置。复用实际 CLI、脚本和工具，重复困难再整理为可调用能力；本地检查与 CI 尽量使用同一实现。开发实例使用明确的数据目录、样本与日志，需要并行时能够区分实例。

Orca 内置浏览器用于探索日常 UI 调试，e2e 框架维护可重复执行的关键流程。探索同一份工作台前端的浏览器开发入口；实际业务连接同一领域实现，布局样本与真实接线结果明确区分。开发通信适配由架构和原型决定。preload、IPC、原生功能和生命周期在真实 Electron 实例中验证。

Orca 简单页面的 snapshot、点击与 console 已实测；截图仍有空白问题，详见[事实核查](../research/orca-ui-and-researchspec-dogfooding.md)。框架选择、实际接入与验收安排集中在 [UI 调试与 e2e](20-ui-debugging-and-e2e-harness.md)；实际运行验证随业务实现开展。

### e2e 与必要检查

关键流程首次能从入口经过实际领域执行、持久化到产物时，开始建立并规范 e2e；后续相关跨层改动优先维护这些场景。单元测试覆盖有价值的行为缺口，不能代替端到端接线验收。

确定性 e2e 可在外部模型边界使用受控响应，内部核心接线运行实际实现；真实模型效果由 dogfooding 检验，具体边界由专票落实。

类型、协议及稳定行为由程序检查；架构与维护规则仅在明确、可稳定判定且有收益时落实为工具。交互与科研效果结合真实情境、独立评估与用户判断。检查反馈提供相关位置、预期／实际行为及定位线索。日常先做受影响的必要检查，复杂整合与发布扩大范围；局部问题局部处理，失败或未验证的相关行为不得声称已完成。避免低价值覆盖率、脆弱精确文本断言和形式分数。

### 真实科研 Agent dogfooding

主要功能与接线完成后，通过产品公开入口实际调用 Scholoom 原生科研 Agent，验证其运行时、工具、持久化和产物。外部 Agent 可以驱动或评价，不能绕过产品写出预期产物后将其视为验收通过。

参考 ResearchSpec 的场景、真实执行和评价分工。Orca 管理工作树与 terminal，场景和评价方法保存在项目中。每次运行使用独立的文献库、研究项目、应用配置和输出空间；代码工作树分离还需配合运行时数据与必要权限隔离。

| 评价方面 | 关注结果 |
| --- | --- |
| 完成效果 | 首次完成、重试后完成、实际交付 |
| 科研质量 | 依据与引用正确、产物可用 |
| 用户摩擦 | 人工纠正、无效确认、需要接管 |
| 持续工作 | 取消、恢复、材料变化后的适应 |
| 执行代价 | 耗时、可取得的模型用量与费用 |

客观行为由程序检查，产物质量由独立评估者判断，人工重点审阅争议、失败及代表性成果。重复运行分别保留首次结果、重试与恢复，基础设施失败和产品失败分别统计，未知不算通过；客观指标与模型评分分别展示，关键失败不被平均分掩盖。

可判定样本先验证接线及适应变化，逐步加入真实论文和项目材料；根据每轮任务明确模型、样本、重复次数、超时和预算。指标定义、评分尺度、阈值和首次场景由[真实 Agent dogfooding](21-agent-dogfooding-and-evaluation.md)落实，发布组合由[验证与发布纪律](15-validation-and-release-discipline.md)决定。测试范围的先后不改变全流程产品要求，测试记录按评价需要保存，不扩张为日常科研操作门禁。

### 持续改进与后续边界

依据真实失败与用户反馈改进相应工程资产：反复找错位置改善代码组织；重复操作失败改善入口和反馈；可复现回归补足必要验证；反复有效的方法整理为 Skill 或经验。当前代码和运行结果用于判断经验是否适用，不将每次局部故障变为长期规则。已批准任务内可改进相关配套，核心方向与权限变化仍由用户决定。

**实现路线继续搁置，由用户判断时机成熟后再规划。** 本地图可随讨论扩展，决策票完成不自动触发实现规划。工程规范文件和可执行配套在后续真实工作中依据已选工具落实；本次未创建应用代码、项目规范或 OpenSpec 变更。
