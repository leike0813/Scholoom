## Question

在已确认的共同科研运行时及模块划分上，科研能力与 workflow 怎样实际进入 harness，Agent 执行上下文怎样组织，嵌套调用与流程步骤如何关联，独立检查怎样成为可执行的交付要求？

### 已确认的依据

- [科研 Agent harness](07-agent-runtime-boundaries.md)已选定 LangGraph、LangChain 和 Deep Agents；普通任务与正式流程共用运行时，按实际需要委派 worker。
- [核心模型](17-native-research-capability-model.md)已区分任务、能力调用、执行记录与会话；加载 Skill 或执行一次工具不自动创建任务，工作流可作为能力调用。
- [原生内容与执行契约](18-native-capability-runtime-and-content.md)已确定标准 Skill、YAML 能力声明、JSON Schema 输入／交付、Agent／程序／图执行绑定，以及 execute(request, context) -> submission 的共同职责。普通方法可由通用科研 Agent 执行，正式研究决定仍按授权确认。
- [七个逻辑模块](24-logical-modules-and-responsibilities.md)已划分科研业务定义与 harness 运行机制，并将执行环境作为 harness 子系统。
- [工作区承接](35-research-workspace-context.md)已确认科研过程持续保存为工作区工件，内容形成时写入，后续步骤使用已保存材料；接续独立于 Agent 的 session context 与 transcript。

### 本票需要细化

- 当前 Agent 使用已声明能力时，默认沿用当前执行上下文还是隔离调用上下文，哪些情境需要 worker 或独立会话；同一 Agent 配置、Agent 会话与能力调用分别怎样使用。
- workflow 调用内部能力时，外层调用、内部调用、流程步骤和负责的研究任务怎样关联；取消、分批交付与恢复时能读取哪些工作事实。
- 内置能力声明的交付检查怎样指定独立复核，检查者需要什么材料，检查失败或分歧怎样交回负责 Agent；正式决定继续沿既有授权办理。
- 科研步骤怎样调用持久化工具、关联研究记录与实际产物，并核对保存结果；更新触发、分批交付与中断后的继续方式须落实工作区承接契约。
- 按[多模型协作票已确认的文风 advisor 接线](37-multi-model-research-collaboration.md)，怎样显式开启／关闭 advisor、提供当前有效写作上下文并更新增量、在生成文本后注入修改建议；落实后台评审、本轮结束有限等待、建议引发的继续不自触发监督及主动停止后的处理。关联建议与写作 Agent 的实际修改，落实材料授权、持久化及中断恢复。[omp 官方机制](../research/omp-advisor-writing-reference.md)作为接线参考，业务行为以多模型协作票 Answer 为准。

以文献自动分析／综合维护、分工审稿和专门文风监督核对共同运行机制；业务角色、方法与用户体验由各自票确认，本票只承担执行上下文、调用关联与运行交付的共同契约，避免重复定案。跨 session 的材料取回沿[工作区承接](35-research-workspace-context.md)处理。

具体内置科研方法清单、各领域完整操作接口、沙箱实现、工作台布局、SDK 精确字段与源码布局由后续相应讨论或实现规格承接。本票不重新选择技术栈，不创建另一套 workflow 执行系统。

## Answer

2026-10-09，用户认可复用方法加载、能力入口自动记录及工作流步骤记录的简化方案。下方执行、持久化、复核与 advisor 接线沿已确认的 #17／#18／#35／#37 整理，未另增业务对象或流程。精确字段、框架扩展点和版本随实现规格核对。

### 复用现有执行与记录

2026-10-13 补充：按 [#45](45-interactive-research-reports.md)，Agent、科研能力与工作流共用一等原生交互接口，工作台呈现、界面更新与用户交互回传沿共同路径接入。迁入的 zotero-agents 与 ResearchSpec 工作流复用这一入口；工具签名、消息契约和等待恢复细节继续细化。

普通研究由当前 Agent 加载方法、使用获授权工具并保存科研产物，关联已有任务。明确调用科研能力入口时，输入核对、必要调用记录及结果检查由运行时随执行处理；不要求 Agent 为每项方法另外执行登记、开工和结项操作。纯 Skill 使用沿既有轻量约定。

工作流整体沿已有能力调用管理，内部复用方法或能力实现时利用 LangGraph 步骤及结果记录，必要产物关联对应步骤。内部实现不逐层自动创建新的业务能力调用；确有独立科研使用或交付需求时，再沿已有核心模型记录相应调用与任务。

必要的任务授权、实际成果保存、交付检查及中断恢复沿已确认契约落实。文风 advisor 接到写作执行的上下文更新与生成文本边界，通过建议消息影响写作 Agent，按已确认规则有限等待和停止；共同运行接口的具体字段随实现规格确定。

### 执行上下文与协作

普通方法默认由当前 Agent 在当前工作中使用，沿共同执行上下文取得任务／调用身份、获授权服务、事件、取消信号与交付通道。需要并行、独立审阅或独立上下文时，沿原生工作包委派 worker；加载方法或调用工具本身不改变任务、调用或会话身份。此为执行职责，不预定通过递归调用同一个 Agent 图实现。

声明明确要求独立复核时，把检查目标、实际产物、必要材料和交付标准交给相应审阅者。学术分工审稿沿 #37 独立初审，保留原意见；负责 Agent 根据问题安排补充或修订，再按原交付要求检查。程序检查结构、引用、实际保存及必要正式要求，科研判断由对应 Agent 依据材料作出，执行成功不能替代交付成立。

### 持续保存、分批交付与恢复

沿 #35，把分析、方案比较、理由及下一步作为相关科研工作段的产物，通过文件或领域工具在形成时保存。工具返回实际保存结果与可读取引用，运行时沿交付通道关联任务、调用或工作流步骤，并核对保存与声明的必要产物。后续步骤直接读取这些材料；提示词要求或 Agent 自述不能替代实际保存。

各批产物及相关问题随执行保存并局部核验，已满足用途的成果可以使用；整体完成仍依据整体交付要求。取消停止未完成执行并保留已保存成果。恢复时读取当前材料、步骤结果、待解决问题和正式决定，继续尚未完成工作；高代价或难以重复的操作先核对实际效果。跨会话科研承接沿工作区事实，执行 checkpoint 仅辅助运行恢复。

2026-10-14，用户确认以安全接续工作为恢复目标，允许 checkpoint 失效后重新组织执行，不要求还原原图节点或完整会话上下文：

- checkpoint 可用且兼容时，核对当前材料、有效授权及实际操作结果后恢复原执行；缺失、损坏或不兼容时保留旧执行记录，从持久材料开启新的执行尝试，接续原工作。允许重新读取和分析，未保存的临时上下文可能丢失。
- 目标、约束、研究理由、成果、正式决定和未决问题从各自持久事实源取得。已受理但未处理的指令和协作消息保留可查询的处理状态；可能发生的副作用保留必要核查线索，不另存一套完整 Agent 状态或默认复制全量工具历史到领域表。
- 效果未知的操作先核查，不能确认时暂停相关步骤，其他独立工作可继续。用户暂停或取消的工作不因恢复自动启动。普通会话没有关联研究任务时，仍可沿已保存指令、材料和执行记录接续，不为恢复自动创建任务。
- 产物先实际保存，再登记关联；关联允许部分成功，保留已确认关联，逐项说明未关联或结果未知的项。重试补齐缺项，重复提交同一关联不制造重复记录。关联失败不删除实际文件，部分登记不表示任务完成；数据库写入失败按实际确认结果报告，文件检查成功不等于关联已提交。事务及分批方式由实现确定。

2026-10-18，[持久化与恢复决议](../../runtime-architecture/issues/04-execution-persistence-and-recovery.md#answer)进一步确认会话可用完即弃，任何工作推进不依赖会话记录或上下文；用户发送消息统一推进工作，恢复属于内部机制。工具收据复用已有 harness 机制，核查复用所属模块状态和实际结果，不另建通用调用台账。后台结果由 Agent 判断后续；必要记录无法保存时停止依赖它的新操作，独立工作可继续。正常跨轮有效上下文、保存顺序及实例接管沿该票，具体接线由后续 OpenSpec 变更落实。

正式流程沿共同服务保存待决定事项、依据和授权主体，等待与恢复接入原生执行机制。图的步骤完成不自动满足正式要求；决定返回后核对当前适用条件，再继续相关工作。

### 文风 advisor 接线

沿 #37，将显式开关、当前有效写作上下文的初始化及后续增量更新接入写作执行。Agent 生成文本完成后触发后台评审；建议提交提供目标定位、理由和改写，通过可消费的执行边界注入写作上下文。写作 Agent 结合研究依据处理，并保存建议、处理理由与实际修改关联。

本轮结束时有限等待已触发评审，建议引发的继续不再次触发同一轮监督。关闭或主动停止后停止新增监督与自动继续，未注入建议保留供查看；超时或失败如实标明监督未完成，模型切换沿既有政策。当前协作使用运行上下文，后续会话沿已保存科研材料继续。

### 三类情境核对

以下为既有决定与简化方案的语义核对，未运行应用或科研模型。

| 情境 | 执行与记录 | 交付和继续 |
| --- | --- | --- |
| 单篇精读 | 当前 Agent 加载方法、读取材料、保存分析；明确调用能力时由入口管理必要调用记录 | 按实际分析及来源核验；缺全文时保留成果与问题，继续获授权获取，不因方法加载另建任务 |
| 文献综合 | 整体工作流关联负责的任务，内部分析及比较利用步骤与结果记录，保存综合依据 | 已完成部分可供后续使用；中断后沿保存材料与未完成步骤继续，需要独立目标与交付时才另立调用或任务 |
| 带正式决定的审阅修订流程 | 审阅者沿工作包形成独立意见，负责 Agent 汇总修订；正式事项由共同服务保存 | 核对实际修改、必要复核及正式决定后推进；待决定期间已保存成果继续可读，恢复核对当前材料与授权 |

这些情境未暴露需要新增核心概念或业务流程的缺口。本票设为 resolved；后续工作台交互、执行环境与跨模块走查沿各自票继续，业务实施仍由用户决定时机。当前只有开发骨架，尚未验证运行时自动记录、持久化核对、独立复核、advisor 消息时机或中断恢复。
