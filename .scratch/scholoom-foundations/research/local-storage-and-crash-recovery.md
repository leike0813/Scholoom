# 本地科研工作台的源文件与数据库：修改和崩溃恢复边界

调查日期：2026-10-03。范围是本地 Electron/Node 工作台中“正文源文件权威、SQLite 保存结构化数据”时，能对真实写入和崩溃恢复作出什么保证。以下依据为当日静态阅读的 SQLite、Node.js 与 Git 官方文档；未运行代码、故障注入或平台实验，也未选择 Scholoom 的最终存储方案。

## 结论先行

SQLite 的事务可以让一个数据库事务中的数据在数据库范围内提交或回滚，并按其文件系统、同步和硬件假设抵御进程中断、系统崩溃或断电。它不会把正文文件写入纳入 SQL 事务。Node.js 提供写入、重命名、同步和监听文件变化的接口，但这些接口组合起来并不自动成为文件系统事务；Node API 对 `rename` 也没有给出跨平台的崩溃原子性/持久性承诺。因而，“SQLite 已提交”与“多份正文文件均已更新”是两个提交事实，二者间断电可能留下混合状态。

真实的跨资源保证必须明确发布边界、故障范围和恢复方式。可选路径包括串行协调写入、可恢复的持久操作记录，以及先写入不可变内容再以单一权威指针发布。前两者让应用负责协调和恢复；第三种通过约束读者只沿一个原子更新的权威入口读取来隐藏未发布内容。若必须要求数据库与可直接打开的多个可变文件在任意断电时同时全有或全无，就需要一个共同事务边界，SQLite 与普通 Node 文件 API 本身没有提供这个边界。

## SQLite 事务实际覆盖的范围

- SQLite 文档把原子提交定义为：单个事务内的数据库变更全部发生或全部不发生；数据库能在操作系统崩溃或断电时维持这种数据库内原子性。其回滚日志提交过程会先持久化恢复信息，再写数据库页并同步，最后完成提交标记。这个承诺依赖文件系统、锁、`fsync`、设备行为等假设；SQLite 文档也明确指出错误实现的同步/刷新可能导致断电后数据库损坏。[SQLite Atomic Commit](https://sqlite.org/atomiccommit.html)
- SQL `BEGIN`/`COMMIT` 管理数据库读写；错误、关闭等情形的回滚行为有其数据库语义。事务不会自动包含 Node 对源文件执行的 `writeFile` 或 `rename`。[SQLite Transactions](https://sqlite.org/lang_transaction.html)
- 单个连接 `ATTACH` 多个 SQLite 数据库，在回滚日志模式和满足前提时可以使用 super-journal 实现跨数据库文件的原子提交；WAL 模式下，涉及多个附加数据库的事务只保证每个数据库各自原子，不保证这些数据库作为整体原子。即便是回滚模式的多库事务，也仍然只涉及数据库文件，不包括普通正文文件。[SQLite Atomic Commit：Multi-file Commit](https://sqlite.org/atomiccommit.html#multi_file_commit)、[SQLite WAL：限制](https://sqlite.org/wal.html#overview)
- WAL 让读者和写者可并行，但同一数据库仍只有一个 WAL 写者。WAL 依赖共享内存索引，访问同一库的进程必须在同一台主机，不能把网络文件系统当作等价部署环境。[SQLite WAL：并发与限制](https://sqlite.org/wal.html#concurrency)
- WAL 中已提交但尚未 checkpoint 的内容可能只存在于 `数据库-wal`。SQLite 明确要求复制或移动数据库时连同 WAL 一起保留；只拷贝主数据库文件可能丢失已提交事务或损坏副本。对运行中的数据库制作快照，应优先使用 SQLite Online Backup API（或等价的 SQLite 原生备份接口）：文档描述它可在线逐步复制，并产生开始复制时数据库状态的快照。普通文件复制即便加锁也有其适用条件，且复制过程中断电可能损坏副本。[SQLite WAL 文件](https://sqlite.org/wal.html#the_wal_file)、[SQLite Online Backup API](https://sqlite.org/backup.html)

## Node 文件 API 能保证什么、不能保证什么

- `fsPromises.writeFile()` 的 API 是异步写入并替换已有目标；默认 `flush` 为 `false`。即使设置 flush，文档承诺的是成功写入后调用 `filehandle.sync()`，不是把写入与数据库提交或其他路径合并为事务。写入取消是尽力而为，取消时仍可能已有部分数据写出；Node 也提醒不要在同一文件上并发调用多次 `writeFile` 而不等待前次完成。[Node.js `fsPromises.writeFile`](https://nodejs.org/api/fs.html#fspromiseswritefilefile-data-options)
- `fsPromises.rename(oldPath, newPath)` 的文档只说明将路径重命名，没有声明跨平台的原子可见性、断电后持久性、目录项同步语义，亦没有多路径事务语义。临时文件写完后再重命名可以作为单个文件的发布技巧，但若把它提升为崩溃保证，仍须限定并核实操作系统、文件系统、同卷/跨卷条件、替换行为和同步顺序；不能仅由 Node API 推出普遍保证。[Node.js `fsPromises.rename`](https://nodejs.org/api/fs.html#fspromisesrenameoldpath-newpath)
- `filehandle.sync()` 请求把该打开文件的数据刷新到存储设备，具体实现依操作系统和设备而定。它不等于 Node 明确承诺目录项、重命名或多个文件已一起持久化。[Node.js `filehandle.sync`](https://nodejs.org/api/fs.html#filehandlesync)
- `fs.watch()` 提供变化通知，不是可靠变更日志或持久提交信号。事件语义依平台而异；文件名可能缺失；Linux/macOS 对路径解析到的 inode 监听，删除后重建路径时 watcher 可能仍监听旧 inode；网络文件系统和虚拟化宿主目录上监听可能不可靠甚至不可用。应把 watcher 当作尽快触发重新扫描的提示，启动、重连或发现不确定事件后仍需以磁盘内容和版本信息核对。[Node.js `fs.watch` 与 caveats](https://nodejs.org/api/fs.html#fswatchfilename-options-listener)
- 因而，“一次 rename 原子替换一个路径”“writeFile promise 成功”“watch 收到一次事件”均不能单独推出：所有相关文件已经持久、目录树处于同一代、SQLite 已与文件同步，或外部编辑没有并发写入。Node 当前 API 文档未给出这些合并保证。

## 将承诺写成可检查的状态

设计讨论应先分别说明以下三种承诺，而不要统称“原子保存”：

1. **数据库原子性**：一个 SQLite 事务提交或回滚哪些结构化记录；所用 journal mode、`synchronous` 策略和文件系统假设是什么。
2. **可见性/发布原子性**：哪些读者通过哪个权威入口观察某一代内容；提交过程中是否允许读者看到部分文件已更新；成功响应表示内容已写入、已发布，还是只记录了待处理操作。
3. **崩溃后收敛/恢复**：覆盖进程退出、操作系统崩溃、断电中的哪些情况；启动后如何识别未完成操作、冲突和外部修改；系统会继续完成、回滚到旧版、保留新内容待人工裁决，还是拒绝自动恢复。SQLite 可以自动恢复其数据库事务，不能替应用判断文件与数据库哪一方符合用户意图。

对于正文文件权威的约束，还需定义版本核对：写入前所基于的源文件版本如何识别；若用户或外部编辑器已改变它，应用如何避免静默覆盖；结构化数据库记录引用哪一代正文；崩溃后发现记录与磁盘代际不一致时以何种规则重建或暂停。文件监听只能辅助发现，不能充当版本事实源。

## 少数实现方向及维护代价

这些是供取舍的机制类别，不是预选方案或完整设计。

下表中的维护成本是按需要实现和长期维护的协调、校验及恢复职责作的相对判断，不是 SQLite、Node 或 Git 文档给出的指标。

| 方向 | 可对外描述的保证 | 主要代价与边界 |
| --- | --- | --- |
| 单个协调写者 | 应用内所有写请求串行经过同一协调者；数据库部分各自使用 SQLite 事务；文件按约定次序更新。可以减少应用内竞争，并让提交过程易于追踪。 | 需要所有应用写入口遵守单写者规则，还要处理外部编辑器、崩溃和“文件成功而数据库失败/反之”。串行化不等于跨资源原子性；通常是低到中等维护成本。 |
| 持久操作记录 + 启动恢复 | 先在 SQLite 事务中记录操作意图、目标路径/版本及可验证的进度，再执行幂等文件步骤并记录完成；启动时扫描未完成记录，校验磁盘实际状态后继续、回滚或标记冲突。可承诺“已记录操作最终被恢复或显式报告”，前提是日志与恢复分支覆盖所有中断点。 | 需定义状态转换、幂等性、旧内容保留策略、重复请求、版本冲突和人工介入。中间物理状态仍可能部分更新；若读取者不检查发布状态，也可能观察到混合版本。维护成本中到高。 |
| 未发布的不可变产物 + 单一发布入口 | 先生成新的、不可变且可校验的文件/目录版本；准备完成后，只更新一个权威指针/manifest/数据库记录作为“当前版本”。读者必须先解析该入口，不能按可变路径拼接当前版本。若唯一发布入口本身有明确的单资源原子替换语义，未发布产物可在崩溃后清理或重用。 | 需要管理产物生命周期、垃圾回收、磁盘空间、版本引用和读者协议。若正文要求能以普通可变路径直接打开多个文件，或权威指针与 DB 又各自独立，仍没有跨资源原子切换；必须明确唯一事实源及其他状态如何重建。成本中等，取决于现有文件布局。 |
| 把需原子提交的权威状态放入同一事务资源 | 例如让同一 SQLite 事务包含内容本身及结构化元数据；或采用另有明确共同事务协议的存储。这样可在该事务资源范围内定义整体提交。 | 正文源文件权威的要求可能不再成立；若导出文件仍可被外部直接编辑，则导出与数据库之间仍需同步/冲突规则。引入具备跨资源事务语义的底层存储还会增加平台与运维约束。 |

核心区别是：**原子可见**要求观察者只见旧版或新版；**崩溃后可恢复**允许暂时留下中间态，但要求持久事实足以检测、解释并收敛。前者依赖单一发布边界和读者遵守协议；后者依赖持久操作状态、可验证的目标版本和明确冲突策略。仅有备份、文件 watcher 或 SQLite 事务无法代替这两类协议。

## 可选补充：Git 的精确边界

Git 的 `update-ref --stdin` 支持把多个 ref 更新放进一个 ref 事务，也支持基于旧值校验更新；这是 Git ref 命名空间内的能力。它不把任意工作区正文文件或 SQLite 数据库纳入同一事务，故不能作为跨资源原子性的证明。只有在内容原本就是 Git 对象且所有消费者以 ref 作为发布入口时，这项能力才可能作为某一发布设计的组成部分。[Git `update-ref`](https://git-scm.com/docs/git-update-ref)
