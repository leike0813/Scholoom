## 结论

Zotero 用户文献数据的本地权威是其活动数据目录中的 `zotero.sqlite`；数据库记条目字段、关联、附件 link mode 与路径，托管附件文件另在同目录 `storage/`。linked 附件的原文件位于库外，数据库保存引用路径。Zotero schema 升级以版本化步骤迁移 SQLite，并在数据结构升级前备份数据库；这证明的是 Zotero 自身升级责任，不会自动迁移或完整备份 Scholoom 数据。

BBT 与 Zotero 的 SQLite 接口和原生 schema 耦合很直接：它用 `Zotero.DB.queryAsync` 查询 `itemData`、`fields`、`itemDataValues` 等原生表读取 citation key，并用 `Zotero.DB.executeTransaction` 组合写入。可写条目的 key 经 `Zotero.Item` 字段 API 保存为 Zotero 原生 `citationKey` 字段；BBT 另有只读条目 key 缓存和旧版私有数据库迁移。若原包要访问 Scholoom 管理的文献，宿主适配必须兑现它所见的 Zotero DB/API 契约。这个插件契约本身不要求 Scholoom 把自己的科研领域数据改由 Zotero SQLite 主持：它可以由 Zotero 兼容宿主内的数据视图、映射或隔离的 Zotero 兼容存储满足，具体路线待 16 与实现决策。

茉莉花对文献数据主要走 Zotero 领域 API：元数据抓取交给 Zotero translators 创建条目，再通过 `Zotero.Item` 字段、Extra、集合和 `saveTx()` 操作；从用户文件夹匹配到的附件经 `Zotero.Attachments.importFromFile()` 导入，成为 Zotero 管理的附件。其直接约束是这些对象、翻译器与附件 API 的行为以及 Extra 保真，不是它自行要求读取某种 SQLite schema。茉莉花偏好、插件安装的 translators/styles 等属于宿主或插件配置/资源；BBT 的 citekey 内存映射及 `read-only.json` 是查询缓存，旧 BBT `citationkey` 数据库是升级时的迁移源。这些都不能不加区分地视为 Scholoom 的第二份文献权威。只读条目的 BBT 私有 key 缓存是该插件在不能写回条目时提供 key 的插件级状态，须在兼容承诺中保留其行为，但它不改变可写 Zotero 条目以原生 `citationKey` 为准的事实。

数据变更、附件字节变化与搜索索引变化是三类事件。更新标题、作者、`extra` 或 `citationKey` 是条目元数据变更；下载/替换 PDF 或写入 PDF 书签会更改附件文件内容；全文索引 `fulltext.sqlite` 是可重建派生数据，重建它不等于修改条目元数据或材料内容。条目表的事务可以保证数据库记录的提交边界，不能据此宣称跨 SQLite 与文件系统的崩溃原子性。Scholoom 的迁移、变更历史与恢复边界需要分别记录数据库变更、文件变更和索引重建。

## Zotero 的权威、版本迁移和备份

官方数据目录说明指出，`zotero.sqlite` 包含大部分数据，例如条目元数据、笔记和标签；`storage/` 的随机八字符子目录存放导入的附件。linked files 不在该目录中。Zotero 源码的 `itemAttachments` 表用 `linkMode`、`path`、`storageModTime`、`storageHash` 等列表达附件关联；条目对象为已存储附件解析 `storage:` 相对路径到附件目录，为 linked file 解析 linked base directory 相对路径或外部路径。[Zotero 官方数据目录](https://www.zotero.org/support/zotero_data#data_directory_contents)、[Zotero 官方附件说明](https://www.zotero.org/support/attaching_files#stored_files_and_linked_files)；源码：[userdata.sql:204-220](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/resource/schema/userdata.sql#L204-L220)、[item.js:2899-2958](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/data/item.js#L2899-L2958)、[item.js:3003-3078](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/data/item.js#L3003-L3078)。

托管（stored/imported）与 linked 两种附件不可在完整迁移时混作同一种文件：前者要迁移文件内容并保持 attachment 记录的相对文件定位；后者要迁移引用记录，并确保外部文件和 base-directory/path 关系仍可解析。Zotero 也有 linked URL，它只有 URI 引用而没有本地文件路径。官方说明 linked files 不随 Zotero 文件同步，也不会因删除 Zotero 附件条目而删除原文件。群组库不接受 linked files。[附件说明](https://www.zotero.org/support/attaching_files#stored_files_and_linked_files)；本地实现对 linked file 不允许非个人库见 [item.js:2202-2204](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/data/item.js#L2202-L2204)。

数据库结构升级由 `schema.js` 读取 userdata/global schema 版本，在升级、完整性修复或 global schema 更新前执行强制 DB 备份，再在 `Zotero.DB.executeTransaction()` 中推进 system、userdata 与 triggers schema 更新；`_migrateUserDataSchema()` 按版本号逐级执行步骤。Zotero 的 8.0 文件路径迁移步骤会把旧 Mozilla 路径描述转换为统一的 UTF-8 相对路径，说明迁移中路径语义本身也需要处理。[schema.js:150-178](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/schema.js#L150-L178)、[schema.js:208-224](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/schema.js#L208-L224)、[schema.js:2990-3011](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/schema.js#L2990-L3011)、[schema.js:3862-3908](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/schema.js#L3862-L3908)。这套版本迁移机制是 Zotero SQLite schema 的演进流程，不是跨产品的通用数据导入机制。

完整备份与“有同步”也不同。Zotero 官方建议关闭应用后复制整个数据目录，包括 `zotero.sqlite`、`storage/` 与其他目录；自动 `.bak` 数据库备份不含文件。使用按需下载时，附件可能尚未落地，所以本地目录副本也不必然是完整附件备份。链接文件不在 `storage/`，必须单独保护其真实文件和路径配置。Zotero 官方明确不建议把 RDF/BibTeX/RIS 导出重导当作精确备份，因为日期和已有文档中的引用链接等会改变。[备份与恢复说明](https://www.zotero.org/support/zotero_data#backing_up_your_zotero_data)、[自动 DB 备份范围](https://www.zotero.org/support/zotero_data#restoring_from_the_last_automatic_backup)。源码中的 `saveTx()` 对象保存会通过 DB transaction 执行写入、最终化并挂接 undo state；DB 事务只涵盖数据库连接的语句。[dataObject.js:1079-1109](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/data/dataObject.js#L1079-L1109)、[dataObject.js:1130-1134](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/data/dataObject.js#L1130-L1134)。

全文索引 `fulltext.sqlite` 保存附件、笔记等的全文索引以加速检索；官方称其未纳入数据库备份，因为必要时可重新创建。[数据目录说明](https://www.zotero.org/support/zotero_data#data_directory_contents)。因此，对 Scholoom 来说全文索引不是引用元数据权威，也不是材料文件本身；索引重建记录为派生状态的再生成，不能冒充元数据变更、PDF 内容版本变化或文献库迁移。

## Better BibTeX：原生 schema、事务和私有状态

BBT `content/db/zotero.ts` 的包装函数直接转调 `Zotero.DB.queryAsync`、`queryTx`、`columnQueryAsync` 与 `valueQueryAsync`，不是打开 SQLite 文件的独立 driver。[db/zotero.ts:11-22](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/db/zotero.ts#L11-L22)。`key-manager.ts` 查询 `items`、`itemData`、`fields` 与 `itemDataValues`，以字段名 `citationKey` 连接并取值；本地 Zotero schema 将 `citationKey` 列入 Zotero 全局字段定义。[key-manager.ts:37-58](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager.ts#L37-L58)、[schema.json:664-673](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/resource/schema/global/schema.json#L664-L673)。因此兼容面包含原生表/字段布局、item ID 与库 ID 关系、DB query API 语义；静态代码没有显示 BBT 自己持有 Zotero 主库的另一份可写镜像。

写入使用两层 Zotero 接口：批量补齐缺失 key 时，BBT 通过 `Zotero.DB.executeTransaction()` 运行一组针对 Zotero DB 的写入；普通 key 更新通过 `item.setField('citationKey', …)` 和 `item.saveTx()`，少量场景在 transaction 内调用 `item.save()`。[key-manager.ts:311-319](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager.ts#L311-L319)、[key-manager.ts:213-255](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager.ts#L213-L255)、[key-manager.ts:335-355](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager.ts#L335-L355)。Zotero 自己的 `executeTransaction` 管理 DB transaction，`queryAsync` 在该 DB connection 上执行 SQL。[db.js:441-497](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/db.js#L441-L497)、[db.js:648-682](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/db.js#L648-L682)。若 Scholoom 宿主让插件对本地条目工作，兼容适配不能只实现同名方法而忽略 transaction 的一致性边界和 Zotero item/save lifecycle。

BBT 私有存储有不同职责：

- `Keys` 在内存中缓存 `{ itemID, itemKey, libraryID, citationKey }`，定时把列表写到插件目录下 `read-only.json`；加载时先读它，再从 Zotero DB 查询可见 key。这个 JSON 主要供只读条目使用，因为此类条目不能写回 Zotero 字段；可写条目修改则进入 Zotero `citationKey` 字段。[key-manager.ts:110-172](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager.ts#L110-L172)、[key-manager.ts:289-309](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager.ts#L289-L309)、[key-manager.ts:337-355](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager.ts#L337-L355)。它是插件查询行为的持久缓存/只读例外状态，不是普通条目 metadata 的第二份可写权威。
- `key-manager/migrate.ts` 会用 SQLite API 打开 BBT 自己的旧 `citationkey` 数据库，读取旧 key，再查询 Zotero 原生 citationKey 与 item 列表，对差异做选择后写回 Zotero item 字段。这是从旧插件私有 schema 迁移到 Zotero 原生字段，不代表当前 key 的权威仍在 BBT 数据库。[migrate.ts:45-70](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager/migrate.ts#L45-L70)、[migrate.ts:108-134](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager/migrate.ts#L108-L134)、[migrate.ts:157-214](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager/migrate.ts#L157-L214)。
- key 变更还可编辑 Zotero `extra` 中的 BBT aliases。它与 `citationKey` 是不同条目字段值；alias 的语义不可因存在 BBT 缓存就当作数据库外元数据。[key-manager.ts:231-245](https://github.com/retorquere/zotero-better-bibtex/blob/71cec8067843bc5cdcbac7e1e794a3803638a5e1/content/key-manager.ts#L231-L245)。

对 Scholoom 的约束由“未改的原包如何连接宿主”决定：BBT 的 SQL 预期直接查看宿主暴露的 Zotero 原生数据视图；如果 Scholoom 条目仅存在于另一套 schema 且未映射到 Zotero 表/字段视图，这些原 SQL 查询就不会自动理解它。反过来，为满足 BBT 而在 Scholoom 领域库里复制 Zotero 全部 schema，既不是 BBT 源码要求，也不是研究结论；需由 16 的宿主原型决定适配放在哪一边，以及提交、冲突和 undo 如何与 Scholoom 的真实文献对象对齐。

## 茉莉花：条目、Extra、附件和本地状态

茉莉花以 Zotero `Translate.Import/Export` 执行相应 CNKI 等 translator，将译出的 Zotero Item 返回给服务层；多个 translator 分支都传入 `libraryID`，并关闭 translator 自行保存附件的选项。[cnki.ts:358-428](https://github.com/l0o0/jasminum/blob/b63a6a1e0ac4ce25fcd0c9200ec647b063ce02c0/src/modules/services/cnki.ts#L358-L428)、[services/index.ts:237-303](https://github.com/l0o0/jasminum/blob/b63a6a1e0ac4ce25fcd0c9200ec647b063ce02c0/src/modules/services/index.ts#L237-L303)。单条结果经过 `globalItemFix`，复用旧条目的集合和 tags，调用 `newItem.saveTx()`；CNKI 引文和 advance-online 状态经 `ztoolkit.ExtraField.setExtraField()` 写到该 Item 的 Extra 字段，并可补 `date` 字段。之后任务流会把条目字段复制回 snapshot 项、重绑附件 parent、删除旧 parent 或保存当前 `task.item`。[services/index.ts:320-348](https://github.com/l0o0/jasminum/blob/b63a6a1e0ac4ce25fcd0c9200ec647b063ce02c0/src/modules/services/index.ts#L320-L348)、[services/index.ts:364-419](https://github.com/l0o0/jasminum/blob/b63a6a1e0ac4ce25fcd0c9200ec647b063ce02c0/src/modules/services/index.ts#L364-L419)。这表明其元数据修改进入 Zotero Item 模型和 Zotero 保存路径；Extra 是条目 metadata 的一部分，迁移时须保留未知/插件字段文本，不能只导入标准化字段而静默丢弃它们。

有一个静态边界：`globalItemFix` 先 `newItem.saveTx()`，随后再调用 ExtraField helper 和可能的 `date` setField；当前仓库未提供该 helper 的依赖源码，因此这次阅读无法独立确认 helper 是否立即保存，或这些后续字段由任务中的哪次保存最终持久化。可确认的是写入目标是 Item 的 Extra/field API，而非茉莉花自有条目数据库；不把未经核对的保存时点说成事实。

对用户选定本地 PDF 的附件匹配，茉莉花按条目标题在配置目录找相似文件；选中后以路径、parent item 与展示标题调用 `Zotero.Attachments.importFromFile()`。这条路径将文件交给 Zotero 导入/管理，而不是只把原路径登记成 linked file。[localMatch.ts:18-63](https://github.com/l0o0/jasminum/blob/b63a6a1e0ac4ce25fcd0c9200ec647b063ce02c0/src/modules/attachments/localMatch.ts#L18-L63)、[localMatch.ts:66-85](https://github.com/l0o0/jasminum/blob/b63a6a1e0ac4ce25fcd0c9200ec647b063ce02c0/src/modules/attachments/localMatch.ts#L66-L85)。Zotero 的 `importFromFile()` 将附件设为 `LINK_MODE_IMPORTED_FILE`，在同一 DB transaction 里创建 attachment 记录、创建 storage 子目录、复制文件并保存相对路径；遇到异常会尝试清理目标目录。[attachments.js:93-148](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/attachments.js#L93-L148)、[attachments.js:156-175](https://github.com/zotero/zotero/blob/2cdc2cc3b7dbc39d2ba152f03b680ca84a23bae9/chrome/content/zotero/xpcom/attachments.js#L156-L175)。这是 API 提供的有序写入与失败清理；静态代码不能证明进程在 DB commit 与文件复制/清理之间崩溃时具备跨资源原子性。导入后配置还可将源文件保留、移至 `jasminum-backup` 或删除；这些是对来源目录的文件系统副作用。[attachments/index.ts:32-57](https://github.com/l0o0/jasminum/blob/b63a6a1e0ac4ce25fcd0c9200ec647b063ce02c0/src/modules/attachments/index.ts#L32-L57)。PDF 大纲/书签路径会对 PDF 附件本身工作；若功能将书签写入 PDF，审计和变更记录应归入附件字节变化，而非索引重建。当前有关此功能的行为概览另见既有 [宿主研究](zotero-plugin-host.md)，本次结论不扩大到未执行的文件写入运行验证。

茉莉花的 plugin preferences、远端 translator 下载文件、CSL 样式安装和其插件 UI/任务状态由宿主或插件维护。它们可能影响插件运行与渲染，却不取代已翻译进 Zotero Item 的条目 metadata。中文 translator/CSL 是供翻译或呈现使用的可替换资源；源下载记录、translator 文件和用户条目事实应分层存放。既有研究记录的插件资源路径及运行时依赖见 [zotero-plugin-host.md](zotero-plugin-host.md)；本研究只将上游固定 HEAD 的条目与附件调用作为数据写入事实。

## 对存储与变更模型的设计影响

1. **把 Zotero 输入迁移作为显式边界流程。** 需读取条目、集合、作者/标签/关系、Extra 与 citationKey 等字段，迁移 attachment 元数据；针对托管文件、linked file、linked URL 分支保存字节、路径与可达性信息。使用 Zotero 导出格式可作为交换输入，但不得承诺它本身是精确备份。迁移前后需区分“条目事实迁入 Scholoom”“原始材料是否复制/仍可达”“全文索引何时重建”。
2. **保留外部文件引用事实和管理文件内容的区别。** attachment 记录、真实文件和引用路径不是两份可以随意互相覆盖的当前状态：DB 记录说明 link mode/parent/path/hash 等；托管文件字节是材料；linked 文件由外部位置提供。备份和恢复覆盖的资源也须分别说明。Scholoom 若复制一份材料为新版本，应表达版本关系，不要把它伪装成普通 metadata 更新。
3. **保留事务之外的文件变更结果。** 一次用户动作若同时写条目记录和导入/替换文件，需要定义崩溃中断后的检查/补偿状态；仅有单库 ACID transaction 不证明跨资源原子性。可将写入意图、文件落地确认、DB 引用提交和恢复检查作为设计问题，但本调查不指定实现方案。
4. **对 BBT 兼容建立 Zotero 视图契约。** 重点是它直接 SQL 读取的字段和关联表、native citationKey 字段、`queryAsync/executeTransaction` 行为，以及通过 item API 保存时的可见结果。若数据驻留 Scholoom 原生库，宿主如何把领域记录投影给原包属于 16/宿主适配设计；此处不主张 Scholoom 全库照搬 Zotero schema，也不选择 SQLite driver。
5. **把插件缓存和插件专属事实标成不同类别。** BBT `read-only.json` 及内存 map 是插件查询缓存/只读 key 状态，需按原包兼容承诺持续可读写；可写项 citationKey、BBT aliases 和茉莉花 CNKI citation/status 存在 Zotero 字段/Extra 时，是条目 metadata。translator/CSL 下载文件和 preferences 是插件资源/设置；PDF 书签若落到文件里属于附件内容变更。分类应按被修改的持久化对象，而不是按哪个插件发起操作。
6. **不混淆三种版本/变更。** metadata 版本反映题录等结构化字段变更；附件内容版本反映 PDF/CAJ 等字节变化（包括写入 PDF 书签）；全文索引版本是可丢弃、可重建的派生状态。索引重建不应制造“材料修改”或“citationKey 修改”事件，插件偏好/缓存变化也不应混成文献事实变更。
