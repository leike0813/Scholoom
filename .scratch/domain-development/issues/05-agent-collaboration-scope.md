## Answer

2026-10-21，用户依次确认 Q1–Q6，其中 Q4 按用户意见修订为由 Agent 通过工具理解上下文、无法确定时询问。以下确定本域支撑范围、后续设计顺序与交付边界，不表示功能已实现或授权业务实施。

### Q1：职责分工

| 责任方 | 负责内容 |
| --- | --- |
| 通用 harness | 会话与执行上下文、工具接入、委派与通信、等待、取消及恢复 |
| 模型模块 | 模型配置、凭据、实际模型调用及连接限制 |
| 科研运行模块 | 业务 Graph、科研角色指导、工作包内容、科研交付要求与判断 |
| 宿主与共同工程主线 | 模块装配、进程监督、应用级资源准入、共同协议与工作台接线 |

例如业务 Graph 要求独立审阅时，科研模块明确材料与标准，harness 启动相应执行并返回结果，科研模块判断意见是否满足交付要求。各领域复用共同协作机制；实际 SDK 调用、模型准入及进程部署继续沿[进程决议](../../runtime-architecture/issues/03-session-execution-processes.md#answer)，不因上表逻辑职责改变物理部署。

### Q2：后续设计顺序

1. **共同执行支撑。** 固定全局工作域、隔离临时区、跨项目只读、文献选择查询与工具接线，对齐科研 Graph 的执行接口。
2. **子 Agent 委派闭环。** 工作包、角色与模型选择、成果回传、独立审阅、等待、失败及取消；可独立验证，不等待完整科研流程。
3. **已有会话通信与 advisor。** 沿已定方向分别细化持久收件与有界唤醒、上下文增量与建议注入；不阻塞基础文献综合。

本顺序组织后续设计；具体 SDK、消息字段、并发参数与实施范围由相应 OpenSpec 承接。首条基础路径仍可由单 Agent 完成，用户或能力要求独立复核时须满足真实依赖。

### Q3：角色配置与业务 Graph

角色配置承载指导、命名模型配置和可用工具范围；Graph 决定科研工作步骤及角色之间的协作关系。例如学术审阅者配置审阅指导与模型，具体 Graph 决定何时审阅、实际材料及是否汇合多个意见。通用会话也可按工作需要委派该角色，角色配置本身不成为另一套科研流程。

用户／项目沿已开放配置派生或覆盖，实际权限取有效授权的交集；角色调整不改变 Graph 的必要步骤。执行记录保留实际采用的配置与模型。模型未指定时继承、实际执行钉入配置、显式切换及外发授权继续沿[模型政策](../../scholoom-foundations/issues/22-model-data-and-execution-policy.md#answer)，不新增自动模型路由。

### Q4：由 Agent 通过工具理解工作台上下文

用户明确不对指令中的隐含对象作预设。Agent 按需要调用工具获取用户当前选择等上下文，结合指令尝试理解所指对象；工具结果仍不足以确定时，询问用户并等待澄清后再推进依赖该对象的工作。

工具如实表达查询所得的状态、范围及不可用情况。选择提供上下文线索，不自动等同于用户指定的工作对象。材料读取与模型外发继续经领域接口和授权核对，库导航不改变会话工作域。

### Q5：协作中的材料、权限与成果责任

材料或权限变化时，沿共同权威和既有授权规则分工：

| 责任方 | 保证与判断 |
| --- | --- |
| harness | 保留委派关系、实际执行与工具结果，落实后续操作的授权检查；权限收紧不撤回已发送内容，不回滚已完成成果 |
| 所属领域 | 掌握材料身份、版本及读写规则，返回当前状态、冲突和失败原因 |
| 负责 Agent／业务 Graph | 根据实际材料判断审阅是否仍适用、是否补读或重做，保留判断依据；无法确定时询问用户 |

例如子 Agent 审阅期间稿件被修改，领域提供可核对的当前材料及版本，负责 Agent／业务 Graph 判断已有意见是否覆盖实际交付对象。委派不扩大授权，后续读取、写入及模型外发继续核对有效权限。

成果回传包含实际产物引用、发现、未完成项和障碍。子执行结束、成果已保存、科研交付达标分别表达，由负责 Agent 和科研业务检查实际交付，不把执行成功直接算作研究完成。等待、取消、已受理操作核查与子执行收尾继续沿[进程决议](../../runtime-architecture/issues/03-session-execution-processes.md#answer)及[协作初设](../../scholoom-foundations/issues/46-multi-agent-interaction.md#answer)，不另设生命周期。

### Q6：设计包、必要界面与独立验收

先形成两个设计包，分别沿既有模块和共同调用路径细化，不预设新增包、进程或执行系统：

| 设计包 | 独立验证重点 |
| --- | --- |
| 共同执行支撑 | 全局工作域与临时区、跨项目只读、工作台上下文工具、Graph 执行交接及授权 |
| 子 Agent 委派 | 工作包与角色模型、独立上下文、实际成果回传、等待与取消、失败及接续 |

验证接入真实模块和共同调用路径，模型可使用受控响应；覆盖材料变化、权限收紧、部分成功、停止与重启。独立审阅沿既定初审规则提供原始材料与标准，不预先注入其他审阅者结论。上述验证证明执行支撑和交接行为；科研质量另经产品入口的真实业务验收。

用户通过既有会话界面查看委派、进展、阻塞原因与成果，并能停止所属执行。诊断区分发送、受理、执行及结果刷新；浏览器和 Electron 沿共同工作台路径，实际宿主能力按既有双宿主验证要求核对。具体布局与呈现遵循工作台设计，不在本票展开。

已有会话通信及 advisor 分别在后续设计中补充验证；前者依赖持久收件、执行边界消费和有界唤醒，后者依赖上下文增量、按实际生成操作明确的文本范围、建议注入及有限等待。它们不阻塞基础单 Agent 综合；明确要求独立复核或 advisor 的工作须满足对应真实依赖。

### 后续交接与设计启动条件

共同执行支撑可依据本票与[科研业务 Graph 运行基础决定](04-research-methods-scope.md#answer)开展详细设计；共享协议、全局工作域、上下文提供者与宿主装配由[共同工程主线](09-shared-engineering-responsibility.md)统筹。委派设计随后沿共同执行接口推进，以受控模型响应独立验证，不等待完整科研流程。

[并行设计与交付安排](10-parallel-design-and-delivery.md)汇总两个设计包与其他领域的实际依赖；具体 Schema、SDK 复用、文件范围和实施任务由相应 OpenSpec 调查与设计确认。首条真实综合路径仍由主 Agent 整合验收，各设计包独立通过不代替跨模块与科研质量验收。
