## Question

首批设计的共同输入见[首条文献综合路径与最小跨域契约](01-literature-synthesis-path.md#answer)。

文献与知识管理域首先怎样形成一套完整的“类 Zotero 文献管理工具”，其基础功能、界面和操作行为应如何设计，再以此承接知识分析与研究综合？

- 以 Zotero 的功能与界面为参考建立基础能力清单，核对日常收录、组织、检索、阅读、笔记和引用等操作，以及当前代码已具备与仍缺失的部分；“完整”的具体范围由用户确认。
- 明确集合导航、条目列表、详情编辑、附件、阅读器及相关操作的界面形态，与当前工作台骨架和设计事实源衔接。需要调整既有布局时先明确产品取舍。
- 形成可分别细化、独立验收的基础功能与界面设计入口，再安排分析成果管理、语义检索和持续维护的衔接；首条文献综合路径继续作为后续跨域整合目标。
- 保留已确认的维护责任及文献获取／生态分工，列出与科研方法、项目资产和兼容层的共同操作及依赖。

本票确定基础产品设计的范围、责任及后续入口；具体界面稿、完整实施规格与技术选型由后续工作承接。

依据：[分层知识决议](../../scholoom-foundations/issues/33-layered-literature-knowledge.md)、[分析维护决议](../../scholoom-foundations/issues/34-analysis-synthesis-maintenance.md)、[文献初设](../../../docs/initial-spec/literature.md)。

### 首步：完整个人桌面文献管理

以项目既定的固定 Zotero 基线核对功能和操作行为，形成足以日常使用的个人桌面文献管理工具，再衔接知识分析与研究综合。详细设计从“功能—界面入口—现有能力—缺口—可观察验收”清单开始，不能仅以知识成果、检索和维护等宏观概念替代基础产品设计。

基础功能清单至少核对以下方面，完整性仍需对照基线逐项检查：

| 功能面 | 需要细化的内容 |
| --- | --- |
| 主界面 | 集合导航、标签区、条目列表、详情编辑、工具栏、菜单及其操作联动。 |
| 收录 | 手动新增、标识符添加、文件拖入、格式导入、浏览器采集及实际摄取结果。 |
| 整理 | 条目类型与字段、作者、集合与标签、附件、笔记、关联条目、重复合并、删除与恢复。 |
| 检索 | 快速搜索、高级搜索、保存搜索、全文搜索、排序与筛选。 |
| 阅读与笔记 | 打开附件、阅读导航与搜索、批注、文献笔记及独立笔记，复用共同编辑阅读能力。 |
| 引用与输出 | 引用复制、参考文献生成、CSL 样式及文献导入导出。 |

Word／LibreOffice／Google Docs 引用插件独立后续接入。云同步与群组协作继续后置；本次确认不扩大这些产品范围。

现有题录、材料、阅读及授权能力先核对后复用，具体差距通过功能清单与实际路径识别。独立交付包含可操作界面、GUI 与 Agent 共用的领域操作、诊断入口，以及按风险选择的真实验证，不要求一次性交付全部功能。

### 界面与共同编辑阅读接口

功能与操作组织参考 Zotero，界面按当前工作台合理安排，保留总体三区、tab 组与 Agent 双形态。集合、条目和详情等区域如何组合在后续界面设计中落实；视觉继续沿共同语义 token，快捷键最后统一做全局设计。设计事实源为 [UI 设计文档](../../../docs/ui-design/README.md#文献管理设计方向)。

项目文件和库附件通过同一套资源打开、编辑器及阅读器接口进入工作台，由共同机制选择格式视图。文献域提供库资源引用及所属材料能力，项目域提供项目文件能力，编辑阅读域承接共同接口与呈现。来源、材料版本和读写授权由所属领域保持，接口不以资源属于项目还是文献库而分成两套。

统一接口由[共同资源变更](../../../openspec/changes/archive/2026-10-20-unify-workbench-resource-opening/tasks.md)实施与验收，不能仅以共享 tab 容器报告此要求已经满足。后续交接由[阅读写作与成果交互职责票](07-research-interaction-scope.md)细化，[共同工程主线](09-shared-engineering-responsibility.md)统筹公共契约与装配。

### harness 工作域与文献工具

harness 始终在所属工作域中工作，工作域包括用户研究项目与后续确认的[系统全局工作域](04-research-methods-scope.md#全局会话与工作域)。切换文献库 tab、选择条目或打开附件只改变界面上下文，不改变其工作域、会话接收者或授权。

Agent 与文献库始终通过工具交互，包括查询用户当前选择的条目、读取题录与正文、取得附件信息以及操作库。界面选择与明确附加给 Agent 的材料分别表达；具体上下文工具的载荷和作用范围在相应设计中落实。当前库读取与写入工具可以复用，查询 UI 当前文献选择的工具仍需接线，交由[Agent 运行协作职责票](05-agent-collaboration-scope.md)与共同工程主线核对。

### 知识维护责任

文献域掌握库内可复用成果及其材料依赖，保存更新需求、变化依据与关联执行。科研运行时组织 Agent 判断科研影响及补充或重做方式并执行方法，实际执行记录仍归运行时；结果交回所属领域保存。上次成功成果与本次更新障碍分别可查，库管理能力可独立于 harness 的具体实现测试和诊断。

分层读取、四类分析产物、统一混合检索、主题范围与实际依赖、旧成果保护等产品约定继续沿原决议。项目定向采用、项目判断及持续研究记录归项目域；闲置项目受到变化影响时由用户手动启动复核。本票改变细化顺序，不删除这些已确认目标，也不另建一套知识执行权威。

研究主题归属、项目任务的文件承载、库知识指针、材料身份与删除恢复，以及引用异常处理，采用后续已确认的[研究项目与研究资产共同契约](03-project-research-assets-scope.md#answer)。文献域详细设计据此提供对象状态、删除记录及读取诊断，具体策略只在该票的行为矩阵维护。

### 获取与生态分工

文献域负责线上来源查询、标识符解析、全文获取及摄取后的稳定身份、冲突与逐项结果。生态域负责 Connector、translators 的宿主适配、插件兼容及迁入来源适配。各种入口使用同一文献操作、授权和材料保护规则，具体适配经[生态职责票](08-zotero-ecosystem-constraints.md)联合核对。

### 后续入口与证据边界

文献域首先产出基础功能及界面差距清单，按实际使用路径分别设计和交付；共同资源接口与 UI 选择工具同时由相关域协同细化。首条[项目定向综合路径](01-literature-synthesis-path.md#answer)保留为后续三域整合目标，知识成果与科研方法的交接在基础能力上继续展开。各域的并行启动条件最终由[并行设计及交付安排](10-parallel-design-and-delivery.md)汇总。

本票依据用户讨论、官方文档和代码核对形成决定；A 批的实际实现、测试及待验收项见[同一变更交接](../../../openspec/changes/archive/2026-10-20-unify-workbench-resource-opening/delivery.md)。完整类 Zotero 工具仍按实施计划逐批交付。
