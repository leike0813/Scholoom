## Question

依据校准路径、七域职责和共同工程主线，确认哪些详细设计可以并行启动，哪些实施必须等待共同契约或调查结论，如何组织首批独立交付及跨域验收？

本阶段采用用户明确的[多工作树并行模式](09-shared-engineering-responsibility.md#本阶段的开发模式)，并沿[先规划并完成公共基础、再并行开发的顺序](09-shared-engineering-responsibility.md#q1先规划并完成公共基础再并行开发)推进。并行阶段没有统一协调 Agent；本票据此明确公共基础交付与工作树启动的依赖、工作树划分、共享改动承接及整合验收责任。

启动并行前沿[公共基础完成标准](09-shared-engineering-responsibility.md#q2公共基础完成与并行启动条件)核对实际证据与各工作树入口；公共基础范围限于本批并行功能所需共同部分，不把固定样例或替身通过视为全部业务整合通过。

并行期间的公共基础补充沿[当前工作树实现、dev 接入后再同步的路径](09-shared-engineering-responsibility.md#q3公共基础补充先在当前工作树实现再经-dev-同步)及[独立提交与接入验证约定](09-shared-engineering-responsibility.md#q4公共补充提交的独立性与接入验证)承接；后续安排据此核对实际依赖与整合验证。

验证分工沿[工作树、dev 接入及跨域整合责任](09-shared-engineering-responsibility.md#q5工作树dev-接入与跨域整合的验证责任)：分别声明独立通过、接入检查及真实路径整合结果；本票为具体跨域路径安排有明确负责人的整合任务，不预设统一协调 Agent。

科研业务域已确认先形成[共同 Graph 运行基础设计包](04-research-methods-scope.md#answer)，具体业务流程及用户／项目自定义 Graph 后置。固定夹具可接入真实模块独立验证基础交接，尚未就绪端口使用明确替身；其通过不代表首条真实综合路径或科研质量已经验收。

Agent 域的两个设计包、协作责任及独立验收边界见[Agent 运行协作决定](05-agent-collaboration-scope.md#answer)，据此核对设计与整合依赖。

科研计算域的“项目内程序执行与环境供给”设计包、基本操作及独立验证范围见[科研计算与执行环境决定](06-managed-computation-scope.md#answer)，据此安排与项目文件、科研方法及成果交互的交接。

阅读写作交互域的“材料批注与修改”和“交互报告”两个设计包、Codex 式交互目标与真实接线的独立验收范围见[阅读写作与成果交互决定](07-research-interaction-scope.md#answer)。两条线可分别设计，基础综合不等待交互报告；具体资源隔离、保存及无工作台接续在相应设计中闭合，科研质量另行验收。

生态域的四个设计入口、提前调查及生产写入前置见[Zotero 生态职责决定](08-zotero-ecosystem-constraints.md#answer)；身份映射与插件写入调查须在相关基础契约定案前闭合，阅读写回调查不晚于对应阅读及材料修订契约定案，不能因生态生产验收安排在后段而推迟这些调查。

- 汇总已确认的最小依赖图，区分设计前置、实施前置、可替换依赖和真实整合前置；只保留实际约束，避免以整个领域完成作为另一领域启动的条件。
- 将 Q1 已纳入本轮规划的七域近期工作落实为可分别启动的设计范围，标明共同约定、所需调查及跨工作树接口的维护与变更责任。
- 确认 Agent 协作、科研计算、阅读写作交互、生态接入的设计时机和启动条件；早期兼容调查的结果影响哪些并行工作。
- 给出各设计入口的预期输出、独立诊断及验收边界，以及首条真实综合路径的整合责任。详细设计和实施由后续领域讨论及 OpenSpec 承接，不在本票展开全部任务。
- 将本轮安排与既有分阶段路线核对，必要时更新路线入口或顺序；具体决定继续引用所属票，避免复制实施进度。

完成时应能从当前规格和本地图继续各域设计，并由用户确认全局分工及首批安排；不以固定工期或 Agent 数作为完成判据。

### Q2：公共基础先行，七域各自一条开发线

初始采用公共基础先行、随后七域各自一条开发线的工作树划分。同域的近期设计包在同一开发线上按依赖推进：Agent 线先共同执行支撑再子 Agent 委派，阅读交互线承接材料批注与交互报告，生态线先完成前置调查再按依赖推进四个接入方向并共用兼容宿主。

各线按依赖分批启动。公共接口及共同挂载入口在前面的公共基础阶段准备好。后续出现边界明确、可独立交付的子任务，再按需要拆分；具体文件写入边界在详细规划中核对，不将初始划分当作固定并发数量或永久工作树数量。

### Q3：公共基础优先补齐四组共同部分

| 共同部分 | 各域所需的接入能力 |
| --- | --- |
| 资源与成果交接 | 按统一身份及版本引用材料、保存成果并查询实际结果；复用已交付共同资源接口 |
| 执行与授权接线 | Graph 调用 harness，程序运行接入宿主进程能力；工作域、权限、取消及失败沿共同契约传递 |
| 工作台与 Agent 接线 | 工具查询当前窗口的选择，选区及批注进入共同输入框，各域视图接入既有工作台 |
| 独立开发与验证入口 | 各域能替换未完成依赖，运行自身模块、检查实际结果及定位失败 |

按这四组调查缺口并组织公共基础交付。已有部分直接复用；依赖尚未完成的领域实现时，用明确测试替身验证共同接入口，各域随后补上真实业务实现。公共基础准备接入能力不替代各领域的业务职责及真实路径验收。

生态身份映射、插件写入及阅读写回调查，在受其影响的共同契约定案前完成，时机沿[生态调查决定](08-zotero-ecosystem-constraints.md#q2提前调查的范围与优先级)。这些调查在规划及相关契约定案阶段开展，不等到公共基础全部交付、生态开发线进入并行后才开始。

### 后续规划入口与交付责任

下一步先围绕 Q3 调查已实现部分、共同缺口及受影响接口，闭合会影响契约的调查，形成公共基础的实际实施规划。按可独立验证的共同结果拆分 OpenSpec，不从四组范围直接推定必须新增四个包或四个变更。

用户本轮进一步要求“形成OpenSpec实施规划”后，实际共同缺口与三项实施入口记录于[公共基础实施规划](../public-foundation-plan.md)；该入口引用所属 OpenSpec 的调查、规格、设计和任务，不把规划工件当作实施结果。

用户随后确认三个公共基础 change 采用共同契约先交付到 dev、三个工作树并行实现、真实整合按依赖验收的方式。共同文件按职责划分修改范围，增量经 dev 验证后同步，不设置常驻协调 Agent；七域开发继续等待全部公共基础验收。契约任务、局部前置及整合归属由上述规划入口和所属 tasks 维护。

七域各自的详细规划以 Q1 的所属职责票及 Q4 首个结果为入口，核对模块与文件写入范围、接口提供者与消费者、真实前置、允许的依赖替身、操作入口、诊断及必要验证。规划沿 `scholoom-dev` 的实际阶段要求完成，任务及运行结果仍由所属 tasks／delivery 保存，不提前编写交付结果。

公共补充在发现问题的工作树实现，以独立提交经 dev 接入验证后同步，沿[共同补充约定](09-shared-engineering-responsibility.md#q3公共基础补充先在当前工作树实现再经-dev-同步)。工作树、自身 dev 接入与真实跨域路径分别验收；每次真实整合任务在开展前明确负责人和完成依据，沿[既定验证分工](09-shared-engineering-responsibility.md#q5工作树dev-接入与跨域整合的验证责任)，并行阶段没有统一协调 Agent。

浏览器、Electron、权限和数据保护随实际接线验证；真实科研质量、SSH 远端、对外 MCP 及目标平台分发按所属范围另行验收。本轮固定样例或历史 Linux 结果不代替这些证据。文献计划及路线图只同步规划入口、顺序与依赖，不维护另一份任务进度。
