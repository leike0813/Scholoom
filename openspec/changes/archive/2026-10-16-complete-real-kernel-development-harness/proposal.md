# 变更提议

## Why

开发入口已存在真实内核接线，但复用了跨调试轮次驻留的实例。只读实测中，默认配置的旧实例可以认证并查询生命周期，却对当前工作台和文献库请求返回 Unknown method，导致连接成功但业务不可用。日常调试需要加载当前实现、操作真实业务，并在最后一个调试进程结束后可靠回收内核；独立内核的驻留能力应由单独路径验证。

## What Changes

- 两个 dev 命令共用受管内核，默认配置为 `.scholoom-dev/debug/`，保留业务数据，支持环境变量覆盖。
- 增加开发所有权登记及断开回收，复用真实内核的单实例、认证、停机与持久化实现。
- 共用 Vite 引导模块，Electron 开发态经该模块引导，普通产品及 CLI 的驻留行为保留。
- 核验全部已实现业务的双宿主操作，补齐实际 dev 命令、异常退出、数据读回及真实 MiniMax UI 验收。

## 完成判据

- 双入口同时运行时访问同一实例；任一退出不影响另一端，最后一个退出后确认内核进程结束。
- 启动失败、未完成所有权登记和调试进程异常退出不会遗留内核；新一轮启动使用新实例，保留原业务数据。
- 现有项目、文件、会话、科研能力、文献库、附件、PDF 和阅读记录沿真实内部接线完成既有业务测试。
- 真实 MiniMax 经工作台读取合成材料、调用工具、保存成果；另一宿主能够读回并独立核对成果。

## Capabilities

### Modified Capabilities

- `development-foundation`：真实开发入口的业务接线、调试配置与命令验收。
- `kernel-lifecycle`：开发进程所有权、共享实例及最后退出时回收；与独立驻留入口区分。

## 决策与授权依据

- #20 要求共同工作台连接真实内核，从用户入口核对持久化及产物；#14/#15 规定模块交付和验证边界。
- 用户在本次会话明确选择全部已实现业务、真实 MiniMax UI 验收、保留调试数据、双入口共享实例及独立固定调试目录，并明确调试结束应回收内核。
- 用户指示 Implement the plan，授权本 change 的工件、代码、测试、文档及验证所需的隔离开发服务和模型调用。不安装依赖、不提交代码，不接管已有驻留实例。
