# 02 技术平台与运行环境

> 事实来源：`package.json`（根与各包）、`tsconfig.json`、各 `vite.config.ts`、`vitest.config.ts`、`playwright.config.ts`、`tailwind.config.ts`、`postcss.config.js`、`.nvmrc`、`.npmrc`。
> 本篇只讲**跑起来需要什么、构建怎么组织**；包边界见 [06 工程体系与包结构](06-工程体系与包结构.md)。

## 运行时基线

| 项 | 值 | 出处 |
| --- | --- | --- |
| Node | **>= 24** | 根 `engines.node` |
| npm | **>= 11** | 根 `engines.npm` |
| 模块系统 | ESM（`type: module`） | 根 `package.json` |
| 许可 | MIT | `LICENSE` |
| 仓库 | `github.com/nimbalyst/nimbalyst` | `package.json` |

`.nvmrc` 固定 `24`；`.npmrc` 只有一行 `engine-strict=true`，注释写明原因：**npm 10 与 npm 11 对 `overrides` 写出的 lockfile 结构不兼容**，需要阻断错误工具链。

`check-toolchain.mjs` 在 pre-push 时校验运行中的 node/npm 不低于最低主版本——因为 `engine-strict` 只在 `npm install` 时生效，而 IDE 内置终端可能用不同版本的 node。

## 状态管理：Jotai 为主，zustand 并存

分层描述称 renderer 用「zustand store」，但代码事实是：

- `renderer/store/index.ts` 摘要写「创建并导出 **Zustand/Jotai** store 实例」；
- `store/atoms/*Atoms.ts`（90 文件）按 Jotai 的 atom 组织；
- `store/listeners/atomRevalidation.ts` 是 atom 失效机制。

**结论：主用 Jotai，zustand 仍然并存。** `docs/JOTAI.md` 是规范文档。

### 严格的 atoms ↔ listeners 配对

这是 renderer 状态层的组织原则：

```
store/atoms/     90 文件   按业务域切分（sessions、workstreamState、terminals、fileTree、appSettings、trackers、openProjects）
store/listeners/ 71 文件   按 IPC 事件源切分（voiceMode、conversationDirectory、fileState、deepLink、orgProjectWalk）
```

**atoms 定义「是什么」，listeners 定义「外部变化如何改写它」**。两者一一配对，边界清晰。

配套工具：

| 文件 | 职责 |
| --- | --- |
| `store/sessionStateListeners.ts` | 会话状态监听的**单一入口**（1200 行） |
| `store/transcriptStreamAccumulator.ts` | 高频 `transcript:event` 合并为**每帧每会话一次更新** |
| `store/workspaceStatePruner.ts` | 订阅 `openProjectsAtom`，项目关闭时调用各 atom 的清理 |
| `store/conversationDirectoryViewModel.ts` | 纯选择器集合 |
| `runtime/src/store/atoms/editors.ts` | **以 `editorKey = 文件 + 位置` 为键** |
| `runtime/src/store/atoms/interactiveWidgetHost.ts` | 按会话维护交互式 widget host 多实例 |

## TypeScript 配置

### 根配置

```jsonc
{
  "strict": true,
  "target": "ES2020",
  "module": "ESNext",
  "moduleResolution": "bundler",
  "jsx": "react-jsx",
  "noEmit": true,          // 根配置只做类型检查
  "types": []
}
```

`paths` 只映射 5 个包到源码：`@nimbalyst/{tracker-engine, tracker-schema, runtime, extension-sdk}`（extension-sdk 另有 `/file-tree` 特例与 `/*` 通配）。

`exclude` 排掉 `**/e2e/**`、`packages/collabv3`、`packages/marketplace`、`packages/extension-sdk-docs/examples`、`worktrees`、`test-utils`。

**`noEmit: true` 的含义**：monorepo 没有单一的 tsc 产物，**每个包用各自的构建工具（vite / esbuild / tsc）发版**，根 tsc 只负责跨包类型检查。

### 22 个包级 tsconfig

命名即变体：

| 文件 | 用途 |
| --- | --- |
| `collab-protocol/tsconfig.build.json` | 源码直出 vs 编译产物两套 |
| `collab-bundle/tsconfig.types.json` | 校验 `.d.ts`（配 `check:production-output`） |
| `runtime/tsconfig.node.json` | `build:node` 的 Node 变体 |

`runtime/tsconfig.json` 用 ES2024/ESNext/Bundler/严格/只做类型检查；`tsconfig.node.json` 把「会话执行与个人同步」这一小段闭包**以逐文件 Node ESM 方式 emit**——为 `@nimbalyst/node` 与 Cloudflare sandbox 容器准备。

### 路径别名的工程含义

`vitest.config.ts` 里 11 条 alias 把同样的映射指向 `src`，`vite.config.ts` 用 `resolve.alias`，根 tsconfig 用 `paths`。**三处保持一致，是 monorepo 内构建一致性的关键**——不一致会导致「测试通过但构建失败」。

## 构建体系

### Vite 库构建模板

`packages/runtime/vite.config.ts`：

| 配置 | 值 |
| --- | --- |
| 入口 | 双入口 `index` 与 `ui/index` |
| formats | `['es']`（只有 ESM） |
| 插件 | `@vitejs/plugin-react`、`vite-plugin-dts`（**排除 `mcp-stdio-server.ts`**）、`vite-plugin-static-copy`（拷 `src/editor/images/**`）、自写 `copyThemes()` |
| external | react/react-dom/lexical/`@lexical/*`/yjs/y-websocket/extension-sdk/collab-adapters 及子路径 |
| manualChunks | 单独切出 `prettier` |
| sourcemap | 非生产开 |
| watch | 仅 development |

**两个裁剪手法值得记**：

1. `resolve.alias` 里 40+ 条 `@shikijs/langs/*` 全部指向 `src/editor/mocks/shiki-lang-stub.js`——**裁掉冷门语言包**；
2. `external` 显式列出宿主提供物——**runtime 不打包 React/Lexical/Yjs，由宿主提供**。

### Electron 构建

`packages/electron/electron.vite.config.ts` 基于 `electron-vite`，串 main/preload/renderer 三段：

- 用 `vite-plugin-node-polyfills`；
- 内联 `optimizeShikiPlugin`（拦掉所有非 common 语言与 `prettier/parser-*`）；
- 内联 `optimizeExcalidrawPlugin`（拦掉 Excalidraw 的 locale 导入）；
- **直接 import `../../scripts/main-bundle-graph-policy.mjs` 与 `main-bundle-require-policy.mjs`——把架构边界检查嵌进构建过程本身**。

### 共享 vite 插件

`packages/shared/viteNimbalystPlugin.ts`（该目录唯一内容物）给没有自己 vite 配置的包提供 dev/prod 双态别名：

```
dev  → ../runtime/src/index.ts
prod → ../runtime/dist/index.js
```

### 移动端双目标

iOS 与 Android 各有两份 vite 配置，把**「编辑器」和「transcript」拆成两个独立构建目标**：

- `ios/vite.config.editor.ts`、`ios/vite.config.transcript.ts`
- android 同名两份

CI 中 `transcript-bundle` 是独立 job——**transcript 渲染是移动端的关键路径，需要单独验证**。

## 样式与主题

### Tailwind

`tailwind.config.ts`：

| 项 | 值 |
| --- | --- |
| content | `packages/*/src/**`、`packages/extensions/*/src/**`（含 `samples/**/*.html`）、`packages/extension-sdk-docs/examples/*/src/**` |
| darkMode | `['variant', '&:is([data-theme="dark"] *, [data-theme="crystal-dark"] *)']` |
| 色板 | 所有 `nim*` 映射到 `var(--nim-*)`，六类：背景/文本/边框/交互/状态/代码 |

**用 `data-theme` 属性而非 class 驱动暗色模式**——因此每个 Electron 窗口可以独立设置主题。

### 主题事实源

`packages/runtime/src/editor/themes/NimbalystTheme.css` 是唯一事实源，`docs/CSS_VARIABLES.md` 是规范文档。四条原则：

1. **单一事实源**——所有颜色变量定义在这一个文件；
2. **语义命名**——`--nim-bg-secondary` 而非 `--gray-200`；
3. **每个内置主题重新定义**——`light`、`dark`、`crystal-dark` 各自完整定义；
4. **禁止硬编码颜色**。

硬约束由 `scripts/check-ui-invariants.mjs` 执行：从规范主题 CSS 抽出已定义 token 集合，再校验 `WorkspaceManager.tsx`、`UnifiedOnboarding.css`、`project-graph/src/styles.css` 里出现的 `var(--nim-*)` 均在集合内。

`packages/electron/THEMING.md`（32 节）**强调禁止在 CSS 中硬编码颜色**。

`runtime/src/themes/ThemeLoader.ts` 负责主题发现、加载与校验（扫描可用主题、解析并缓存）；`runtime/src/editor/context/ThemeContext.tsx` 从 `documentElement` 的 `data-theme` 读取；`renderer/hooks/useTheme.ts` 由基础色**推导派生色**。

内置主题 6 个：`dark`、`light`、`crystal-dark`、`monokai`、`solarized-dark`、`solarized-light`。

### PostCSS 的 Windows 陷阱

`postcss.config.js` 有一条值得记的注释：

> 用 `fileURLToPath` 而非 `URL.pathname`，否则 Windows 上路径变成 `/D:/...`，tailwind 加载配置失败后只会在 `setupContextUtils` 里报 "Cannot read properties of undefined"。

**这是典型的「错误信息完全指错方向」案例**——真实原因是路径格式，报告的却是 tailwind 内部空对象。

## 测试运行环境

| 项 | 值 |
| --- | --- |
| 框架 | Vitest 4（`jsdom` + `node` 两个 project） |
| E2E | Playwright（真实 Electron，`testDir: packages/electron/e2e`） |
| 扩展活体测试 | CDP 9222 连运行中的 dev 实例 |
| 超时 | `testTimeout` / `hookTimeout` 统一 20000ms |
| 隔离 | `vitest.globalSetup.ts` 隔离 better-sqlite3 原生二进制并设 `NIMBALYST_BETTER_SQLITE3_NATIVE` |
| 规模 | 约 1070 个测试文件 |

`globalSetup` 的 `ensureNodePrebuild` 按版本与 Node ABI 定位或下载 better-sqlite3 预编译产物，做 ad-hoc 签名后写入缓存目录——**避免测试重编译工作区里正被 dev server 使用的安装**。

CI 缓存：`node_modules` 按 lockfile+patches 键，runtime 构建缓存按输入键，**没有部分恢复键**，collab-bundle 每次都重建。

## 安装脚本白名单

根 `package.json` 的 `allowScripts` 字段逐个列出允许执行安装脚本的包：

`better-sqlite3`、`esbuild`（五个版本）、`sharp`、`workerd`、`node-pty`、`@vscode/ripgrep`、`electron-winstaller` 等。

配套 `scripts/ensure-sandbox-dependencies.mjs` 复用成功安装标记。

**这是现代 npm 供应链安全的必要措施**——依赖的 postinstall 可以执行任意代码。

补丁机制：根 `postinstall: patch-package` + 顶层 `patches/`。

## 权限与安全模型

| 机制 | 说明 |
| --- | --- |
| contextIsolation | 渲染进程无 Node 能力，一切经 `window.electronAPI` |
| 自定义协议白名单 | `nim-asset` 只允许白名单根目录内媒体；`nim-preview` 是受限 HTML 预览 |
| 路径校验 | `SafePathValidator.ts` |
| 写入原子性 | `safeFileWrite.ts`（原子写 + 拒绝空内容覆盖） |
| 凭据文件权限 | `PrivateSettingsStore` 每次读写前后加固权限 |
| MCP 令牌 | 每次启动随机生成，0600 权限写发现文件，**失败关闭** |
| 扩展权限 | 三层：声明 → 授予（双作用域）→ 执行（运行时上下文限定，**payload 无法扩大权限**） |
| 工作区信任 | `extensionCapabilityPolicy` 把「工作区是否受信任」与「用户是否授权」组合判定 |
| 遥测白名单 | 每个事件名必须分类，否则被服务端静默丢弃 |

## 环境相关的坑（都有门禁脚本记录）

| 坑 | 后果 | 门禁 |
| --- | --- | --- |
| npm 10 写出的 lockfile 与 npm 11 不兼容 | 依赖升级被无提示抵消 | `engine-strict=true` + `check-toolchain` + `check-override-sync` |
| 相对路径逃逸到 `packages/electron` | `ClaudeCodeProvider` 曾拉进约 51 个桌面端文件 | `check-runtime-host-boundary` |
| 懒 chunk 二次求值 main | 重复注册 electron-log 抛 "second handler" | `main-bundle-require-policy` |
| `json_extract` 声明索引 + `->>` 谓词 | 静默全表扫描，SQLite worker 31% 时间 | `check-json-accessor-indexes` |
| renderer 直接 `new WebSocket` | Shared Docs 全线静默失效，浏览器只报 1006 | `check-renderer-sync-sockets` |
| 漏注册 reference node 类型 | 桌面文档在 Web 端打不开，异常伪装成 "Skipping undecodable update" | `check-shared-document-nodes` |
| 裸 NUL 字节 | — | `check-text-file-nuls` |
| WebSocket 响应的重复 `Upgrade`/`Connection` 头 | TLS 拦截下握手失败 | sandbox 的出站响应处理器显式剥离 |
