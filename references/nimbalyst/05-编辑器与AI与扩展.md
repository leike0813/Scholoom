# 05 编辑器内核、AI 会话与扩展系统

> 事实来源：`.ua/wiki/layers/editor-runtime.md`、`layers/ai-services.md`、`layers/plugin-system.md`、`layers/shared-foundation.md`，以及 `runtime/src/**` 的模块页。
> 这三块是 Nimbalyst 最核心也最有借鉴价值的部分：**同一份编辑器内核如何被多进程、多宿主复用，以及 agent 如何安全地往里写。**

## 编辑器内核：全部在 runtime 包

**Electron 侧不重复实现编辑器**。`packages/runtime/src/editor/` 承载完整的 Lexical 内核，宿主通过子路径 `@nimbalyst/runtime/editor` 消费。

### 无头 / 有头二分

这是编辑器层最重要的内部组织原则：

| 位置 | 数量 | 性质 | 例子 |
| --- | --- | --- | --- |
| `editor/extensions/builtin/` | 21 | **无头**：只注册 Lexical 命令与节点，不含 UI | AutoLink、Collapsible、Comments、Decision、Diff、DragDropPaste、Embed、Images、KanbanBoard、Layout、Mermaid、PageBreak、TabFocus |
| `editor/plugins/` | 36 | **带 UI**：承载渲染 | AutoEmbed、CodeActionMenu、CodeHighlight、ComponentPicker、DiffPlugin、DraggableBlock、EmojiPicker、Table 系列、Toolbar、TreeView、Typeahead |

节点集合也刻意分两份：`nodes/EditorNodes.ts`（渲染进程基础节点集）与 `nodes/headlessBodyNodes.ts`（主进程 headless 编辑器从 markdown 重建用）。

**这让同一个编辑器内核能被主进程无头、渲染进程有头、离屏窗口复用而不重复实现**——直接对应「headless 渲染/导出」这类需求。

### Editor.tsx 的装配策略

`runtime/src/editor/Editor.tsx` 是编辑器外壳，把插件分成两类装配：

- **必须留在 React 树中的插件**：工具栏、浮动菜单、评论、代码高亮；
- **可按扩展图挂载的插件**：由扩展系统决定。

`NimbalystEditor.tsx` 合并默认配置并读取 DOM 主题；`EditorConfig.ts` 是静态配置契约。

### DiffPlugin：最有特色的能力

agent 提出的改动以红/绿 diff 呈现，由人逐条接受或拒绝。`editor/plugins/DiffPlugin/` 内部结构：

```
DiffPlugin/
  core/      22 文件
  handlers/  13 文件
  README.md  DiffState 体系与相关 hook、组件的完整 API
```

`plugins/DiffApprovalBar/useLexicalDiffState.ts` 是一个值得记的重构：把原先内联在 `DiffApprovalBar` 中的**全部差异管理逻辑抽成 hook**，暴露 diff 状态、分组高亮、滚动定位与逐组/整体的批准拒绝操作，供 `UnifiedDiffHeader` 复用。

配套的编辑器侧状态对象：

| 对象 | 职责 |
| --- | --- |
| `services/document-model/DiffSession.ts` | diff 评审会话对象：tagId、sessionId、phase、基线/已应用内容与哈希、待应用内容 |
| `editor/services/document-model/DocumentModel.ts` | 定义 AI 编辑 apply 的**看门狗**与失败语义（冲突 / 不完整 / 被取代） |

### AIChatIntegrationPlugin 与 EditorRegistry

`ai/plugins/AIChatIntegrationPlugin/` 把编辑器实例注册进 `ai/EditorRegistry.ts`，于是 agent 能**对指定文件做定向替换与流式写入，而不是粗暴地重写整篇文档**。

`EditorRegistry` 按**文件路径**管理多个 Lexical 实例（出边较高），**取代了单例事件**——同一文件开多个 tab 时各自独立。

配套 `ai/editorBridge.ts`（出边 6）经 `globalThis.aiChatBridge` 驱动宿主；`ai/streaming.ts` 处理 `<!-- STREAM_EDIT: {...} -->` 内联指令；`ai/client.ts` 是流式编辑客户端。

### transcript 管线：canonical 事件三段式

这是 AI 层最值得学的结构：

```
provider 原始输出
      ↓  IRawMessageParser（每 provider 一个）
canonical 事件
      ↓  TranscriptWriter（唯一写入通道）
ITranscriptEventStore
      ↓  TranscriptProjector（静态 project）
渲染层消息列表
```

| 环节 | 文件 | 职责 |
| --- | --- | --- |
| 选择与驱动 | `TranscriptTransformer.ts`（85–643） | 选 parser、传 ParseContext、**维护工具与子代理 ID 追踪表** |
| 写入 | `TranscriptWriter.ts`（22–496） | **canonical 事件进入存储的唯一通道** |
| 投影 | `TranscriptProjector.ts`（126–201） | 静态 `project`，把事件序列投影为渲染层消息 |
| 缓存 | `InMemoryTranscriptEventStore.ts`（23–225） | 会话级内存缓存 + 过期回收 |

三个 parser 都维持跨消息的状态映射，因为工具调用是「开始」与「完成」两条消息：

- `ClaudeCodeRawParser`（37–715）按行类型分发；
- `CodexACPRawParser`（74–534）维护进行中工具调用映射；
- `OpenCodeRawParser`（47–617）额外维护权限决策映射。

**存储与 provider 无关的 canonical 事件、渲染投影而非原始流**，因此新增 provider 完全不影响渲染层。

### 模型目录：不写死

`ai/server/ModelRegistry.ts` 按 provider 动态拉取模型目录，**带按 apiKey 缓存**；`ai/models.ts` 分别向 OpenAI、Anthropic 与 LM Studio 拉取，**缺 key 或请求失败时才回退到最小内置清单**。

## 扩展系统

### EditorHost 契约：自建编辑器是一等公民

README 的说法是「Every editor, including the built-in ones, goes through the same `EditorHost` contract」。实现路径：

```
runtime/src/extensions/editorHost.ts     从 extension-sdk 再导出 EditorHost 契约
        ↓
ExtensionLoader.ts                     平台无关加载器：发现、manifest 校验、加载、卸载
        ↓
ExtensionContext                       注入式，暴露 AI 工具、编辑器、面板、命令等 contributions
```

关键设计（`tour.md` 第 9 步）：**把纯类型契约（EditorHost、Diff、协作上下文）单独放在一个再导出的模块里**，让 runtime 内部统一依赖它——既避免循环引用，也让 SDK 与实现共享同一份类型定义。

### 主进程侧：特权扩展宿主

`main/extensions/`（23 文件）把扩展后端跑在独立进程：

| 文件 | 职责 |
| --- | --- |
| `PrivilegedExtensionHost.ts` | **主进程单例**，掌管所有扩展后端模块生命周期——组合工作区信任与授权策略、拉起运行时、走类型化 RPC、崩溃后回收 |
| `extensionBackendBootstrap.ts` | 运行在 utilityProcess 或 worker_thread 内的引导：动态加载扩展入口、装配服务、转发 broker 请求/事件，**不依赖任何 Electron 主进程代码** |
| `extensionBackendRpc.ts` | 主进程与后端之间的**类型化 RPC 桥，只定义消息形状，不含传输实现**；utility-process 与 worker-thread 各自包裹同一套协议 |
| `extensionBrokerDispatch.ts` | 按方法分发 broker 请求：**权限闸门通过后在此执行**，所有作用域由宿主派生的运行时上下文限定，**payload 无法扩大权限** |
| `extensionCapabilityPolicy.ts` | 把「工作区是否受信任」与「用户是否已授予该权限」组合成 `canModuleStart` / `assertPermission` |
| `permissionRegistry.ts` | `PERMISSION_CATALOG` 权限 id 唯一事实源 |
| `permissionGrantStore.ts` | 按工作区/全局两种作用域持久化，提供授予、撤销、查询、**收缩到声明范围** |
| `permissionPrompt.ts` | 权限弹窗形状与进程内待办队列，**由渲染层注册的 resolver 消费，使特权宿主无需自己拥有 UI** |
| `permissionPromptTargeting.ts` | 纯窗口寻址逻辑，修正多项目栏下只按 `activeWorkspace` 匹配造成的漂移 |
| `permissionUsageTracker.ts` | 按 `(扩展, 模块, 权限)` 分桶的内存环形缓冲，重启即清空 |
| `backendModuleLifecycle.ts` | 按 `(扩展, 模块, 工作区)` 三元组启停 utility-process 运行时 |
| `AgentProviderRegistry.ts` | 登记扩展贡献的 `aiAgentProviders` 元数据（状态、contribution、后端模块 id） |
| `extensionAgentBridge.ts` | 按 contribution key 查注册表，惰性驱动同意流程启动后端，转发 sendMessage/abort/destroy |
| `extensionAgentHistory.ts` | 把主进程会话历史转为 `BackendHistoryMessage[]`，**兼容 canonical Message 与 TranscriptViewMessage 两种形状**并限制回放长度 |
| `backendModuleAllowlist.ts` | 区分内置与用户安装扩展，但**明确它不是安全闸门**——真正的信任决策是首启原生代码同意弹窗 |
| `claudePluginDefaultEnabledMigration.ts` | 一次性迁移：Claude 插件加载器开始遵守 `defaultEnabled: false` 之前，钉死已生效的扩展为 `enabled: true`，避免技能被静默收走 |

**权限模型的三层收敂值得记**：

1. **声明**（manifest 里的 permissions）；
2. **授予**（`permissionGrantStore`，工作区/全局双作用域，可收缩到声明范围）；
3. **执行**（`extensionBrokerDispatch` 中宿主派生的运行时上下文限定作用域，payload 无法扩大权限）。

### 内置扩展的发布契约

`runtime/src/plugins/referenceNodeContributions.ts` 的摘要写得很明确：

> 所有打开 Nimbalyst 文档的宿主**都必须发布**的引用节点贡献：注册 tracker 与 document 两类节点类及其 markdown transformer，**缺失会导致 `@lexical/yjs` 绑定中断、整个文档无法渲染**。

这条约束有专门的门禁脚本 `check-shared-document-nodes.mjs` 强制（详见 [06 工程体系](06-工程体系与包结构.md#门禁脚本每条架构约束一个可执行断言)）。

### 扩展面板的注册表模式

`plugins/shared/fixedTabHeader/`（5 文件）是一套干净的扩展点实现：

- `FixedTabHeaderRegistry.ts`——**单例注册表**，插件注册/反注册表头组件；
- `FixedTabHeaderContainer.tsx`——按当前 tab 上下文从注册表**筛出应渲染的 provider**，按优先级顺序挂载；
- `types.ts`——`TabContext`、`FixedTabHeaderProps`、`FixedTabHeaderProvider` 三类共享契约；
- `index.ts`——barrel，**供编辑器与 tab 栏共享同一套头部扩展点**。

`FrontmatterPlugin/index.ts` 以**优先级 50** 向 `DocumentHeaderRegistry` 注册通用 frontmatter 头部——注册表用优先级而非硬编码顺序决定挂载次序。

### Tracker 插件的 schema 驱动

`plugins/TrackerPlugin/`（9 根 + components 36 + models 21 + builtins 10 + documentHeader 6）展示了一套 **schema 驱动的完整元数据界面**：

| 文件 | 设计要点 |
| --- | --- |
| `components/trackerCellEditors.ts` | 把 schema 的 `FieldDefinition` 映射到编辑器；**保持纯函数无 React 依赖** |
| `components/trackerColumns.ts` | 列注册表：**列 ID 一律取自 schema 解析出的真实字段名** |
| `components/trackerChipFields.ts` | 把字段拆分为 chip 行展示项与剩余项，**使所有 chip 界面对同一份 schema 做出同样取舍** |
| `components/trackerFieldLayout.ts` | 共用字段布局规则：**同一份 schema 在文档头、详情面板得到相同字段顺序与相同省略结果** |
| `components/labelRefValue.ts` | 纯函数读取 label-ref 值；**单独拆出以避免只读展示场景加载选择器组件** |
| `components/trackerClaimAtoms.ts` | 全局索引随任意条目变化重建，而**按 subject 的 atom 在该 subject 未变时返回同一数组，充当隔离边界** |
| `components/LabelRefPicker.tsx` | item 上有但注册表未声明的标签会被置顶并标记，**避免下次保存时被静默丢弃** |
| `TrackerReferenceNodeCore.ts` | **React-free** 的引用节点：只存引用 key 与 view，标题/状态在渲染时由宿主实时解析，序列化为可移植的 `nimbalyst://` markdown 链接 |
| `TrackerReferenceNode.tsx` | 把 React 装饰器绑定到 core 上：**未注册渲染器时降级为纯 key 文本** |
| `TrackerReferenceReadOnlyChip.tsx` | 无 tracker store 的宿主（如 Web 控制台）使用的只读 chip：形状一致但无弹层、无导航、点击无副作用 |

**这组设计有三条通用原则**：

1. **core 与宿主 UI 分离**（`NodeCore` 不含 React，`Node.tsx` 只做绑定与降级）；
2. **同一份 schema 驱动所有界面**，不各自硬编码字段顺序；
3. **纯函数与选择器组件分离**，避免只读路径加载重组件。

## 小结：五个可复用的设计手法

| 手法 | 例子 |
| --- | --- |
| **按进程而非领域分层** | `main/services/ai/` 112 文件留在主进程，provider 抽象在 runtime |

| **穷尽表代替条件分支** | `agentCapabilities.ts`、`PERMISSION_CATALOG`、`providerPayloadSlots.ts` |
