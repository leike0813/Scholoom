## 硬约束：数据库

| 规则 | 出处 |
| --- | --- |
| **双后端并存，迁移进行中，任何代码都不得假定只有一个后端** | `CLAUDE.md:82` |
| **最大坑：`data->'someKey'` 在 PGLite 返回已解析对象，在 SQLite 返回 JSON 字符串**。要么整列取出再解析，要么用 `typeof x === 'string' ? JSON.parse(x) : x` 防御式解析 | `CLAUDE.md:84`（真实 bug：2026-06-02 损坏 tracker `labelsMap`） |

| SQLite 表达式索引不得用 `->>` 访问器 | `check-json-accessor-indexes.mjs` |

### 启动期维护：延后 + 分片

`runWhenFirstUsable(label, fn)` 是唯一入口。三条硬性要求：

1. 禁止无界扫描（如 `COUNT(*) WHERE <unindexed>`）；
2. 必须按 id 范围分片 + `interChunkDelayMs` 让出 worker；
3. worker 内批量写走 `WriteCoordinator.runBackground`。

> **事故 NIM-899**：全扫 130 万行 12 秒，head-of-line 阻塞 30–39 秒。

## 硬约束：破坏性数据路径

`.claude/rules/destructive-data-paths.md` 是全仓库优先级最高的一组规则。

### 五条强制要求

1. **先重试再破坏**——一次失败只说明「出过一次问题」，不等于数据坏了；
2. **验证损害真实存在**——`integrity_check`、大小检查、解析，**不得靠错误消息的子串匹配**；无法验证就不许破坏；
3. **事件必须在动手前发出**，不是事后；
4. **除应用确实起不来外，一律先问**；
5. **留下可恢复产物，并在第一天就给它启动心跳**。

第 5 条附了一个极有说服力的案例（#1347）：

> 心跳给了「成功」产物 `pglite-db.migrated-*`，没给「丢失」产物 `pglite-db.backup-*`，**一行代码本可以把 bug 定位到十一月**。

### 三条禁令

- **绝不让用户手动删除自己的数据**——恢复备份是主动作，破坏性选项是次要动作且必须先备份；
- **只在无法复现的环境里才能触发的破坏性决策，位置就是错的**——要抽成纯函数（`pgliteInitRecovery.js` 是范式）；
- **验证绝不信任被验证的源**——从源为空时平凡通过的检查回答不了「源是否为用户的真实数据」。

### 串行化

`databaseOperationLock.ts` 覆盖恢复、迁移、备份还原——**这些操作都会关闭引擎并重命名目录**，设计上**直接拒绝而不是排队等待**。

### 环境变量事故

> 用户 `.env` 里的 `ANTHROPIC_API_KEY` 被静默读取并持久化，**$100+ 记到用户个人账户**。

对应的**正向硬约束**：所有 agent lane 只用用户在 Nimbalyst 设置里录入的 key 或用户已登录的 CLI，**不从环境变量读任何 provider**。`ai/server/providerApiKeyScrub.ts` 维护一份必须从 CLI agent 子进程环境中删除的 key 名单。

### 个人 / 团队 JWT 的职责划分

| | Personal JWT | Team JWT |
| --- | --- | --- |
| 用途 | **仅**个人同步到移动端 | **一切**团队协作 |
| 覆盖房间 | PersonalIndexRoom、PersonalSessionRoom、PersonalProjectSyncRoom | TeamRoom、DocumentRoom、TrackerRoom、ConversationRoom、TeamInboxRoom |
| 加密 | 客户端持钥（zero-knowledge） | 服务端托管 DEK |

`runtime/src/auth/jwtScopes.ts` 的 branded type 让混用变成编译错误——**但团队侧目前基本未 branded**，存在一条洗白路径（`getPersonalSessionJwt()` 会把 team JWT 标成 `PersonalJwt`）。

### `NIM-###` 的作用域规则很值得学

`Fixes NIM-123` 只出现在 **commit message**（那是 `CommitTrackerLinker` 用来自动关闭条目的，且不会随产品发布）；**代码注释与运行时日志字符串必须引用 GitHub issue 号**。

理由：`NIM-###` key 是 tracker-room 作用域的，在公开仓库的源码里写它**比不写更糟**——外部读者点进去看到的是无权限的错误页。

## 硬约束：前端与状态

### React 组件绝不直接订阅 IPC

`IPC_GUIDE.md:96-107`：

> 中心 listener 启动时订阅一次，事件触发时更新 Jotai atom，组件用 `useAtomValue()` 读。

理由列了四条：**竞态、陈旧闭包、`MaxListenersExceededWarning`、内存泄漏**。

这与 `store/atoms/`（90）+ `store/listeners/`（71）的严格配对结构是同一件事的两面。

### workspace 作用域的 IPC handler

> workspace 作用域的 handler **必须把 `workspacePath` 作为必填参数**。主进程不得回落到单例上的 "current workspace" 状态（多窗口 last-write-wins）。例外仅限真正全局的通道（主题、应用设置、版本、分析同意、更新检查）。**判断不了是否 workspace 作用域时，它就是。**

这条兜底规则（不确定时按更严格的一侧处理）值得直接抄。

### 编辑器状态禁止「lift state up」

`EDITOR_STATE.md:3-5`：

> 编辑器拥有自己的内容状态，父级只知「tab X 用 editor Y 打开 file Z」；**有状态编辑器不能被父级重渲染**。

配套的扩展契约（`EXTENSION_ARCHITECTURE.md:224-231`）：用 `useEditorLifecycle` hook 或手动订阅 host 事件；**自己拥有全部内部状态——复杂编辑器的内容绝不放在 React state**；save 请求时调 `saveContent()`；**绝不依赖父组件重渲染它们**。

### Jotai：每份状态只有一个权威源

`JOTAI.md:538` 的黄金法则：

> **如果你在写代码「同步」两个 atom，你大概有架构问题。**

派生值必须计算而非另存。

`plugins/TrackerPlugin/components/trackerClaimAtoms.ts` 是一个漂亮的落地：全局索引随任意条目变化重建，而**按 subject 的 atom 在该 subject 的 claim 未变时返回同一数组，充当隔离边界**。

### 持久化状态必须与默认值合并

`STATE_PERSISTENCE.md:18-76`：每个持久化接口需要 `createDefault*()` + `init*()`；**禁止 `{ ...loaded }`、禁止无默认值的 `loaded.field`、禁止手写字段枚举**。

### Git 集成绝不加轮询

原 30 秒轮询已移除（浪费、滞后、冗余）。`GitStatusService` 的 5 秒缓存 TTL **不是轮询**。

## 领域不变式

### 会话层级只有两层

`SESSION_HIERARCHY.md:9-15`：

> `parent_session_id` 的父行必须是 NULL；`session_type='workstream'` 行自身不得有 `parent_session_id`；**三层（workstream→workstream→session 或 worktree→workstream→session）是 bug 不是特性**。

配套：

- **worktree 就是 workstream**——worktree 行的每个会话都是扁平兄弟，共用 `worktree_id` 且 `parent_session_id = NULL`。为 worktree 建 `session_type='workstream'` 行**永远错**；
- 禁止 `session_type='workstream'` 且 `worktree_id IS NOT NULL`；
- 禁止 `parent_session_id` 与 `worktree_id` 同时非空（会在 `worktreeGroupsData` 里重复计数）。

三种结构角色由 `session_type` + `parent_session_id` + `worktree_id` 三字段组合决定：独立会话、workstream 父容器、workstream 子会话、worktree 常驻会话、blitz 父容器。

### Tracker 生命周期

```
to-do → in-progress → in-review → done
```

提交时用 `Fixes NIM-123` 让 `CommitTrackerLinker` 自动移到 `done` 并把 session 标 `complete`；**裸露的 `NIM-123` 只建立链接不关闭**。`approved` 在 review lane 上**永远是人类专属**（AI 可推进但只有人能 approve）。

`decision` 类型用于「在方案间做选择/决定不做某事」，格式固定为 `## Context / ## Alternatives considered / ## Reasoning / ## Trade-offs accepted`，做类似决定前先 `tracker_list({type:"decision", search:...})`。

**tracker 分享模型**：tracker 要么是个人要么是团队的；团队的话**服务端拥有它——schema 与条目一起**，`.nimbalyst/trackers/*.yaml` 只是本地副本。

## Markdown 兼容性：往返无损

`MARKDOWN_COMPATIBILITY.md`（仓库根级）的目标与三条禁令：

- 目标是 **CommonMark 兼容**；
- **禁止 HTML passthrough**；
- **禁止无法序列化为 Markdown 的布局与交互式 widget**；
- 每个特性必须能「编辑 → markdown → 编辑」**无损往返**。

这条约束解释了为什么 tracker 引用序列化为 `nimbalyst://KEY` 链接而不是自定义结构，为什么 17 类编辑器里没有一类引入不可导出的富文本特性。

## 命名约定

| 类别 | 约定 |
| --- | --- |
| 标识符 | TypeScript/Swift 接口、字段、变量一律 **camelCase** |
| Wire protocol | WebSocket/HTTP JSON 载荷一律 camelCase，**JSON payload 里绝不许 snake_case** |
| 消息判别符 | camelCase（`'syncRequest'`、`'appendMessage'`，**不是** `'sync_request'`） |
| SQL 列名 | **snake_case**，row→wire 时在边界映射 `{ sessionId: row.session_id }` |
| Alpha feature tag | kebab-case（`'my-feature'`） |
| 扩展 id | 反向域名式，字母开头，可含字母数字点下划线连字符 |
| IPC 通道 | `namespace:action`（`'history:create-snapshot'`、`'session-files:get-by-session'`） |
| ID 前缀 | `ws_<uuid>`、`doc_<uuid>` |
| 计划文档 | `plans/` 目录，描述性 kebab-case 文件名 + YAML frontmatter |
| Worktree 名 | 形容词-名词（`swift-falcon`）；分支 `worktree/{name}`；目录 `../{project}_worktrees/{branch}/` |

> **`NAMING_CONVENTIONS.md:6` 的理由值得记**：绝不为「更像 API」而引入 snake_case——这是私有协议，只有自家 TS 与 Swift 客户端消费。

## 写作与 CHANGELOG 约定

`CLAUDE.md:7-17`：

- CHANGELOG 一句话 subject、一句话 bullet；**一个功能一条 bullet，不管用了几个 commit**；
- **禁止把内部脚手架写进 CHANGELOG**——表/列名、IPC 通道名、服务/store 类名、环境变量管道、迁移注册、轮询间隔、「为即将到来的 X 做的内部脚手架」都不许；
- 只写用户视角的「我现在能做什么/什么被修好了」。

### 功能清单的纳入判据

`CLAUDE.md:23` 提了一个很少见的判据：

> 「有人探索 Nimbalyst 能做什么时，**会不会单独去找这个能力**？」

远程 agent 执行、结构化同事反馈**算**；elapsed-time 计数器、状态徽章、按钮位置、缩放、自动滚动**不算**。

> **用户可见 ≠ 值得写进清单。**

收尾时必须报告「Feature inventory updated」并附 section，或「No inventory impact」加简短理由。

### 文档风格

- 禁用 emoji；
- 禁用过度热情的措辞。

## 事实核验与协作

### 自己跑观察命令

**绝不要求用户跑 `curl`/`wrangler tail`/`tail -f`/`gh` 或粘贴日志。**

> 事故：某 session 花 23 轮让用户自己跑命令排查 Stytch JWKS 轮换。

工具对应关系：日志用 `get_main_process_logs`/`get_renderer_debug_logs`，数据库用 `database_query`，HTTP 用 `curl`，Workers 用 `wrangler tail`，DOM 用 `renderer_eval`。

### 宣布「修好」前必须端到端验证

> 需要 `/restart` 或用户手动走 UI 流程才能验证的 bug，**第一交付物是必须由修复变绿的失败测试**；不能基于「代码路径看起来对」或「测试通过」宣布修复。

> 事故：某工作流至少 4 次宣布「修好」。
