### 两个刻意的类型/实现分离

1. **`collab-protocol` 条件导出**：Node 条件解析到编译产物（sync server / CLI 用），其他条件解析到 `src/index.ts`（构建期直接吃源码，省一次预构建）。
2. **`CollabContentAdapter` 类型定义在 `extension-sdk`，注册表实现在 `collab-adapters`**。包描述里明确写扩展通过 `context.services.collab` 注册适配器，不直接依赖实现包。

## 构建体系

### TypeScript

根 `tsconfig.json` 的 `paths` 只映射 5 个包到源码：`@nimbalyst/{runtime, extension-sdk, tracker-engine, tracker-schema}`（extension-sdk 另有 `/file-tree` 特例与 `/*` 通配）。`exclude` 排掉 `**/e2e/**`、`packages/marketplace`、`worktrees`、`test-utils` 等。

共 22 个包级 tsconfig，命名即变体：`collab-protocol/tsconfig.build.json`（源码直出 vs 编译产物两套）、`collab-bundle/tsconfig.types.json`（校验 `.d.ts`）、`runtime/tsconfig.node.json`（`build:node` 变体）。

### Vite

`packages/runtime/vite.config.ts` 是库构建模板：双入口（`index` 与 `ui/index`）、`formats: ['es']`，插件为 `@vitejs/plugin-react` + `vite-plugin-dts`（排除 `mcp-stdio-server.ts`）+ `vite-plugin-static-copy` + 自写 `copyThemes()`。`external` 显式列出 react/lexical/yjs/extension-sdk 等宿主提供物；`manualChunks` 单独切出 `prettier`。`resolve.alias` 里 40+ 条 `@shikijs/langs/*` 全部指向 stub，**裁掉冷门语言包**。

`packages/electron/electron.vite.config.ts` 内联两个裁剪插件（拦非 common 语言与 Excalidraw locale），并**直接 import 了 `../../scripts/main-bundle-graph-policy.mjs`**——把架构边界检查嵌进构建过程本身。

`packages/shared/viteNimbalystPlugin.ts` 提供 dev/prod 双态别名：dev 指向 `../runtime/src/index.ts`，prod 指向 `../runtime/dist/index.js`。移动端把「编辑器」和「transcript」拆成两个独立构建目标（ios/android 各两份 vite config）。

### Electron 打包

打包配置内联在 `packages/electron/package.json` 的 `build` 键，构建器 `electron-builder@^26.0.12`。`packages/electron/build/` 是完整的钩子与校验工具目录：`afterPack.js`、`notarize.js`、`sign-windows.js`、`generate-update-yml.js`、`generate-third-party-licenses.js`（配 `license-approvals.json` 人工批准清单）、`validate-extra-resources.js`、`validate-packaged-sdks.js`、`verify-native-runtime.js`、`build-extensions.js`、`claude-runtime.js` 等，并自带 `__tests__/`。

### 样式与主题

`tailwind.config.ts` 的 `darkMode: ['variant', '&:is([data-theme="dark"] *, [data-theme="crystal-dark"] *)']`，所有 `nim*` 色板映射到 `var(--nim-*)`。主题事实源是 `packages/runtime/src/editor/themes/NimbalystTheme.css`，规范文档 `docs/CSS_VARIABLES.md` 的四条原则：单一事实源、语义命名、每个内置主题重新定义、禁止硬编码颜色。硬约束由 `scripts/check-ui-invariants.mjs` 执行：从规范主题 CSS 抽出已定义 token 集合，再校验具体文件里出现的 `var(--nim-*)` 均在集合内。

`postcss.config.js` 留了一条 Windows 注释：用 `fileURLToPath` 而非 `URL.pathname`，否则 Windows 上路径变成 `/D:/...`，tailwind 加载失败后只会在 `setupContextUtils` 里报 "Cannot read properties of undefined"。

## 测试体系

### Vitest：jsdom + node 两个 project

vitest 4 移除了 `environmentMatchGlobs`，改用 `projects`。`nodeOnly` 数组逐项给出理由：`packages/electron/src/main/**` 触碰 better-sqlite3、`packages/cli/src/**` 与 `packages/node/src/**` 是终端进程、memory 引擎是零应用依赖的宿主无关引擎。

> **一处值得记住的工程教训**：node 项目的 `include` 与 jsdom 的 `exclude` 曾是两份手工维护的清单。只改一处会让两边都丢掉这批测试，而整体仍然报绿。现在 `nodeOnlyInclude` 由 `nodeOnly` **程序化派生**。

别名 11 条把 tracker/runtime/extension-sdk 等指向 `src`；`@/` 指向 `runtime/src/editor`。替身桩（`test-utils/`）的两个注释解释了 why，比"stub 了什么"有用得多：

- `monacoStub.ts`——monaco 的 ESM 入口静态 import `.css`，node loader 处理不了。
- `electronLogStub.ts`——`electron-log/renderer` 导出 Proxy，`then` 也是函数，被 vitest 当 thenable 挂起，**import 阶段永久 hang，`testTimeout` 都够不着**。

其他策略：`testTimeout/hookTimeout` 统一 20000ms（注释记录了 vitest 4 升级后 `vi.setConfig` 副作用失效的历史）、`silent: 'passed-only'`（一次全量曾产出约 1MB 输出，90% 来自通过用例的 console）、失败持久化到 `.vitest/last-run.log`、全量规模约 **1070 个测试文件**。

**覆盖率不设阈值**，只用于观察，不作门禁。

### Playwright

根 `playwright.config.ts` 只管一个 project，`testDir` 指向 `packages/electron/e2e`，`fullyParallel: false`，timeout 120s。`maxFailures` 本地 1 / CI 0——真实 Electron 窗口占桌面，失败后继续跑只是抢机器。另有 `playwright-extension.config.ts` 走 CDP 9222 连活着的 dev 实例做扩展活体测试。

## 门禁脚本：每条架构约束一个可执行断言

这是本仓库最值得借鉴的部分。`scripts/run-validation.mjs` 是薄调度器，任务表在 `validation-inventory.mjs`。`unit` 任务被严格定义为「与 `test:prepush` 完全相同的 argv」——带 filters/shards 的调用不算全量结果，不能复用。

**每个 `check-*.mjs` 脚本的头部注释都写清了它对应哪次真实事故。** 全部 25 个门禁脚本在 `scripts/__tests__/` 里有回归测试。

| 脚本 | 约束什么 | 记录的事故 |
| --- | --- | --- |

| `check-main-bundle-graph` | Electron main bundle 模块图**零预算**：禁 `react-dom`、`@lexical/*`、`.tsx`、`src/renderer/` | 改 UI 会重建 main 并重启整个应用 |
| `main-bundle-require-policy` | main bundle 内 `require` 的两类隐患 | 懒 chunk 二次求值 main，重复注册 electron-log 抛 "second handler" |

## pre-push 门禁：分阶段 + 严格复用规则

`.githooks/pre-push` 由 `scripts/install-git-hooks.mjs` 经 `core.hooksPath` 挂载（`prepare` 生命周期自动执行），逐段计时写 `.vitest/last-prepush.json`：

| 阶段 | 命令 |
| --- | --- |
| toolchain | `check-toolchain.mjs "$(npm -v)"` |
| authors | `check-push-authors.mjs "$base..HEAD"` |
| lockfile | 变更 manifest 时 `npm ci --dry-run` |
| override-sync | `npm run check:override-sync` |
| text-nuls | `npm run check:text-nuls -- --ref HEAD` |
| typecheck | `npm run typecheck:prepush` |
| test gate | `npm run test:prepush-gate`（scripts + sandbox） |
| unit | `npm run test:prepush`（指纹一致可复用） |

两个短路：`pushDeliversNewCommits()` 判断本次 push 是否真带新 commit（发布时第二次推 tag 不重跑全套）；`shouldRunFullPrePushSuite()` 在本地 Windows 跳过全量 Vitest，但 CI 与其它平台仍强制。

**复用规则极严**（`docs/PREPUSH_AND_CI.md`）：只有最后一步 Vitest 可复用，且要求 argv 完全一致、完整 PASS、Git/内容指纹（HEAD、每个脏路径内容、Node major、平台/架构）全部一致。build/typecheck/静态检查/Sandbox 每次都跑。脏工作树允许复用——只要是同一棵脏树。

`scripts/run-workspace-script.mjs` 是另一个自研工具：npm 的 `run <script> -ws` 严格串行，实测 24 个 `tsc --noEmit` 串行 66s、8 路并行 29s，因此它自己做 workspace 展开、筛选、限流池与按 workspace 缓冲输出。

## CI

6 个工作流：`ci.yml`（job：`changes` 验证选择、`unit-tests`、`typecheck`、`transcript-bundle`）、`electron-build.yml`、`android-build.yml`、`ios-transcript-tests.yml`、`publish-cli.yml`、`publish-extension-sdk.yml`。

`ci.yml` 步骤顺序与 pre-push 完全对应。缓存策略被明确限定：`node_modules` 按 lockfile+patches 键，runtime 构建缓存按输入键，**没有部分恢复键**，collab-bundle 每次都重建。`ci-changes.mjs` 的 `classifyChanges` 决定走「仅文档」快路径还是全量验证。

## Marketplace

`packages/marketplace` 是 Cloudflare Worker，**从不流式传输文件字节**。四个端点：

| 端点 | 职责 |
| --- | --- |
| `GET /registry` | 读 R2 的 `registry.json`，注入 KV 下载计数，Cache API 缓存 5 分钟 |
| `GET /dl/:id/:version` | HEAD 校验 `.nimext` 存在、KV 计数 +1、302 跳 CDN |
| `GET /screenshots/:id/:filename` | 302 跳转 |
| `GET /health` | 健康检查 |

R2 布局：`registry.json` + `extensions/{id}/{version}.nimext` + `screenshots/{id}/{filename}.png`，公开域 `cdn.extensions.nimbalyst.com`。

`packages/electron/src/main/data/extensionRegistry.json` 是**客户端侧**注册表快照（schemaVersion 1，26 个官方扩展的 id、版本、权限、下载与校验和、截图与 changelog），是 marketplace 安装与自动更新的数据源。

## 一处 DRY 范式：wiki 插件的生成与工具改名表

`.claude-plugin/marketplace.json` 是 **Claude Code 插件市场清单**（不是 npm 概念）。`plugins/nimbalyst-wiki/` 包含 commands/hooks/scripts 与三个 skill。

其中 `knowledge-graph`、`knowledge-setup` 两个 skill 是**生成物**：`scripts/build-wiki-plugin.mjs` 从 `packages/extensions/knowledge/claude-plugin/skills` 构建过去，`--check` 模式检测陈旧（对应 `npm run check:wiki-plugin`）。脚本里维护了一张**工具改名表**（`tracker_list` → `wiki_list` 等）与「tool contract rev 3」注释——桌面 skill 调 loopback 的 `tracker_*`，远端插件改调 wiki server 的 `wiki_*`（多带一个 `repo` 参数）。这是"同一份写作规范、两处工具契约"的标准处理。

## CLI（`nim`）：双访问模式

核心设计是**同一接口下的两条通路**：

- **Live 模式**：通过 loopback MCP-HTTP 服务与运行中的应用通信，端点由启动时写入的描述符发现（`<userData>/mcp-endpoint.json`，权限 0600）。
- **Direct 模式**：应用未运行时直接打开 better-sqlite3。读用**只读**句柄（WAL 保障应用在线时也安全）；写打开可写 WAL 句柄并在 `BEGIN IMMEDIATE … COMMIT` 内执行，但**只在没有活实例持有该库时允许**——若描述符显示默认库上有运行中的应用，所有写一律拒绝并以 **exit 5** 退出，绝不与应用的写者竞争。离线修改的条目置 `sync_status='pending'`，应用下次启动按正常 backfill 排空。

自动探测顺序是「先试 live 发现，再回落 direct」，`--live`/`--offline` 可强制，`--db <file>` 指定库。状态为「Phase 1–3 complete」，剩 Phase 4 打磨（`--jq`/`--template`、配置文件、shell 补全、预编译二进制）。

## cloudflare-sandbox：私有部署的安全默认值

要点：设置面板使用本地 Wrangler 具名 SSO profile 并要求显式选账户，**应用不索取也不保存 Cloudflare API key**。每个安装管理一个 sandbox，能力为 review / deploy / status / wake / stop / delete，且「部署成功」与「容器就绪」是两个独立观测。

安全默认值相当具体：`enableInternet = false`；出网白名单是具体 DNS 主机与 `github.com`、`api.anthropic.com`、`platform.claude.com`、`console.anthropic.com`、`sync.nimbalyst.com` 的并集（**尽管 SDK 支持 `*` 通配，该 RPC 拒绝**）；provision 拒绝路径穿越与符号链接，文件总量限 256 KiB、权限默认 `0600`、最多 32 文件 / 16 主机；空闲 5 分钟自动休眠，最多一个 `standard-3` 实例。`release.json` 用 `docker.io/<org>/<repo>@sha256:<digest>` 固定镜像。

README 结尾有一句很克制的话：「以上检查都不构成对真实 Cloudflare 部署的证明」。

## 发布流程

### 两阶段：alpha 预发布 → stable 晋级

**Overview** 记录了一次架构收敛：alpha 与 stable 两条渠道现在**完全由 GitHub Releases 承载**，Cloudflare R2 过渡桥已移除且凭据已吊销。`CHANGELOG.md` 是发布说明的事实源，annotated git tag 仍携带说明快照。

**Phase 1 — Alpha**，六步：

1. 准备说明——写进 `CHANGELOG.md` 的 `[Unreleased]`，并与 `docs/FEATURE_INVENTORY.md` 对账（要求报告更新内容或说明「无 inventory 影响」）
2. 跑 `/release-alpha patch|minor|major`，生成**两版**说明（开发者技术 CHANGELOG + 用户向 PUBLIC_RELEASE_NOTES）并等审批
3. `./scripts/release.sh`——bump 版本 → 更新 lockfile → `[Unreleased]` 移入新版本节 → 提交 → 打 annotated tag
4. `git push origin main` 后 `git push origin vX.Y.Z`
5. 推 tag 触发 Actions：构建 macOS(arm64+x64)/Windows(x64+arm64)/Linux(x64)，macOS 签名+公证，Windows 用 DigiCert KeyLocker 签名，发布**可见的 pre-release**
6. 从预发布下载实测

Windows 每次发三个文件：`Nimbalyst-Windows-x64.exe` 与 `-arm64.exe` 是 `latest.yml`/`alpha.yml` 引用的架构专属包，`Nimbalyst-Windows.exe` 是签名 x64 包的副本，**仅为兼容旧下载链接、不参与自动更新元数据**。

**Phase 2 — Stable**：`/promote-public-release` 定位当前 tag 的 prerelease 与上一个 stable，重建累积性公开说明、交用户编辑、翻转 pre-release 为 stable。

### 公开说明的风格

`PUBLIC_RELEASE_NOTES.md` 与技术 CHANGELOG 严格分离，当前条目分 New Features / Improvements / Fixed 三节。两个可借鉴点：功能描述直接说用户能做什么（「Sonnet row 现在跑 Sonnet 5.5，且 Sonnet 5 仍可选」）；修复条目带 issue 号与贡献者署名（`(#1579, contributed by @jszobody)`）。

### 许可

仓库 MIT；第三方依赖各自授权；协作 sync server（`wss://sync.nimbalyst.com` 的 Cloudflare Worker）**是另一个独立项目**，客户端按 `packages/collab-protocol/` 的线协议与之通信。应用侧有 `licenses:generate`/`licenses:check` 与人工批准清单 `build/license-approvals.json`。

## 其他值得记的工程设施

- **补丁机制**：根 `postinstall: patch-package` + 顶层 `patches/`。
- **安装脚本白名单**：根 `package.json` 的 `allowScripts` 逐个列出允许执行安装脚本的包（`better-sqlite3`、`esbuild` 五个版本、`sharp`、`workerd`、`node-pty`、`@vscode/ripgrep` 等），配 `scripts/ensure-sandbox-dependencies.mjs` 复用成功安装标记。
- **设计资产**：`design/` 按功能分子目录（agents、Collaboration、Extensions、MenuBar、MobileSync、permissions、trackers 等）；`examples/` 放演示文件（mindmap、namenym、obj、csv）。
- **文档规模**：`docs/` 下 79 份文档。`AGENTS.md` 要求每个 AI session 开始先读根 `CLAUDE.md` 与相关包级 `CLAUDE.md`，并在新增/移除显著产品能力时同步 `docs/FEATURE_INVENTORY.md`。
