## 关系类型口径

理解依赖表前必须先记住这六种关系，归属类关系不计入层间依赖：

| 关系 | 含义 |
| --- | --- |
| `imports` | 文件之间的 import |
| `calls` | 符号之间的调用 |
| `depends_on` | 显式记录的依赖 |
| `configures` | 配置作用于目标 |
| `defines_schema` | 定义目标的结构约束 |
| `implements` | 实现目标声明的接口 |

`contains`、`exports`、`documents` 只表示内容归属，**不算层间依赖**。

跨层有向边共 46 条。出度最高的是渲染进程 UI 层（1845），入度最高的是渲染进程状态层（1018）与共享基础层（583）。

## 15 组双向依赖

按边数和排序。前五组值得展开。

### 1. renderer-ui ↔ renderer-state（1018 / 55，合计 1073）

**性质：记账假象，不是真循环。** UI 层把 1018 条边指向状态层（atoms、hooks、utils、services、contexts）。反向 55 条来自 `renderer-state` 的选择器与视图模型消费 UI 类型/组件（`store/conversationDirectoryViewModel.ts`、若干 `store/actions/`），以及 renderer-ui 内部子目录之间被归到不同层。

**根因：分层与实现目录不完全对齐。**

### 2. ai-services ↔ main-process（234 / 158，合计 392）——最值得注意的真实耦合

正向 234 条意味着**大量 AI 代码住在 runtime 却直接 import 主进程模块**。成因三类：

1. `runtime/src/electron/claudeCodeEnvironment.ts`（出边 10）等**故意放在 runtime 的 Electron 专用模块**；
2. `packages/electron/src/main/services/ai/`（112 文件）本就是 AI 代码但归入主进程层——因为它做 PTY 提交、进程观测、权限 hook，必须留在主进程。**层边界是按「进程归属」而非「领域归属」划的**；
3. `main/services/tracker/localKeyAllocator.ts` 的 `assignChunk` 被两侧同时引用。

**这一组是 Scholoom 最值得避免的：领域横跨两个包时，进程归属与领域归属必然冲突。**

### 3. main-process ↔ data-persistence（167 / 38，合计 205）

正向 167 条是正常使用数据库（`utils/store.ts` 53、`database/*` 25、`mcp/mcpWorkspaceResolver.ts` 17）。反向 38 条是**结构性回边，成因已在文件中自陈**：

- `database/bootMigration.ts` 是「把 SQLite worker 代理适配成 orchestrator 需要的」**接线层**；
- `database/sqlite/migrationControl.ts` 是「主进程安装在迁移代理上的控制钩门」；
- `DatabaseErrorTelemetry`、`recovery/recoveryEventMapper`、`MigrationProgressReporter` 需要主进程的 analytics、窗口与 IPC 广播能力。

**正确做法：基础设施层通过显式的接线/控制钩子模块向宿主申请能力，而不是让 database 直接依赖 main。**

### 4. main-process ↔ shared-foundation（181 / 1，合计 182）

反向仅 1 条，几乎纯粹的单向地基依赖。那唯一 1 条反向边是这一组唯一的异常点。

### 5. editor-runtime ↔ plugin-system（42 / 9，合计 51）

plugin-system 几乎全是 editor 的插件，向 editor-runtime 依赖 42 条正常。反向 9 条来自 `editor/nodes/EditorNodes.ts` 引用了 `DecisionPlugin`/`EmbedPlugin`/`EmojisPlugin`/`ImagesPlugin`/`MermaidPlugin`/`PageBreakPlugin`/`DocumentLinkPlugin`/`TrackerLinkPlugin` 各 1 条——**节点集合反向引用了提供节点的插件**，属于真实的结构倒置。合理做法应是节点由插件侧注册而非 `EditorNodes.ts` 直接 import。

## 三个值得借鉴的横向模式

### 模式 A：「无头 / 有头」二分

`runtime/src/editor/extensions/builtin/` 下 21 个**无头扩展**只注册 Lexical 命令与节点，不含 UI（AutoLink、Collapsible、Comments、Decision、Diff、DragDropPaste、Embed、Images、KanbanBoard、Layout、Mermaid、PageBreak、TabFocus 等）；`editor/plugins/` 下 36 个**带 UI 插件**承载渲染（Toolbar、CodeHighlight、Table 系列、Typeahead、DiffPlugin 等）。

`nodes/EditorNodes.ts`（渲染进程基础节点集）与 `nodes/headlessBodyNodes.ts`（主进程 headless 编辑器从 markdown 重建用）也刻意分开。

**这是让同一个编辑器内核能被主进程无头、渲染进程有头、离屏窗口复用而不重复实现的关键。**

### 模式 B：显式的间接引用层破循环

项目里有**两处显式为破循环而存在的文件**，文件摘要里直接写明了：

- `src/main/mcpConfigServiceRef.ts`——「通过注入式 getter 打破主进程模块间的循环依赖」
- `src/main/extensions/extensionBackendRpc.ts`——「只定义消息形状，不含传输实现」，utility-process 与 worker-thread 各自包裹同一套协议

`runtime/src/host/hostEnvironment.ts` 是同思路的第三例：把 runtime 此前直接问 Electron `app` 的两个问题收口成宿主能力契约。

**主进程模块图大到需要专门的破环手段——说明这类注入式间接层应当一开始预留，而不是事后打补丁。**

### 模式 C：「唯一事实源表」收敂分支

反复出现的模式是把散落的条件判断收敂为一张穷尽表：

| 表 | 收敂了什么 |
| --- | --- |
| `storage/providerPayloadSlots.ts` | 各 provider chunk 中重负载放在哪里 |
| `storage/nonRenderingFrames.ts` | 哪些帧「不产生任何 transcript 事件」 |
| `storage/rawMessagePrune.ts` | 哪些原始行可整行剪除 |
| `ai/server/agentCapabilities.ts` | agent 能力声明（**无可选成员的穷尽 Record**） |
| `main/extensions/permissionRegistry.ts` | `PERMISSION_CATALOG` 是权限 id 唯一事实源，**扩展只能引用不能注册** |
| `shared/fleetStripColors.ts` | 菜单栏状态条唯一调色板 |
| `core/dbBoolean.ts` | PGLite 返回真布尔而 SQLite 返回 0/1 的读路径归一化 |
| `editors/monacoLanguages.ts` | 后缀到 language id 的唯一映射表 |
| `shared/alphaFeatures.ts` / `betaFeatures.ts` / `developerFeatures.ts` | 三张特性开关注册表 |

**在 provider 数量、插件数量、后端数量都很多时，这是控制分支爆炸的主要手段。**

### 两处已知历史遗留

- `src/main/file/FileWatcher.ts` 摘要写「已改由 WorkspaceEventBus 统一广播，这些函数保留为空实现以免改动调用点」；
- 分层描述称 renderer 用 zustand，实际主用 Jotai。

**照抄架构描述前要先知道这两处。**

## 同步与协作层细节（91 文件）

分两条主线。

**个人同步（CollabV3）**：`CollabV3Sync.ts` 基于 WebSocket 与 Durable Object 实现会话同步；配套 `collabV3Crypto.ts`（无状态加密工具集：解析 JWT、派生密钥）、`collabV3WireTypes.ts`（**桌面 provider、协作 worker、iOS 三方共用的线协议**）、`indexReplicationClient.ts`（个人索引 v2 复制协议客户端状态机，按修订号维度）、`indexPublication.ts`（发布闸门、按 key 串行队列）、`indexPublishRetry.ts`、`personalSyncWriteGate.ts`（**只有索引完整读取且客户端受支持才允许写**）、`syncedMetadata` 声明式字段清单。

**团队/文档同步**：`TeamSync.ts`（TeamRoom）、`DocumentSync.ts`（DocumentRoom Durable Object）、`ConversationSync.ts`、`TeamInboxSync.ts`、`FeedbackRequestSync.ts`、`CollabLexicalProvider.ts`（把加密的 DocumentSyncProvider 适配为 Lexical provider）。传输裁剪集中在 `syncContentTruncator.ts`（出边 16）。另有 `ProjectSyncProvider.ts`（主进程按项目建立**单条** WebSocket）、`OutboxDrainer.ts`、`LocalDocumentReplica.ts`（Y.Doc + 持久化 store + outbox 的组合）。

**outbox 模式**是这一层的核心机制：本地写入先落到本地队列表（`collab_document_outbox`），再由后台批量上送服务端，从而把「本地读到的内容」和「服务端已确认的内容」解耦，也给了快照重放一条退路。
