# 07 数据持久化与协作同步

> 事实来源：`.ua/wiki/layers/data-persistence.md`、`layers/collab-sync.md`，以及 `main/database/**`、`runtime/src/sync/**` 的模块页摘要。
> 图谱记录了 **107 张表**、154 个 schema 标签、142 个 migration 标签——**数据模型是这个系统的重心之一**。

## 本地数据层：双后端与一次产品级切换

### 双后端现状

Nimbalyst 的本地数据层同时支持 **PGLite**（Postgres 编译为 WASM）与 **better-sqlite3**，且**正在做一次产品级的后端切换**。因此任何代码都不能假定只有一种后端。

| 组件 | 职责 |
| --- | --- |
| `database/initialize.ts` | 启动时完成后端选择、迁移、备份定序 |
| `database/userDataPath.ts` | **整个安装的数据库根目录唯一答案** |
| `database/sqlite/BackendSelector.ts`（出边 9） | 「本地库跑在 PGLite 还是 SQLite」的**唯一事实源：既有安装视为待迁移** |
| `database/sqlite/PGLiteDatabaseWorker.ts` | 把 PGLite 封装进 Worker Thread |
| `database/sqlite/worker/sqliteWorker.ts` | 持有 better-sqlite3 连接、写入协调器 |
| `database/sqlite/SQLiteDatabaseProxy.ts` | 在主线程代理 worker |
| `database/sqlite/ActiveDatabaseFacade` | **门面 + 双实现**，把后端差异挡在一层接口之后 |
| `database/databaseOperationLock.ts` | 覆盖所有破坏性数据库操作的**主进程单锁** |
| `database/DatabaseErrorTelemetry.ts` | 隐私安全的数据库错误遥测，原始错误本地归类 |

**为什么放进 Worker Thread**：让数据库运算不阻塞主进程事件循环。

### 切换过程：三件套

这是本仓库最完整的一次「不可逆迁移」工程，值得完整记录：

| 文件 | 职责 |
| --- | --- |
| `cutoverJournal.ts` | **持久化日志**：原子写入记录每个阶段，**落盘后才进下一步，拒绝阶段倒退** |
| `cutoverMachine.ts` | 迁移与采纳**共用的唯一切换状态机**：静默源库 → 移走源目录 → 提交后端 |
| `cutoverReconciler.ts` | 未完成切换的**启动期对账** |
| `cutoverStartup.ts` / `cutoverVerification.ts` / `rollbackTransaction.ts` | 启动、验证、回滚 |
| `PGLiteToSQLiteMigrator.ts`（273–935，**662 行**） | 数据面：逐表分批拷贝、**校验行列数与抽样值**、翻译方言差异、切换前最后一次 catchUp |
| `dialectTranslator.ts` | PG→SQLite 机械改写 |
| `migrationTableCopy.ts`、`migrationBatchPolicy.ts` | **按载荷字节估算与 2 秒读耗时自适应批大小** |

三件套的分工很值得学：**日志负责"走到哪了"，状态机负责"能往哪走"，对账负责"崩了怎么续"**。

### 双后端差异：收敂为小型适配层

差异不散落在各处条件里，而是显式收敂：

| 适配点 | 文件 | 说明 |
| --- | --- | --- |
| 布尔读路径 | `runtime/src/core/dbBoolean.ts` | **PGLite 返回真布尔，SQLite 返回 0/1** |
| JSON 列 | `main/database/sqlite/jsonColumn.ts` | **PGLite 返回已解析对象，SQLite 返回字符串**。历史上曾因此写坏数据 |
| JSON 索引表达式 | `jsonKeyExpr(engine, column, key)` | 抹平方言差异，见下方门禁 |

> ⚠️ `DATABASE.md` 记录的**最关键硬约束**：JSON 列的子字段提取在 PGLite 返回对象、在 SQLite 返回字符串。这条差异曾导致数据损坏。

### 破坏性操作一律串行化

`databaseOperationLock.ts` 值得单独注意：**恢复、迁移、备份还原都会关闭引擎并重命名目录**，这些破坏性操作必须串行化，设计上选择**直接拒绝而不是排队等待**。

仓库一贯的取向（`tour.md` 第 12 步原话）：**任何会破坏用户数据的路径都要串行化并留下可恢复的痕迹**。

### 恢复子系统

`database/recovery/`（16 文件）同样严谨：

| 文件 | 要点 |
| --- | --- |
| `recovery/recoveryTransaction.ts` | 文件摘要明确写「**顺序本身就是全部安全论证**」 |
| `recovery/recoveryReconciler.ts` | **刻意拆成纯规划器与薄执行层** |
| `recovery/recoveryJournal.ts` | **在动任何文件之前先写下打算做什么** |
| `recovery/index.ts` | 恢复子系统的**唯一对外入口**，把服务、候选评估、验证器与 reconciler 统一收口 |
| `recovery/recoveryEventMapper.ts` | 映射到主进程的 analytics/窗口能力 |

**「纯规划器 + 薄执行层」的拆分**是这里最值得借鉴的：规划可测试、执行不可测，分开后测试成本骤降。

### 一个真实事故：JSON 索引访问器

`check-json-accessor-indexes.mjs` 背后的事故值得完整记住，因为它同时体现了**性能问题的隐蔽性**和**门禁脚本的价值**：

> 四个 `document_history` 部分索引用 `json_extract` 声明，但查询谓词全用 `->>` 访问器。**`json_extract` 声明的索引不会被 `->>` 谓词命中**，于是静默全表扫描。热查询扫 46,110 行、约 76ms/次，代价是 SQLite worker **31% 的时间**。

正确解法是统一走 `jsonKeyExpr(engine, column, key)`。

### outbox 模式

`tour.md` 第 13 步的核心机制：

> 本地写入先落到本地队列表（`collab_document_outbox`），再由后台批量上送服务端，从而把「本地读到的内容」和「服务端已确认的内容」**解耦**，也给了**快照重放一条退路**。

`DocumentSyncHandlers.ts` 一人就有 **44 个通道**，覆盖 WebSocket 开关、文档开关、资产上传与 GC、副本 outbox 队列以及快照恢复。

### JWT 作用域：最常见的同步 bug 来源

同步区分**个人 JWT** 与**团队 JWT**：

- 个人 JWT **只用于**个人会话同步到移动端；
- 团队 JWT 授权**一切**团队协作。

**两者混用是本仓库最常见的同步 bug**。`check-identity-scopes.mjs` 专门为此设门禁，基线按「文件 + 声明源码文本」而非行号键入（注释写明这份清单「只会越来越短」）。

### 协作服务器 URL 的唯一来源

`main/utils/collabSyncUrl.ts` 规定 URL 的唯一来源，**只有开发构建显式设为 development 才指向本地 worker**。

### 传输层的两条硬约束

| 约束 | 实现 |
| --- | --- |
| renderer 不得直接开 socket | `check-renderer-sync-sockets.mjs`：必须传 `createProxiedWebSocket` 由 main 开 socket |
| 团队通道**不是**客户端加密 | `check-team-lane-crypto-names.mjs`：服务端托管下是 TLS 上的**明文**，禁止出现 `Encrypted*` 标识符 |

第二条的事故记录很典型：**agent 读到旧命名后判定「服务端读不了 payload」，进而否掉了正确的冲突合并设计**。个人通道与本地副本是真加密，不在扫描范围。

### 一个值得记住的模型

`serviceAnalytics` 层的 `deriveFleetSnapshot`（`main/tray/fleetSnapshot.ts`）把会话集合归约为计数、优先会话、等待时长与停滞信息，**是菜单栏、托盘面板与锁屏共用的唯一事实源**。同一个派生值被三个 UI 消费，因此必须只有一处实现。

## 小结：不可逆操作的四条通用规则

1. **日志先于动作**——`cutoverJournal` 与 `recoveryJournal` 都在动文件前先写下打算做什么。
2. **拒绝优于排队**——`databaseOperationLock` 对并发破坏性操作直接拒绝。
3. **规划与执行分离**——`recoveryReconciler` 拆成纯规划器与薄执行层，使规划可测。
4. **本地与服务端解耦**——outbox 模式让「本地读到的」与「服务端已确认的」不同时成立，并留有重放退路。
