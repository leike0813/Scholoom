# 14 开发约定与已知坑

## 冲突裁决顺序

`docs/README.md:12-13` 规定了文档冲突时的权威顺序：

> 若文档之间存在冲突：
> 1. **用户使用模型** 负责产品行为
> 2. **OpenSpec main specs** 负责可验收要求
> 3. **代码与 typed contracts** 负责当前实现事实

**参考这个项目时遇到矛盾，按此顺序判断。** 代码 > spec > 文档描述。

## 六条合约设计原则

`AGENTS.md:726-779`，这是整个项目最有价值的方法论部分。

### 1. Separate Contracts From Artifacts

> 稳定 specs 拥有已确认的研究承诺，project change 拥有尚未应用的高影响更新，gate 记录 verdict，handoff 记录边界交换，patch 只带路径与计数，check 记录诊断。

**每个概念只有一个 owner。** 产物（artifact）是外部文件，通过 handoff 引用而不被管理。

### 2. Make Claims First-Class

> Claims 不能藏在散文里。每条 claim 需要来源支撑、适用边界、强度判断和不确定性声明。

`claims.yaml` 的字段直接对应：statement / strength / scope / evidence[] / uncertainty。

### 3. Make Human Decisions First-Class

> ResearchSpec 不用 model runtime，不判定学术价值，不由模型自动批准 Gate。模型可以准备 findings，verdict 由人确认。

所以 Gate 有 `pending` / `pass_with_conditions` / `fail` 三态 + 人工 verdict 流程，而不是布尔值。

### 4. Keep Workflow State Separate From Research Specs

> 运行状态与研究语义各自成文件。specs 不包含运行状态，run files 不复制研究内容。

**四个状态是四种不同的事，混在一起就无法独立演进。** 这一条是前面三条的基础。

### 5. Gate Progress, Do Not Invent Semantics

> Graph 表达流程控制，不表达语义推断。Capability 可以准备 findings，verdict 由人确认。系统不发明研究事实。

### 6. Prefer Proposed Changes For High-Impact Updates

> 范围、结构、输出格式、来源采纳等高影响语义更新先走 project change。稳定 specs 是已确认基线。

对应状态机：`propose → decide → 实际修改 specs → archive`，且 **accepted ≠ applied**。

## 九条工程规则

`AGENTS.md:817-837`：

1. **单一事实源**：领域规则只有一个权威定义
2. **单一写入所有者**：特定状态的写入者明确且唯一
3. **YAML 存结构化数据，Markdown 存人类可读叙述**
4. **JSON 用于机器生成派生物**（CLI 响应、生成目录、快照）
5. **结构化失败优于异常穿透**
6. **边界遵循 fail-closed**
7. **测试断言领域行为和结果结构，不锁定实现细节**
8. **生成输出是确定性的**
9. **命令影响面在用户文档中显式声明**

第 6 条展开（`AGENTS.md:829`）：

> Command fail-closed：未知 schema 报告为 unsupported，不静默转换。Command 缺参数返回清晰错误，不猜测。

第 7 条展开（`AGENTS.md:831`）：

> 测试断言领域行为和结果结构，不锁定实现细节。

这解释了为什么测试用 `assert.equal` 断言信封字段而非文案。

第 9 条就是 `presenter.ts` 的 `READ_COMMANDS` / `WRITE_COMMANDS` 集合 + handbook 标注。

## 十一条文件写入规则

`AGENTS.md:839-870` 是最具体的部分：

> 1. Write ordinary project files directly when they are your own deliverable.
> 2. Use `researchspec handoff add` for a handoff to files outside the run.
> 3. Task notes are informal and live in `work/researchspec-notes/<task-id>.md`.
> 4. Research state changes go exclusively through ResearchSpec CLI commands.
> 5. Project change acceptance is never state application.
> 6. The assigned capability writes its declared output scope.
> 7. Do not modify `references/cli-handbook.md` by hand.
> 8. CLI adapters, the code, and the documents are the sources of truth — don't document by reflection.
> 9. No runtime rules based on filenames, directories, or external tool metadata.
> 10. No free-form model execution, autonomous verdict, or free-form human confirmation.
> 11. Annotate all edits with the change id.

四条最需要记住的：

**第 4 条**（`:849`）：

> Research state changes go exclusively through ResearchSpec CLI commands.

**普通项目文件可以直接写，受管状态只能走 CLI。** 这条边界就是「文件是接口」的技术含义。

**第 8 条**（`:859`）：

> CLI adapters, the code, and the documents are the sources of truth — **don't document by reflection**.

即：**不要靠「看代码然后写文档」来更新文档**，因为那还是在制造第二事实源。要么改 typed catalog 让文档生成，要么改 contract schema。

**第 9 条**（`:861`）：

> No runtime rules based on filenames, directories, or external tool metadata.

**运行时行为不能靠「看文件名猜」**。这条极其重要——它是本项目所有 schema 化的理由。如果运行时根据目录名判断类型，就无法校验，也无法 fail closed。

**第 11 条**（`:869`）：

> Annotate all edits with the change id.

所有编辑都要标注 change id，保证可追溯到 `openspec/changes/` 的某个变更。

## Definition of Done

`AGENTS.md:888-899`：

1. `pnpm build` 通过
2. `pnpm test` 通过
3. `pnpm lint` 通过
4. `pnpm check` 通过
5. `pnpm arsu:check` 通过
6. `pnpm arsu:idempotence` 通过
7. `pnpm docs:check` 通过（生成文档未漂移）
8. 受影响 vendor 的 `*:check` 与 `*:idempotence` 通过
9. `pnpm release:verify` 通过
10. `pnpm dlx @fission-ai/openspec@1.5.0 validate --specs --strict`
11. `git diff --check` 通过

**七条与 ResearchSpec 自身相关的检查**（转换器幂等性、文档漂移、包验证、spec 校验）都进 DoD。

## Agent 编辑本仓库时的行为

`AGENTS.md:872-886`：

- **不要提交或发布**，除非明确要求
- 不要用 shell 脚本直接改文件，用 `apply_patch` 等编辑工具
- 如果某条指令在仓库里不成立，**停下来说明**而不是绕过

> 遇到看似违反规则的仓库状态，先检查是不是仓库处于「计划中的重构中间态」，再决定是否修复。

最后一条很有意思：**它预期仓库会处于中间态**。调研时确实发现 `converter.ts:118` 的恒假表达式和重复的 discovery 文件——这符合它的自我认知。

### 10. Graph profile 源不是 YAML

### 11. 已知代码缺陷

**`src/arsu-converter/converter.ts:118` 恒假表达式**：

```ts
if (JSON.stringify(buildPresetGraphProfileRegistry()) !== JSON.stringify(buildPresetGraphProfileRegistry())) {
  errors.push("Preset graph profile registry projection is not deterministic");
}
```

两边调同一个无参函数，**条件永远 false**，这条确定性检查从未生效。正确写法应拿预先生成的期望值或独立路径的产物来比。

这是 `pnpm arsu:check` 的一部分，CI 每次都跑——但它跑的是一条死代码。

同一函数中 `buildPresetGraphProfileRegistry`（`workflow/generate.ts:15-26`）**确实**为每个 profile 计算 `profile_sha256`，所以实现确定性校验所需的数据是现成的，只是 check 里没用上。

### 12. 重复实现

`src/core/workspace/discover.ts` 与 `graph-discover.ts` 逐行相同。`layout.ts` 与 `graph-workspace-index.ts` 双份列举必需目录/文件。

## 「不要这样写」的边界

`AGENTS.md:35-51` 的反面清单值得完整记住：

- ❌ LLM API 集成层
- ❌ 平台专属的 Claude Code / Codex 适配器
- ❌ Web app、database-first 研究平台、引用管理器替代品
- ❌ 手工维护的生成产物副本

`docs/developer/architecture.md:21-22` 补充：

> ResearchSpec 不调用模型 API，不管理数据库，不执行 vendor 脚本，也不接管 Zotero 或交付物。

## 给 Scholoom 的启示

1. **先定冲突裁决顺序**。三个层次：产品行为 / 可验收要求 / 实现事实。写下来比吵一架有用。
2. **「不要靠反思更新文档」**。要么改 typed catalog 让文档生成，要么改 contract。这条杜绝了手写文档的必然漂移。
3. **运行时规则不能靠文件名**。这是所有 schema 化的根本理由。靠目录名判断类型，就无法校验也无法 fail closed。
4. **明确预期仓库会处于中间态**。Agent 被告知「发现违反规则的状态先停下来说明」——这比让它默默修复更安全。
5. **DoD 里包含文档漂移检查**。不是「记得更新文档」，而是「CI 会告诉你没更新」。
