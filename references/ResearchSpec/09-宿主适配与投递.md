## 投递模式：三种

`--delivery skills | commands | both`（默认 `skills`）：

| 模式 | 产物 | 适合 |
| --- | --- | --- |
| `skills` | `SKILL.md` 包 | 大多数现代宿主 |
| `commands` | 命令 wrapper（Markdown + frontmatter） | 显式命令式工作流 |
| `both` | 两者都投 | 兼容性优先 |

命令 wrapper 有 `enabled: true/false` 标志，`update` 可在 `skills`/`commands` 之间切换而不重装。

**关键事实**：`src/adapters/command-renderer.ts:18-29` 的 `COMMAND_WRAPPER_CONTENTS` **只有 1 个条目** —— `id: "navigate"`。

```ts
export const COMMAND_WRAPPER_CONTENTS: readonly CommandContent[] = [{
  id: "navigate",
  family: "cli",
  category: "researchspec",
  tags: ["researchspec", "navigate", "procedures"],
  body: `Route the user's request: {{arguments}}...`,
}];
```

**即：无论投给多少个 command-capable 宿主，实际只生成一个 `researchspec-navigate` 命令 wrapper。** 16 个 CLI 顶层命令通过 `LEGACY_COMMAND_IDS`（`command-renderer.ts:16`，直接取自 `CLI_TOP_LEVEL_COMMANDS`）记录在文档里，但命令面只暴露 navigate 这一个路由入口。

> 调研中曾出现「28 个 command-capable 工具只有 16 个 wrapper」的说法。以 `command-renderer.ts` 为准：**1 个 wrapper**。

**约束**（`usage-model.md:37-41`）：

> 只有 5 个仅命令工具默认支持 `both`。**update 保持已选择模式，不静默切换。**

`src/adapters/installations.ts` + `managed-target.ts` 定义 manifest 与区域管理（详见 [06 篇](06-工作区与文件合约.md)）。`src/adapters/workspace-delivery.ts` 把所有东西合并成**一份统一写入计划**。

### 交付后置条件

`usage-model.md:51-53` 的顺序要求：

> Delivery ordering 先准备 manifest 与 baseline，再受控写入文件，最后投影参考资料。**只有交付完成后才 report managed paths。**

### 失败语义：strict vs warn

`tool-projection.ts:30-32`：

> 安装和更新在 strict 模式下目标失败即整体失败，warn 模式报告后继续。

**Post-write validation 失败也不回滚**——只报告。写入已经发生，回滚反而可能破坏用户内容。

## Agent 入口机制：三种

`docs/user/agent-entry-matrix.md`（生成文档）列出 24 个 class-A 宿主。这是本项目最实用的工程决策。

### 1. 专用入口文件

```text
.codex/AGENTS.md
.claude/CLAUDE.md
.cursor/rules/researchspec.mdc
.agents/AGENTS.md
.gemini/GEMINI.md
.github/copilot-instructions.md
...
```

整文件托管。**ResearchSpec 是该文件的唯一所有者**——用户不能在里面加自己的内容。

### 2. 共享标记区域

```text
<!-- researchspec:begin -->
...ResearchSpec 生成的入口...
<!-- researchspec:end -->
```

`source-managed` 的宿主（多数支持 custom agent 的）用这种方式。**只托管标记内区域，标记外的用户内容完全保留。**

**这是「工具要与用户共存」的核心答案**：托管专用文件 = 独占；托管标记区域 = 共存。

### 3. 显式发现回退

宿主不读项目文件时，用户必须手动触发。README 明确列出这类：

- Claude.ai / Claude Web
- Gemini Gems
- NotebookLM

**这些是产品级边界，不是缺陷。**

### 遗留目录迁移

`legacySkillDir` 的设计很讲究：

> 遗留目录在安装时迁出但**不删除**。

安装时把旧目录内容移出，但**保留目录本身**。这样用户手动放进去的东西不会丢，同时新内容不再被两处发现导致重复。

## MCP 配置：路径与信任都是问题

**路径**（`usage-model.md:57-60`）：`mcp.json` 放项目根（Copilot、Antigravity、Codex），`.mcp.json` 放隐藏目录（Codex、Claude Code、Cursor、Trae、openclaw）。多 MCP 工具分块追加，**绝不覆盖**。

**信任**（`usage-model.md:63-67`）：

> Claude Code 的 `.mcp.json` 受项目级信任对话框保护。用户选择 remember 后，**项目设置必须指向项目级 `.mcp.json`，不能改指 `~/.codex` 或 `~/.gemini`**。Claude Code 在不支持的平台上把配置合并进 `.claude/settings.json`。

**默认不加 `--yolo`**：stdio servers 不加；`npx` servers 加 `--yes`（避免交互式安装挂起）；`bunx` 不加（会回落到 npx）。

**凭据零落盘**（`usage-model.md:69-75`）：

> ResearchSpec 永不生成或持久化 API key、MCP token、Zotero API key 或云凭据。只交付配置结构，由用户在宿主或 runtime 中提供凭据。

## 工作区投递：一份统一计划

`src/adapters/workspace-delivery.ts` 合并五类内容成一份写入计划：

```text
graph profile 投影
agent tool 投影（Skills + Commands）
遗留清理
literature adapter（Zotero）
plugin 投影
  ↓
单次提交
```

**一次提交而非多次**——避免部分安装状态。

### 确定性原则

`tool-projection.ts:126-128` 的设计要求：

> 安装计划按目标路径与相对内容 key **确定性排序**。相同工作区状态产生相同计划，相同计划产生相同写入。

这条约束让「幂等性检查」成为可能（见 [11 篇](11-转换器与审计.md)）。

## 文献 Adapter：Zotero

`--literature-adapters zotero-library` 交付**两族**：

### 1. 文献工具包（7 个 Skill）

`src/literature-adapters/catalog.ts:7-12`：

```text
zotero-library
zotero-shared
zotero-ingest
zotero-drafts
zotero-claims
zotero-review
zotero-sync
```

同时注册为 Agent Skill **和** `zotero-*` 命令（`literature-adapters.md:6-8`）。这是 researchspec 宿主表面**之外唯一的命令命名空间**。

### 2. Zotero Bridge runtime（离线资产）

`zotero-bridge/` → 项目内 `.zotero-bridge/bin/`：

- `bridge.js`（Node 运行时，**bundle 含 Node 核心与所有依赖，零 npm 依赖**）
- `bridge-schemas/`（CLI 协议 schema）
- `manifest.json`（`release-set: hbrs-8c6de08010d459a0e87e74f2`，revision `ff1475eea7d3fb6cb07dbdd872e3c7603e7f1a19`）
- `bundle-revision.json`（bundle 字节哈希）

**「离线复制到项目内」这个选择很重要**：用户不需要全局安装，也不依赖 npm 可用性。Zotero 插件升级不影响 ResearchSpec 资产。

### 授权模型

`usage-model.md:85-89` 三条独立授权：

1. **route confirmation**：接受 workflow preset 导出到 Zotero 时的路由
2. **plugin consent**：安装 Zotero Adapter 本身
3. **bridge readiness**：本机 bridge 可执行

**三者都不等于 managed-library authorization**（写 Zotero 用户库需单独确认）。

### 取消选择

`update --literature-adapters none`：

- managed **hash 未变** → 删除
- managed **文件 drift** → 保留并报告，**不覆盖**

这是 drift 不覆盖原则在投递层的直接体现。

## Plugin 投影

`src/plugins/graph-delivery.ts` 把 domain 解析为 graph profile 与宿主投影。Plugin 确认与 run 确认**分离**（`usage-model.md:133-135`）：

> 确认只覆盖领域能力投影和所需宿主工具集合。Agent 必须确保项目工具包含 plugin 的交付目标（**`init --tools` 与 `update` 可以补投**）。Plugin 投影本身**不创建 run**。

## 交付时序（`docs/developer/cli-interface.md:19-28`）

```text
1. 渲染         Renderer adapter
2. 受管写入     Manifest-owned（工具表面的受管文件）
3. 遗留清理     Legacy migrator（迁出但保留）
4. 参考文献投影 Post-delivery projection（references/、templates/、examples/）
5. 报告         Managed paths（仅在全部成功后报告）
```

第 5 步的顺序要求在 `usage-model.md:51-53` 有明确表述：**只有交付完成后才 report managed paths。**

## 给 Scholoom 的启示

1. **三种入口机制分层**（专用文件 / 标记区域 / 显式回退）。这是「给项目装 AI 工具」的完整解法——既要能装进去，又不能霸占用户的文件。
2. **遗留目录迁出但不删**。用户手动放的东西保留，同时消除重复发现。
3. **按语义生成 wrapper 而非全量**。28 个工具只生成 16 个 wrapper，多出来的是噪音。
4. **凭据零落盘**。工具只交付配置结构，凭据永远由用户提供。这条应该写进任何 Agent 工具的安全基线。
5. **一次提交 + 后置校验不回滚**。部分安装状态比失败更难排查；写入后的校验失败只报告。
6. **卸载时 hash 未变才删**。用户改过的内容永远保留。这个模式和 [06 篇](06-工作区与文件合约.md) 的 drift 原则是同一个。
