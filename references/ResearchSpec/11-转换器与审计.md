## 转化哲学

`AGENTS.md:111-122` 的四条：

1. **方法内容不重新发明**：转换器搬运 ARSU 已有的方法内容，ResearchSpec 不改方法
2. **合约、触发、授权都是 ResearchSpec 自己的**：
   - contract = 结构化依赖、验收证据、停止条件
   - trigger = 何时这个能力被调用
   - authorization = 谁可以运行
3. **逐项接受，不批量搬运**：单个方法可以接受、适配或留在 ARSU
4. **可追溯性是硬要求**：`arsu:converted` origin + `seed_method` / `doc_anchor` / `citation`

这四条合起来定义了什么叫「派生」而不是「抄」。

## 七阶段转换管线

`src/arsu-converter/converter.ts:44-112`：

```text
1. 读取 ARSU workflow 源
2. 枚举 ARSU 实体（skills / tools / workflows / methods）
3. 计算 ARSU 输入契约指纹（sha256）
4. 识别 & 转换（对每类实体）
5. 构建 capability 分类
6. 注册命令与路由（从 routing-catalog.yaml）
7. 生成 skills 目录 + 转换报告
```

### 关键实现

`converter.ts:61-88` 是最密集的一段：

- **anchor 替换**（36 处 `replaceInContent` 调用）：`{seeds:…}`、`{bundle:…}`、`{contract:…}`、`{doc:…}` 模板标记
- **`{seeds:ARSU_ENTITY_ID}` → `bundle.seeds/ARSU_ENTITY_ID`**
- 输出确定性（`converter.ts:33,86` 的注释）：
  - capability 顺序按遍历顺序
  - `references` 按 POSIX 序排序
  - **YAML 解析结果直接以 `JSON.stringify` 写出**（不经过 `yaml` stringify）
  - graph profile 注册表用 `JSON.stringify(..., null, 2)`（profile 定义在 `src/arsu-converter/workflow/graph-profiles/*.ts`，共 7 个 authored profile）

最后这条很有意思：**用 JSON 格式写 YAML 文件**。因为 YAML 是 JSON 的超集，这样能保证字节级确定性（`yaml` 库的 stringify 可能有键序/缩进差异）。

### anchor 替换语义

`contract-anchors.json:8-15`：

> 转换器把 ARSU 内容里的 `{contract:ARSU-<TYPE>-<NNN>}` 替换为本项目的能力契约段落。`contract_text` 声明替换后的验收依赖、停止条件与授权边界；`binding_points` 声明替换的宿主文档位置；`citation` 保留上游出处。

| 字段 | 含义 |
| --- | --- |
| `required` | 该 anchor 缺失会导致转换失败 |
| `recommended` | 缺失产生 warning |
| `diagnostic` | 只用于诊断，不影响产物 |
| `binding_points` | 替换的宿主文档段落（宿主必须包含这些段） |
| `citation` | 上游出处 |

**这是「方法不重新发明」的技术实现**：ARSU 文档里的方法说明保留，但验收标准、停止条件、授权边界换成 ResearchSpec 自己的。内容继承，合约替换。

## 幂等性：convert / check / idempotence 三连

每个 vendor 和 ARSU 都有这三个命令：

| 命令 | 作用 |
| --- | --- |
| `convert` | 生成产物 |
| `check` | 校验产物符合 schema + anchors 完整 |
| `idempotence` | **同样输入重跑，产物字节不变** |

**幂等性进 CI**。这是「生成器」和「脚本」的根本区别——脚本跑一次，生成器跑一万次结果都一样。

> **⚠️ 发现的真实缺陷**：`src/arsu-converter/converter.ts:118` 有一个恒假表达式：
>
> ```ts
> if (JSON.stringify(buildPresetGraphProfileRegistry()) !== JSON.stringify(buildPresetGraphProfileRegistry())) {
>   errors.push("Preset graph profile registry projection is not deterministic");
> }
> ```
>
> 两边调用同一个无参函数，条件**永远为 false**，这条确定性检查从未生效。正确写法应是拿一个预先生成的期望值或独立路径的产物来比。
>
> 同处还有个 `contractManifestHash` / `routingCatalogHash` / `profileRegistryHash` 的传递链（`converter.ts` 内）值得注意：**这三个哈希没有进入任何转换产物**，只是被当作参数往下传。
>
> 另外注意：**仓库中不存在 `graph_profiles.yaml` 或 `contract-workspace-mapping.json` 这两个文件**。7 个 authored graph profile 定义在 `src/arsu-converter/workflow/graph-profiles/*.ts`（academic-paper / academic-paper-reviewer / academic-pipeline / minimal / paper-humanizer / research-main / review-response），由 `emitPresetGraphProfiles` 在构建时投影成 `<profile-id>.yaml` + `registry.json`（`workflow/generate.ts:28-37`）。

## 暂存区协议与 SHA-256 漂移检测

`src/vendor-converters/shared/staging.ts`（75 行）：

```text
prepareVendorStage   复制基线插件树到 stage，删掉本 vendor 旧投影与 registry.json
  ↓
  converter 在 stage 内写全部产物（不碰真实输出）
  ↓
commitVendorStage    只把 vendors/<id>/ 与三个 <id>.* 产物 + registry.json 拷回
```

**为什么需要暂存区**：转换器中途失败不会留下半成品。真实输出要么是上一个成功版本，要么是新的完整版本。

`vendorProjectionDiff`（`:26-31`）的漂移检测：

1. 对 expected/actual 两棵树调 `relativeFileMap`（`:66-73`）逐文件算 `sha256`
2. 只比较 `isVendorProjectionPath`（`:58-63`）白名单路径
3. 返回**排序后**的差异路径列表

白名单：4 类（`registry.json` / `vendors/<id>/**` / `vendor-bundles/<id>.json` / `vendor-manifests/<id>.json` / `conversion-reports/<id>.md`）。

## 为什么决策必须是签入的数据

`production-policy.json` 里的冻结内容：

```json
{
  "audit": { "sha256": "..." },
  "expected_skills": 165,
  "expected_admitted": 136,
  "expected_excluded": 29,
  "tree_hash": "...",
  "domains": { "expected_admitted_counts": { ... 54/9/73 } }
}
```

加上 `admission-decisions.json` 里 19 条 `original_framework_exclusions` + 10 条 `third_party_author_exclusions`（具名 Skill ID 列表）。

**运行时无从「重新判断」**：

| 若决策在运行时 | 若决策签入数据 |
| --- | --- |
| 每次转换重新读 SKILL.md 重新判断 | 转换器只做比对 |
| 同一上游不同时间可能得到不同结论 | 结论永久固定 |
| 无法复核「为什么排除它」 | 每条带 reason code + 证据路径 |
| 上游升级影响面无法预估 | 差集一眼可见 |

## 给 Scholoom 的启示

1. **三连命令是生成器的标准动作**。`convert` / `check` / `idempotence`，尤其第三条要进 CI。
2. **暂存区避免半成品**。转换器在副本里写，成功才提交。生成器失败时输出目录应该是「上一个成功版本」而不是「半新半旧」。
3. **上游 provenance 进产物**。`origin: arsu-converted` + `doc_anchor` + `citation` 是硬要求，不是可选元数据。
4. **用 JSON 写 YAML 换确定性**。绕开库的 stringify 行为差异，是个务实的小技巧。
5. **差异格式必须统一**。本项目 10 种决策枚举并存是反面教材——6 个 vendor 各自定义审计格式，汇总时无法机读。
6. **evidence map 是可选的第二层**。只有 1/6 vendor 做了。这说明这类追溯成本很高，不必强推，但高价值领域值得。
