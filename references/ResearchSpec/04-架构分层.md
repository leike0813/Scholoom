## 十个分层

| 分层 | 文件数 | 定位 |

## 双向依赖（改动时要同时看两侧）

图谱逐对列出这 8 组（`.ua/wiki/architecture.md:71`）：

- 能力目录层 ↔ 核心层
- 宿主适配层 ↔ 核心层
- ARSU 转换层 ↔ 核心层
- 测试层 ↔ 工具链层
- ARSU 转换层 ↔ 能力目录层
- 宿主适配层 ↔ 能力目录层
- 宿主适配层 ↔ CLI 层
- 宿主适配层 ↔ ARSU 转换层

**改这些分层时必须两侧同时检查。** 例如宿主适配层同时依赖核心层的路径安全工具和 CLI 层的命令目录，是合理耦合（投递目标要引用 CLI 命令 ID 白名单），但也是改动时的连带风险。

## 显式模块方向（`docs/developer/architecture.md:73-91`）

文档给出的方向声明比图谱更清晰：

```text
typed contracts
  -> workspace discovery / validation
  -> graph runtime + project changes + handoff
  -> CLI handlers and read models
  -> Agent delivery adapters

现有 ARSU / Companion / capability / extension registries
  -> runtime-derived Procedure catalog
  -> standalone 或 graph activation packet

authored profile sources -> projected profiles -> workspace runs
```

一句话总结：**契约在最底，运行时在其上，CLI 在其上，投递在最高。**

## 核心层内部：7 个文件承担全部事实源

`.ua/wiki/tour.md` 第 4-7 步把核心层拆成四块：

### 契约定义（Zod = 单一事实源）

| 文件 | 定义什么 |
| --- | --- |
| `src/core/contracts/graph-workspace.ts` | `GRAPH_WORKSPACE_SCHEMA_VERSION = "2"`；config、四份 stable spec v2、project change、run、node instance、handoff |
| `src/core/contracts/capability-graph.ts` | `CAPABILITY_GRAPH_SCHEMA_VERSION = "2"`；图节点类型、并行组、Gate、Decision、revision round template |
| `src/core/contracts/capability-manifest.ts` | schema `"1"`；能力包契约（class、execution type、validators、maturity、origin） |
| `src/core/contracts/control-selector.ts` | `run:` `node:` `gate:` `decision:` `change:` 选择器正则，round 后缀 `@[1-9][0-9]*` |
| `src/core/contracts/annotation.ts` | 批注契约，`semantic_impact.level` = `ordinary` / `high` |
| `src/core/contracts/project-path.ts` | 路径安全原语 |

**Zod schema 同时是运行时校验器和类型来源**：`z.infer` 派生 TypeScript 类型，parse 失败即诊断。因此契约只有一份定义，不存在「文档说的」和「代码校验的」两套标准。这是整个项目最值得学的一条。

### 写入计划（fan-in 最高的机制）

`src/core/workspace/write-plan.ts` 是全仓 fan-in 最高的文件（42 条依赖）。所有状态变更必须先攒成一份写入计划再原子落地，**没有别的地方可以直接写 `researchspec/` 下的文件**。

配套的 `project-path.ts` 与 `boundary-path.ts` 定义词法级路径安全。两层共同构成「Agent 不能越权改状态」的技术保证。

### 图谱运行时（唯一状态变更处）

`src/core/runtime/graph-run.ts` 是整个系统里**唯一**实现工作流状态变更的文件（fan-out 36，覆盖 27 个 handler 依赖）。理解「一次 start/advance 到底写了哪些文件」，答案就在这里。

### 只读索引

`src/core/runtime/graph-workspace-index.ts` 一次性扫描整个工作区，产出内存结构。`status` 这类只读命令完全建立在它之上。

**索引模式的价值**：遍历文件系统一次、结果落成内存结构，后续查询都读这份结构。命令因此不随项目文件数量增长而变慢，且天然无副作用。

## 关系类型口径

图谱的关系类型（`.ua/wiki/architecture.md:75-84`）：

| 关系 | 含义 |
| --- | --- |
| `imports` | 文件间 import |
| `calls` | 符号间调用 |
| `depends_on` | 显式依赖 |
| `configures` | 配置作用于目标 |
| `defines_schema` | 定义目标结构约束 |
| `implements` | 实现目标声明的接口 |

归属类关系（`contains` / `exports` / `documents`）**不计入层间依赖**，只表示内容归属。

## 14 步阅读路径（`.ua/wiki/tour.md`）

这个 tour 是理解项目最高效的入口，完整路径：

1. 项目定位与使用模型（README + `docs/user/usage-model.md`）
2. CLI 入口与命令目录（`bin.ts` → `main.ts` → `command-catalog.ts`）
3. 结果信封与手册渲染（`types.ts`、`presenter.ts`、`payload-catalog.ts`、`handbook.ts`）
4. 核心契约层：Zod 定义事实源
5. 路径边界与写入计划
6. 工作区发现与只读索引
7. 图谱运行时：唯一状态变更处
8. 能力注册表与 Procedure 目录
9. 宿主适配与工作区投递
10. 插件注册与领域分类
11. ARSU 转换器

每步都给出「这一步体现出的语言/框架要点」。例如第 2 步的要点是：

> Commander 的 command 对象在此被当作**数据结构**而非运行时注册点使用：目录描述完命令，main.ts 再统一遍历注册，因此同一份声明可以同时喂给 CLI 与文档生成器。

**这个 tour 本身就值得作为参考物**——它把「按依赖顺序读什么、每步学到什么」显式写下来了，而不是让人自己摸索。

## 图谱分层的已知问题

`.ua/wiki/layers/core.md` 把 `src/annotation-intake.ts` 和 `src/utils/*` 归入「核心契约与工作流运行时」，而 `src/core-skills`、`src/graph-profiles` 不在其中。但实际依赖方向是 annotation 契约被 `annotation-intake` / `review-workspace` 使用，而不是相反。**分层命名与实际依赖不完全吻合**——这是图谱自动分层的固有误差，不是代码问题。

## 给 Scholoom 的启示

1. **Zod schema 一份定义两用**（校验器 + 类型来源）。这消除了「类型定义」和「运行时校验」两份代码必然不同步的问题。
2. **写入计划作为中间对象**。把「先校验后写入」抽象成计划对象而非散落的顺序调用，让事务边界显式化，dry-run 和幂等性检查也能复用同一套逻辑。
3. **唯一状态变更处**。`graph-run.ts` 是唯一写工作流状态的文件。这意味着状态机可以整体替换而不影响其他层。
4. **索引模式**。遍历一次、查询多次，天然无副作用、不随规模变慢。
5. **命令目录当数据结构用**。同一份 typed 声明同时驱动 CLI 注册、帮助文本、读写影响标注和文档生成——这是消除文档漂移的根本手段。

## 一处需要注意的重复

`src/core/workspace/discover.ts` 与 `src/core/workspace/graph-discover.ts` **逐行相同**的向上查找逻辑（两份各 ~42 行）。`layout.ts:19,87` 与 `graph-workspace-index.ts:32-40` 也对必需目录/文件做了双份列举。

这是自动分层过程中逐步演化留下的痕迹。参考时不要以为「有两个 discovery 是因为有两种需求」——实际上只有一种。
