## 测试助手：断言结构而非文案

`tests/helpers/cli.ts:7` 硬编码编译产物路径：

```ts
const CLI = path.resolve(".test-dist/src/cli/bin.js");
```

`runCli`（`:25-28`）用 `spawnSync(process.execPath, [CLI, ...args])`，支持 cwd 与 env 覆盖。

`parseEnvelope`（`:30-32`）解析 stdout JSON 信封。`Envelope` 形状（`:9-24`）：

```ts
{
  schema_version, command, ok, data, diagnostics,
  error: { code, message, hint, validation[] }
}
```

**断言重心在结构化 `code` 而非文案。** 断言分布：

| 断言 | 次数 |
| --- | --- |
| `assert.equal` | 1551 |
| `assert.ok` | 478 |
| `assert.deepEqual` | 416 |
| `assert.match` | 231 |
| `assert.rejects` | 78 |
| `assert.throws` | 57 |

231 次 `match` 主要用于检查文件内容包含某些片段（生成物结构），不是检查用户可见文案。

**这与项目的整体立场一致**：CLI 对 Agent 的契约是 JSON 信封，测试就该断言信封字段。

## `.test-dist`：独立的测试编译目录

`tsconfig.test.json`：

```text
outDir:  .test-dist
declaration: false
include: src + tests + harness
```

区别于 `tsconfig.build.json`（`outDir: dist`、`declaration: true`、排除 tests）。

`scripts/run-tests.mjs`：

1. 递归收集 `.test-dist/tests/**/*.test.js`
2. 排序（保证执行顺序确定）
3. 交给 `node --test`
4. 设 **`PYTHONDONTWRITEBYTECODE=1`**

最后一条很有意思：**防止上游 Python 脚本写 `__pycache__` 污染工作树**。这是一个真实踩过的坑的修补——测试会调用 vendor 的 Python 脚本。

`pnpm test` = `clean` + `tsc -p tsconfig.test.json` + `run-tests.mjs`。

## ESLint：strictTypeChecked 全量

`eslint.config.js`：

```ts
// :9-16  ignore
["dist", "vendor", "references", ".*/**"]  +  2 个 legacy 测试文件

js.configs.recommended + typescript-eslint strictTypeChecked

// 仅关闭两条
"no-confusing-void-expression"
"no-unnecessary-condition"
```

**`strictTypeChecked` 全量启用**，且 `projectService: true` 让规则能看类型信息。这是相当严格的配置——`no-unsafe-*`、`no-floating-promises`、`require-await` 全部生效。

只关掉两条是经过判断的：

- `no-confusing-void-expression`：与 void 返回的 callback 模式冲突
- `no-unnecessary-condition`：在 Zod refine 等场景会产生误报

## CI：一个 job，6 个组合

`.github/workflows/ci.yml`：

```yaml
jobs:
  verify:                      # :21  只有一个 job
    strategy:
      matrix:
        os:   [ubuntu-latest, macos-latest, windows-latest]   # :27-36
        node: [22, 24]
      fail-fast: false
    timeout-minutes: 30
```

**3 OS × 2 Node = 6 个组合，但只有一个 job。** 参考文档写「6 个 job」即为错误。

### 步骤顺序

```text
1. checkout
2. pnpm/action-setup 10.13.1
3. setup-node（pnpm cache）
4. pnpm install --frozen-lockfile
5. pnpm test
6. pnpm lint && pnpm check
7. pnpm arsu:check
8. pnpm arsu:idempotence
9. git submodule update --init vendor/zotero-library-agent-bundle   ← 显式
10. zotero-adapter:check + idempotence
11. pnpm release:verify
12. pnpm dlx @fission-ai/openspec@1.5.0 validate --specs --strict
```

**第 9 步是全流程最值得学的一行。** 6 个 vendor submodule 里，只显式初始化 Zotero 这一个。原因是 Zotero 适配器是唯一「安装后需要验证」的：它验证「先安装 Zotero Agent 插件，再装 ResearchSpec 工具」这条用户流程。**其他 vendor 转换器不需要验证「还没装插件就装工具」是否可用。**

第 12 步用 `@fission-ai/openspec@1.5.0` 校验 59 个 spec——**项目治理工具本身进 CI**。

## 文档漂移检查

`docs:check` = `pnpm build && node scripts/generate-docs.mjs --check`：

对每个输出目标**重新渲染**并与磁盘文件做**逐字节字符串比较**，不一致则：

```text
<label> does not match the typed CLI catalog renderer.
exitCode = 1
```

生成前还有**硬门禁**（`generate-docs.mjs:23-25`）：

```ts
CLI_TOP_LEVEL_COMMANDS.length !== 16 || includes("submit")  →  throw
```

**即「16 个命令且不含 submit」这条不变式被写死在文档生成器里。** 改命令数量会立刻让 CI 失败。

## 给 Scholoom 的启示

1. **测试夹具伪造而非真实**。不依赖 submodule 初始化，让大部分测试在 CI 上无条件可跑。
2. **`PYTHONDONTWRITEBYTECODE=1`** 这类环境变量设置都是踩坑记录。每个都是「曾经污染过工作树」的证据。
3. **只验证真正需要验证的 vendor**。CI 里只初始化 Zotero submodule，因为只有它有「先装插件」的用户流程。这个判断力比全量验证更值钱。
4. **命令数量写死在文档生成器里**。用硬门禁把不变式变成 CI 失败，而不是靠人记得。
5. **语义评审记录不被自动生成覆盖**。`records` 命令保留既有 `05-semantic-review.md`——自动生成物不该覆盖人工判断。
6. **沙箱 dogfood 作为人工发布 Gate**。bubblewrap 里跑 36×3 种组合，这比任何静态检查都更接近真实用户环境。
7. **文档三类读者分周期维护**。可再生报告和现行知识分开放，避免 `docs/` 被历史材料淹没。

## 一处需要注意的重复

`src/core/workspace/discover.ts` 与 `src/core/workspace/graph-discover.ts` 逐行相同；`layout.ts:19,87` 与 `graph-workspace-index.ts:32-40` 双份列举必需目录/文件。

**这是自动分层过程中逐步演化留下的痕迹。** 读代码时不要以为「有两个 discovery 是因为两种需求」——实际只有一种需求、两份实现。
