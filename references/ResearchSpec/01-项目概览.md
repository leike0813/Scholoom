# 01 项目概览

## 一句话

ResearchSpec 是一个 **Agent 中立的、spec 驱动的学术研究工作流框架层**：用户用自然语言描述研究目标，Agent 通过「能力（Procedure）」发现与执行来交付成果，**CLI 是工作流状态的唯一写入入口**。正式的 graph run 提供 Gates、Decisions、并行执行、修订轮次与可审计状态。

它不是 LLM 集成层，不是 Web 应用，不是文献管理器，也不是某个 Agent 平台的插件。

## 它要解决的三个问题

README 与 `AGENTS.md:35-51` 反复强调的动机：

| 问题 | 表现 | ResearchSpec 的应对 |
| --- | --- | --- |
| **平台锁定** | 研究 Skills（文献综述、论文写作、同行评议）被实现成 Claude Code / Codex 的专有指令，无法跨平台复用 | 能力以 agent-neutral 文件包分发；宿主只常驻一个 Navigate 入口，具体能力按需加载 |
| **状态碎片化** | 研究意图、文献来源、论证主张、Gate 决策散落在聊天记录里 | 每个概念有明确的文件 owner（Markdown / YAML / JSON），状态由扫描推导 |
| **人工决策不可追溯** | 关键范围、贡献、方法论选择通过自然语言隐式完成 | 决策是 first-class 记录，写进所属 node instance 或 project change 文件 |

## 设计立场：应该成为什么 / 不应该成为什么

`AGENTS.md:35-51` 写得很直接：

**应该成为**
- 学术论文写作工作流的 OpenSpec 式框架
- ARSU 派生 skills 的 agent-neutral 宿主
- 覆盖研究意图、来源、claims、稿件、workflow state、gates、decisions、artifacts、patches 的 spec-driven 合约系统
- ARSU 产物被吸纳后的 converter / maintenance 层

**不应该成为**
- LLM API 集成层
- 平台专属的 Claude Code / Codex 适配器
- Web app、database-first 研究平台、引用管理器替代品
- 手工维护的生成产物副本（应由 converter 规则拥有输出）

补充约束（`AGENTS.md:78-79`）：

> Files remain the interface. Tool adapters may render and write files, but should not call agent APIs or depend on a specific model.

## 灵感来源：OpenSpec 的两级套娃

ResearchSpec 明确承认设计受 [OpenSpec](https://github.com/Fission-AI/OpenSpec) 启发，并且**自己内部也用 OpenSpec 管理产品变更**（`openspec/` 目录，59 个 spec）。

这里有一个值得注意的「两级 spec-driven 治理」（`docs/developer/runtime/core_runtime_model.md:24-29`）：

| 层级 | 位置 | 管什么 | 有无共享 runtime |
| --- | --- | --- | --- |
| 仓库治理 | `openspec/changes/` | ResearchSpec 这个**产品**的变更 | 无 |
| 研究工作区 | `researchspec/changes/` | 用户**研究语义**的变更 | 无 |

两层都区分 current / proposed，但**不共享 runtime**。这个隔离是刻意的——产品工程节奏与研究决策节奏完全不同。

## 与 Scholoom 的关系

ResearchSpec 与 Scholoom 目标高度重合：**Agent 驱动 + 学术研究工作流 + 可审计产物**。但两者切入点不同：

| 维度 | ResearchSpec | Scholoom（推测定位） |
| --- | --- | --- |
| 核心问题 | 研究工作流的**状态治理**：谁写状态、决策是否可追溯、状态如何跨会话恢复 | — |
| 交付物 | 文件合约 + CLI 控制面 + 能力包 | — |
| 明确不做 | 引用管理、文献数据托管、Web 应用 | — |

**最值得借鉴的三点**（详见 [15-对Scholoom的启示](15-对Scholoom的启示.md)）：

1. **CLI 作为唯一写入入口**——Agent 永远不直接改状态文件，只能请求 CLI 变更。这让状态机可以用确定性代码实现并完整测试。
2. **每个概念只有一个 owner 文件**，其余全是扫描推导的 read model。没有全局索引，没有隐藏事务日志。
3. **准入决策数据化**——vendor Skill 的取舍是签入仓库的 JSON 而非运行时判断，审计结论可复核、上游升级影响面可预估。

## 调研中注意到的两点

**一、这个项目对自己的文档质量有清醒认知。** `docs/README.md:9-13` 明确写了文档冲突时的裁决顺序：

> 用户使用模型 负责产品行为，OpenSpec main specs 负责可验收要求，代码与 typed contracts 负责当前实现事实。

这是一个三层权威分级。参考时遇到文档矛盾，按这个顺序判。

**二、CHANGELOG 的数字是历史快照，不能当现状。** 0.1.0 条目说「fifteen-command public CLI」「four ARSU and four Companion Skills across 31 registered tools」——而当前是 16 命令、35 宿主。这不是漂移，是发布记录，但容易误读。详见 [14-开发约定与已知坑](14-开发约定与已知坑.md)。
