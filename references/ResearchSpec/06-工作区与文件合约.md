# 06 工作区与文件合约

## 概念与文件 owner 一一对应

`docs/developer/runtime/core_runtime_model.md:5-13` 是全文最重要的一段：

> 四份 stable specs 拥有**已确认的研究承诺**；graph profiles 拥有**能力执行图**；每个 run 拥有 **frozen graph 与 lifecycle**；每个 node instance 拥有**状态、Gate attempts 和 Decisions**；handoff 拥有**边界 input/output role/path**；project change 拥有**尚未应用的高影响更新**。

这句话定义了 ResearchSpec 全部的状态模型：**每个概念恰好一个 owner，没有第二个地方保存同一事实。**

| 概念 | Owner 文件 | Schema |
| --- | --- | --- |
| 研究问题、范围、方法、贡献 | `specs/project.md` | 2 |
| 已接受来源 | `specs/sources.yaml` | 2 |
| 稳定 claims | `specs/claims.yaml` | 2 |
| 稿件体裁、结构、格式 | `specs/manuscript.yaml` | 2 |
| Workspace 配置 | `config.yaml` | 2 |
| Run 身份与生命周期 | `runs/<run>/run.yaml` | 2 |
| 一次运行的**冻结调度图** | `runs/<run>/graph.yaml` | 2 |
| Node instance（状态、Gate attempts、Decisions） | `runs/<run>/nodes/<node>.yaml` | 2 |
| Handoff（边界 role/path） | `runs/<run>/handoff.md` | Markdown |
| Project change（未应用的提案） | `changes/<change>/proposal.md` + `decision.yaml` + `spec-delta/` | 2 |
| 能力执行图 | graph profile YAML | 2 |
| 能力包 | `skills/capabilities/*/manifest.yaml` | 1 |

`GRAPH_WORKSPACE_SCHEMA_VERSION = "2"`（`src/core/contracts/graph-workspace.ts:1`）。

## 目录布局

```text
<project>/
├── researchspec/                    # 唯一受管状态
│   ├── config.yaml
│   ├── specs/{project.md,sources.yaml,claims.yaml,manuscript.yaml}
│   ├── changes/<change-id>/{proposal.md,decision.yaml,spec-delta/}
│   ├── profiles/<profile-id>.yaml
│   └── runs/<run-id>/
│       ├── run.yaml
│       ├── nodes/<node-id>.yaml
│       └── handoff.md
├── work/researchspec-notes/         # 普通任务笔记（非 owner）
├── references/                      # 生成的上下文与手册
├── literature-adapters/zotero/      # 可选 Zotero Adapter
├── review-workspace/                # 静态工作台 HTML
├── openspec/                        # 可选：用户自有的 OpenSpec 治理
├── <论文/报告/review/图表/数据>       # 边界产物，在 researchspec/ 之外
└── .zotero-bridge/                  # 可选文献 adapter 运行时
```

## 三条硬边界

### 1. 边界产物在 `researchspec/` 之外

论文、报告、review、图表、数据都在外面。ResearchSpec **不复制、不 hash-bind、不管理**它们。

`handoff.md` 只是**记录**边界交换（role、type、path、purpose、source run、intended consumer、format、`renderer: quarto`）：

> 节点 binding 按 role 连接生产者与消费者。**路径不是工作流关系的事实源。**

这是一个重要的设计选择：系统不假装能保证外部文件没被改过，只负责声明「谁产出、谁消费」。

### 2. 私有工作材料在 owning 项目之外

`core_runtime_model.md:9-10`：

> Private working material 位于 owning 项目**外的**普通 `work/`，需要跨 run 使用时通过 handoff 明确声明。

即：草稿、临时计算、中间产物不放进受管区，跨 run 复用走 handoff。

### 3. 任务笔记不进入 runtime

`work/researchspec-notes/` 由 Navigate 主 Agent 维护，但**不属于任何 owner**：

- 不进安装 manifest
- `status` / `check` 不扫描、不校验
- CLI 不提供 task selector
- **不能用来声称 run、node 或 Gate 已完成**

`docs/user/usage-model.md` 的明确表述：

> 这些文件是 Agents 面向用户工作的**非正式进展记录**，不是 workflow state。

## 派生视图，不持久化

`core_runtime_model.md:17-18`：

> Status、list、show、history、parent/child summaries 和 frontier 均通过**扫描当前 files** 得到。Child control 的 parent reference 是唯一关系事实；不会持久化 children list 或全局 index。

**没有全局索引，没有隐藏事务日志，没有反规范化表。**

所有汇总视图都是读时计算。这意味着：

- 不存在索引与文件不一致的可能
- 手工编辑文件是合法的（只要通过 schema 校验）
- 代价是 `status` 慢——所以有了 `graph-workspace-index.ts` 的一次扫描内存索引

## 路径安全合同

两层，词法级，无 IO：

### `src/core/contracts/project-path.ts`（12 个拒绝原因）

| 原因 | 拒绝什么 |
| --- | --- |
| `empty` | 空路径 |
| `not_project_relative` | 绝对路径 |
| `escapes_project` | 逃出项目根 |
| `escapes_researchspec` | 逃出 `researchspec/` |
| `has_parent_segment` | 含 `..` |
| `is_reserved_root` | `.` / `..` |
| `is_reserved_segment` | 保留段 |
| `has_control_character` | 控制字符 |
| `has_reject_character` | `< > : " \| ? *` |
| `has_trailing_space_or_dot` | 尾随空格或点 |
| `has_reserved_name` | Windows 保留名（`CON` `PRN` `AUX` `NUL` `COM1-9` `LPT1-9`） |
| `is_trailing_dot_or_space` | 组件以点或空格结尾 |

**Windows 保留名和尾随点/空格规则是跨平台写入的硬需求**——在 Linux 上开发、写到 Windows 上会炸。提前在词法层挡住。

### `src/core/runtime/boundary-path.ts`（边界产物，同类 12 原因）

`researchspec/` 之外的产物路径（论文、图、数据）用独立 schema 校验，额外拒绝 `.zotero-bridge` 内部路径：

> `researchspec/` 内的路径不能通过 boundary 引用，`zotero`/`mcp`/`none` 不是合法 type。

**`has_mismatched_type_prefix`** 这条尤其值得学：它强制 **kind 与路径前缀一致**——声明 `source: codex` 的文件必须在 `.codex/` 下，声明 `handoff: task` 的必须不在受管区。kind 不匹配就拒绝，而不是相信声明。

## 写入计划（fan-in = 42）

`src/core/workspace/write-plan.ts` 是全仓被依赖最多的文件。所有状态变更先攒成计划再落地。

### planFile 判定（7 种 action）

`src/core/workspace/write-plan.ts:7` 的类型定义：

```ts
export type PlannedAction = "create" | "refresh" | "remove-owned" | "move"
  | "skip-unchanged" | "skip-drift" | "conflict";
```

| action | 触发条件 | reason 示例 |
| --- | --- | --- |
| `create` | 目标缺失（`:73`） | `target is missing` |
| `skip-unchanged` | 存在且内容与模式均已最新（`:85`） | `content and mode are current` |
| `refresh` | manifest 所有且哈希匹配，可安全覆写（`:101`） | `safe manifest-owned refresh` |
| `skip-drift` | 哈希与记录不符且未 `--force`（`:100`） | `generated file has user modifications` |
| `remove-owned` | 撤销受管文件 | — |
| `move` | 遗留迁移 | — |
| `conflict` | 见下 | — |

**`conflict` 不是一种情况而是五种**（严格 fail-closed）：

| 行号 | reason | 含义 |
| --- | --- | --- |
| `:61` | `generated write has no trusted root` | 写入没有可信根 |
| `:68` | `target is outside trusted root` | 目标越界 |
| `:76` | `existing target is …, not a regular file` | 目标是目录/符号链接 |
| `:81` | `existing path is not manifest-owned` | 目标不是本工具创建的 |
| `:94` | `existing user-owned file is protected` | 用户自有文件受保护 |

**`skip-unchanged` 的「零 IO 零写入」是幂等性的基础**：内容没变就完全不碰文件，因此 mtime 不变。

**注意 `conflict` 的默认行为是「不动」**：遇到不属于本工具的文件，工具宁可失败也不覆盖。这与 `skip-drift` 的区别在于——`skip-drift` 是「保留并报告成功路径」，`conflict` 是「硬失败，交给上层决定」。

### 前置条件与区域管理

`planFile` 的输入含 `ownership`（`manifest-owned` / `user`）、`recordedHash`（清单里记录的哈希）和 `force`。判定逻辑就是「目标是谁的 + 哈希对不对」：

| 情况 | 结果 |
| --- | --- |
| 目标是 `user` 所有 | `conflict`（`:94`） |
| 目标非 manifest 所有 | `conflict`（`:81,97`） |
| 哈希与记录不符且未 `--force` | `skip-drift`（`:100`） |
| 哈希匹配 | `refresh`（`:101`） |

**区域（region）模式只适用于 `project-entry` 一种记录。** `src/adapters/installations.ts:27-30`：

```ts
kind: z.literal("project-entry"),
mode: z.enum(["file", "region"]),
region_id: z.literal("researchspec-entry").optional()
```

`superRefine` 强制 `mode === "region"` ⟺ `region_id === "researchspec-entry"`，否则报错。`src/adapters/managed-target.ts:100` 再校验一次。

两种模式：

| mode | 含义 | 适用 |
| --- | --- | --- |
| `file` | 整文件托管 | 宿主专用入口文件（独占） |
| `region` | 只托管 `researchspec-entry` 标记区域 | 宿主共享入口文件（共存） |

**`region` 是本项目最巧的一个设计**：标记外的用户内容完全不碰，标记内的内容由区域哈希管理。**整文件与区域并存**，是「工具要与用户共存」这个问题的正解。

> **注意**：`codex.toml` / `mcp.json` **不是**通过 region 模式管理的。它们是 ResearchSpec 独占写入的配置文件，**不做合并、不做标记区域**。region 只解决「用户和工具都要写同一个文件」的问题。

标记的确切格式（`src/adapters/project-entry.ts:11-12`）带 region ID，不是裸标记：

```text
<!-- researchspec:begin researchspec-entry -->
…ResearchSpec 生成的块…
<!-- researchspec:end researchspec-entry -->
```

`:68` 的 `owned` 缓冲在 `mode === "region"` 时用 `BEGIN + 换行 + body + END + 换行` 拼出受管内容，其余内容视为用户所有。`:204-205` 用正则定位区域，`:212` 从 `BEGIN.length` 之后开始计算。

### 前置条件不满足 → skip-drift 而不是覆盖

`graph-workspace.ts:90`：

> 观测到的内容与 precondition 不一致时保留原内容并报告 drift。

**这是本项目最重要的安全姿态之一**：工具永远不覆盖它没创建的内容，宁可留下 drift 报告。

### 事务保证

`src/core/workspace/write-plan.ts:145-225`（实际实现）：

1. `:145` 为每个待写操作建 `WriteTransaction`：临时路径 `<path>.researchspec-<uuid>.tmp`、备份路径 `<path>.researchspec-<uuid>.bak`
2. 先写临时文件，`:194` 把原文件 rename 到 backup，`:198` 把临时文件 rename 到目标
3. `:186` 逐个提交
4. `:214-215` 失败时从 backup 恢复，`:207` 把未提交的移回，`:225` 清理 backup

**明确的非保证**（同处注释）：

即**提交前崩溃安全，提交后不安全**。这是文件系统 rename 语义的现实边界——`:225` 的 backup 清理在提交后才发生，进程若在提交后被杀，`.bak` 残留但不会自动恢复。

另外注意 `planFile` 的判定是**严格 fail-closed**：`conflict` 有四种触发（`:61` 无可信根、`:68` 目标越界、`:76` 目标是目录/符号链接、`:81,94,97` 非 manifest 所有），不是一种。

## Schema 迁移 fail closed

`core_runtime_model.md` + `usage-model.md:307-309`：

旧或未知 workspace 被报告为 `unsupported`，**保持字节不变**。

`check all --strict` 可以按版本过滤：

```bash
researchspec check all --strict --min-schema-version 2
```

**没有自动迁移**。理由充分：自动猜测旧状态的意图，本身就是在替用户做语义决定。

## 确定性打包

`pack` 命令（`usage-model.md:229-239`）：

```bash
researchspec pack run:<run-id> --format md --out <path> --max-chars <n>
```

三档：run、task（用 `--task-id`）、或显式输入路径。

三个约束：

- **只选正常解析的 spec/run/change 文件**
- 按 `run → change → claims → sources → manuscript` 固定顺序拼接
- 包含 project id、schema version、run id 等身份头

**明确不做**：不隐式扩展 handoff、raw input 或 task notes，**不复制外部文件字节**。超预算的段落标记为显式 `truncated` 状态。

`--task-id` **不校验 task 笔记存在**。传了就扫描那个目录，不管有没有匹配文件。

## handoff 命令

```bash
researchspec handoff add    --role <role> --type <type> --path <path> --purpose <s> [--consumer <s>] [--format <f>]
researchspec handoff list
researchspec handoff update --role <role> ...
```

只写 `researchspec/` **之外**的边界文件（普通 `handoffs/*.md`）。`--task-id` 模式额外写 tasks 目录的 task handoff。

**手工 handoff 不获得 run/node 关系事实。** 同一 run 内可以一次声明多个 handoff；跨 run 引用由 producer 自己写入目标 run 的 `handoff.md`。

## 给 Scholoom 的启示

1. **一个概念一个 owner，其余全是派生**。没有全局索引意味着「索引与文件不一致」这个经典 bug 类别根本不存在。
2. **区域管理与整文件双轨**。工具要写用户也拥有的文件时，管理标记区域而不是整个文件。这条几乎可以原样搬到任何「给项目装 AI 工具」的场景。
3. **drift 不覆盖**。工具发现文件被改过时保留并报告，绝不静默覆写。覆盖用户内容是这个领域最常见也最不可原谅的错误。
4. **路径 kind 与前缀强制一致**。声明的语义类型必须和实际路径形态吻合，不吻合就 fail closed。
5. **跨平台路径规则前置**。Windows 保留名、尾随点空格这类规则要在词法层挡，不要等在目标文件系统上炸。
6. **承认事务的边界**。「提交前崩溃安全，提交后不安全」——把非保证写清楚比假装原子性更有用。
