# 12 评审批注与静态工作台

## 两套系统，不要混淆

| 系统 | 用途 | 位置 | 状态 |
| --- | --- | --- | --- |
| **Interactive Review Workspace** | 审阅 `v1` 或 `v2` 稿件 | `review-workspace/` | 当前 |
| **revision-master** | 规划一次受控修订（v3+） | `review-workspace/revision-master.html` | 当前 |

README 里的表述很明确：

> 交互式评审只处理现有 `v1`（Markdown）或 `v2`（QMD/Quarto）稿件。**revision-master 是另外一条路径**，不是 v1/v2 工作台的模式开关。

## revision-master 的设计意图

`AGENTS.md:126-134` 和 `docs/developer/manuscript-annotations.md`：

> revision-master 把「已发表的 v1/v2」当作**可读基线**，生成独立的**受控 v3+ 草稿**。

三条不变量（`manuscript-annotations.md:7-13`）：

1. **不修改 `v1`/`v2` 稿件**
2. **不修改 stable specs**
3. **不通过 ResearchSpec mutation command 创建 v3+ 状态**

即：**revision-master 的产物是「受控草稿」，不是「工作流状态」**。它生成的 v3 目录既不进入 graph runtime，也不被 `status` 扫描。是否采纳由后续流程决定，不在 revision-master 内部决定。

这解释了 `package.json` 里的 `prototype:revision-master`——它是独立原型，不参与主 CLI。

## 静态原则

`docs/user/review-workspace.md:7`：

> 导出是**静态**的：本地 HTML 打开即可，不启动服务、不访问网络，也不做身份认证。

`docs/user/review-workspace.md:5-7`：

> 审阅交付优先是一个**页面**，不是一个应用。页面不连接任何服务。

`usage-model.md:243-249` 的安全姿态：

> 所有工作均在本地静态文件中完成。工作台从不运行任意脚本，从不回连 ResearchSpec 或 Zotero 服务。

**这是一个 HTML 文件，不是 Web 应用。** 没有 server、没有 API、没有网络请求。

## 四个工作区

| 文件 | 用途 |
| --- | --- |
| `index.html` | 入口（`v1` 稿件） |
| `v1.html` | Markdown 稿件审阅工作台 |
| `v2.html` | QMD/Quarto 稿件审阅工作台 |
| `revision-master.html` | v3+ 受控修订规划 |

生成方式（`package.json` scripts）：

```bash
pnpm dev:review-workspace       # 准备 v1
pnpm prototype:revision-master  # 准备 revision-master
```

`AGENTS.md:32` 把 `review-workspace/index.html`、`v1.html`、`revision-master.html` 列为发布前必须与 `dist/` 一起重新生成的产物。

## 准备与渲染分离

这是本模块最重要的架构决策。

### `prepareReviewWorkspace`

**只生成标注与草稿载荷**，由宿主或用户完成真实稿件编辑，然后执行 `renderReviewWorkspace` 把编辑后的稿件合入。

分开的原因很实际：

1. 工作台不写回 `manuscript.yaml` 或 stable specs
2. `form` 模式让编辑结果**先落到本地草稿载荷**，用户确认后才写回文件
3. **Quarto/Pandoc 渲染在导入浏览器前完成**，失败时保留 `raw-source` 惰性块而不是崩掉页面

`docs/user/review-workspace.md:19-23` 记录的三步流程：

```text
1. prepare     生成标注 + 草稿载荷
2. 用户/宿主编辑稿件
3. render      合入编辑结果
```

**「Quarto 渲染在导入浏览器前完成」是一个重要的安全边界**。理由见 [02 篇](02-技术平台.md#外部运行时边界)：

> Quarto 项目的 `pre-render`、脚本、过滤器、可执行 cell 会运行用户代码。

所以工作台页面里**不能**有 Quarto 渲染。渲染必须在导入前完成，页面只展示结果。渲染失败则保留原始源码块，让用户看到未渲染内容而不是空白。

## 三种导出模式

`docs/user/review-workspace.md:25-31`：

| 模式 | 行为 |
| --- | --- |
| `form` | 默认。编辑结果落到本地草稿载荷，**用户确认后**才写回文件 |
| `link` | 链接到 `manuscript.yaml` 的**原始路径** |
| `copy` | 在工作区**内**复制稿件 |

`link` 模式的「原始路径」特指 `manuscript.yaml.source_path`，不是工作区路径。

**写回需要显式确认**这条设计贯穿全文：工作台不静默修改项目文件。

## 批注契约

`src/core/contracts/annotation.ts`，`semantic_impact.level` 两个取值：

| level | 含义 |
| --- | --- |
| `ordinary` | 普通批注，不影响语义结构 |
| `high` | 影响语义结构，需要人工判断 |

`docs/developer/manuscript-annotations.md` 的分级：

| 级别 | 建议动作 |
| --- | --- |
| `blocker` | 必须先处理 |
| `suggestion` | 建议采纳 |
| `question` | 需要回答 |
| `note` | 仅记录 |

**批注分「影响级别」和「建议动作」两个正交维度**——`semantic_impact.level` 说的是「这条会不会改变研究结论」，`severity` 说的是「这条建议怎么处理」。混成一个字段就无法表达「一条 note 但影响 semantic」。

## 外部依赖

| 依赖 | 何时需要 | 缺失时 |
| --- | --- | --- |
| Zotero | 引用/文献操作 | 提供 `reference-viewer.html`，只读呈现缓存的文献数据 |
| Quarto | v2（QMD）稿件渲染 | 见上文 `raw-source` 兜底 |
| Pandoc | 格式转换 | 同上 |

**Zotero 不可用时的降级路径值得学**：不给「功能不可用」的错误页，而是提供一个只读的文献查看器。用户在 Zotero 挂掉时仍然能读文献信息。

## 三个导出子路径

`package.json` 的 `exports` 只有两个，都服务于这个模块：

```json
"./annotation-intake":  "批注摄取（工具侧）"
"./review-workspace":   "工作台准备与渲染（宿主侧）"
```

**这两个是 ResearchSpec 唯一对外暴露的实现细节。** 其他一切都是 CLI 命令或生成产物。

`annotation-intake` 被 `src/annotation-intake.ts` + 2 个脚本使用——它是「外部工具把批注喂进来」的入口。

## 与 graph runtime 的关系

工作台**不在** frontier 计算里：

- 它不创建 run
- 它不写 node state
- 它不被 `status` 扫描
- 它不产生 Gate 或 Decision

**它是稿件层的工具，不是工作流层的东西。** revision-master 尤其如此——它明确不通过 mutation command 创建 v3+ 状态。

这个隔离避免了「在审阅过程中顺便改了工作流状态」这类难以审计的副作用。

## 给 Scholoom 的启示

1. **页面不是应用**。能做成静态 HTML 就不做服务。零网络、零鉴权、零后端，部署和审计成本都最低。
2. **准备与渲染分离**。让编辑结果先落到「载荷」再确认写回，中间多一步但换来「不静默改文件」。
3. **外部工具渲染前置**。任何会执行用户代码的渲染必须在导入前完成，页面里绝不放。失败时降级到原始源码而不是空白页。
4. **两个正交维度分字段**。「影响级别」和「建议动作」混成一个字段就表达不了「重要但仅记录」这类情况。
5. **依赖缺失要降级不要报错**。Zotero 挂了给只读查看器，比整页不可用有用得多。
6. **工具层与工作流层隔离**。审阅工具不写工作流状态，避免「顺手改状态」这类不可审计副作用。
