# 07 图谱运行时与工作流引擎

## 入口

`src/core/runtime/graph-run.ts` 是**整个系统里唯一实现工作流状态变更的文件**（fan-out 36，27 个 handler 依赖它）。

理解「一次 `start`/`advance` 到底写了哪些文件」，答案只在这一个文件里。

## 核心工作流原语

### Frontier 计算：派生，不持久化

`evaluateGraphFrontier` 的 15 步判定（`graph-run.ts:319-450`）：

```text
1. 输入契约诊断非空              → 全部阻塞（input_contract_invalid）
2. run.status !== "active"      → run_not_active
3. 已完成 child run 投影为 complete 实例
4. 从 entry 沿 prerequisites / Decision unlocks 求可达闭包
5. round 候选确定
6. 跳过 complete / cancelled / skipped
7. Quarto 交付要求且 probe ≠ available  → quarto_unavailable
8. 必需 Gate 最新 verdict = fail 且无有效 override  → gate_failed
9. 依赖满足（parallel group all/any、普通依赖 complete）
10. 分支：被 Decision unlocks 覆盖的节点必须有对应 option 被记录
11. 必需 Gate 全部 accepted、必需 Decision 全部已记录
12. gate/decision 型节点 → pending_gates / pending_decisions（不进 eligible）
13. 输入解析失败 → blocker
14. subgraph 节点：0 child → pending_subgraph_starts；>1 → child_run_ambiguous
15. 其余 → eligible_nodes
```

**第 12 步是设计要点**：Gate 和 Decision 型节点永远不会出现在 eligible 列表里。它们被推到 `pending_gates` / `pending_decisions`，**必须等人处理**。这样「等待人工确认」在数据结构层面就无法被绕过——Agent 拿到 `eligible_nodes` 时，看到的天然全是可执行节点。

### 输入绑定：结构是唯一来源

`graph-workspace.ts:66-72`（注释）：

> Node inputs 始终投影成 **run/node 角色绑定**，而非具体文件路径。

> 项目文件路径是运行时 handoff 产生的**投影**。节点输入绑定拥有语义结构；它只消费 handoff 的角色与格式，不把外部文件路径当作图内关系事实。

对比 `handoff.md:41-43`：

> 节点 binding 按 role 连接生产者与消费者。路径不是工作流关系的事实源。

**这是两层分离**：图内结构用角色引用（如 `claims`），具体路径由 handoff 在运行时解析。好处是换一份稿子不用改图。

### Revision 轮次

`docs/developer/runtime/runtime_protocols.md` 的四步循环：

1. 在 `revisions/<n>/` 记录修改了什么、为什么
2. review 在 `reviews/<n>/` 记录发现
3. 每个 round 一个 Decision：`accept` / `continue`
4. `continue` 递增轮次；`accept` 解锁 format

**轮次计数属于 graph runtime，Capability Skills 不能另建计数器**（`usage-model.md:202-204`）。这条约束防止能力包自己发明一套「我第几版了」的记账，破坏 runtime 的唯一事实源。

### Child run

`graph-run.ts` 提供 `startProfileRun` / `startChildRun` / `completeChildRunForParentInstance`。

- profile 声明 `subgraph.nodes` → 启动 child run
- child run **冻结自己的图**（可与父不同）
- 共享项目边界
- 能力必须声明 `required_capabilities`，父先校验再启动 child
- **超过一个 child 的 subgraph 节点被阻塞**（`child_run_ambiguous`）——这实际上强制 subgraph 节点与唯一 child run 配对

## 四份 stable spec 的状态与 v2 升级

### 各自的状态字段

| spec | 状态字段 | 阶段 |
| --- | --- | --- |
| `project.md` | 隐式（v2 移除 `status`） | 已确认承诺，无阶段 |
| `sources.yaml` | `assessment` | 1 pending → 2 accepted |
| `claims.yaml` | `status` | 1 proposed → 2 supported |
| `manuscript.yaml` | `status` | 1 planned → 2 writing-ready |

**注意 project.md 的隐式状态**：v2 把显式 `status` 去掉了，理由是「项目定义要么存在要么不存在」。

### sources v2：pending / accepted

```yaml
sources:
  - id: smith-2024
    assessment:
      status: pending | accepted
      verification:
        method: none | doi | url | pdf-text
        verified: true/false
        verification_note: …
```

### claims v2：proposed / supported

```yaml
claims:
  - id: c1
    status: proposed | supported
    statement: …
    strength: strong | moderate | speculative
    scope: …
    evidence:
      - source_id: smith-2024
        locator: …
        supports: true/false/partial
    uncertainty: …
```

### manuscript v2：planned / writing-ready

```yaml
manuscript:
  status: planned | writing-ready
  genre: research-article
  language: en
  audience: …
  venue: …
  structure: […]
  delivery:
    format: markdown | qmd
    final_output_format: docx | pdf | html | md
```

**`status` 的语义边界**：

> `writing-ready` 表示范围、体裁、语言、结构与目标格式已经确定，**不是稿件完成**。稿件完成状态由 workflow state 与 Gate/Decision 记录拥有。

## 关键枚举

### Gate verdict 与 override

`graph-workspace.ts:78-85`：

| verdict | 语义 |
| --- | --- |
| `pass` | 通过 |
| `pass_with_conditions` | 附条件通过（conditions 必须记录） |
| `fail` | 不通过 |

> **任何 Gate verdict 都不会自动完成节点。** 每个 verdict 都需要后续显式 `advance`。

Override：`decision: gate_override` / `decision: gate_override_request`；`override_type: one_time | persistent`；`reason` 必填；`decided_by_decision` 指向被覆盖的 Decision。

**Gate 自身也不完成节点**（`handoff.md:15-19`）。这是刻意设计：Gate 是检查点，不是动作终点。

### Run 状态

`draft | active | completed | cancelled`（`handoff.md:25-31`）。

### Change 状态与自洽校验

`draft | proposed | accepted | rejected | deferred | superseded | applied`

校验规则（`graph-workspace.ts:97-99`）：

- 非 `draft`/`proposed` 必须带 `decision`
- `decision.outcome` 必须等于 `status`
- `applied` 要求 `decision.outcome === "accepted"`

**`accepted` ≠ `applied`**：接受方案只是决定「要这么改」，实际修改 stable specs 并通过检查后才成为 `applied`。

### Node instance 状态

`pending | running | blocked | complete | cancelled | skipped` + `blockers` 数组。

### 失败/停止原因

`docs/developer/runtime/runtime_protocols.md` 区分三类：

| 类型 | 含义 | 恢复方式 |
| --- | --- | --- |
| **Transient** | 临时故障（quarto 未安装、依赖未就绪） | 补环境后重试同一 node |
| **Terminal** | 工作流逻辑不再可行 | 停止或 `cancelled` 收尾 |
| **Blocked** | 等待用户决定 | 记录 `blockers` 数组，Gate/Decision 解决后恢复 |

`node_command_protocol.md` 补充命令失败、Gate 自动 `fail`、`step_id` 标记与 terminal error 传输。核心原则：**失败被记录成结构化状态，而不是抛异常中断。**

## 验证与诊断

### Diagnostic 三字段（`src/core/validation/types.ts`）

```ts
{ severity: "error" | "warning", code: string, path?: string, message: string }
```

`src/core/validation/parse.ts` 把 JSON/YAML 语法错误转成**带 path 和行列号的诊断对象**，不抛异常：

- 复用解析库已经算好的 `line` / `column`（如 `yaml` 的 `linePos`）
- 缺结构时补 `path`、缺行列号时填 `unknown`
- 没有原始行号就不填，**绝不用行列号 0 冒充**

`parse.ts:11-13` 的注释把原因写得很清楚：

> Zod throws a `ZodError`; graph context promises `{ errors, warnings, content, data }` 并以 `value === null` 表达「未通过校验」。因此把 schema 问题翻译成带行列号的诊断，而不是让 `ZodError` 逃逸。

**理由不只是整洁**：CLI 输出机器可读诊断时，裸的 `ZodError` 栈没有位置信息，Agent 无法定位问题。

### 只读索引

`src/core/runtime/graph-workspace-index.ts` 一次扫描产出内存结构，fan-in 13（`loadGraphWorkspaceIndex` 是最热的符号）。

被 `status` / `check` / `doctor` / `list` / `show` 全部复用。**遍历一次、查询多次，天然无副作用、不随规模变慢。**

## 运行时协议集

`docs/developer/runtime/` 实际只有 **6 篇 md + 1 个 README**（目录里没有 `failure_protocol.md` / `revision_protocol.md`，这些内容合并在 `runtime_protocols.md` 里）：

| 文档 | 协议 |
| --- | --- |
| `core_runtime_model.md` | 核心模型：owner、派生视图、Agent 边界、两级治理 |
| `runtime_protocols.md` | 运行时总览与跨协议不变量 |
| `runtime_protocols.md` | 跨协议不变量 + 失败/修订/命令等子协议 |
| `deep_research_workflow.md` | deep-research 工作流协议 |
| `academic_paper_workflow.md` | academic-paper 工作流协议 |
| `academic_paper_reviewer_workflow.md` | academic-paper-reviewer 工作流协议 |
| `academic_pipeline_workflow.md` | academic-pipeline 工作流协议 |

运行时不变量（`runtime_protocols.md:34-36`）：

1. **状态只经 `researchspec/` 下的文件暴露**，其他文件是运行条件、产物或证据。
2. **确定性命令不产生任何变更**。破坏性写入一律在 write plan 之后。
3. **已选择能力不是运行前提**。能力目录必须可读，但能力缺失不删除既有文件和状态。

第 3 条值得注意：**「能力缺失不删除既有文件和状态」**——这让用户可以卸载能力而保留工作成果。

## 给 Scholoom 的启示

1. **Gate 节点在数据结构上不可被自动执行**。把它们排除在 eligible 之外，比在代码里加「记得先问人」的检查更可靠。
2. **角色绑定而非路径绑定**。图内只说「消费 claims」，具体文件由 handoff 运行时解析。替换产物不用改图。
3. **瞬时/终局/阻塞三分**。失败不是一个状态而是三个，其中阻塞态显式列出 `blockers` 数组——这是多 Agent 工作流崩溃恢复的关键。
4. **轮次计数归属 runtime**。禁止子系统自建计数器，否则双份记账必然不同步。
5. **Schema 错误转诊断不抛异常**。工具化 CLI 的错误路径应当和成功路径一样结构化。
6. **能力缺失不删数据**。卸载能力等于「以后不能用」，不等于「以前做的白做」。
