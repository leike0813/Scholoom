# 03 功能地图与用户模型

## 一句话架构

> **用户表达研究目标 → Navigate 按需发现能力 → 普通工作直接交付项目文件；需要正式流程控制时才冻结一张 graph。CLI 独占状态写入，文件就是接口。**

## 三个角色（`docs/user/usage-model.md:15-23`）

这是理解整个系统最重要的一张表：

| 角色 | 负责什么 | 明确不负责什么 |
| --- | --- | --- |
| **用户与宿主 Agent** | 对话、选择入口、确认成本和关键决定、执行语义工作 | 不直接改 run/node 状态 |
| **Procedures** | 按激活包读取必要输入，产出论文、报告、评审等项目文件 | 不写 run/node/Gate/Decision |
| **ResearchSpec CLI** | 唯一负责 run、node、Gate、Decision 和 graph transition 的持久化 | 不做学术判断、不写论文 |

补充一句定位（同一处）：

> ResearchSpec 不调用 Agent API，不替代用户选择的 Agent，也不接管 Zotero 或论文文件。**文件就是接口。**

## 两种工作模式

这是 ResearchSpec 最关键的产品设计决策：**大多数研究工作不需要 graph**。

| | Standalone（普通工作） | Graph（正式流程控制） |
| --- | --- | --- |
| 触发条件 | 默认路径 | 需要 formal Gate/Decision、parallel/join、重复轮次或可审计状态 |
| 写哪些文件 | 只写 `researchspec/` 外的普通项目文件 | 项目文件 + 通过 CLI 写 run/node/Gate/Decision |
| 恢复方式 | 从 `work/researchspec-notes/<task-id>.md` 任务笔记恢复 | 从 `status --json` + 精确 node instructions 恢复 |
| 完成时 | 把路径返回调用者 | `advance node:<run>/<node>` |
| 成本 | 无 run 级确认 | 一次确认授权整张冻结图 |

`docs/user/usage-model.md:81-85` 的原文很直接：

> 不需要正式流程控制的普通任务使用 standalone 模式，**持续工作也可留在此模式**……恢复普通工作不需要 graph。

**这是一个刻意的「反过度工程」设计**。很多同类框架默认所有工作都进状态机，ResearchSpec 明确拒绝——README 的 CHANGELOG Unreleased 条目记录了这个转向：

> Sustained ordinary work and its recovery use plain task notes without requiring a graph run; formal controls still use graph runs.

## 完整工作流（11 步，`docs/user/usage-model.md`）

### 1. 初始化只准备工作区

```bash
researchspec init . --tools codex
researchspec check all --strict
```

`init` **只**创建 schema 2 workspace、投影所选 Agent 表面和 preset profiles。**不开始学术工作，不创建 run**。

四份 stable spec 只保存**已确认的研究承诺**：

| 文件 | 内容 |
| --- | --- |
| `specs/project.md` | 研究问题、范围、边界、方法立场、贡献 |
| `specs/sources.yaml` | 已接受来源、identifier、用途、限制 |
| `specs/claims.yaml` | 稳定 claim、强度、证据、适用范围 |
| `specs/manuscript.yaml` | 体裁、语言、读者、venue、结构、交付格式 |

> 早期 workspace 可以有空的 sources、claims 或 manuscript。**不要为了通过检查编造占位事实。**

候选研究问题、暂定观点、草稿提纲留在 `researchspec/` 外的普通文件，可自由迭代。承诺建立或修改走 `propose → decide → 实际修改 specs → archive`。

### 2. 从一个入口按需选择 Procedure

宿主常驻的**只有一个** `researchspec-navigate`。三阶段渐进披露：

```text
list procedures --query <意图> --json
  → show procedure:<id> --json
    → instructions procedure:<id> --json
```

| 命令 | 返回 | 实现 |
| --- | --- | --- |
| `list procedures` | 紧凑卡片：selector / id / kind / title / 描述(截断 240 字符) / modes / domains / profiles / resource_count | `src/cli/handlers/graph-context.ts:31` |
| `show procedure:<id>` | **同一张卡片**的 pretty JSON，不含正文 | `graph-context.ts:71` |
| `instructions procedure:<id>` | 完整激活包，stdout 输出 procedure 正文全文 | `src/cli/handlers/graph.ts:149` |

搜索打分（`src/procedures/catalog.ts:163-172`）：完全相等 4 分、全词命中 3 分、部分命中 2 分，同分按 id 字典序。默认 limit 10，范围 1–50，**游标绑定内容指纹** `sha256(JSON.stringify(items))`——workspace 未变化时可重复分页。

隐藏的 Procedure inventory：4 个 ARSU 工作流、3 个非 Navigate Companion、47 个 core capability、339 个 plugin extension。**它们从已有 registry 即时派生，不投影进宿主 Skill catalog。**

### 3. 两种委派角色

24 个支持 custom agent 的宿主额外收到两个**非入口**角色：

| 角色 | 何时用 |
| --- | --- |
| `researchspec-executor` | producer，隔离或并行确有帮助时 |
| `researchspec-reviewer` | 纯 LLM 的 checker/observer，需要独立上下文时 |

约束很严（`usage-model.md:109-111`）：

> 每个 worker 只执行一个 packet，只写声明的普通输出，**不能调用 ResearchSpec mutation command、询问用户、选择模型或继续委派**。它返回 Procedure hash、输出路径、检查结果和 blocker；Navigate 校验后才串行执行 `advance` 等 CLI mutation。**worker 回报本身不改变 run、node、Gate 或 Decision。**

`mixed`、`script`、无输出参考程序和协调程序留在主 Agent。

### 4. 普通任务笔记

`work/researchspec-notes/<task-id>.md`，由 **Navigate 主 Agent** 维护。记录：用户目标与交付期望、输入产出文件及用途、已完成的实质工作与证据限制、待解决问题、下一步、有关联时的 run selector。

明确边界（`usage-model.md:144-146`）：

> 笔记是 `researchspec/` 外的**非正式工作材料**：不进入安装 manifest，`status` 和 `check` 不扫描或校验它，CLI 也不提供 task selector。**它不能用来声称 run、node 或 Gate 已完成。**

委派 worker 不写笔记；主 Agent 校验其返回路径后才更新。

### 5. 一次确认授权一张冻结图

启动根 run 前，Agent 必须向用户展示 **profile entry summary**，至少包含：

- 选择的 route、entry 和首节点
- prerequisites 与已确认的 handoff inputs
- 预期边界 outputs
- graph 中的 formal Gates 和 Decisions
- 预计成本、外部工具与交互强度

用户确认后才可 `start profile:<profile-id>`。

**这次确认只授权冻结图内声明的节点、重复轮次和绑定 child runs**，不替代以下独立确认：

- 每个 formal Gate
- 每个 graph Decision 和 failed-Gate override
- 当前 run/node 的异模型复核
- Plugin 安装、Adapter 访问
- QMD 渲染时的代码执行

### 6. Frontier 决定「现在能做什么」

`status` 和 `instructions` **即时计算** frontier，不持久化。判定顺序（`src/core/runtime/graph-run.ts:319-450`）：

1. 输入契约诊断非空 → 全部阻塞
2. `run.status !== "active"` → `run_not_active`
3. 已完成 child run 投影为父节点 complete 实例
4. 从 entry 沿 prerequisites / Decision unlocks 求可达闭包
5. round 候选确定
6. 跳过 `complete` / `cancelled` / `skipped`
7. Quarto 交付要求且 probe ≠ available → `quarto_unavailable`
8. 必需 Gate 最新 verdict = fail 且无有效 override → `gate_failed`
9. 依赖满足（并行组 `all`/`any`、普通依赖 complete）
10. 分支：被 Decision `unlocks` 覆盖的节点必须有对应 option 被记录
11. 必需 Gate 全部 accepted、必需 Decision 全部已记录
12. gate/decision 型节点进入 `pending_gates` / `pending_decisions`，**不进入 eligible**
13. 输入解析失败 → blocker
14. subgraph 节点：0 child → `pending_subgraph_starts`；>1 → `child_run_ambiguous`
15. 其余进 `eligible_nodes`

### 7. Handoff 连接图与真实文件

论文、报告、review、图表、数据都在 `researchspec/` **外**。ResearchSpec **不复制、不 hash-bind、不管理**它们。

`runs/<run>/handoff.md` 只记录边界交换：role、type、path、purpose、source run / intended consumer、format、`renderer: quarto`。

> 节点 binding 按 role 连接生产者与消费者。**路径不是工作流关系的事实源。**

### 8. Gate、Decision 与重复轮次

Agent 或 validator 可以**准备** Gate findings，但 **verdict 必须由人确认**。`decide gate:...` 把 attempt 追加到 Gate 所属 node instance。

> `pass`、`pass_with_conditions` 和 `fail` **都不会顺便完成节点**。

Decision 逐项确认，记录 choice 后只有对应分支进入 frontier。**探索笔记、普通工具调用和日常文件修改不应伪装成 Decision。**

动态 revision template 每轮实例化 revision、re-review 与 round Decision。选择继续开启下一轮；选择接受才解锁 format。轮次计数属于 graph runtime，**Capability Skills 不能另建计数器**。

### 9. Project change：accepted ≠ applied

```text
propose  →  decide  →  实际修改 specs  →  archive
```

`accepted` 只代表用户接受方案。**stable specs 修改并通过检查后，change 才能成为 `applied`。**（`docs/developer/architecture.md:77-79`）

change 状态枚举（`graph-workspace.ts:97`）：`draft | proposed | accepted | rejected | deferred | superseded | applied`。约束：非 draft/proposed 必须带 decision，且 `decision.outcome` 必须等于 `status`（`applied` 要求 `accepted`）。

### 10. 稿件格式：Markdown / QMD / Quarto

首次进入稿件工作时用户在 `manuscript.yaml.delivery` 选 `markdown` 或 `qmd`。QMD 还需安全的 `final_output_format`。

**读命令永不探测 Quarto。** 宿主 Agent 在写作 intake、QMD 恢复或 format 节点前按 instructions 执行只读 `quarto --version`，把 probe summary 随 start 输入记录。

> 对要求 Quarto 的 QMD format 节点，`available` 才能推进；未知或不可用**只阻塞该节点，不阻塞前面的写作**。

默认渲染 `no-execute`；执行文档代码需另行取得当前 run/node 的 `render_consent`。

### 11. 恢复、检查、打包与结束

**没有 `finalize` 命令。** 全部选中节点、Gate、Decision 满足后，`status` 派生 `completion_ready`；完成状态由最后一次合法推进写入。

旧或未知 workspace 被报告为 `unsupported` 并**保持字节不变**。

## 功能域总览

把上面 11 步按能力域归类：

| 功能域 | 关键命令 | 说明 |
| --- | --- | --- |
| **工作区引导** | `init` `update` | 创建 schema 2 workspace、投影 Agent 表面、刷新受管文件 |
| **能力发现** | `list procedures` `show procedure:` `instructions procedure:` | 三段式渐进披露，339+ 隐藏能力按需加载 |
| **流程控制** | `status` `instructions` `start` `advance` | frontier 即时计算，一次确认授权冻结图 |
| **人类决策** | `decide` | Gate verdict / override / Decision choice / change decision |
| **合约治理** | `propose` `archive` `check` | 两级 spec-driven 变更，accepted ≠ applied |
| **只读诊断** | `status` `check` `doctor` `list` `show` | 不执行外部工具、不修语义、不改文件 |
| **上下文打包** | `pack` `handoff` | 确定性有界上下文包，不复制外部文件字节 |
| **领域能力** | `plugin list/show/install/update/uninstall` | 按 ANZSRC 学科域选择经审查 Skill |
| **文献接入** | `init/update --literature-adapters` | 可选 Zotero Adapter，7 个 Skill + `.zotero-bridge/` |
| **交互审阅** | 无公开命令（通过 `instructions` 的 `review_workspace` 字段） | 静态 HTML 工作台，只读草稿 + 建议性导出 |

## 「不做什么」清单

`AGENTS.md:45-51` 的反面清单值得单独记住，因为同类项目最容易在这里越界：

- ❌ LLM API 集成层
- ❌ 平台专属的 Claude Code / Codex 适配器
- ❌ Web app、database-first 研究平台、引用管理器替代品
- ❌ 手工维护的生成产物副本

`docs/developer/architecture.md:21-22` 补充：

> ResearchSpec 不调用模型 API，不管理数据库，不执行 vendor 脚本，也不接管 Zotero 或交付物。

## 确认边界总表

这是 ResearchSpec 安全模型的核心，一张表看完：

| 动作 | 需要什么确认 |
| --- | --- |
| 启动根 run | 一次 entry summary 确认（授权整张冻结图 + 绑定 child runs） |
| 每个 formal Gate | 独立人工确认 |
| 每个 graph Decision | 独立人工确认 |
| Failed-Gate override | 独立确认 + 理由 + Decision identity |
| 异模型复核 | 说明模型、内容类别、成本；只对当前 run/node 有效 |
| Plugin 安装 | 与 run 确认**分离**的 plugin consent |
| Adapter 访问 | 独立授权（route confirmation / plugin consent / bridge readiness **都不等于** managed-library authorization） |
| QMD 代码执行 | `render_consent`，逐次 |

## 给 Scholoom 的启示

1. **默认路径要能绕开状态机。** 「大多数工作不需要 graph」这个判断是产品级的正确取舍。状态机是给需要审计的场景用的，不是给所有场景用的。
2. **委派必须封死写权限。** worker 不能调 mutation command、不能问用户、不能选模型、不能再委派——这四条约束让并行委派变得安全。
3. **状态完成不由「完成命令」决定。** 没有 `finalize`，`completion_ready` 是派生状态。这避免了「一个 finalize 命令把状态推到完成」的漏洞。
4. **accepted 与 applied 分离。** 这条在软件工程里常见（PR approved ≠ merged），用在研究合约上同样成立。
5. **探索产物与已确认承诺物理隔离。** 草稿在 `researchspec/` 外，承诺在四份 stable spec 里。检查工具只校验后者。
