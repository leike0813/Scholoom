## TypeScript 配置：四份 tsconfig 各司其职

`tsconfig.json` 是基线（`noEmit: true`，只做类型检查）；另外三份各有明确边界：

| 文件 | 用途 | 关键差异 |
| --- | --- | --- |
| `tsconfig.json` | `pnpm check` 类型检查 | `noEmit: true`，`include: src + tests + harness` |
| `tsconfig.build.json` | `pnpm build` → `dist/` | 只编译 `src/`，产出可执行文件 |
| `tsconfig.test.json` | `pnpm test` → `.test-dist/` | 编译测试到独立输出目录，避免污染 `dist/` |
| `tsconfig.harness.json` | `harness/` 预览代码 | 独立于主构建 |

**基线编译器选项**（`tsconfig.json`）：

```json
{
  "target": "ES2022",
  "module": "NodeNext",
  "moduleResolution": "NodeNext",
  "strict": true,
  "esModuleInterop": true,
  "forceConsistentCasingInFileNames": true,
  "skipLibCheck": false,      // 注意：不跳过
  "noEmit": true,
  "types": ["node"]
}
```

两个细节值得注意：

- **`strict: true`** 全开。
- **`skipLibCheck: false`**——连依赖的类型定义都要检查。这会让 `zod` 升级更容易触发 CI 失败，是刻意的严格度。
- **`forceConsistentCasingInFileNames: true`**——跨大小写敏感/不敏感文件系统的正确性保证。

## 构建与产物

```bash
pnpm build
# = node scripts/clean-output.mjs dist && tsc -p tsconfig.build.json && node scripts/mark-cli-executable.mjs
```

三步：清空 `dist/` → `tsc` 编译 → **给 CLI 入口打可执行位**（`mark-cli-executable.mjs`）。

产物布局：

```text
dist/src/
  cli/bin.js                    # bin 入口
  arsu-converter/cli.js         # arsu:convert / check / idempotence
  vendor-converters/*/cli.js    # 各 vendor 的 convert / check / idempotence
  vendor-audits/…
  vendor-evidence/…
```

**大量维护脚本直接跑编译产物**（`arsu:convert`、`tooluniverse:check` 等 60+ 条 script 都以 `pnpm build && node dist/...` 开头）。这意味着这些工具在运行前必定已经是编译通过的状态。

## npm 包边界：`files` 白名单

`package.json` 的 `files` 字段定义了实际发布的边界，这里有一处**反直觉的负向规则**：

```json
"files": [
  "dist",
  "!dist/src/vendor-audits",      // 审计不进包
  "!dist/src/vendor-evidence",    // 证据不进包
  "!dist/src/vendor-converters",  // 转换器不进包
  "skills",
  "review-workspace/index.html",
  "review-workspace/v1.html",
  "review-workspace/revision-master.html",
  "literature-adapters",
  "README.md", "CHANGELOG.md", "SECURITY.md",
  "LICENSE", "LICENSES", "NOTICE",
  "docs",
  "artifacts/release/mvp-release-checklist.md"
]
```

**审计、证据、转换器实现全部不发布**。发布的是它们的**产物**（`skills/` 树）+ 审核结论（`LICENSE`/`NOTICE`/`LICENSES`）。维护者工具留在仓库里，不进用户机器。

两个 export 子路径供外部使用：

```json
"exports": {
  "./annotation-intake":  { "types": "./dist/src/annotation-intake.d.ts",  "import": "./dist/src/annotation-intake.js" },
  "./review-workspace":   { "types": "./dist/src/review-workspace.d.ts",   "import": "./dist/src/review-workspace.js" },
  "./package.json": "./package.json"
}
```

只有两个：`annotation-intake`（批注摄取）和 `review-workspace`（审阅工作台准备/渲染）。**其余全部内部使用**。

`prepack` 钩子是 `pnpm build`，`release:verify` 是 `node scripts/verify-package.mjs`。

## 外部运行时边界

ResearchSpec 自身**不运行**任何科学计算或文献访问运行时。这些是「用户配置后才存在」的外部依赖：

| 外部运行时 | 谁需要 | ResearchSpec 的姿态 |
| --- | --- | --- |
| **Quarto** | QMD 稿件渲染 | 读命令**永不探测**；由宿主 Agent 按 instructions 执行只读 `quarto --version` |
| **Pandoc** | 审阅工作台的格式转换 | 渲染在导入浏览器前完成；失败时保留 `raw-source` 惰性块 |
| **Zotero + Zotero-Agents 插件** | `zotero-library` 文献适配器 | 交付时不探测、不安装 XPI、不联网 |
| **zotero-bridge runtime** | 上述适配器的执行机制 | 离线复制到项目内 `.zotero-bridge/bin/` |
| **材料科学工具链**（Atomsk、DPGEN、GPUMD、PhonoPy、UniMol、deepTB） | Materials 域扩展 | 「reviewed external resources rather than provisioned assets」 |
| **各种模型/HPC 环境** | 多个 vendor | 同上，ResearchSpec 从不调用或配置 |

**关键安全姿态**：Quarto 项目的 `pre-render`、脚本、过滤器、可执行 cell 会运行用户代码。因此这类渲染需要**逐次单独批准**，获批后在临时副本中运行——而且文档明确承认「临时副本保护的是相对路径下的原稿，项目脚本仍以主机权限运行，**并非安全沙箱**」。

## 34 条 package.json script 的分类

94 条 script 高度规律化。看懂分类就懂了这个项目的维护动作空间：

| 类别 | 数量 | 形态 | 说明 |
| --- | --- | --- | --- |
| 基础构建 | 4 | `clean` `build` `test` `check` | 加上 `lint` |
| 文档 | 3 | `docs:generate` `docs:check` `cli:handbook*` | **从 CLI catalog 生成，检查漂移** |
| 每个 vendor 三连 | 6×3=18 | `<vendor>:convert` `:check` `:idempotence` | 转换器标准动作 |
| 每个 vendor 维护 CLI 四连 | 6×4=24 | `<vendor>-maintenance:artifacts` `:records` `:baseline` `:check` | 准入记录管理 |
| ARSU | 7 | `arsu:convert` `:check` `:idempotence` `:author` `:anchors:*` `:runtime-policy:check` | |
| 能力审计 | 5 | `capability:parity` `:parity:report` `:review-html` `:assessment-html` `:gap-review-html` | 三个 HTML 审阅产物 |
| dogfood | 2 | `dogfood` `dogfood:test` | 宿主沙箱演练 |
| Zotero 适配器 | 4 | `zotero-adapter:convert` `:audit` `:check` `:idempotence` | |
| 发布 | 3 | `prepack` `release:verify` `whitespace:check` | |
| 本地预览 | 4 | `dev:harness` `dev:review-workspace` `prototype:revision-master` `install:stable` | |

**`convert` / `check` / `idempotence` 这个三连是关键**：转换器不是一次性脚本，而是**确定性生成器**。同样的输入必须产出同样的字节，所以幂等性本身就是一条测试，CI 每次都跑。

## 文档即代码：生成链

`docs/user/cli-handbook.md` 第一行就写着：

> Generated from the typed public CLI catalog. Do not edit this file by hand.

生成链（`scripts/generate-docs.mjs`）：

```text
src/cli/command-catalog.ts   （typed 声明，SSOT）
        │
        ├──→ CLI handbook      (docs/user/cli-handbook.md)
        ├──→ payload catalog  (输入 schema 文档)
        ├──→ Docusaurus 命令页 (website/docs/cli/**)
        └──→ Navigate 的 references/cli-handbook.md
        └──→ references/arsu-routes.md
```

**同一份 typed 声明同时驱动 Commander 注册、帮助文本、读写影响标注、工作区要求和文档生成**。`--check` 模式验证生成内容未漂移，CI 会跑。

这解决了一个真实问题：Agent 消费 CLI 依赖文档，文档手写就必然漂移。让代码生成文档，漂移就在 CI 里变成红灯。

## 安全与隐私姿态

`SECURITY.md` + README 的关键点：

- CLI **无运行时 LLM API 集成，不发送遥测**
- Agent 工具可能有自己的网络、模型和遥测行为，**需单独审查**
- `handoff` 只引用外部边界文件；`pack` **排除 run 私有 work 和外部文件字节**
- 研究内容保留在项目内，除非用户或 Agent 工具主动导出
- 正式 Gate、failed-Gate override、scope、claim、structure、branch 选择**均需人工确认**

## 给 Scholoom 的可迁移点

| 点 | 说明 |
| --- | --- |
| **四份 tsconfig 分离产物** | `dist/`（发布）、`.test-dist/`（测试）、harness 独立，互不污染 |
| **`skipLibCheck: false`** | 依赖升级的破坏性变更在 CI 暴露，而不是运行时炸 |
| **audit/evidence/converter 不进包** | 维护工具与产物严格分离，用户包只带产物与审核结论 |
| **convert/check/idempotence 三连** | 任何生成器都该有的三个动作，尤其 idempotence 进 CI |
| **文档从 typed catalog 生成 + 漂移检查** | 文档漂移从「靠人记得更新」变成「CI 红灯」 |
| **负向 files 白名单** | `!dist/src/vendor-converters` 这种写法比逐个列举要稳 |
