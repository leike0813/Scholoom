# 10 领域插件与文献适配器

## 设计前提：Reviewable units

`docs/developer/domain-plugins.md:7-9`：

> Plugin 的产品前提是**可审阅的单元**。一个 vendored 工具只有在它的知识来源、工具访问、依赖、并发限制、审计记录与责任边界都能被明确陈述时才有价值。

`domain-plugins.md:20-23`（仓库立场）：

> 仓库只维护**通用可复用**的领域。specific-for-one-lab 的内容由项目或受管 Plugin 拥有。

**分工很清楚**：仓库提供跨项目可复用的学科能力；单实验室的专用能力由项目自己拥有。

## 两层结构

| 概念 | 数量 | 位置 | 含义 |
| --- | --- | --- | --- |
| **Vendor** | 6 | `skills/plugins/registry.json` | 上游来源包（一个 GitHub 仓库 / 项目） |
| **Domain** | 218 | 同上 | 稳定标识的学科或工具领域（213 学科 + 5 工具） |
| 非空 domain | 59 | 同上 | 至少含一个已审 Skill |
| 已审 Skill | **338** | `skills/plugins/vendors/<id>/` | vendor 中逐个审计通过的 Skill |

**这是两层，不是三层。** Domain 不是 vendor 派生的分类层，而是**平行的稳定标识集合**。一个 vendor 可以贡献给多个 domain，一个 domain 可以从多个 vendor 获得 Skill。

## ANZSRC 2020 FoR 分类

`src/plugins/taxonomy.ts:27-131` 的分类依据是 **ANZSRC 2020 Field of Research (FoR) 分层**，官方名称与数字均取自 ABS（`https://www.abs.gov.au/statistics/classifications/australian-and-new-zealand-standard-research-classification-anzsrc-2020/research-classification`）：

- **213 个学科域**（hierarchical，逐层展开 FoR 36 → 顶部学科群）
- **5 个工具域**：`tool-*` 命名（读取、检索、写作、可视化、文档）

`domain-plugins.md:6` 特别说明：学科分类**不是研究领域完整字典**。`tool-*` 命名是为了让「与学科无关的工具能力」保持统一、稳定、不与学科概念冲突。

## Vendor 准入清单

`src/plugins/registry.ts:91-150` 的 `validatePluginRegistry` 七项检查：

1. **Domain 分类完整性**：每个 domain 必须在 `domain-catalog.json` 中；学科域必须落在 213 个 FoR 域之一，工具域必须以 `tool-` 开头
2. **Vendor 定义完整**：`release` / `revision` / `admission_count` / `capability_count` / `exclusion_count` / `domains` 齐全
3. **Skill manifest 存在**：每个 skill id 有 `vendor-manifests/<vendor>.json` 条目
4. **保留 ID 冲突检测**：`registry`、`shared` 等保留 id 不能被 vendor 占用
5. **依赖闭合**：声明的依赖必须在注册表内或显式排除
6. **非空 domain 有 Skill**：59 个非空域各至少一个
7. **依赖环检测**：`plugin:taxonomy.ts:83-112` 的 `assertNoCyclicDomainDependencies`

**assembler 是 `registry.json` 的唯一写入者**（`src/plugins/assembler.ts:40-65`）：

- 只读 `domain-catalog.json`（强制 218 域）
- 只读各 `vendor-bundles/*.json`
- 校验后**原子写** `registry.json`
- vendor converter **不写** `registry.json`

这条写入边界的意义：domain 归属是**中央决策**，不能由各 vendor 转换器各自决定。否则「这个 Skill 属于哪个学科域」会变成 6 个转换器各自的判断。

## 非原生 Skill 标准

`docs/maintainer/non-native-vendor-skill-standard.md:5-7` 明确适用范围：

> 本标准只适用于**非原生** vendor（HistAgent、FinRobot、Materials Science）。不要求改写 ToolUniverse、Scientific Agent Skills、Education Agent Skills 的原生 Skill 上游。

### 四层厚度

`non-native-vendor-skill-standard.md:19-24`：

| 层 | 适用 | 说明 |
| --- | --- | --- |
| **Baseline** | 所有 adapter | 归类决策 + ID + reason code + 来源标注 |
| **Script-assisted** | 有结构化描述的 vendor | 确定性预生成决策 |
| **Stateful** | 有持久化/共享状态的 vendor | 状态依赖显式建模 |
| **Resource-backed** | 依赖真实外部资产/工具的 vendor | 资源获取契约 |

对应模板在 `src/vendor-converters/shared/non-native-skill-standard/templates/`。

### 决策枚举

`production-policy.json` 的 `production_action`：

- `excluded`
- `retained-evidence`
- `independent-reimplementation`

配 `audit_disposition` ∈ `retain | exclude | adapt | replace | confirmed-failure`

**`confirmed-failure` 值得注意**：它记录的是「审计过、确认这个 Skill 上游有问题」，是一个正面结论而非「还没看」。

## 排除决策的实际形态

这是「准入决策数据化」最有说服力的例子。Materials vendor 排除 `ase` 的完整记录（`src/vendor-converters/materials-science-skills-for-llm/admission-decisions.json`）：

```json
{
  "upstream_skill_id": "ase",
  "generated_skill_id": "materials-science-skills-ase",
  "disposition": "excluded",
  "reason_codes": ["development-maintenance-scope"],
  "license": null,
  "content_review": {
    "outcome": "failed",
    "evidence": ["ase/SKILL.md", "ase/references/testing.md"],
    "note": "The Skill owns upstream development, testing, changelog, documentation, and Git maintenance."
  },
  "permission_review": { "outcome": "not-applicable", ... },
  "overlap": { "conclusion": "not-applicable", ... }
}
```

**每条排除都带：reason code + 三类复核结论 + 证据路径**。运行时无从「重新判断」——它只有一份签入的 JSON。

对比一下：如果是运行时判断，那每次转换都要重新读 SKILL.md 重新判断，得到的结果可能不同，而且无法复核。

> plugin 确认与 run 确认是**分离的 Gate**。确认只覆盖领域能力投影和所需宿主工具集合。Agent 必须确保项目工具包含 plugin 的交付目标（`init --tools` 与 `update` 可以补投）。**Plugin 投影本身不创建 run。**

## Plugin extension 资产

`skills/plugins/extensions/`：

- `capabilities/`：339 个 plugin capability 目录（与 `profiles/` 一一对应）
- `profiles/`：339 个 `plugin-<vendor>-<slug>.yaml` graph profile

**`profiles/` 里的 `plugin-*` profile 就是让「历史研究」「金融分析」这类领域工作能进 graph runtime 的载体**——它们是 graph profile，不是 run。

## 给 Scholoom 的启示

1. **Domain 是稳定标识，不是 vendor 的分类层**。让 domain 独立于 vendor 存在，才能支持「一个 domain 多来源」和「换 vendor 不换 domain」。
2. **中央 assembler 是注册表唯一写入者**。分布式的分类决策必然发散。
3. **决策是数据不是判断**。每条排除带 reason code + 复核结论 + 证据路径，运行时只比对。这是可审计性的根本。
4. **`confirmed-failure` 是一种正面结论**。区分「确认有问题」和「还没看」，避免审计状态二值化。
5. **非原生标准只约束非原生**。不要求改写原生 Skill 上游——这个克制避免了大量无谓工作量。
6. **领域分类可以不是完整字典**。`tool-*` 独立命名空间让工具能力不必挤进学科分类。
