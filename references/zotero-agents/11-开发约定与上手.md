### 五条最该记住的硬约束

**① E2E 测试约束**（149–154）

- 统一入口 `tests/zotero/e2e/full` + `npm run test:zotero:e2e`；**不得另建平行 runner**
- 真实库/profile 只能**只读复制**到 `.scaffold/test` 后运行，测试不得直接改来源目录
- 金例只提交**去标识化结构契约**，禁止提交标题/作者/正文/本地路径/原始数据库
- E2E 必须使用**当前源码构建**的本地 Synthesis sidecar

**② Workflow Host 投影约束**（248–253、264–271）

- `src/modules/runtimePersistence.ts` 是**跨运行时文件系统 adapter 的唯一事实源**
- runtime adapter 必须**按调用晚绑定**；不得因缓存 projection 而缓存运行时 global、picker window 或 fs adapter
- `WorkflowHostApi` 必须通过 member-level `Pick` + 显式对象字面量投影 broker；**禁止 spread、proxy、运行时 capability catalog、隐式成员继承**
- broker 不负责 authorization / permission / exposure / noninteractive policy / transport / remote locality

**③ Synthesis Sidecar 生命周期**（218–227）

- `runtime_service::serve(&Path)` 是生产生命周期**唯一入口**
- **discovery 原子发布 = ready commit**；stdout listening 事件仅诊断
- ready 前失败必须回滚 owner；ready 后所有终止走同一清理路径
- `system.shutdown` 成功响应只表示"停止请求已接受"：先刷响应再发布 stopping，**进程退出才算清理完成**
- **primary/secondary 失败语义**：terminal result 形成前的第一个 failure 是 primary，后续只能作 secondary；terminal result 一旦形成不可改
- 共享 deadline 内未退出的 background task 仍可能引用 storage，**不得提前关闭**
- worker-pool 状态机测试**禁止 `#[path]` 重编译生产源码**

**④ 发布流程**（278–291）

- Host Bridge 发布只能由 Agent 在**版本、release set、本地门禁、用户授权**四项明确后，通过 `npm run release:host-bridge:dispatch` 显式触发；**普通 `main` push 和 CI 不得触发发布**
- 七平台 CLI 预构建**只能以内容寻址集合发布到 `host-bridge-cli-prebuilds` 分支**，不得创建 GitHub Release 充当预构建仓
- **GitHub `main`、tag/release、content feed 是正式发布的唯一事实源**；发布门禁不得依赖 Gitee 状态
- Gitee 同步只能在**用户单独要求**时运行 `npm run sync:gitee-release`，且**必须复用 GitHub 已发布的原始字节**
- content package 的 GitHub release asset 是**不可变产物**：同名同版本仅允许复用 SHA-256 一致的文件；内容不同**必须提升 content package 版本**

**⑤ ACP Transcript Projection**（211–216）

- 不得假设后端已正确整流 assistant message chunks
- `tool_call_update` / usage / status / workspace activity **不得**作为 assistant message 的硬切分边界
- coalescing **禁止**按 backend id、provider id、agent family、命令名或产品字符串特判
- ACP Chat 与 ACP Skills 共享同一类 boundary 分类，改动必须同步审查两条路径

### 三个值得单独记住的规则

**① 后端配置的容错粒度**（§4）

- 整体 JSON 非法 → **阻断 workflow 执行**
- 单条 backend 非法 → **只影响绑定它的 workflow**

**② workflow 的 `provider` 是 backend 兼容性的唯一来源**（§6）

`requestKind + backend.type` 只在选定 backend 后用于执行解析，**不用于推断兼容性**。规则：`acp -> acp`，`skillrunner -> skillrunner/acp`，其他 provider 只匹配同名 backend type。

**③ 菜单可调用性只做轻量预检**（§7）

菜单只做 selection / input 层预检。**backend 存在性、连接状态只能在提交窗口或执行时反馈，不得作为菜单门禁**——否则后端临时不可用会让用户连菜单都点不开。

## OpenSpec 使用方式

```
openspec/config.yaml     schema: spec-driven；context/rules 段全是注释（可填充的空白）
openspec/specs/          366 个 capability 目录
openspec/changes/        当前只有 archive/，含 878 个历史 change
```

**工作流**：change 是增量提案 → archive 时把 delta spec 合并回 `openspec/specs/<capability>/`。已 apply 的能力留在 specs，新能力先在 change 里。

新增 change 的流程（`.agents/skills/openspec-new-change/SKILL.md`）：

1. 需求模糊时先开放式提问，从描述派生 kebab-case 名
2. `openspec new change "<name>"`
3. `openspec status --change <name> --json` / `instructions` / `validate` / `archive`
4. 支持 `--store <id>` 指向本机注册的独立 OpenSpec repo

**878 个已归档 change + 366 个 capability**，说明这个项目所有较大改动都走 OpenSpec 提案流。

## 对 Scholoom 的启示

1. **规范用"硬约束"分级小节写，不混在说明里**。AGENTS.md 把 10 个领域的硬约束分成独立小节，每节标注约束哪些文件。新人知道改动落在哪个域就必须读哪一节。
2. **术语表用 `_Avoid_` 负向约束**。与其罗列"这个东西叫什么"，不如写"不要叫它 A、B、C"。这份文件防的是混用，不是教学。
3. **AI 指令目录要有单一权威副本**。`.agents/skills/` 是权威，其余是工具落地副本，且明确哪些入库。
4. **release 是命令而不是分支**。避免维护 release 分支带来的合并地狱。
5. **产物分支用内容寻址**。`host-bridge-cli-prebuilds` 存的是内容寻址集合，不是发布记录。
6. **发布有"唯一事实源"且显式声明**。GitHub 是唯一事实源，Gitee 同步必须复用原始字节、需用户单独授权、不影响门禁。
