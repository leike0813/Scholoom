# 05 构建与工程化

这个项目 141 条 npm script、330 个测试文件、366 个 OpenSpec capability。它的工程化密度本身就是一个可参考的样本。

## 单一构建入口

```
npm run build
  = build:help-docs
  → check:synthesis-engine
  → check:synthesis-contracts
  → check:synthesis-repository
  → check:synthesis-application
  → zotero-plugin build
  → tsc --noEmit                        (tsconfig.json)
  → tsc --noEmit -p tsconfig.sidebar.json
  → tsc --noEmit -p tsconfig.dashboard.json
  → tsc --noEmit -p tsconfig.synthesis.json
```

这个顺序值得学：**先校验契约与生成物，再打包，最后做四份类型检查**。四份 tsconfig 全部 `noEmit`，说明 esbuild 才是真正的产物生成者，tsc 只负责类型门禁。

注意 `zotero-plugin build` 在类型检查之前——也就是说**类型错误不会阻止打包**，但 `test:gate:release` 会。这一层依赖 CI gate 兜底。

## npm script 的六个域

| 前缀 | 数量级 | 用途 |
| --- | --- | --- |
| `build:*` | 少量 | 生成帮助文档、生成 canonical validators、构建 content feed、构建 Rust sidecar、构建 host-bridge CLI |
| `check:*` | **39** | 治理校验，见下 |
| `test*` | **46** | 分层测试 |
| `start*` | 5 | 开发服务器 |
| `test:gate:*` | 2 | CI gate（pr / release 两档） |
| 其他 | 若干 | 清理、格式化、发布准备 |

### `check:*` 是这个项目的特色

39 条 check 脚本不是形式检查，而是**架构约束的机器化**。按域分类：

| 域 | 代表脚本 | 校验什么 |
| --- | --- | --- |
| 资产闭包 | `check:builtin-workflow-manifest` | `workflows_builtin/` 磁盘文件与 manifest `{version, files[]}` **双向相等**，多一个少一个都失败 |
| 本地化 | `check:localization-governance` | key parity、base locale、ownership matrix |
| 跨语言契约 | `check:synthesis-cross-language-contracts` | TS 与 Rust 两侧的 Synthesis 契约不漂移 |
| 表面平价 | `check:synthesis-*-surface-parity`（8 条） | 每个 Workbench Surface 的 TS/Rust 双实现行为一致 |
| 能力平价 | `check:synthesis-production-capabilities` | 生产 capability 与文档声明一致 |
| 边界 | `check:synthesis-service-boundary` | 禁止跨层依赖 |
| 性能 | `check:synthesis-production-route-performance` | 关键路由性能预算 |
| 产物新鲜度 | `check:synthesis-sidecar-runtime-freshness`、`check:host-bridge-cli-prebuild-freshness` | 派生产物没落后于源 |
| 发布 | `check:content-package-release`（含 `:all`、`:mirror`） | 内容包发布配置与镜像一致 |
| 不变量 | `check:ssot-invariants` | `*.invariants.yaml` 与代码事实深比较 |
| 裁剪 | `check:runtime-diagnostics-release-elision` | debug-only 模块在 release 包里贡献 0 字节 |
| 文档 | `check:help-docs`、`check:host-bridge-doc-sync`、`check:host-bridge-content` | 生成文档未过期 |

**这套 check 的共同结构是：拿代码或磁盘的真实状态，去和某份声明比对。** 这是把架构约束从"文档里的君子协定"变成"CI 里跑不过的红灯"。

## 测试体系

### 三层

| 层 | 入口 | 内容 |
| --- | --- | --- |
| **Node 单元/集成测试**（默认） | `npm test` → `test:node` | `scripts/run-node-test-shards.ts` 分片运行，带 Zotero mock |
| **真实 Zotero 测试** | `npm run test:zotero:full` | 在真实 Zotero 里跑，通过 `zotero-plugin test` |
| **Rust 测试** | `npm run test:synthesis-rust-sidecar` | `cargo test --workspace --locked` |

### 分域分片

`run-node-test-shards.ts` 按域切分，13 个域各一条命令：

```
test:node:acp          test:node:assistant      test:node:dashboard
test:node:host-bridge  test:node:runtime        test:node:skillrunner
test:node:synthesis    test:node:tooling        test:node:ui
test:node:workflow     test:node:zotero-host
```

理由很实际：330 个测试串行太慢，分域后可并行，也可按改动范围只跑受影响的域。`test:node:shards:list` 列出分片。

### 真实 Zotero 测试的档位

```
test:zotero:lite / :full              全部
test:zotero:core / :core:full         核心域
test:zotero:ui    / :ui:full          UI 域
test:zotero:workflow / :workflow:full 工作流域
test:zotero:e2e                       端到端（强制 full）
```

`lite` vs `full` 由 `scripts/run-zotero-test-with-mock.ts` 区分。E2E 必须 `full`，因为它要真实宿主环境。

### 其它测试入口

| 命令 | 说明 |
| --- | --- |
| `test:synthesis:invariants` | 用 `--grep "\[inv\."` 只跑不变量用例 |
| `test:synthesis:legacy-production-migration` | 验证旧 Node 实现已彻底移除 |
| `test:zotero:compatibility:matrix` | Zotero 版本兼容矩阵（prepare/plan/run/acquire/matrix） |
| `test:zotero:e2e:stress` | E2E 压测（`run-zotero-e2e-stress.ts --catalog`） |
| `test:gate:pr` / `test:gate:release` | **CI gate**，两档严格度不同 |

`test:gate:*` 是最值得学的设计：**PR 与 release 用同一个 gate 脚本、不同的档位**。开发者本地跑 `test:gate:pr`，发布前跑 `test:gate:release`。这避免了"发布前才发现问题"。

## Rust 侧门禁

```
check:synthesis-rust-sidecar
  = cargo +nightly-2026-07-25 clippy --workspace --all-targets --locked
    --manifest-path rust/synthesis-sidecar/Cargo.toml -- -D warnings
```

三个要点：**锁定 nightly 版本**（可复现）、**`--locked`**（Cargo.lock 不被改动）、**`-D warnings`**（警告即错误）。另外 `check:synthesis-rust-license-inventory` 强制清点依赖许可。

## 内容包（Content Package）体系

这是这个项目最独特的一块机制：**工作流包可以独立于插件版本分发与更新。**

### `content-package.version.json`

```json
{
  "schema": "zotero-agents.content-version.v1",
  "id": "zotero-agents-official-workflows",
  "version": "0.8.7",
  "content_api": "3.0.0",
  "requires": {
    "plugin": ">=0.9.0",
    "content_api": "^3.0.0",
    "zotero": ">=7 <11"
  }
}
```

**版本解耦**：内容包 version 是 `0.8.7`，插件是 `0.9.0`。内容包声明自己需要 `plugin >= 0.9.0`。这样工作流包可以小步快发，不必等插件大版本。

**三方兼容声明**：`requires.plugin` / `requires.content_api` / `requires.zotero`，用 npm semver range 校验（见 06 篇）。`zotero: ">=7 <11"` 直接覆盖三个 Zotero 分支。

### 订阅机制

`src/modules/workflow/catalog/contentPackageSubscription.ts`（1300+ 行）负责：查询、下载、安装、兼容性校验、目录落位到 `<dataDir>/content/official/workflows`。相关脚本：

| 脚本 | 作用 |
| --- | --- |
| `build:content-feed` | 生成内容包索引 feed |
| `check:content-package-release` | 校验发布配置 |
| `check:content-package-release:all` | 含 dev 通道 |
| `check:content-package-mirror` | 校验镜像源一致 |

**内容包 + 语义化版本 + 兼容区间**这套组合，等于给「插件提供的执行平台」和「跑在上面的业务资产」做了解耦与独立版本线。做类似平台的项目强烈建议照搬。

## 帮助文档生成

```
build:help-docs = tsx scripts/build-help-docs.ts
check:help-docs = tsx scripts/build-help-docs.ts --check
```

`site/docs/`（Docusaurus 源，56 页）→ 渲染为 `addon/content/help-docs/`（离线 HTML，插件内 `help-center` 使用）。

⚠ **渲染不是现成库**：`scripts/build-help-docs.ts` 只 import 了 `fs/promises` / `path` / `url` / `prettier` / `sharp` 五个包，自己实现了 `stripFrontmatter` / `extractTitle` / `convertAdmonitions` 等转换逻辑，并用 **`sharp` 处理图片**（而不是 canvas 之类）。`marked` 是**运行时**依赖，供 `src/modules/dashboard/dashboardSnapshot.ts` 动态 `import()` 用于 Dashboard 内渲染 Markdown，与此无关。

`--check` 模式用于 CI：源改了但没重新生成，CI 就失败。这是"生成物必须同步"的典型防漂移手段。

同理，`addon/content/host-bridge-skills/` 是从 `skills_src/` 构建出来的 skill bundle，由 `check:zotero-library-agent-bundle` 等脚本保证一致。

## 发布治理

### Rust 预编译二进制

`build:local:zotero-bridge-cli` = `node scripts/host-bridge/build-zotero-bridge-cli.mjs`。产物落 `addon/bin/<platform>/`（实测 7 个目标目录：`win32-x64`、`darwin-x64`、`darwin-arm64`、`linux-x64`、`linux-x86`、`linux-arm64`、`linux-arm`），同时生成 `addon/bin/zotero-bridge-release.json`（23 项输入的 build fingerprint）。`check:host-bridge-cli-prebuild-freshness` 校验预编译产物没落后于源码。

`releases/` 目录存的是「受治理的发布身份与 receipt」——每次发布留一份可审计的发布凭据，而不是只打 tag。

### Host Bridge 文档镜像

`check:host-bridge-review-mirror` 校验 `artifacts/host-bridge-review/` 的镜像一致，`render-host-bridge-surfaces.ts --check` 校验 Host Bridge 能力面文档与代码一致。

### Gitee 镜像

项目同步到 Gitee，脚本里有对应的 mirror 校验。涉及发布镜像同步的步骤在 AGENTS.md 有硬约束。

## Release 裁剪：debug 代码必须归零

`scripts/runtime-diagnostics-production-manifest.ts` 是构建期 SSOT，列出：

- debug-exclusive 模块清单
- 每个模块的副作用分类
- 禁止执行标记
- 窄口径的 Dashboard / locale / type 白名单

`check:runtime-diagnostics-release-elision` 的做法值得强调：**它编译真实的插件入口，要求每个 exclusive input 在 release 产物中贡献 0 字节**，而不是比较源码里的开关值（源码相等只作辅助断言）。

这是验证"死代码真的没进包"的唯一可靠方式。

## `.invariants.yaml`：唯一自动化的 SSOT 检查

`docs/components/` 下**只有 3 个** `*.invariants.yaml`，全部属 skillrunner 子系统：

- `skillrunner-provider-state-machine-ssot.invariants.yaml`（330 行）
- `skillrunner-provider-global-run-workspace-tabs-ssot.invariants.yaml`
- `skillrunner-run-lifecycle-ssot.invariants.yaml`

`check:ssot-invariants` 跑 `scripts/check-skillrunner-ssot-invariants.ts`（336 行），做四类校验：

1. **形状** — 8 个必需字段都在；`code_refs` / `doc_refs` / `spec_refs` 必须是非空数组
2. **引用** — 被引用的 md 文件必须真实存在且**正文包含该 invariant id**（否则报 `[ref-missing-id]` / `[ref-missing-file]`）
3. **解析** — 按 `.` 分段解析 `SKILLRUNNER_SSOT_FACTS.…`；任一 `code_ref` 解析不到即 `[code-ref]` 失败
4. **事实比对** — `current_value` 与代码事实**深比较相等**，不一致报 `[fact-mismatch] expected=… actual=…`

不变量示例：

```yaml
- id: INV-SR-RUNKEY-LOCAL-SSOT
  type: identity
  current_value: {localIdentity: runKey, backendCorrelation: requestId}
  must: runKey MUST 在后端请求创建前分配并全程稳定
```

⚠ **这个机制当前只覆盖 skillrunner 子系统，尚未覆盖 workflow 域。** 判断"某条 SSOT 是否有机器校验"时必须实际查这个目录，不能假设有。

## 本地化治理

`check:localization-governance` 校验 11 种语言的 `.ftl`：

- key parity（各语言 key 集合一致）
- base locale 一致性
- ownership matrix（哪些模块拥有哪一片 key 空间）

**ownership matrix 是关键**：它让"这个 key 该在哪个文件里"成为可检查的事实，而不是靠 review 时的自觉。

## 测试与治理的分工

值得单独强调的一点：这个项目把**架构约束**和**行为正确性**分开治理。

| 关注点 | 手段 | 例子 |
| --- | --- | --- |
| 行为正确 | mocha 测试，330 个 | provider 适配、状态机转换 |
| 资产完整 | 闭包校验 | `check:builtin-workflow-manifest` |
| 架构边界 | 依赖禁令 | ESLint `no-restricted-imports` |
| 契约一致 | 深比较 | `check:ssot-invariants`、surface parity |
| 文档同步 | 生成物新鲜度 | `check:help-docs`、`check:host-bridge-content` |
| 发布裁剪 | 字节归零 | `check:runtime-diagnostics-release-elision` |

大多数项目只有第一行。这个项目把剩下的五行也机器化了。

## 对 Scholoom 的启示

按性价比排序：

1. **PR / release 两档 CI gate**。同一脚本不同档位，本地跑宽松档，发布前跑严格档。
2. **资产闭包校验**。「磁盘文件 == 清单」双向检查，5 行脚本，能挡住"漏发一个文件"这类必现 bug。
3. **生成物 `--check` 模式**。任何从源生成的产物，CI 都验一次新鲜度。
4. **按域分片测试**。测试多了之后，串行跑不动这件事会立刻发生。
5. **发布裁剪验字节**。「debug 代码没进包」不能靠看源码，要编译真实入口验 0 字节。
6. **内容包与插件版本解耦**。如果有"平台 + 业务资产"两层，这里是最容易被忽略但收益最大的一层。
