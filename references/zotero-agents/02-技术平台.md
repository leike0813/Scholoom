# 02 技术平台

## 宿主平台：Zotero（Gecko 沙箱）

这是理解整个项目最关键的前提。**Zotero 桌面端不是 Electron，也不是 Node 环境**，它是一个 Gecko 沙箱里的 WebExtension 宿主。

| 项 | 值 |
| --- | --- |
| 最低 Zotero 版本 | 7.0.32 |
| 支持范围 | Zotero 7 / 9 / 10 |
| Node 要求 | ≥ 24（仅用于构建与测试，不进入插件运行时） |
| 插件清单 | `addon/manifest.json` |

`addon/manifest.json` 用 Firefox 扩展的 `applications.gecko` 结构声明宿主，`strict_min_version: "115.0"`（Gecko 115 是 Zotero 7 的基线）。三个 Zotero 分支的差异（9/10 引入了新偏好系统与更新后的 item API）由 `references/Zotero-7|9|10` 三个 submodule 固定版本作为对照基线。

### 沙箱里没有的东西

`AGENTS.md` 用最重的措辞强调过：

> **切勿将 Node.js 环境中才能使用的代码用于插件环境。**

具体缺失的能力与替代方案：

| 你想用 | 插件里没有 | 替代 |
| --- | --- | --- |
| `fs` | ✗ | `IOUtils` / `OS.File` / `Zotero.File.getContentsAsync` |
| `child_process` | ✗ | 预编译二进制 + `nsIProcess` / `Components` / 平台抽象层 |
| `path` | ✗ | `src/utils/path.ts`（自实现） |
| `process.env` | ✗ | `Services.env.get()`（平台抽象层封一层） |
| `Buffer` | ✗ | 编码为 `TextEncoder` / `btoa` / `atob` |

## `src/platform/`：手写的最小可移植层

因为上述原因，平台能力被抽象成四个适配模块，TypeScript 与工作流包都只能经它们访问宿主：

| 模块 | 职责 |
| --- | --- |
| `platform/command.ts` | 命令执行：优先 spawn 能力，回退进程组件 |
| `platform/env.ts` | 环境变量：`globalThis.process.env` → `Services.env.get` |
| `platform/path.ts` | 路径拼接/规范化/分隔符 |
| `platform/subprocess.ts` | 子进程生命周期与流 |

`platform/env.ts` 里有一个值得学的细节：`readEnvValue()` 两侧都读，且对 `Services` 整体做 try/catch。**允许一个受控的 Node 兼容分支，但要求它在目标环境不存在时静默降级**，这样同一份代码在构建环境（Node）与运行环境（Gecko）下都能加载。

JSX 用 **automatic runtime**（7 处 `jsx: "automatic"` + `jsxImportSource: "preact"`），**不是 htm**。

三个共性选项：

```ts
bundle: true,
minifySyntax: true,     // 只压语法，不压变量名 —— 调试时仍能读栈
target: "firefox115",   // 与 manifest 的 strict_min_version 对齐
plugins: [runtimeDiagnosticsSideEffectsPlugin],
```

`minifySyntax` 而非全量 minify 是刻意的：**发布包里保留可读符号，崩溃栈才有排查价值。**

## 四份 tsconfig：按 bundle 边界切分

这是本项目工程上最实用的一个设计。

| tsconfig | 覆盖范围 | 特点 |
| --- | --- | --- |
| `tsconfig.json` | `src`（除三块页面区） | 主体，含 `noEmit` 类型检查 |
| `tsconfig.dashboard.json` | `src/dashboard` | `noEmit: true`，产出 `tsconfig.dashboard.tsbuildinfo` |
| `tsconfig.sidebar.json` | `src/sidebar` | 同上 |
| `tsconfig.synthesis.json` | `src/synthesis` | 同上 |

**三块页面区各有独立的 tsconfig 与 tsbuildinfo**，原因是它们必须能被独立打包成单个 bundle，并且各自受 ESLint 的 `no-restricted-imports` 约束（只允许同目录相对路径 + `src/shared/**` + Preact 入口）。**把类型检查边界和打包边界对齐**，是最容易做到的一条纪律。

## npm workspaces：`packages/`

Synthesis 域的类型共享层，四个包**单向分层**：

```
synthesis-application   → 依赖 repository / engine / contracts
synthesis-repository   → 依赖 engine / contracts
synthesis-engine       → 依赖 contracts
synthesis-contracts    → 无内部依赖（叶子）
```

| 包 | 职责 |
| --- | --- |
| `synthesis-contracts` | 纯类型与常量：canonical JSON 规则、sidecar wire 协议、错误码、契约 schema |
| `synthesis-engine` | 纯计算：引用匹配、引用图、概念/主题图算法 |
| `synthesis-repository` | 存储抽象：定义 Repository 端口与实现 |
| `synthesis-application` | 用例编排：把 engine + repository 组装成应用服务 |

**这四层正是 Ports & Adapters 的标准切法**，而且 TypeScript 侧与 Rust 侧使用同一份 `synthesis-contracts` 作为契约来源。详见 [08-Synthesis领域与侧车.md](08-Synthesis领域与侧车.md)。

## Rust 侧车

`rust/` 是一个独立 Cargo workspace，三个 crate：

| crate | 定位 | 依赖特征 |
| --- | --- | --- |
| `zotero-bridge` | 独立 CLI 二进制，给 agent 提供 **133 个子命令**访问 Zotero | serde / serde_json / clap 类 |
| `acp-ws-bridge` | 本地 WebSocket ↔ 子进程 stdio 中继 | **仅 4 个依赖**：`base64`、`serde`、`serde_json`、`sha1`，**无 tokio / hyper / tungstenite**，RFC6455 手写 |
| `synthesis-sidecar` | 知识综合领域的全部生产实现 | tokio / axum / rusqlite 等 |

`acp-ws-bridge` 的极简依赖是刻意的：它是每次 ACP 会话都要拉起的常驻小进程，**依赖越少，冷启动越快、崩溃面越小**。

### 工具链固定

`package.json` scripts 里出现 `cargo +nightly-2026-07-25`，说明 Rust 侧锁定了一个具体 nightly 工具链，以保证 7 平台预编译二进制可复现。构建脚本负责跨平台交叉编译并把二进制落到 `addon/bin/<platform>/`（实测 7 个目录：`win32-x64`、`darwin-x64`、`darwin-arm64`、`linux-x64`、`linux-x86`、`linux-arm64`、`linux-arm`），同时生成 `addon/bin/zotero-bridge-release.json`（含 23 项输入的 build fingerprint）。

### 谁负责启动

Synthesis sidecar 由插件**监督启动**（supervision）：插件负责发现端口、探活、崩溃重启与回收。Rust 侧用 discovery 文件 + 原子发布（写临时文件后 rename）避免竞态。详见 08 篇。

## 与 Node 生态的边界管理

三条硬机制共同保证「Node 代码不会漏进插件」：

1. **ESLint `no-restricted-imports`**：对 dashboard / sidebar / synthesis 三块页面区各配一条规则，消息形如 `Sidebar page bundles may only import same-directory relative paths, src/shared/** modules, or Preact entry points.`
2. **runtime 持久化 SSOT**：`runtimePersistence.ts` 是跨运行时 fs adapter 的唯一事实源，其余模块禁止自行选 `IOUtils` / `OS.File` / Node `fs` / Components stream
3. **晚绑定**：`AGENTS.md` 明确要求 runtime adapter 按调用晚绑定，禁止因缓存 projection 而缓存运行时 global、picker window 或 fs adapter

第 3 条的理由很实际：Zotero 的某些全局对象在插件启动早期还不可用，缓存早了会拿到空引用。

## 主题

README 称 Markdown Reader 会自动跟随 Zotero 的明暗主题。Zotero 7/9/10 都没有稳定的 `prefers-color-scheme` 传递，因此实现方式是在 `addon/content/shared/` 下用 CSS 变量配合宿主注入的 theme 属性，同时用 `@media (prefers-color-scheme)` 做兜底。`AGENTS.md` 对共享样式有明确约束（`custom-select.css` 是三个 HTML 页面共享的唯一外部样式表，带 `?ui=…` cache-buster）。

## 运行环境小结

| 层 | 运行环境 | 能用什么 |
| --- | --- | --- |
| 插件外壳与工作流执行 | Zotero Gecko 沙箱 | `IOUtils` / `OS.File` / `Components` / Preact / XUL |
| Agent 后端运行时 | 同上 + 外部进程 | 上述 + 子进程 stdio |
| 宿主 CLI | 独立原生进程（`zotero-bridge`） | 完整文件系统与网络 |
| Synthesis sidecar | 独立原生进程 | 完整能力 |
| 构建/测试/文档生成 | Node 24 | 完整 Node 生态 |

**这五层的能力边界是逐级放大的**。任何一层想访问更下一层的能力，都必须走显式的跨边界契约（wire contract / bridge protocol），不能直接调用。
