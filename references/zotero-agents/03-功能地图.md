# 03 功能地图

## 官方定位

README 的原话：

> Zotero Agents is an all-in-one agentic workbench for your Zotero library. 从把 PDF 加进文献库，到三小时后的研究综述，中间每一步都有对应的工作流。

关键差异化的自我陈述：

> 市面上的 Zotero AI 插件大多是聊天框，你可以问它问题；我们把它做成了工作流和产物系统——你可以设定它做什么，用什么方式做，做到什么程度，然后拿回可以审计的结果。

一句话概括产品观：**不是「问 AI」，而是「设定 Agent 按流程做事，拿回可审计的产物」**。

官方给出的差异化维度（README「What makes this different」）：

| 维度 | 官方表述 |
| --- | --- |
| 产物优先 | 分析结果不是聊天记录，而是**可继续编辑的笔记与可追溯的结构化产物** |
| 前沿模型自由 | 不绑定单一服务商，同时支持**需要订阅的 Agent CLI** 与**自带 key 的 HTTP 模型** |
| 任务生命周期完整 | 完整覆盖「取 PDF → 读全文 → 引用 → 改库 → 查错 → 报告」，而非「问一句答一句」 |
| 逻辑与记录分离 | 托管笔记承载推理过程，可编辑笔记只放最终结果与回链 |
| 自带后端观测 | 后端状态、失败原因、重试、运行日志面板化 |
| 声明式工作流 | 可插拔工作流包用 JSON 声明，**插件不写死业务** |
| 可审计 | 每次运行留下 request/result/audit 记录 |

## 四大子系统

官方架构文档把产品拆成四块（`docs/architecture-flow.md`）：

```
Assistant Sidebar ──  ACP / Skill-Runner ──  AI Engines
        │                                        │
        ├── Workflow Catalog ── Workflow Runtime ─┘
        │                    ↓
        │              Zotero Native (broker)
        ↓
Synthesis Workbench
```

### 1. Pluggable Workflows（可插拔工作流）

声明式工作流包，定义「做什么」。详见 [06-工作流引擎与执行.md](06-工作流引擎与执行.md)。

### 2. Assistant Sidebar（助手侧边栏）

Zotero 右侧的常驻侧边栏，提供三个面板：

- **ACP Chat**：与 Agent CLI 的多轮对话
- **ACP Skill Run**：单次技能执行的详细视图
- **Skill Runner**：本地 skill 执行面板

### 3. Synthesis Workbench（综合工作台）

一个独立 tab，8 个 Surface 的知识探索界面。详见 [08-Synthesis领域与侧车.md](08-Synthesis领域与侧车.md)。

### 4. Host Bridge（宿主桥）

让外部 agent CLI 安全访问 Zotero 的三层出口：HTTP server / MCP server / CLI 二进制。详见 [10-宿主能力与Bridge.md](10-宿主能力与Bridge.md)。

## 核心工作流

官方在 README 的「Official Workflows」章节列出 5 个（来自 `literature-workbench-package`），另有 3 个内置工作流包。

### 文献分析工作流（最复杂）

| 子工作流 | 产出笔记类型 | 说明 |
| --- | --- | --- |
| **Literature Analysis** | `analysis` | 读全文 PDF，生成 12 维度的结构化分析：研究问题、背景、方法、样本、指标设计、结果、假设、证据质量、局限、启发、后续验证方向、参考规范 |
| **Search & Ingest** | `search` | 联网检索（OpenAlex / Crossref / Semantic Scholar / Europe PMC）→ 按四维打分（时效性 1–5、期刊质量 1–5、作者声望 1–5、主题契合 0–100）计算综合分 → 决定「入库 / 跳过 / 待定」→ 入库后自动打标签 |
| **Tag Normalization** | — | 把散乱的 `#tag` 归一到受控词表，带同义词映射（`ML` / `机器学习` / `machine learning` → 同一概念），并维护多对多的 tag-article 关系 |
| **Deep Reading** | `reading` | 对**已有笔记**继续追问：追问任意概念、对比任意方法、输出 TL;DR 卡片，产出阅读轨迹（`traces`） |
| **Topic Synthesis** | `synthesis` | 把库中相关论文聚成主题综述，产出可导出的报告 |

**注意这五个子工作流的产���全是 Zotero 原生笔记（HTML + Zotero 的引用键）。** 这不是"生成一个 markdown 文件"，而是走 Zotero 原生 API 写入规范笔记——用户能直接用 Zotero 的全文搜索、相关项、标签、双栏阅读器消费这些结果。

### 其它内置工作流包

| 包 | 作用 |
| --- | --- |
| `synthesis-layer` | Synthesis 知识综合域的前端工作流 |
| `mineru` | 接入 MinerU 做 PDF 版面解析 / 文档结构识别（`mineru-document-analysis`） |
| `workflow-debug-probe` | 调试探针，13 个探针用于验证执行链、apply 合约、Host Bridge 连通性 |

`workflows_builtin/manifest.json` 是内置工作流包的清单，`{version, files[]}` 结构，由 `npm run check:builtin-workflow-manifest` 做**资产闭包校验**（磁盘文件与清单双向相等）。

## AI 引擎与计费

README「AI Engines & Costs」章节的关键点。

### 两种模式

| 模式 | 说明 | 计费 |
| --- | --- | --- |
| **ACP Agent CLI** | 连接 Codex、OpenCode、Claude Code、Gemini CLI、Qwen Code 等本地 agent CLI | **走你已有的订阅**，插件不额外计费 |
| **Generic HTTP** | 直连你自己的模型 API | **按你自己的 key 计费** |

⚠ 注意：ACP 后端是**本地 agent CLI 的协议客户端**，不是云端 API。它通过 stdio 启动 `codex mcp`、`opencode`、`claude` 等进程，用 Agent Client Protocol 与之通信。详见 [07-Agent后端与运行时.md](07-Agent后端与运行时.md)。

### 四类后端

| 后端 | 定位 | 适用 |
| --- | --- | --- |
| **ACP** | 通用 agent CLI 协议 | Codex / Claude Code / Gemini CLI / Qwen Code / OpenCode |
| **Skill-Runner** | 本地 skill 执行器 | 确定性流程、需要工作区复用的批量任务 |
| **Generic HTTP** | 自带 key 的模型直连 | 只要一次文本生成、不需要 agent 循环 |
| **Pass-Through** | 不经过插件 | 手工测试、复用外部产物 |

**选型建议（README 表述）**：只是想快速试一下 → 配一个 Generic HTTP provider；要真正的 agent 能力 → 接一个 ACP CLI；要批量、可复现的流水线 → Skill-Runner。

## 产物如何落回 Zotero

这是整个产品最见功力的地方。四类产物：

| 产物 | 写入方式 | 特点 |
| --- | --- | --- |
| **笔记（notes）** | Zotero 原生笔记 API，写 HTML + Zotero 引用键 | 用户能全文搜索、能被「查找文献」搜到 |
| **标签（tags）** | `statusTags` 能力 | 状态标签（`needs-review` / `reusable` / `canonical`）与主题标签分工 |
| **附件（attachments）** | MinerU 等产出物作为附件保存 | HTML 精读文档、图片、快照 |
| **结构化 artifact** | 渲染自后端数据的 HTML | **不是笔记正文** |

### 最后一条最关键

**分析产物不是笔记正文，而是渲染自后端数据的 HTML。** 这条边界解决了一个真实痛点：AI 生成的文本一旦写进笔记正文，用户就无法再编辑、无法增量更新、无法跨字段检索。这个项目选择把结构化数据存后端，HTML 只是投影。

配套的还有「托管笔记」概念：推理过程放托管笔记（用户可只读查看），可编辑笔记只放最终结果与回链。README 称之为 **logic and record separation（逻辑与记录分离）**。

## Dashboard 承载的功能

Dashboard 是插件的主控制台，包含：

- **任务队列与历史**：正在跑什么、跑过什么、失败原因、重试
- **产物浏览**：每份分析产物的结构化视图
- **运行日志**：分级过滤、诊断包导出（见 07 篇）
- **Skill 反馈面板**：向 Agent 提供上一轮的纠正信息
- **Backend Manager**：后端配置、连通性诊断、预设
- **Workflow Settings**：工作流的参数、触发方式、后端绑定
- **Synthesis sidecar 面板**：sidecar 生命周期与状态
- **Trace & Replay**（仅 debug 构建）：ACP 语义 trace 录制与回放性能剖析

## 一条贯穿全局的设计模式

读完功能层，最值得抽出来的是这个模式，它在多个地方重复出现：

1. **产物与源材料分离** — 分析结果不写进源 PDF 或原笔记
2. **派生知识与结构化数据分离** — HTML 是投影，数据是事实源
3. **推理过程与最终结果分离** — 托管笔记 vs 可编辑笔记
4. **状态与内容分离** — job 状态是投影，事实源在后端
5. **本地数据与附件分离** — WebDAV 同步只同步结构化知识，不碰附件（同步快、不冲突、不撞存储配额）

这五条合起来指向同一个观点：**在 AI 参与的系统里，"什么是事实源"必须先被回答，否则 AI 生成的文本会不可逆地污染用户的原始记录。** 这是这个项目区别于「聊天框 + 总结」类插件的根本原因。

## 对 Scholoom 的启示

抽掉 Zotero 特有的部分后，有 6 条是文献智能体工具的通用范式：

1. **工作流是声明式资产，不是代码**。产品作者能通过 JSON 组合出新能力而不改插件，这个杠杆非常大。
2. **Agent 写入必须经审批**。写前无副作用预检 → 等待审批 → 重新准备 → 摘要变化需重新审批，这四步是任何「LLM 改用户数据」场景的底线。
3. **分析产物是投影不是正文**。这条决定了产品能不能持续演进。
4. **支持三种「有订阅就用」的接入方式**。用户已有 Claude Code / Codex 订阅时，让插件去复用它，比要求用户再买 API key 友好得多。
5. **失败可诊断**。任务面板、运行日志、诊断包、debug 探针、状态文件——把"用不了"变成"看得见为什么用不了"，是这类插件的核心竞争力。
6. **多工作流共享同一批底座能力**（Host Bridge、canonical JSON、SSOT 约束），新工作流的边际成本才能降下来。

反过来，Zotero 特有的、Scholoom 不必照搬的部分：Zotero 9/10 三分支兼容、Gecko 沙箱无 Node 的适配层、`.ftl` 本地化、Fluent 生态、XUL 菜单与 toolbar 集成。
