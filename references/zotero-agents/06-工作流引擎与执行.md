# 06 工作流引擎与执行

这一篇是 zotero-agents 最值得借鉴的部分。核心命题：**把「AI 怎么调用、结果怎么落库、权限怎么管」做成固定外壳，把「做什么」全部推给可插拔的声明式工作流包。**

## 设计出发点

`AGENTS.md` 的原话：

> 插件采用模块化、工作流可插拔的设计理念。插件本体提供通用的 UI 界面及菜单。内部通过统一的工作流协议，由各组件分别按流程执行任务。插件本身不包含任何具体的业务逻辑。业务逻辑由用户通过"可插拔"的工作流文件或工作流包来声明和定义。

README 补上了另一半：**插件是 execution shell，声明「做什么」，插件负责「怎么执行」**。这两句话合起来定义了整个引擎的职责边界。

## 两层 manifest

这是最容易搞混的地方，必须区分。

### ① 包级 `workflow-package.json`（4 个字段）

```json
{
  "id": "zotero-agents.workflows.mineru",
  "version": "1.0.0",
  "workflows": ["mineru-document-analysis"],
  "i18n": { "defaultLocale": "en-US", "locales": { "zh-CN": "locale/zh-CN/..." } }
}
```

schema 声明 `additionalProperties: false`，required 仅 `id` / `version` / `workflows`。

### ② 工作流级 `workflow.json`（能力声明主体）

实测字段全集：

| 字段 | 含义 |
| --- | --- |
| `id` / `version` / `label` / `description` | 身份与展示 |
| `hooks` | 对象，键为 hook 名（`preflight` / `buildRequest` / `applyResult`），值为路径或对象形式 |
| `inputs` | 选区输入源 |
| `parameters` | JSON-Schema 式对象，键上 `required: true` 决定必填项 |
| `validateSelection` | **声明式**输入校验（README 记载它取代了命令式 `filterInputs`） |
| `trigger` | `requiresSelection`（默认 `true`） |
| `provider` | 后端类型 |
| `request.kind` | 请求形状描述，如 `skillrunner.sequence.v1` |
| `executionModes` | `["auto","interactive"]` 等 |
| `supportedInvocationModes` | `["interactive","non-interactive"]` |
| `resourceRequirements[]` | `accept.contentTypes` / `accept.extensions` |
| `result` | `fetch.type`（`bundle` / `result`）、`expects.result_json`、`expects.artifacts[]` |
| `debug_only` | 调试可见性 |
| `i18n` | 本地化 |

### manifest 纯投影（`manifestContract.ts`）

`manifestContract.ts` 把 manifest 一次性归一化成 `WorkflowManifestContract`，下游全部读投影而非原始 manifest：

```ts
executionModes: [...(manifest.executionModes || ["auto"])],
supportedInvocationModes: [...(manifest.supportedInvocationModes || ["interactive","non-interactive"])],
requiredWorkflowOptions: Object.entries(manifest.parameters || {})
  .filter(([, s]) => s.required === true).map(([k]) => k),
resultEvidence: { ..., applyBack: Boolean(manifest.hooks?.applyResult) },
selection: { acceptsNoSelection: manifest.trigger.requiresSelection === false, ... }
```

**一处归一、多处消费**，default 判断不散落各处。同时注意这里有个刻意的双层设计：**JSON Schema 侧严格（`minItems`/`required`），TS 侧温和默认（`||` 兜底）**。

## 包目录结构与发现机制

```
<package>/
  workflow-package.json     # 包 manifest
  <workflow-id>.json        # 或 workflow.json
  hooks/                    # 钩子模块（precompiled-host-hook 模式）
  lib/                      # 包内共享模块，相对导入
  locale/                   # i18n 词条，对应 i18n.locales 路径
  skills/                   # 随包 skill
```

`loader.ts` 有专门的 `normalizePackageRelativePath` 与 `parseLocaleMessageMap` 处理包内相对路径与 locale 映射。

### 四层目录与覆盖优先级

`workflowRuntime.ts` 按顺序加载，**后者覆盖前者**，冲突写入 `duplicateWarnings`：

| 优先级 | 目录 | 用途 |
| --- | --- | --- |
| 1（最低） | official | `<dataDir>/content/official/workflows`，已安装的官方内容包 |
| 2 | dev-local | `ZOTERO_AGENTS_CONTENT_DEV_ROOT` 或 `<dataDir>/content/dev-local`，再按 `workflows_builtin` → `workflows` 探测 |
| 3（最高） | user | 用户目录 |

三目录**并行**加载，最终按 `manifest.id` 排序。

### 版本兼容（npm semver range）

直接用 npm `semver` 的 range 语法，开 `includePrerelease`：

```ts
function isVersionSatisfied(actual: string, requirement: string) {
  if (!requirement) return true;
  const normalizedActual = normalizeVersion(actual);
  return semver.valid(normalizedActual)
    ? semver.satisfies(normalizedActual, requirement, { includePrerelease: true })
    : false;
}
```

三类 requirement 与失败码：

| 字段 | 校验对象 | 失败码 |
| --- | --- | --- |
| `requires.plugin`（`min_plugin_version` 回填为 `>=X`） | `pkg.version` | `plugin_version_unsupported` |
| `requires.content_api` | `CONTENT_API_VERSION` | `content_api_unsupported` |
| `requires.zotero` | Zotero 版本 | Zotero 版本不支持 |

`resolvePackageRequires` 做**旧字段向新字段的无损兜底**：`min_plugin_version` 仅在 `requires.plugin` 缺省时补 `>=X`。安装时对 `content_api` 与 `requires` 做 JSON 等值断言，不一致直接 throw。

## Host API：封闭的工作流表面

### `WorkflowHostApi` v12 实测统计

直接解析 `src/workflows/workflowHostContract.ts` 的 `WORKFLOW_HOST_API_MANIFEST` 字面量：

- **24 个顶层键** = `version` + `interactionMode` + **22 个能力模块**
- 22 个能力模块：`addon`、`environment`、`context`、`library`、`metadata`、`mutations`、`managedNotes`、`literatureArtifacts`、`notes`、`images`、`attachments`、`bibliography`、`researchBundles`、`statusTags`、`file`、`archive`、`resources`、`clipboard`、`editor`、`notifications`、`logging`、`synthesis`
- **92 个 callable**

⚠ **文档漂移**：`docs/components/workflows.md` 写 24/22/92（与代码一致）；`docs/components/workflow-hook-helpers.md` 写 25/23/96（**已过期**）。以代码与 `workflows.md` 为准。

### Contract Identity vs Contract Variant

- **Identity**（`workflowHostContract.ts` 持有）：版本号 + 顶层能力身份 + 诊断探针
- **Variant**：同一 Identity 下的交互形态投影

关键规则（引自 broker SSOT 文档）：

> Interactive and non-interactive variants have the **same complete shape**. Interaction-dependent members remain present and fail with `interaction_required` when invoked non-interactive.

即 **variant 只改 `interactionMode`，不改形状**。缺少必需能力或暴露未声明的顶层能力 → 不合规。生产诊断只报告"观察到的可用性"，**不因某能力未实现就整体拒绝 projection**。

这是一个值得学的取舍：**fail at call time, not at projection time**。能力缺失在调用点返回 `interaction_required` 这类结构化错误，而不是让整包不可用。

### 与 capability broker 的关系

`AGENTS.md` 的硬约束原文：

> `WorkflowHostApi` 必须通过 member-level `Pick` 和显式对象字面量投影 broker；不得传播整个 broker domain，不得使用 spread、proxy、运行时 capability catalog 或隐式成员继承。

broker SSOT 文档的核心原则：**"Adding a broker member does not implicitly expose it"**。

六层模型：

1. Zotero 原生 API = 原始宿主运行时
2. `ZoteroHostCapabilityBroker` = 进程内规范 broker，可移植能力语义的所有者
3. `WorkflowHostApi` v12 = 封闭工作流表面
4. Host Bridge v2 = 远程 locality / exposure / permission 适配
5. MCP = Host Bridge registry 的精确公开投影，复用其 handler
6. broker 私有 native mutation 原语 = 真正落地 Zotero 副作用

## Hook 加载与执行

### 三种执行模式

| 模式 | 含义 |
| --- | --- |
| `precompiled-host-hook` | **默认/生产**。hook 模块被打包成 JS 源码字符串，在受控作用域执行，只能触达 `runtime.hostApi` facade（capability source 为 `host-api-facade`） |
| `legacy-text-loader` | 旧版文本装载器（capability source 为 `legacy-hook-runtime`） |
| `host-hook` / bundled | `createHostHookScope()` + `summarizeHostHookScope()` 做导出白名单审计；`hasKnownHookExport()` 校验导出名 |

关键手法：`transformModuleExports()`（`loader.ts:92`）在**运行时改写**模块导出以适配宿主作用域，而不是静态 import。所有 hook 均为 `async`，由 `runSeam` 统一 await。

### Hook 实际收到什么

`createHookRuntimeContext()`（`runtime.ts:560-587`）构造的精确字段：

`hostApi`、`hostApiVersion`、`invocationMode`、`debugMode`、`workflowId`、`packageId`、`workflowRootDir`、`packageRootDir`、`workflowSourceKind`、`hookName`、`locale`、`signal`，以及 web globals：`fetch`、`Buffer`、`btoa`、`atob`、`TextEncoder`、`TextDecoder`、`FileReader`。

⚠ **文档漂移**：`docs/components/workflows.md` 的 Runtime Context 字段表仍列出 `handlers`、`helpers`、`zotero` 三项，与代码和 `workflow-hook-helpers.md`（明确写 "hooks no longer receive `runtime.helpers`"）都矛盾。**以 `runtime.ts` 为准**。`src/workflows/helpers.ts` 的 `createHookHelpers` 已属遗留。

### 执行作用域串行化

`withWorkflowExecutionRuntimeScope()`（`runtime.ts:520-558`）把 runtime 挂到 `globalThis[GLOBAL_WORKFLOW_EXECUTION_RUNTIME_KEY]`，并用 **Promise 尾链 `workflowRuntimeScopeTail` 串行化所有工作流执行**，`finally` 精确恢复 previous（含"原先不存在则 delete"的分支）。

这是在没有独立进程隔离的沙箱里防止并发 hook 污染全局的实用手法。

## 执行主链路

`docs/architecture-flow.md` 给出完整流程，配合 Mermaid 图理解最快：

```
User Trigger
  → Build SelectionContext
  → Input Filter（声明式 validateSelection + 可选 filterInputs）
  → 无合法单元则 Skip
  → 可选 preflight hook
       ├ skip            → 跳过当前单元
       ├ continue        → 保持当前单元
       ├ replace-units   → 展开为多个虚拟输入单元
       └ short-circuit-apply → 跳过 provider，直接进 applyResult
  → Build Requests（hooks.buildRequest 优先，否则声明式 request 编译）
  → Resolve Execution Context（backend profile / request kind / params / options）
  → Settings Gate（requireSettingsGate=true 且无 run-once override → 弹设置对话框）
  → Duplicate Guard（pending 相同请求检查，全重复则跳过）
  → JobQueue Enqueue（FIFO + provider 决定并发）
  → JobQueue Execute → Provider Execute
  → applyResult Hook
  → 写入 Zotero（note / tag / attachment）
```

### preflight–buildRequest–applyResult 三段式

导览给出的关键结论：

> 执行链固定为 preflight → buildRequest → applyResult 三类 hook：前两者只做无副作用的检查与请求构造，只有最后一步真正写宿主，**这是权限模型成立的前提**。

### 结果形态与聚合

Provider 返回 `ProviderExecutionResult`，形态为 `bundle`（含 `bundleBytes`）或 `result`（含 `resultJson`）。

若 preflight 声明 aggregate single-apply，child provider 结果先被收集，**不逐个**调用 `applyResult`；所有 child 成功后 runtime 构造 `resultContext.aggregate.children` 并只调用一次。**任一 child 失败则不做部分 apply**（无部分落库的中间态）。

### 恢复对账

- 正常单体与 sequence 结果由前台 poll/fetch/apply 完成
- Reconciler **只在**插件启动、后端恢复或显式 recovery context 中执行对账
- 前台 apply summary 不暴露 reconcile-owned pending 作业

### 失败路径

| 场景 | 处理 |
| --- | --- |
| 工作流加载失败 | 跳过该工作流，记录 warning |
| 输入筛选后无合法单元 | 跳过执行 |
| Provider 执行失败 | 任务标记 failed |
| `applyResult` 失败 | 任务标记 failed，进入汇总错误 |

## 任务队列与终态

`src/jobQueue/manager.ts` 的状态机比 `queued/running/completed/failed` 更细，含 `queued`、`waiting_user`、`failed_retriable` 等状态。

**Workflow Job Terminal Resolution**（`src/modules/workflowExecution/terminalResolution.ts`）是这一层的设计要点：把 hook 的多种终局信号（成功、需用户交互、取消、失败）收敛为**单一权威终态**。`docs/components/job-queue.md` 强调 job 状态是**投影**而非事实源，UI 只读，不参与状态判定。

配合 `runTailRegistry.ts`（运行尾队列）与 `cancel.ts`（取消信号）构成完整的取消/等待机制。

## 工作流设置与编辑器

- **编辑器宿主是 manifest 驱动的受限编辑器**：字段由 `parameters` / `resourceRequirements` / `executionModes` 决定，宿主只渲染 manifest 声明过的能力，不提供自由表单
- **设置对话框是独立 HTML 页面**（`workflowSettingsWebDialog.ts`），通过 `DialogHelper` 打开/关闭，DOM 事件回传，样式从 `addon/content/dashboard/workflow-settings-dialog.html` 加载
- **提交流有单一事实源**：一次提交只有一个 owner 负责合并 `options`/`parameters`/`selection`/运行参数，UI 组件不得各自拼装提交载荷

### 一处需要纠正的常见误解

`AGENTS.md` 把 `addon/content/components/` 注释为「可复用 Web 组件」，但**该目录只有一个文件 `custom-select.css`**。全仓库 `customElements.define` 与 `<zs-*>` 自定义标签在 `src/`、`addon/` 下均**零命中**。

**这个项目不使用 Web Components。** UI 技术栈是 **XUL（`createXULElement`）+ 手写 HTML/CSS + Preact 局部**。`custom-select.css` 是被三个 HTML 页面 `<link>` 的共享样式表，带 `?ui=...` cache-buster。

## 插件环境硬约束

`AGENTS.md` 写得很重：**「切勿将 Node.js 环境中才能使用的代码用于插件环境」**。落地机制有五处：

| 机制 | 证据 |
| --- | --- |
| runtime 持久化 SSOT | `runtimePersistence.ts` 是跨运行时 fs adapter 唯一事实源；`AGENTS.md` 禁止 Workflow Host / 输入物化 / 图片准备 / 附件导入自行选 `IOUtils` / `OS.File` / Node `fs` / Components stream |
| 晚绑定 | `AGENTS.md`：runtime adapter 按调用晚绑定，禁止因 `createWorkflowHostApi()` 缓存 projection 而缓存运行时 global、picker window、fs adapter |
| **bundle 边界（ESLint 强制）** | `eslint.config.mjs` 中 4 处 `no-restricted-imports`（sidebar / dashboard / synthesis workbench / …），消息形如 "Sidebar page bundles may only import same-directory relative paths, src/shared/** modules, or Preact entry points."。**这就是依赖白名单** |
| Node 检测 | `loader.ts` 的 `isZoteroRuntime()` 在 hook 加载前探测宿主环境 |
| 环境变量（唯一例外） | `workflowRuntime.ts` 的 `readEnvValue()` 同时读 `globalThis.process.env` 与 `Services.env.get`，且对 `Services` 做 try/catch |

最后一条很值得学：**允许一个受控例外，但要求它容忍目标不存在**。

## SSOT 机制的三种形态

必须区分清楚，否则会写错。

| 形态 | 文件 | 含义 | 检查方式 |
| --- | --- | --- | --- |
| ① `*_ssot.md` | `docs/components/*-ssot.md` | **人类可读的架构 SSOT 文档**，给出不可协商的分层规则 | 无自动检查，靠 review |
| ② `*_ssot.invariants.yaml` | `docs/components/` 下**仅 3 个**，全部属 skillrunner 子系统 | **机器可读的不变量表**（`[inv.` 前缀断言） | `scripts/check-skillrunner-ssot-invariants.ts`（`npm run check:ssot-invariants`）；测试侧用 `--grep "\[inv\."` 只跑不变量用例 |
| ③ 代码级 SSOT | `workflowHostContract.ts`、`manifestContract.ts`、`runtimePersistence.ts` | 唯一所有者模块 | 编译期 + `no-restricted-imports` |

⚠ **重要澄清**：`.invariants.yaml` **不是**工作流引擎的机制，而是 skillrunner 子系统的专属机制，**当前尚未覆盖 workflow 域**。

## 其他值得借鉴的工程手法

1. **资产闭包检查**。`npm run check:builtin-workflow-manifest` 递归收集 `workflows_builtin/` 全部文件，验证 `manifest.json` 的 `{version, files[]}` 与磁盘真实文件**双向相等**——多一个少一个都报错。存在 `UNSHIPPED_BUILTIN_PATH_PREFIXES` 白名单作为豁免。这是"资产不得漏发"的强约束。
2. **注册表状态外化为可诊断文件**。`workflow-registry-status.json`（`schema_id: zotero-skills.workflow_registry_status`）落盘记录各层目录加载数与逐工作流摘要。排查"为什么我的工作流没出现"极其有效。
3. **内容寻址的选区游标**。opaque cursor 绑定"有序选区 ref 摘要 + after-index"，basis 变化时以 `conflict.details.reason = basis_mismatch` 失败——干净的乐观并发控制。
4. **按工作流分包测试**。`tests/workflow-literature-analysis/`、`tests/workflow-mineru/`、`tests/workflow-tag-regulator/`，配负向夹具 `workflow-loader-invalid-json`、`workflow-loader-missing-apply`、`workflow-loader-missing-required-fields`。分片脚本 `scripts/run-node-test-shards.ts --domain workflow`。
5. **调试探针内置**。`workflow-debug-probe` 是随包分发的正式工作流，含 13 个探针，用来验证 sequence 执行、apply 合约、Host Bridge 连通性等。

## 对 Scholoom 的启示

如果要做一个同类系统，下面四点按优先级排序：

1. **manifest 纯投影层不可省**。散落的 `|| 默认值` 会让下游每个消费点都要重复判断，投影一次是最低成本的一致性保障。
2. **preflight 无副作用、applyResult 才落库**。这条三段式不只为了权限，也是为了让"重试"和"聚合"成为可能。
3. **能力面用显式 Pick 投影，不用 spread/proxy**。否则"新增一个 broker 成员就意外暴露出去"几乎必然发生。
4. **注册表与资产闭包要可诊断**。用户装了个包但工作流没出现，是这类系统最高频的支持问题，值得为此专门落一个状态文件。
