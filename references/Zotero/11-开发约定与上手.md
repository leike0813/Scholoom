# 11 开发约定与上手

## 一、代码风格

`CLAUDE.md` 的规定，逐条对照：

| 项 | 约定 |
| --- | --- |
| 缩进 | Tab，不用空格 |
| 变量声明 | 用 `let` 代替 `const`，除真正的标量常量（如 `const MAX_SECONDS = 5 * 60;`） |
| 括号 | 不 cuddled braces——开括号同行，但 `else` / `catch` / `etc.` 各自另起一行 |
| 注释 | 用两个连字符 `--`，不用 em dash |
| 空行 | 缩进到与周围代码相同的层级 |
| 模块化 | 对象挂到全局 `Zotero` 命名空间，而不是用 ES module 导出 |
| 异步 | 全程 `async` / `await` |
| 平台 API | `Cc`、`Ci`、`Cu`、`Cr`、`Services`、`ChromeUtils`、`IOUtils`、`PathUtils` 作为全局可用 |

**「挂全局而不是 ESM 导出」是这套风格的地基**，它和 `zotero.mjs` 的 `loadSubScript` 载入顺序、`CLAUDE.md` 里「模块在全局 Zotero 命名空间上挂载」的说法是同一件事。理解这一点才不会写出「这里为什么没有 import」的困惑。

## 二、命令速查

```bash
npm install            # 安装依赖
npm run build          # 完整构建（Babel 转译 + SCSS + Browserify + symlink）
npm run clean-build    # 清理后重建
npm start              # 构建并进入 watch 模式

test/runtests.sh                   # 全部测试
test/runtests.sh item              # 单个文件（省略 Test 后缀与 .js）
test/runtests.sh item collections  # 多个文件
test/runtests.sh -g "pattern"      # 按模式过滤
test/runtests.sh -f                # 首次失败即停（推荐默认加）
test/runtests.sh -s item -e item   # 指定起止文件
test/runtests.sh -c                # 完成后打开 JS 控制台
test/runtests.sh -b                # 跳过内置 translator/style 安装
test/runtests.sh -d 5              # 调试日志级别 1–5（默认 3）

npx eslint <file>      # Lint 单个文件
```

## 三、常见任务的入口

| 想做的事 | 从哪看起 |
| --- | --- |
| 加一个新的核心模块 | `zotero.mjs` 决定载入位置 → 在 `xpcom/` 建文件 → 挂到 `Zotero` 命名空间 |
| 加一条 UI | `elements/` 建自定义元素 → `customElements.js` 注册懒加载回调 → `scss/elements/` 加样式 |
| 改条目字段 | `data/itemFields.js` + `resource/schema/userdata.sql` + `itemTypeFields` 元数据表 |
| 加一条搜索条件 | `data/searchConditions.js` 注册条件与操作符 |
| 改同步行为 | `sync/syncRunner.js`（调度）/ `sync/syncEngine.js`（对象级）/ `syncLocal.js`（合并） |
| 加一个插件扩展点 | `xpcom/pluginAPI/` 继承 `PluginAPIBase`，参考 `itemPaneManager` / `itemTreeManager` / `menuManager` |
| 加一个本地 API 端点 | `xpcom/server/` 注册到 `Zotero.Server.Endpoints`，参数解析参考 `xpcom/api.js` |
| 加一个翻译器 | **用 Scaffold**（`chrome/content/scaffold/`），不手写 |
| 加界面字符串 | 加到 `.ftl`（`chrome/locale/en-US/zotero/`），**不要**写进 `.properties` 或 `.dtd` |
| 加一个平台特化样式 | `scss/{mac,win,linux}/` 覆盖，或 `chrome/content/zotero-platform/` 纯 CSS；别在组件样式里写平台 if |
| 改构建行为 | `js-build/config.js`（唯一事实源），再改对应任务脚本 |

## 四、容易踩的坑

1. **改源码看不到效果**。应用读的是 `build/` 下的产物，不是源码。先确认构建跑过。
2. **找不到模块的 import**。不是漏写，`loadSubScript` 注入同一全局对象是正常形态。要看依赖关系得看 `zotero.mjs` 的载入顺序。
3. **绕过 `saveTx()` 写数据库**。会跳过脏值追踪、撤销记录和 Notifier 事件，UI 不刷新、自动同步不触发。
4. **新字符串加进 `.properties`**。明确禁止，只能进 `.ftl`。
5. **手写 translator 或生成 UUID**。必须走 Scaffold。
6. **以为 `package.json` 的 7.0.0 是产品版本**。真实版本在 `version` 文件。
7. **本地化三处不同步**。`chrome.manifest`、`xpcom/locale.js`、`app/assets/multilocale.txt` 必须一起改。
8. **`data/history.js` 与 `xpcom/undoHistory.js` 混用**。前者是操作历史记录与回放，后者是数据对象字段级撤销。
9. **在主仓里找不到子模块的实现就以为功能不存在**。子模块之间、以及子模块与主仓之间**没有 import 关系**——reader / note-editor / document-worker 的产物由 `js-build/` 在构建期复制进 `build/`，运行期通过 postMessage 或宿主回调通信。全图 421 条跨层依赖边中跨子域的为 0。找实现要去子模块仓库看，细节见 [10-子模块与第三方.md](10-子模块与第三方.md) 与 [04-架构分层.md](04-架构分层.md) 第三节。
10. **在同步里混淆 412 与 429**。412 是版本冲突走拉取-合并-重试，429 是限流走退避。
11. **在子模块里用主仓的 Node 版本或依赖**。五个子域各有独立工具链（reader Node 22、document-worker Node 24、note-editor Node 20 + Ruby、utilities Node 14），不共享 `node_modules`。主仓的依赖升级不会传播下去。
12. **改 note-editor 的 schema 而不看兼容文档**。`src/core/schema/README.md` 记录了 `data-schema-version` 递增规则、与旧版 TinyMCE 的兼容边界，以及 v2→v5 的逐版本变更。笔记是长期存储数据，schema 一旦发布必须保持向后兼容。

## 五、定位代码的路径

知识 wiki 的组织方式值得借用——从「我要改什么」倒推比从「文件在哪」正推快得多：

```
我要改的东西
  ↓
architecture.md  找到所属层
  ↓
layers/<层>.md    该层的目录分布 + 文件清单摘要
  ↓
modules/<目录>.md 目录聚合页，含每个文件一句话摘要与符号数
  ↓
files/<路径>.md   单文件页：摘要、符号表、依赖与相关节点
  ↓
symbols/...       189 个被独立成页的复杂符号
```

配套的 `tour.md` 是 **58 步**依赖顺序导览，结构为：第 1–14 步走主仓（引导 → 主窗口 → 基础设施 → 数据模型 → 条目分类标签 → 搜索 → schema → 同步 → 服务 → 插件 → XUL 元素 → React 组件 → 样式 → 构建），第 15–58 步依次走五个子域（document-worker 10 步、note-editor 9 步、reader 12 步、translate 7 步、utilities 6 步）。**导览是分域连续的，读某个子域时直接从对应区间的步号开始。**

`catalog.md` 是按类型/复杂度/标签聚合的符号目录（可用于「找所有标记为 data-model 的复杂函数」这类反查），但它的**语言统计不可信**——合并后只剩 `css 20` 一行，`project.name` 与 `project.description` 也被合并过程污染，引用前先回原始图谱核对。

wiki 现有 1513 个页面：47 个分层页、153 个目录页、1120 个文件页、189 个符号页。其中子域部分按目录分：`reader/` 234 文件页 + 47 目录页 + 62 符号页，`note-editor/` 98 + 16 + 18，`document-worker/` 84 + 16 + 58。

## 六、Scholoom 可直接借鉴的几点

按价值排序：

1. **文件摘要目录**。每个源文件配一句「它负责什么」，比完整文档更耐用，也更适合 AI 与人共同检索。Zotero 的 wiki 靠知识图谱自动生成，主仓加五个子域共 1067 个文件维护得起来。
2. **声明式扩展点基类**。`PluginAPIBase` 用一组选项（`optionTypeDefinition`、`mainKeyName`、`notifyType`）统一实现注册、注销、校验与通知，三个扩展点各只需写自己的投影逻辑。Scholoom 若要开放插件面，这能省掉三份重复的注册样板。
3. **数据变更只走一条路径**。所有写入经 `saveTx()`，所有 UI 刷新经 Notifier 一条出口。这条纪律让「自动同步」「撤销」「界面刷新」三个功能互不干扰。
4. **平台差异集中到入口**。三个 SCSS 入口承担全部平台差异，组件样式保持平台无关。
5. **复杂子系统拆成独立仓库 + 窄接口**。reader / note-editor / document-worker 三个子模块各 200–330 个文件，工具链、CI、发布节奏完全独立，主仓只通过构建期复制 + 运行期回调接触它们。子域内部门面文件的扇出（20–39）明显低于主仓超长文件（`zoteroPane.js` 186 个方法）——**拆仓库本身就是最有效的架构手段**。Scholoom 规模变大时这是第一个该考虑的手段。
6. **ctypes 绑定系统库替代原生扩展**。macOS FSEvents / Linux inotify / Windows `ReadDirectoryChangesW` 三个文件全部用 ctypes 实现，跨平台分发不需要为每个平台编译二进制。
7. **增量构建用内容签名**。产物签名未变就跳过编译，比时间戳判断可靠。
8. **自研构建而非 Webpack**。当宿主是 XUL 这类需要「对源码做文本改写」（修正 `createElement`、剥离 `globalThis`）的环境时，通用打包器的抽象反而是阻力。但注意 Zotero 的子模块**全部改用 Webpack**——约束不同，选型就不同。
9. **版本契约由产出方声明**。document-worker 的 `versions.js` 声明各处理器输出版本号，宿主据此判断磁盘缓存是否失效。产物要落盘缓存的子系统，版本号必须由产出方给出而不是让消费方猜。
