# 07 同步与附件存储

同步子系统是 Zotero 里耦合最紧密的一组模块，也是最容易改坏的。图谱把数据同步（`sync/`，8 文件 154 符号）与附件存储（`storage/`，11 文件 91 符号）合为「同步与附件存储层」共 20 个文件。

## 一、数据同步：sync/

| 文件 | 符号 | 职责 |
| --- | --- | --- |
| `syncRunner.js` | 32 | 总调度器（`Zotero.Sync.Runner_Module`）：按库列表驱动同步任务排队与重试，管理超时与延迟策略，解析并按库分类同步错误，负责 API key 登录流程、附件按需下载、UI 状态与图标更新 |
| `syncEngine.js` | 27 | 数据同步引擎（`Zotero.Sync.Data.Engine`）：围绕**库版本号**驱动对象级同步，负责增量/全量下载、批量上传、删除日志同步、设置同步、版本升级检查、上传失败后的回滚恢复 |
| `syncAPIClient.js` | 33 | Zotero Web API 客户端：封装 key 信息、设置、条目、集合、标签、全文索引、朗读等全部端点的请求构造与响应解析，统一处理 gzip、分页 Link 头、退避重试、412/429 状态 |
| `syncLocal.js` | 38 | 本地同步状态层（`Zotero.Sync.Data.Local`）：管理 API key 与登录管理器、跳过库列表、对象同步缓存版本，把服务器 JSON 协调合并进本地对象，跟踪删除日志与未同步状态 |
| `syncFullTextEngine.js` | 6 | 全文索引同步：按库版本下载服务器端全文索引，批量上传本地待同步内容，受批大小与条目数上限约束 |
| `syncEventListeners.js` | 12 | 监听数据变更触发自动同步；按条目类型区分需要同步的库（普通库、文件库、全文库）；在应用空闲或窗口失焦时设置同步时机 |
| `syncExceptions.js` | 2 | `UserCancelledException`，携带是否切换到下一个库的标记 |
| `syncUtilities.js` | 4 | 缓存可同步对象类型 → 数据库 ID 的映射；库失去写权限时弹说明性对话框 |

另有 `xpcom/sync.js`（经典 Zotero Sync 的服务器交互层）：解析服务器 XML 响应（队列、锁、错误码），在客户端版本或数据变化时自动重置 client key，生成类型变更与合并的提示文案。**它与 `sync/` 目录是两套东西**——前者是旧版 XML 协议的服务端交互层，后者是基于 Web API 的新同步。

## 二、核心机制：库版本号

同步不是逐对象对账，而是围绕**库版本号**（library version）推进：

1. 客户端把自己的 library version 报给服务器，服务器返回自该版本以来的变更集。
2. 客户端下载变更，增量应用到本地（走的仍是正常 `saveTx()` 路径，因此撤销、事件、缓存全部一致）。
3. 客户端上传本地待同步对象，携带新的版本号。
4. 412（版本冲突）触发拉取-合并重试，429 触发退避重试。

`storage/queue` 相关的 `syncQueue` 表记录待上传项；`syncCache` 表记录每个对象已同步的版本；`syncDeleteLog` 记录删除日志。

`dataObjectUtilities.diff` / `applyChanges` 就是为这条链路准备的：把本地对象与服务器 JSON 的差异压成最小写入集，既用于增量下载后的应用，也用于上传前的变更计算。

## 三、附件存储：storage/

附件文件不存进数据库，走独立的存储后端抽象。

| 文件 | 符号 | 职责 |
| --- | --- | --- |
| `storageEngine.js` | 4 | 附件存储同步引擎：按库维护上传/下载队列，校验 controller（WebDAV 等）的可用性与配额，把条目附件的增删改请求投递给对应队列 |
| `storageLocal.js` | 17 | 本地协调层：按库维护每个条目的同步状态（待上传/待下载/已同步/冲突），比较本地与服务器文件的修改时间决定下载或上传，冲突时调 UI 解决 |
| `storageRequest.js` | 9 | 单个附件存储请求（`Zotero.Sync.Storage.Request`）：封装目标条目、进度回调、渠道信息与上传下载参数，驱动请求启动、取消与进度上报 |
| `storageResult.js` | 2 | 结果值对象：把存储模式返回的原始状态码（跳过/成功/失败）映射为 Zotero 统一的同步状态常量 |
| `storageUtilities.js` | 4 | 按模式名返回对应存储类、从请求解析条目、为上传生成临时 ZIP 包 |
| `zfs.js` | 15 | Zotero File Storage：调用 Zotero Storage API 完成授权、文件上传下载、存储版本查询与配额检查 |
| `webdav.js` | 18 | WebDAV：Digest/Basic 认证、上传下载附件、探测服务器能力与容量，处理证书验证、目录创建与孤立文件清理 |

`xpcom/storage.js` 是共享的状态命名空间：维护附件下载进度、压缩比统计与默认错误提示，被 `storageEngine` 等子模块共享。

## 四、文件变更监听

附件目录被用户在应用外改动是常态，Zotero 用三套平台后端监听：

| 文件 | 平台 | 实现方式 |
| --- | --- | --- |
| `storage/fileChangeWatcher_fsevents.js` | macOS | ctypes 绑定 libSystem、CoreServices 与 Objective-C 运行时，用 FSEvents 事件日志跟踪 |
| `storage/fileChangeWatcher_inotify.js` | Linux | ctypes 绑定 glibc 的 inotify，为存储目录及各库子目录注册 watch |
| `storage/fileChangeWatcher_rdcw.js` | Windows | ctypes 绑定 kernel32 的 `ReadDirectoryChangesW`，以重叠 I/O 方式递归监控 |
| `storage/fileChangeWatcher.js` | 全部 | 统一入口：按平台选后端，同步会话开始时排空事件、映射变更的附件 key、判断某库是否仍需全量扫描 |

**这四个文件是「不写原生扩展也能用平台能力」的完整样本**：全部通过 ctypes 绑定系统库，没有编译步骤，跨平台分发时不需要为每个平台准备二进制。

## 五、库级设置与推送

| 模块 | 作用 |
| --- | --- |
| `xpcom/syncedSettings.js` | 按 libraryID + settingKey 保存带版本号的设置值，支持未同步标记、变更监听与批量加载；是 Zotero 各类账户设置的统一落库层（对应 `syncedSettings` 表） |
| `xpcom/streamer.mjs` | 服务器事件流客户端（`Zotero.Streamer_Module`）：通过 WebSocket 与 Zotero 服务器保持长连接，订阅同步、样式与翻译器更新主题，驱动自动同步与翻译器/样式自动更新 |
| `xpcom/proxy.js` | 代理配置管理：解析校验每个库的代理设置，持久化到 `syncSettings`，发起请求时把代理地址改写为真实地址 |
| `xpcom/osKeyStore.js` | 需要密码的附件/同步数据交给系统钥匙串；不可用时降级为明文并提示 |

`streamer.mjs` 值得注意：Zotero 不靠轮询，而是让服务器在有更新时通过 WebSocket 推。这让「翻译器更新」「CSL 样式更新」「需要同步」三类事件共用一条长连接。

## 六、改动同步代码的注意事项

1. **写入必须走 `saveTx()`**。同步引擎通过 Notifier 判断「本地是否有变更」，绕过它会导致静默不同步。
2. **`syncLocal.js` 符号数最高（38）**，改动前先看它对服务器的 JSON 如何协调合并进本地对象——这是合并冲突的实际发生地。
3. **错误分类要保留**。`syncRunner` 按库分类同步错误并采取不同策略（重试 / 跳过 / 提示只读），新增错误类型时要同时更新分类逻辑。
4. **412 与 429 语义不同**。412 是版本冲突，需要拉取-合并-重试；429 是限流，需要退避。混淆会导致同步风暴或无限重试。
5. **附件冲突会拉起 UI**。`storageLocal` 遇到冲突时调用 UI 层解决——这是一条真实的跨层依赖（存储层 → 界面层），在自动化测试中需要 mock。
