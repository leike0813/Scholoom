# 06 数据模型与持久化

## 一、整体选择：弱 ORM + 显式事务

Zotero 是一套自研 ORM。数据对象全部继承 `Zotero.DataObject`，字段值经由对象属性间接访问，**落库时显式开启事务**。这是刻意的选择：保存时机、批量写入顺序和失败回滚完全可控——这对同步引擎至关重要，因为同步需要精确知道「哪些字段变了」才能生成最小上传集。

## 二、DataObject / DataObjects 对

| 类 | 文件 | 符号数 | 职责 |
| --- | --- | --- | --- |
| `Zotero.DataObject` | `xpcom/data/dataObject.js` | 15 | 字段读写、加载、关系管理、脏值追踪、undo 快照、`saveTx()` 事务保存、JSON 序列化 |
| `Zotero.DataObjects` | `xpcom/data/dataObjects.js` | 10 | 对象缓存、按 ID/key 批量加载、关系排序（层级/父子）、版本查询、批量擦除 |
| 工具集 | `xpcom/data/dataObjectUtilities.js` | 9 | 对象类型注册、key 生成、属性补丁、数据相等比较，以及跨字段/作者/标签/关系的 `diff` 与 `applyChanges` |

`dataObjectUtilities.js` 里的两个关键函数值得单独记住，因为它们是整个数据层与同步层之间的接缝：

- `diff`（305–397 行）：生成对象间的变更集，综合字段、作者、标签、关系与 HTML 内容的差异。
- `applyChanges`（602–727 行）：把变更集应用到对象，支持 undo、redo、`multiFieldAdd` 与 `partial` 多种模式。

配套的 `equals`（172–216 行）比较两个数据对象的字段值是否一致，可忽略指定字段。

### 最关键的设计：值表 + 关联表

`itemDataValues` 存去重后的原始值，`itemData` 记录 itemID 与 valueID 的关系。同名字段值只存一份，所有条目通过 `itemData` 引用它。

- **收益**：字符串去重后索引极小。Zotero 库动辄几万条，字段值高度重复，这一步收益巨大。
- **代价**：任何字段读取都至少要一次 join。因此 Zotero 用 `dataObjectUtilities` 里的差异计算，把整棵子树的变更压缩成最小写入集——这既是性能手段，也是同步所需。

`itemTypesCombined`、`fieldsCombined` 等 Combined 表是同类型多态查询的加速视图/表，服务于按类型或按字段的检索。

## 五、数据库访问层

`xpcom/db.js`（25 符号）提供 `Zotero.DB` 与 `Zotero.DBConnection`：

- 封装 Mozilla `mozStorage` 的异步查询（`Zotero.DB.queryAsync()`）
- 事务调度：`Zotero.DB.executeTransaction()`，支持嵌套与只读事务
- WAL 降级：文件系统不支持 WAL 时的回退
- 完整性校验与损坏恢复

`xpcom/schema.js` 负责 schema 定义与升级：内置当前版本 schema、从仓库（`resource/schema/global`）拉取更新、从旧版本逐级迁移并执行完整性检查，同时内嵌 translator 与 CSL 样式所需的字段与类型映射表。数据库升级的引导 UI 是 `upgrade.xul`（内嵌 `Zotero_Schema_Upgrade` 对象，会先跑完整性检查再执行升级）。

`xpcom/id.js` 是自增 ID 发号器：内存计数 + 数据库取偏移量，在保证并��唯一的同时尽量少读数据库。

## 六、事件与撤销

| 模块 | 机制 |
| --- | --- |
| `xpcom/notifier.js` | 全局事件中心。事件以「事件名 + 类型 + ID 集合」三元组描述；支持按优先级注册观察者、事件合并（`queue`）、事务化批量派发（`begin`/`commit`）。它是数据层向 UI 广播变更的**唯一出口** |
| `xpcom/undoHistory.js`（21 符号） | 字段级 undo/redo 栈，与数据库事务生命周期挂钩，按库隔离，支持分批暂存变更以合并高频编辑 |
| `xpcom/history.js` | 用户操作历史以数据库记录保存，支持事务分组、回溯与重放，并通过 Notifier 广播 |

**注意这里有两个历史模块**：`undoHistory.js` 是数据对象字段级撤销（给用户 Cmd+Z），`history.js` 是操作历史记录与回放。改动撤销行为时先确认改的是哪个。

## 七、写入路径的标准形状

任何需要落库的改动，标准流程是：

1. 取对象（`Zotero.Items.get(id)` / 复数管理器的批量加载）
2. 改属性、改作者、改标签、改分类
3. `await object.saveTx()` —— 内部开事务，写 diff，走 undoHistory，发 Notifier
4. 事务提交后，Notifier 观察者刷新 UI；同步引擎被 `syncEventListeners.js` 唤醒排队自动同步

**不要绕过 `saveTx()` 直接写 SQL**。绕过它意味着跳过脏值追踪、撤销记录和事件广播，UI 与同步都会失步。
