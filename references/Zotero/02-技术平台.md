# 02 技术平台与运行时

这一篇回答一个问题：Zotero 到底跑在什么之上，以及这层平台约束了哪些设计。

## 宿主：Gecko / XPCOM，而不是浏览器与 Node

Zotero 借用 Firefox 的平台能力，把自身做成一个 XUL 应用。因此它在代码里可以直接使用一整批 Mozilla 全局对象（`CLAUDE.md` 明确列出）：

- `Cc`、`Ci`、`Cu`、`Cr`：组件与服务管理器
- `Services`：`Services.prefs`、`Services.locale`、`Services.scriptloader` 等
- `ChromeUtils`、`IOUtils`、`PathUtils`：工具函数

这批全局在普通 Node 或浏览器环境里都不存在。**任何「把 Zotero 的某个模块抽出来在 Node 里跑」的想法都要先补一层垫片**，仓库里确实有这类垫片文件：

| 文件 | 作用 |
| --- | --- |
| `browserWindowShim.js` | `nsBrowserAccess` 多版本兼容，让 translators 子模块在现代 Gecko 上继续工作 |
| `osfile.mjs` | 把已移除的 `OS.File` / `OS.Path` API 以 ESM 形式重新提供 |
| `bluebirdShim.mjs` | 为旧代码补 `Promise.defer` 等 Bluebird 专有 API |
| `resource/loader.sys.mjs` | 从 Firefox DevTools 移植的 ESM 加载器，提供 sandbox、模块缓存、`require` |
| `resource/require.js` | 在上述加载器之上建标准 loader，把 `containers/`、`components/`、`zotero/` 前缀映射到 chrome URL |

## 资源与协议

`chrome.manifest` 是打包与寻址的清单，它把 URL 空间划成四块：

| 映射 | 目标目录 | 备注 |
| --- | --- | --- |
| `chrome://zotero/content/` | `chrome/content/zotero/` | 主应用内容 |
| `chrome://zotero-platform/` | `chrome/content/zotero-platform/{mac,win,unix}/` | 按 `os=Darwin` / `os=WINNT` / `os=Linux`（另含 SunOS、FreeBSD、OpenBSD）分支 |
| `chrome://zotero-platform-version/` | `chrome/content/zotero-platform/default-version/` | 平台版本判定 |
| `resource://zotero/` | `resource/` | 非 UI 资源：SQL schema、feed 解析器、vendored 库 |

另外注册 `skin zotero default`、`content scaffold`（翻译器脚手架）、以及数十条 `locale zotero <lang>`。

**平台分支是靠 manifest 做的，不是靠代码里的 if**。任何新增资源如果需要平台特化，先想清楚是走 `zotero-platform` 还是走代码分支。

除了 chrome 与 resource 协议，Zotero 自己注册了 `zotero://` 协议（`ZoteroProtocolHandler.mjs`），用于外部唤起应用：打开附件、数据、报告、选定位点、调试输出、PDF.js、打开外部编辑器等。

## 进程模型：主进程 + 内容进程 Actor

Zotero 是多进程应用，跨进程通信走 Mozilla 的 Actor 机制。`chrome/content/zotero/actors/` 下是成对的父子进程文件：

- `TranslationParent` / `TranslationChild`：翻译器在内容进程执行，主进程通过 `RemoteTranslate.mjs` 转发 detect / translate / runTest 请求
- `SingleFileChild`：网页整页快照
- `ZoteroPrintParent` / `ZoteroPrintChild`：打印
- `ExternalLinkHandlerParent` / `Child`：外部链接
- `FeedAbstractParent` / `Child`：feed 抓取
- `SequoiaContextMenuParent` / `Child`：邮件客户端（Sequoia）右键菜单
- `ProfilerViewerParent` / `Child`：性能剖析
- `DocumentIsReadyChild`：文档就绪通知
- `ActorManager.mjs`：统一管理 Actor 的注册与生命周期
- `actors/translation/http.js`、`translate_item.js`：翻译器在内容进程一侧的执行沙箱

同时 `HiddenBrowser.mjs` 封装了一个隐藏的远程 `browser` 元素：创建 frame、加载 URI、等 document ready，再向内容进程查询页面数据、序列化文档、生成快照或触发打印，销毁时注销 `BlockingObserver` 并清理 frame。它是抓取/翻译/快照/验证码处理的公共底座。

**设计启示**：需要执行不受信任网页代码的能力，Zotero 一律放进内容进程的 browser 环境，而不是在主进程直接 fetch。这是 Mozilla 沙箱能力被当作一等公民使用的例子。

## XPCOM 组件与全局命名空间

Zotero 的模块不是 ESM 依赖图，而是共享一个全局对象：

- `zotero.mjs` 用 `makeZoteroContext()` 自建 sandbox，按固定顺序把 `xpcom/` 下的脚本以 `loadSubScript` 载入，构造全局 `Zotero` 命名空间。
- 载入后 `Zotero.DB`、`Zotero.Items`、`Zotero.Sync`、`Zotero.Preferences` 等子命名空间就绪。
- `zotero.mjs` 同时负责加载 `resource://zotero/require.js`、注册 `zotero:` 协议处理器、把 `dateOverrides.js` 注入每个新窗口，并提供 `ZoteroContext` 供 reinit 时重建整套上下文。
- 少量能力改用 `Modules.*` 合约注册为标准 XPCOM 组件，例如 `optionsAutoComplete.mjs`（nsIAutoCompleteSearch）、`zotero-autocomplete.mjs`（同样注册到 autocomplete/search 合约）、`fileDragDataProvider.js`（nsIFlavorDataProvider）、`mimeTypeHandler.js`（nsIObserver）。

读代码时找不到 import 语句不是漏写，而是这套运行时的正常形态。**模块间协作靠共享全局，不靠静态依赖图**，所以调用关系只能靠运行时或搜索发现。

## 界面技术：三代混合

| 形态 | 位置 | 特点 |
| --- | --- | --- |
| XUL/XHTML 文档 + 控制器脚本 | `zoteroPane.xhtml/js`、各对话框 | 传统 XUL 模式，视图与逻辑分离 |
| XUL 自定义元素（Web Components） | `elements/` 54 个文件 | 继承 `elements/base.js` 的 `XULElementBase` mixin，继承 Mozilla XUL 元素基类以支持 `customElements.define`，统一 `init()` / `destroy()` 生命周期与指向内部 `<template>` 的 `content` getter |
| React 18 组件 | `components/`、`collectionTree.jsx`、`collectionViewItemTree.jsx` 等 | 只用于复杂交互与大数据量视图（树、虚拟表格、标签选择器） |

`customElements.js` 是注册中心：先 `loadSubScript` 载入 `include.js`、全局 `customElements.js`、`elements/base.js`、`itemTreeMenuBar.js`，再为约 50 个元素调用 `customElements.setElementCreationCallback` 做懒加载。全仓库共有 60 处 `customElements.define` 调用（含 scaffold 与其他窗口）。

它同时是一份**原生行为补丁集**：修复 `<tab>` 缺失属性、菜单延迟命令、macOS menupopup 淡出动画、menulist 键盘导航等 XUL 缺陷。这类补丁是「用平台原生控件」必须付出的代价。

## 网络栈

`Zotero.HTTP` 基于 `nsIChannel` 而非 `fetch`，提供请求/下载/重试/代理/安全校验、Cookie 上下文，以及保持首字母大小写的 Header 容器。原因很直接：Zotero 需要控制重定向、Cookie 与反爬挑战，而 Mozilla 的 channel 提供了更细的钩子。

反爬处理集中在 `browserRequest.js`：识别 ScienceDirect 等站点的验证码 / Cloudflare 拦截，通过隐藏浏览器或可见窗口清除挑战后再下载 PDF；配套 `captcha.js` / `captcha.xul` 弹验证码输入框，`BlockingObserver.mjs` 按谓词拦截特定 URI 请求。

## 文件系统与平台能力

| 模块 | 能力 |
| --- | --- |
| `file.js` | 路径转换、文件读写、目录创建/移动、符号链接、云存储检测、压缩 |
| `ipc.js` | Linux 上通过命名管道（FIFO）与外部进程通信，动态加载 libc 提供 `mkfifo` |
| `storage/fileChangeWatcher_{fsevents,inotify,rdcw}.js` | 分别用 ctypes 绑定 macOS FSEvents、Linux inotify、Windows ReadDirectoryChangesW |
| `osKeyStore.js` | 把需要密码的附件/同步数据交给系统钥匙串，不可用时降级为明文并提示 |
| `resource/hide.vbs`、`redirect.vbs`、`redirect.sh` | Windows 无窗口启动与输出重定向的小工具 |
| `platformKeys.js`、`titlebar.js` | 按平台调整快捷键、菜单行为与自定义标题栏 |
