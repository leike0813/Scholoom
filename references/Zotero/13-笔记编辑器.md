# 13 笔记编辑器子模块（note-editor）

`note-editor/` 是 Zotero 主仓库的 Git 子模块，基于 ProseMirror schema 与 React 18 实现富文本笔记的编辑、Markdown 互转、表格与数学公式。本文基于子模块自身的知识图谱（94 个文件节点、221 节点、469 边、9 个分层）撰写，调研时子模块 commit 为 `7c92b77b`。

笔记数据是长期存储的，所以这个子系统有一条主仓没有的硬约束：**schema 一旦发布就必须保持向后兼容**。这是理解下面几乎所有设计选择的前提。

## 一、文档 Schema：唯一的地基

`src/core/schema/index.js` 是全项目**唯一**引用 schema 的入口，其余模块一律经它访问。它用 `nodes.js` 与 `marks.js` 组装出带版本号（当前 **10**）的 Schema，并导出 `toHTML` / `fromHTML`、剪贴板序列化器与调色板常量（`colors.js`）。

- `nodes.js` 覆盖段落、标题、列表、引用、代码块、公式、图片、表格等块级与行内节点。
- `marks.js` 覆盖 strong / em / underline / link / textColor / backgroundColor 等行内标记。
- `metadata.js` 负责引用 metadata 的序列化。

两者的 `parseDOM` 与 `toDOM` 规则**同时**是 HTML 导入导出与 Markdown 互转的依据——同一个 spec 派生出三条转换路径，schema 因此成为真正的单点事实源。

`src/core/schema/transformer.js` 是 HTML 进入 schema 之前的预处理与归一化：`preprocessHTML` 提取 metadata 容器属性，把背景图、带 `src` 的非图片元素转换为合法的图片/链接；`schemaTransform` 依据 schema 版本修正文档结构。它是外部 HTML 能否被正确解析的最后一道关。

`schema/README.md` 记录 `data-schema-version` 的递增规则、与旧版 TinyMCE 编辑器的兼容边界，以及 v2 到 v5 的具体变更。**要新增一个元素前先读这份文档。**

## 二、内核枢纽 editor-core.js

`src/core/editor-core.js`（扇出 32）是整个内核的装配点。它向下依赖 30 余个模块，向上只暴露一组稳定接口：`getHTML` / `getData` / `applyExternalChanges` / `execCommand` / `on-off` 订阅。

它的职责链条就是编辑器的完整生命周期：**数据进来 → 解析成 doc → 构建 EditorState 与 EditorView → 按序注册全部 plugin 与 nodeView → 状态机就绪 → 对外发事件**。理解这个文件就理解了整个子系统。

`node-views/index.js` 汇总各 nodeView 构造函数（citation、highlight、image、table）在此一次性注入；`provider.js` 提供订阅式数据通道，让宿主异步送到的图片数据能推给对应视图。

## 三、命令层：界面无关

`src/core/commands.js` 扇出 38，是全库最高的文件级扇出。它提供带属性的 mark 增删改、缩进、对齐、书写方向、列表切换、引用与公式插入等 ProseMirror command。**命令层必须与任何具体界面无关**，因为 UI 与快捷键都依赖它。

`src/core/helpers.js` 的 `getMarkRange` 系列解决了 ProseMirror 原生命令的一个硬限制：原生命令只能按 mark 类型匹配，无法区分同类型的不同 attrs。这是 `commands.js` 移植自 TipTap 的关键改造——没有它，「把这一段高亮改成蓝色」就实现不了。

其余内核文件：`keymap.js` 把命令绑到全局快捷键，`history-commands.js` 把 input rules 的撤销与 prosemirror-history 的 undo/redo 组合成可直接绑定的命令常量，`utils.js`（扇入 23）提供内核内共享能力。

## 四、插件层

`src/core/plugins/` 下 18 个 plugin 挂在 ProseMirror 状态机上，各自维护 plugin state 与 decoration，承担节点级交互而**自身不含 UI 组件**。

| 关注点 | 文件 |
| --- | --- |
| 表格 | `table.js` 基于 prosemirror-tables 封装行列增删、单元格合并拆分、表头切换，并实现 Tab 键在单元格间移动光标 |
| 引用 | `citation.js` 维护引用节点的选中态与浮动操作菜单，处理引用与批注节点**成对插入增删**的判定 |
| 公式 | `math.js` 在事务中检测光标进出行内/块级公式节点，必要时把公式替换为普通段落，保证公式前后能继续输入 |
| Markdown | `markdown-parser.js` / `markdown-serializer.js` |
| 拖放粘贴 | `drop-paste.js` / `drag.js` |
| 其他 | 高亮与颜色、链接、图片、菜单、搜索、只读、占位符、trailing-paragraph、schema 迁移、node-id、pull-item-data |

`menu.js` 把同一批命令包装成带 active 状态的菜单项定义供 React 界面消费——**界面层只消费命令与 menu 定义，不直接操作文档**。

## 五、Markdown 与剪贴板

这是富文本与外部格式之间的双向通道，也是子系统最贴近用户输入的部分。

`markdown-parser.js` 基于 markdown-it 构建支持行内与块级公式的 MarkdownParser，并用**多层启发式规则**判断纯文本是否应按 Markdown 解析（纯文本和 Markdown 的边界本身是模糊的）。`markdown-serializer.js` 定制 prosemirror-markdown 的记法——加粗用 `*`、高亮用 `==`——复制时还经 Zotero 桥接接口输出。

`input-rules.js` 把 Markdown 式触发模式映射为自动转换：`#` 标题、`>` 引用、`-` 列表、`---` 分割线、代码块、行内公式。

`drop-paste.js` 统一拦截粘贴、拖放与移动事件，把 HTML、纯文本、RTF 与外部图片转成符合本 schema 的 Slice 并过滤不合规内容。`rtf.js` 负责解析 macOS 剪贴板中的 RTF 内容——这是一处明确的平台特化。

## 六、React 界面层

`src/ui/editor.js`（扇出 13）是编辑器外壳，把 toolbar、findbar、noticebar 与各类 popup 组织起来，并把 ProseMirror 的 view DOM 挂载进 React 树。

`toolbar.js` 组装按钮与各类下拉菜单，由一组 `toolbarState` 对象驱动链接、缩进、引文与批注颜色的启用态。通用交互基元有三件：

- `toolbar-elements/dropdown.js` 处理弹层开合、相对定位与方向键循环导航（扇入 6，全项目被引用最多的复杂符号之一）。
- `popups/popup.js` 依据目标节点矩形在父容器内定位，空间不足时向下翻转。
- `findbar.js` 封装查找替换，把结果驱动到搜索插件状态。

`src/fluent.js`（扇入 7）为界面提供 Fluent 本地化运行时，合并 `zotero.ftl` 与 `note-editor.ftl` 两个资源文件。**所有新文案都必须进 `.ftl`**——这条约定与主仓一致。

## 七、平台入口、样式与构建

`src/index.zotero.js` 是四平台中功能最全的一支宿主入口，处理 XUL iframe 下的拖放补丁、上下文菜单、字体与阅读视图设置、撤销重做与同步数据接口。`index.web.js` 改用 `window.postMessage` 通信并支持明暗配色切换。`html/editor.zotero.html` 以 `resource://` 协议从 Zotero 内部加载 React 运行时。

样式上 `main.scss` 按 abstracts → themes → base → components 顺序导入，并依据 `$platform` 推导 `$mobile` 开关；`_light.scss` 与 `_dark.scss` 输出**同名色板变量**以适配系统主题。

构建侧 `webpack.config.js` 为 dev / web / zotero / ios / android 五个目标各生成一份配置，串联 Babel、SCSS、SVG、字体与 Fluent 资源（`webpack.zotero-locale-plugin.js` 负责 FTL 打包）。CI 在 push 与 pull_request 时以固定 Node 与 Ruby 版本跑构建校验——Ruby 的存在是为了 Fluent 编译。

## 八、主仓对接

主仓一侧有三个文件负责桥接：

- `xpcom/editorInstance.js`（`Zotero.EditorInstance`）管理编辑器生命周期、保存、引文插入与批注序列化。
- `elements/noteEditor.js` 是宿主自定义元素，承载 iframe 包装，加载保存笔记并管理关联信息区域。
- `data/notes.js` 持有笔记数据本身。

`js-build/note-editor.js` 以子进程运行其构建脚本获取产物，清空并重建 `build/` 下的目标目录，再把产物及共享资源复制进去。

## 九、给 Scholoom 的启示

1. **schema 是唯一入口，且是唯一事实源**。`schema/index.js` 一个文件收敛全部引用，让 `parseDOM` / `toDOM` 一处定义派生出 HTML 导入导出、Markdown 互转、剪贴板三条路径。文档模型复杂的编辑器都该这么收口。
2. **长期数据必须写明兼容边界**。`schema/README.md` 记录版本递增规则与每个版本的具体变更，这份文件本身就是发布契约。
3. **命令层与界面层彻底解耦**。`commands.js` 扇出 38 但不引用任何 UI，界面反过来只消费命令与 menu 定义。快捷键、工具栏、右键菜单三个入口共享一份实现。
4. **绕过框架限制要有文档化的改造**。`getMarkRange` 补上 ProseMirror 无法按 attrs 匹配 mark 的缺口——这类改动在原生命令做不到时非常必要。
5. **状态编排层不感知渲染**。与 reader 的 `read-aloud/manager.ts` 同一个思路，见 [12-阅读器.md](12-阅读器.md)。
