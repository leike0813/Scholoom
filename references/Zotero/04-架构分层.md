# 04 架构分层

Zotero 没有架构设计文档，但它有清晰的分层。知识图谱把文件级节点归入 47 层，函数与类归属到所在文件，不重复计入。

**这是上次调研之后变化最大的一篇**。上次只有主仓库的 10 层；现在子模块被检出并单独分析、合并回父仓库，全图 47 层 = 主仓 10 层 + 五个子域的 37 层。因此本文分两段讲：主仓 10 层维持原样，五个子域的分层单独成表并指向各自文档。

## 三、层间依赖

方向为「源分层 → 目标分层」。关系类型口径：`imports`（文件间 import）、`calls`（符号调用）、`depends_on`（显式依赖）、`configures`（配置作用于目标）、`defines_schema`（定义结构约束）、`implements`（实现声明接口）。归属类关系（`contains`、`exports`、`documents`）与弱关联（`related`）不计入。

### 最重要的一条发现：跨子域依赖边为 0

全图 421 条跨层依赖边，**主仓 10 层与五个子域 37 层之间没有任何一条边**。这不是因为它们真的没有耦合，而是因为子模块以不透明 gitlink 的形式存在于父仓库，静态分析在主仓侧只能看到调用侧的 `pdfWorker/manager.js`、`editorInstance.js`、`sdt.js`，看不到被调用方。

真实的耦合关系是有的，只是图谱捕获不到：

| 宿主侧文件 | 目标子域 | 实际职责 |
| --- | --- | --- |
| `xpcom/pdfWorker/manager.js` | document-worker | 启动 worker、消息队列串行调度 |
| `xpcom/sdt.js` | document-worker | 按源文件哈希缓存抽取结果 |
| `xpcom/editorInstance.js` | note-editor | 编辑器生命周期、保存、引文插入、批注序列化 |
| `elements/noteEditor.js` | note-editor | 承载 iframe 包装，加载保存笔记 |
| `xpcom/reader.js` | reader | 阅读标签页、独立窗口、预览面板管理 |
| `xpcom/translation/*.js` | translate / utilities | 注入 `Zotero.Translators` / `Zotero.HTTP` / `Zotero.Translate.ItemSaver` |

**主仓与子域是构建期 + 运行期 message-passing 的关系，不是 import 关系。** 想看这两侧怎么接，得读上表左列的六个文件。

## 五、三条架构主线

读这张分层表时，抓住三条主线就够：

1. **数据向下汇聚**。UI → 核心运行时 → 数据模型 → SQLite。所有写入最终收敛到 `saveTx()` 事务，变更通过 `Notifier` 向上广播。图谱里跨层边数最多的就是「数据模型 → 核心运行时」（8 条）。

2. **样式是配置而非依赖**。样式与皮肤层对界面层、核心层、外部集成层的关系全部是 `configures`（12 + 3 + 3 条），没有一条 `depends_on`。SCSS 通过类名与属性选择器作用于 XUL/HTML，不反向引用代码。子域里这条主线同样成立——`configures` 边全部来自「构建配置与项目文档」类分层。

3. **同步与存储自成闭环**。同步层对核心层只有 5 条出边，对数据层的写入也走正常数据对象路径，所以同步可以整体替换或替换后端（ZFS ↔ WebDAV 正是这样做的）。

补一条子域独有的主线：**子域是构建期产物，不是运行期依赖**。主仓通过构建脚本把子模块产物复制进 `build/`，运行期通过 postMessage / 回调通信。这解释了为什么跨子域依赖边为 0。

## 六、违反分层的已知情况

- `zoteroPane.js` 单文件约 7700 行、186 个方法，同时承担树初始化、选中状态、菜单构建、拖放导入与条目增删改。它事实上是界面层的中心枢纽，跨层调用多。
- `xpcom/integration.js` 单文件 3830 行、18 个符号，混合了引文域操作、状态同步与文档序列化三件事。
- 核心层与 UI 层共享全局 `Zotero` 对象，`loadSubScript` 注入让「哪个层调用哪个层」在静态上不可判定，图谱的层间边数只是下界。
- 子域内的门号文件扇出普遍在 20–39 之间（`pdf/index.js` 39、`citation-refs.js` 39、`commands.js` 38、`editor-core.js` 32），比主仓最高的门类（`zoteroPane.js` 186 个方法）更集中。子域的模块化程度明显高于主仓。

**给 Scholoom 的启示**：如果要复刻类似规模的应用，值得显式建立「数据层只经由事务写、UI 只经由事件读」的硬边界，并给超长文件设上限；Zotero 在这两点上主要靠约定而非机制。但子域（reader / note-editor）在这两点上做得明显更好——**把复杂子系统拆成独立仓库、独立构建、窄接口的子模块，本身就是最有效的架构手段**。

## 七、图谱口径与合并瑕疵

读本文数字时必须知道三件事：

1. **47 层是合并结果**。主仓 10 层来自对主仓的分析，37 层来自五个子域各自的分析，合并工具是 `merge-subdomain-graphs.py`（报告：3859 节点、7436 边、47 层、58 步导览，无丢弃边）。
2. **子域分层名有重名**。reader 与 note-editor 都有「样式与主题层」「构建配置与项目文档」，utilities 与 translate 的层名也不完全唯一。按名字统计会出错，必须带域前缀。
3. **合并图的项目元数据有瑕疵**。`knowledge-graph.json` 的 `project.name` 变成了 `Zotero Utilities（@zotero/utilities）`（取自某个子域），`project.description` 是六个子域描述用 `|` 直接拼接的结果。`catalog.md` 的「按语言」统计只剩 `css 20` 一行。这些字段**不可引用**，本文的数字全部重新从图谱原始数据计算过。
