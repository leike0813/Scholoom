# 10 子模块与第三方依赖

Zotero 的一批核心能力**不在主仓库里**，主仓库只保留宿主与集成代码。读代码时如果找不到某个能力的实现，先查这里。

**这是上次调研之后变化最大的一篇**。上次所有子模块目录都是空的，本文中关于它们的描述只能来自主仓调用侧。现在 15 个子模块已全部 checkout，五个关键子域还各自有了独立分析的知识图谱，本文因此重写为「子域索引 + 各自架构要点 + 第三方清单」三段。

## 二、五个已分析子域速查

每个子域的详细文档单独成篇，这里只给「它是什么、边界在哪、关键数字」。

### document-worker

**定位**：PDF / EPUB / HTML 快照的结构化文本抽取与 PDF 标注读写。源码以 ESM 在 Node.js 中运行，生产构建产出**单个 Web Worker bundle**，同时被 Zotero 桌面端与 iOS 的 JavaScriptCore/JSContext 复用。

**边界**：不碰存储，不做 UI，只做纯计算 + 字节级 PDF 读写。宿主通过 postMessage RPC（`pdf.*` 指令）调用。

**关键数字**：76 个文件节点、395 节点 / 856 边、9 层。全库扇出最高的文件是 `src/pdf/index.js`（39 出边，能力门面）与 `src/pdf/structure/citation-refs.js`（39）。

**主仓对接**：`xpcom/pdfWorker/manager.js`（`Zotero.PDFWorker`，串行调度）、`xpcom/sdt.js`（按源文件哈希缓存抽取结果）。

→ [14-文档处理Worker.md](14-文档处理Worker.md)

### reader

**定位**：PDF、EPUB 与网页快照的渲染、批注、高亮与朗读。

**边界**：**不碰存储**。所有批注读写通过宿主回调完成，「渲染 + 交互，存储外置」是理解全部代码的前提。

**关键数字**：223 个文件节点、531 节点 / 1287 边、10 层。`src/common/reader.js`（扇出 24，约 3000 行）与 `src/pdf/pdf-view.js`（扇出 25）并列架构中心。

**主仓对接**：`xpcom/reader.js`（阅读标签页、独立窗口、预览面板）、`xpcom/annotations.js`（批注缓存图片与序列化）。

→ [12-阅读器.md](12-阅读器.md)

### note-editor

**定位**：基于 ProseMirror schema 与 React 18 的富文本笔记编辑器，含 Markdown 互转、表格与数学公式。

**边界**：schema 版本当前为 **10**，一旦发布必须保持向后兼容——这是主仓没有的硬约束。`schema/README.md` 记录 v2 到 v5 的变更与兼容边界。

**关键数字**：94 个文件节点、221 节点 / 469 边、9 层。`src/core/schema/index.js` 扇入 23（唯一入口），`commands.js` 扇出 38、`editor-core.js` 扇出 32。

**主仓对接**：`xpcom/editorInstance.js`（`Zotero.EditorInstance`）、`elements/noteEditor.js`（宿主自定义元素，承载 iframe）。

→ [13-笔记编辑器.md](13-笔记编辑器.md)

### translate

**定位**：翻译器框架，解析并执行 Zotero translator 定义。

**边界**：**不含 `package.json`，不自带任何能力**。宿主必须自行实现 `Zotero.Translators`、`Zotero.HTTP`、`Zotero.Translate.ItemSaver`，并调用 `Zotero.Schema.init` / `Zotero.Date.init` / `cachedTypes.setTypeSchema` 灌入数据。`src/http.js` 是纯契约层。

**关键数字**：20 个文件节点、74 节点 / 157 边、5 层。`src/rdf/` 是内嵌的 rdflib 栈，内部 24 条依赖边集中在一层，对外只被 example 引用。

**主仓对接**：`xpcom/translation/` 与 `actors/Translation{Parent,Child}.mjs` 做调度与内容进程执行；`xpcom/browserRequest.js` 提供宿主实现。**`example/` 目录是对宿主契约的最小可运行实现，也是权威加载顺序参考。**

→ [15-翻译框架与共享工具库.md](15-翻译框架与共享工具库.md)

### utilities

**定位**：Zotero 生态共用的 utility 库，以 npm 包形式分发。

**边界**：同样没有自举入口。调用方必须先 `Zotero.Schema.init` / `Zotero.Date.init`，先加载 `zoteroTypeSchemaData.js` 再加载 `cachedTypes.js`，并自行实现 `Zotero.localeCompare()`。

**关键数字**：9 个文件节点、74 节点 / 96 边、4 层。`utilities.js` 扇出 23（npm 主入口），`date.js` 在 SQL / ISO / HTTP / EDTF / multipart **五套日期表示**之间互转。

**主仓对接**：作为全局命名空间模块被 `xpcom/` 大量调用。

→ [15-翻译框架与共享工具库.md](15-翻译框架与共享工具库.md)

### 子域与主仓如何相连

**主仓与子域之间没有任何 import 依赖**——全图 421 条跨层依赖边中，跨子域的为 0。连接靠两条通道：

1. **构建期**：`js-build/` 下三个任务脚本（`reader.js` / `note-editor.js` / `document-worker.js`）以子进程运行子模块自己的构建脚本，把产物复制进 `build/`。`reader.js` 对 git-lfs 未拉取等特定错误做了降级处理。
2. **运行期**：postMessage RPC（document-worker）、宿主回调（reader）、全局命名空间注入（translate / utilities）。

`js-build/symlinks.js` 还负责把子模块源码与 node_modules 产物链接进 `build/`，`copy` 模式处理必须真实拷贝的文件。

## 五、构建与平台资产

`app/` 目录是各平台打包资产，不进知识图谱分析范围（属于构建产物侧）：

- `app/assets/application.ini`、`app/assets/chrome.manifest`、`app/assets/prefs.js`、`app/assets/commandLineHandler.js`、`app/assets/updater.ini`、`app/assets/multilocale.txt`、`app/assets/branding/`
- `app/assets/{mac,win,unix}/` 三套平台资产
- `app/build.sh`、`app/config.sh`、`app/linux/mozconfig`（Mozilla 编译配置）、`app/linux/icons`

`.gitattributes` 记录两条规则：SQL 文件强制 LF 行尾；打包产物（各平台 updater 压缩包）标记为 **Git LFS** 跟踪。

`chrome.manifest` 注释里写明 locale 列表需与 `locale.js` 和 `app/assets/multilocale.txt` 保持同步——**同一个事实源被写在了三个地方**，改动语言支持时三处都要动。

**五个 CI 流水线并存**，各管各的仓库：主仓（push/PR/手动/月度，Linux 测试拆 4 个并行分片 + macOS NFS + Windows x64/arm64）、reader（Node 22）、document-worker（Node 24）、note-editor（Node 20 + Ruby 3.3）、utilities（Node 14）。四者都会把 build 产物打包上传 S3 供 Zotero 客户端拉取。translate 没有独立 CI。

## 六、类型声明

`types/gecko/` 为 Mozilla/Gecko 的 XPCOM API 提供 TypeScript 声明：

- `generated/lib.gecko.{xpcom,dom,services,modules,darwin,win32,linux,nsresult,glean}.d.ts`（自动生成）
- `index.d.ts`、`lib.gecko.{custom,tweaks,xpidl}.d.ts`（手写补充）
- `subs/` 下有 `AppConstants.sys.d.mts`、`FeatureManifest.sys.d.mts`、`RFPTargetConstants.sys.d.mts`、`PromiseWorker.d.ts` 等内部子模块声明

知识图谱把 `types/gecko`（6 文件）与 `types/gecko/subs`（7 文件）归入「平台适配与外部依赖层」。这批声明的价值在于：**XPCOM 的类型信息不在 Gecko 文档里，而在这些 `.d.ts` 中**，查 API 签名直接看它们。

**子域的类型化程度不同**：reader 的 `tsconfig.json` 启用 strict 但**只覆盖 `./src`**，显式排除仍是 JavaScript 的 `src/common` 与 `src/pdf`；document-worker 与 note-editor 同样是部分 TypeScript。主仓则几乎全是 JavaScript + 一份手写 `.d.ts`。
